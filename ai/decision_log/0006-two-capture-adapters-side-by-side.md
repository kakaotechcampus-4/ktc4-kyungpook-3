# 0006. 회의 캡처 구현 두 개를 한 브랜치에 나란히 둔다

- 날짜: 2026-09-12
- 상태: 검토중 (어느 쪽을 남길지는 멘토 리뷰에서 정한다)

## 배경

디스코드 회의 캡처를 두 사람이 따로 만들었다. develop 에 있는 쪽은 `/record` 로 py-cord
`WaveSink` 를 걸어 화자별 wav 를 받아 두고, 회의가 끝난 뒤 별도 스크립트로 전사한다.
이 브랜치 쪽은 회의 중에 발화마다 전사해서 명령을 친 채널에 줄을 올린다.

처음에는 이 브랜치가 `capture/discord_adapter.py` 를 통째로 갈아끼웠다. 그러면 diff 가
"동료 파일을 지웠다" 로 읽힌다. 두 구현을 놓고 고르는 자리인데 한쪽이 없어진 상태로
리뷰가 시작되고, 비교하려면 리뷰어가 직접 develop 을 체크아웃해서 번갈아 봐야 한다.

## 검토한 선택지

덮어쓴 채로 둔다. diff 가 작고 파일이 하나다. 대신 리뷰가 "왜 지웠나" 부터 시작한다.

파일을 나누고 명령 이름을 바꾼다. 동료 파일은 develop 그대로 두고 실시간 쪽을
`capture/realtime_adapter.py` 로 옮긴 뒤 `/live` `/live-join` `/live-stop` 으로 부른다.
한 봇에 둘 다 붙고 서버에서 번갈아 눌러 볼 수 있다. 대신 같은 음성 연결을 두고 두 Cog 가
다투는 자리가 새로 생긴다.

실시간 쪽을 다른 브랜치나 다른 레포로 뺀다. 서로 안 건드리지만 나란히 비교하기가 가장
어렵다. 두 구현을 한 화면에서 보는 것이 이번 리뷰의 목적이라 먼저 뺐다.

## 결정

파일을 나눈다. 리뷰어가 브랜치 하나만 받아서 두 구현을 다 돌려 볼 수 있는 것이, 우리 쪽
diff 가 작은 것보다 중요했다.

클래스 이름도 바꿨다. `Bot.add_cog` 는 클래스 이름을 키로 쓰고 같은 이름이 이미 있으면
`ClientException` 을 던진다. 명령 이름은 py-cord 가 걸러 주지 않는다. 같은 이름 둘을 서로
다른 Cog 로 붙여 보면 `pending_application_commands` 에 둘 다 남아 그대로 등록 요청으로
나간다. 디스코드가 그때 무엇을 하는지는 확인하지 못했고, 확인하지 않아도 되게 이름을
갈라 놓았다.

`capture/recording_store.py` 하나만 공유 파일로 남긴다. `save_session` 안에 있던 매니페스트
쓰기를 `write_manifest` 로 뽑아내고 `save_session` 이 그걸 부르게 했다. 실시간 쪽은 화자별
wav 를 sink 에서 스트리밍으로 쓰기 때문에 `save_session` 의 입력 형태(메모리에 다 올린
raw bytes)를 쓸 수 없는데 매니페스트 형식은 같아야 한다. `stt/transcribe.py` 와
`stt/eval/eval.py` 가 `recordings/` 를 얕게 훑어 `session_*.json` 을 그 형식으로 읽는다.
되돌리면 형식이 두 벌이 되고 시간이 지나면 갈라진다. 두 함수의 출력이 바이트 단위로 같은
것은 `tests/test_realtime_adapter.py` 의
`test_write_manifest_and_save_session_write_the_same_bytes` 가 확인하고, 동료의
`tests/test_recording_store.py` 는 손대지 않은 채로 통과한다.

봇 계정은 서버마다 음성 연결을 하나만 갖고 그 연결의 리더도 하나다. 두 명령이 동시에
걸리면 오디오가 어긋난다. 그래서 실시간 쪽 명령은 `is_recording(vc)` 로 먼저 보고, 우리
sink 가 아닌 녹음이 돌고 있으면 시작하지도 멈추지도 않는다. 무엇이 돌고 있는지와 무엇으로
끝내는지를 답에 적는다. sink 를 못 읽으면 남의 것으로 센다. 판단이 틀릴 때 "우리 것을 못
멈춘다" 로 틀리는 편이 "남의 것을 멈춘다" 로 틀리는 것보다 낫다.

가드는 지금 한쪽만 온전하다. develop 의 `/record` 는 `is_recording` 을 보고 거절하므로
실시간 녹음 위에 겹쳐 걸리지 않는다. 그런데 `/join` 에는 그 검사가 없어서 녹음 중에
`move_to` 로 방을 옮길 수 있고, `/stop` 과 `/leave` 는 누가 건 리더인지 보지 않고
`stop_recording()` 을 불러 실시간 회의를 끝낸다. 동료 파일이라 고치지 않았다. 어떻게
할지는 같이 정하는 것이 맞다.

`required_intents()` 도 두 벌이고 값이 다르다. 동료 쪽은 `message_content` 를 켜고 실시간
쪽은 켜지 않는다. 봇은 인텐트를 하나만 갖기 때문에, 둘 다 붙이는 구성에서는 개발자 포털의
MESSAGE CONTENT 를 켜 두어야 한다. `.env.example` 주석을 그렇게 고쳤다.

## 다시 볼 조건

멘토가 한쪽을 고르면 이 항목은 끝난다. 남길 파일과 명령만 두고 나머지는 지운다.
둘을 합치기로 하면 이 결정을 번복하고, 어떤 구조로 합쳤는지를 새 항목에 적는다.

실시간 파이프라인은 2026-09-12 에 실제 음성 채널에서 끝까지 돌렸다. DAVE 복호화 563건에
실패 0, 패킷 크기는 전부 3840바이트로 설계 전제와 같았고, 종료 명령부터 회의록 파일까지
3.0초였다. 발화 사이 구간은 85~96% 가 무패킷이라 디스코드가 침묵에서 전송을 끊는 것도
확인했다.

다만 그 실행은 파일을 나누기 전이라 명령 이름이 `/record` `/stop` 이었다. 코드 경로는
그대로 옮겼지만 `/live` `/live-stop` 이라는 이름으로는 아직 실제 서버에서 다시 돌리지
않았다. 오프라인 쪽은 우리가 돌려 보지 않았다. 두 구현의 비용·부하 비교도 아직 같은
오디오로 나란히 재지 않았고, 그것이 이 결정을 닫기 전에 남은 일이다.
