# 0010. 임베딩 유사도 검색 threshold 를 0.4 로 잡는다

- 날짜: 2026-09-22
- 상태: 결정됨. 실제 서비스 데이터가 쌓이면 재보정 대상

## 배경

BE 가 벡터 검색으로 기존 Notion 후보를 찾아올 때(`search_similar_tasks`), 몇 점 이상을 "같은 task 로
볼 만한 후보"로 취급할지 기준이 없었다. #62(벡터 검색 연결)는 이 조립 자체가 BE 책임이라 닫았지만,
AI 가 소유한 `embed()`/`find_similar_candidates()`(PR #27)가 실제로 의미 있는 점수를 내는지, 그리고
threshold 를 어디에 둘지는 여전히 AI 쪽에서 근거를 줘야 하는 부분이었다.

## 검증 방법

fixture task 10개(로그인/소셜로그인/결제/환불/디자인시스템/회원가입/알림/검색/프로필/온보딩)에 대해
실제 임베딩 API로 시나리오 50개를 돌렸다(`judge/eval_embedding_search.py`, `runs/embedding_search_eval.csv`).
명확한 매치 10 / 명확한 불일치 10 / 짧은 보고 5 / 다중후보 구분 8 은 채점하고, 경계 케이스 8 / 엣지
케이스 9 는 정답이 없는 관찰용으로 점수 분포만 봤다. 결과: 채점 대상 36개 중 35개 통과(97%).

## 결정

| 구간 | 점수 |
|---|---|
| 명확한 불일치 최고점 | 0.33 |
| 명확한 매치 최저점 | 0.42 |
| **threshold** | **0.4** |

명확한 매치와 명확한 불일치 사이에 0.33~0.42 라는 빈 구간이 있었고, 그 사이인 0.4 를 threshold 로
잡는다. 단 이 값은 "후보로라도 Terra 2단계에 넘길 가치가 있는가"를 거르는 낮은 문턱이지, "같은 task 다"를
보장하는 기준이 아니다 — 경계 케이스(관련은 있지만 다른 하위작업)들이 0.34~0.59 구간에 걸쳐 있어서, 0.4를
넘겨도 실제로는 다른 task 인 경우가 있다(예: "결제 실패 알림을 푸시로" → task_payment 0.54). 같은 task 인지
최종 판단은 threshold 가 아니라 Terra 2단계가 문맥으로 한다.

부정문("로그인 기능은 안 하기로 했다")도 여전히 해당 task 로 높은 점수(0.52)가 나오는 것을 확인했다 —
임베딩은 주제만 보고 후보를 찾을 뿐, "하기로/안 하기로"라는 결정 내용까지는 못 잡는다. 이것도 threshold
로 해결할 문제가 아니라 Terra 2단계가 맡아야 한다는 근거다.

## 재검토 조건

- fixture 대신 실제 서비스에서 쌓인 Notion task 제목/문장으로 같은 검증을 다시 돌릴 수 있게 되면, 그
  데이터로 threshold 를 재보정한다
- BE 가 threshold 미만 후보를 전부 버리면 새로 들어온 내용이 반영 안 될 수 있으므로, threshold 미만이면
  "새 항목" 경로로 보내지 "무시"하지 않도록 한다(BE 쪽 구현 시 확인 필요)
