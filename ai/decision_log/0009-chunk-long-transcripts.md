# 0009. 긴 회의록을 청킹해서 추출한다

- 날짜: 2026-09-17
- 상태: 결정됨

## 배경

골든셋의 기존 최대 케이스가 16턴/29문장이었는데 실제 회의는 그보다 훨씬 길다. 약 10분 분량
(81턴/115문장/할일 34개)의 `long_meeting` 케이스를 만들어 돌려 보니 두 가지가 동시에 터졌다.

**(1) 출력이 잘려 케이스가 통째로 죽는다.** `max_completion_tokens=4000` 에 정확히 걸려
`LengthFinishReasonError` 가 났다. 잘리면 일부만 손실되는 게 아니라 JSON 파싱이 실패해서
**그 회의의 할일 전량이 사라진다.** 값을 16000 으로 올렸더니 이번엔 6000 에서 죽었다 —
게이트웨이를 직접 찔러 확인한 결과 Elice MLAPI 는 **요청값과 무관하게 완료 토큰을 6000 에서
하드캡**한다(16000 요청 → 3535 stop / 8000 요청 → 6000 length / 6500 요청 → 6000 length).
항목당 한국어 evidence_span+reasoning 포함 ~180 토큰이므로 **할일 약 30개가 한 번에 뽑을 수 있는
천장**이고, 이건 파라미터로 못 넘는다.

**(2) 길면 애매한 문장을 조용히 빠뜨린다.** 같은 내용을 짧은 케이스로 따로 돌리면 R=96% 인데
`long_meeting` 안에 넣으면 R=79% 로 떨어졌다. 놓친 7개의 위치가 앞 2 / 중간 2 / 뒤 3 으로
고르게 퍼져 있어 흔히 말하는 lost in the middle 이 아니었고, 전부 경계선 종결어미
("~하죠", "~기로 했어요")였다. 즉 **관련성 필터**가 후보 목록이 길어지면 보수적으로 변한다.

## 검토한 선택지

- **A. `max_completion_tokens` 만 올린다**: 코드 한 줄. 하지만 게이트웨이 하드캡 6000 이 진짜
  천장이라 **애초에 불가능**했다. (2)번 문제도 그대로 남는다.
- **B. 추출만 청킹**: 잘림은 막힌다. 실측 P 93%→97%, 그러나 R 은 79% 그대로 — 관련성 필터가
  이미 문장을 버린 뒤라 추출을 아무리 쪼개도 회복되지 않았다.
- **C. 관련성 필터까지 청킹**: 호출 수가 늘지만(115문장 = 관련성 3회 + 추출 3회) 실측
  P 100% / R 94% / F1 97% 로 길이에 의한 손실이 사실상 0 이 됐다.
- **D. 맵리듀스식 요약 후 추출**: 요약 단계에서 원문 표현이 뭉개져 `assignee_mention`(원문 그대로)과
  `evidence_span` 이 깨진다. 이 시스템은 근거 문장을 PM 에게 보여주는 게 핵심이라 안 맞는다.

## 결정

**C.** `extract_structured()` 는 관련 문장 20개씩, `filter_relevant()` 는 전체 문장 40개씩
연속 구간으로 끊어 호출한다.

| | P | R | F1 |
|---|---|---|---|
| 청킹 전 (한 번에) | 93% | 79% | 86% |
| B. 추출만 청킹 | 97% | 79% | 86% |
| C. 관련성 필터까지 청킹 | 100% | 94% | 97% |

청킹 비용이 낮은 이유가 있다 — **추출 프롬프트에는 원래 전체 대화록이 아니라 관련 문장만 들어간다.**
그래서 청킹으로 더 잃는 문맥은 청크 경계를 넘는 지시대명사 해소뿐이고, 연속 구간으로 끊어 그것도
최소화했다. 호출이 늘어나는 비용은 프롬프트 캐시가 상당 부분 흡수한다(2회차부터 입력의 절반이 캐시 히트).

청크 크기 20 / 40 은 6000 토큰 천장(≈할일 30개)에 여유를 둔 값이다. 근거 없는 정밀한 수치가
아니라 "천장의 2/3" 정도로 잡은 안전 마진이다.

## 다시 볼 조건

- **게이트웨이 출력 상한이 바뀌면.** 6000 이 올라가면 청크를 키워 호출 수를 줄일 수 있다.
  상한은 `ai/extract/llm.py` 의 `_CHUNK_SIZE` / `_RELEVANCE_CHUNK_SIZE` 주석에 근거와 함께 적어 뒀다.
- **60분(수백 턴) 회의록을 검증할 때.** 지금은 10분까지만 쟀다. 청크 수가 선형으로 늘 때
  비용·응답시간이 감당되는지, 청크 경계를 넘는 지시대명사 해소 실패가 눈에 띄게 늘지 확인해야 한다.
  거기서 무너지면 청크 간에 앞 청크의 이름·결정을 요약해 넘기는 방식을 검토한다.
- **모델을 바꿀 때.** 항목당 토큰 수와 긴 목록에서의 보수성은 모델마다 다르다. 두 숫자 다 재측정 대상.
