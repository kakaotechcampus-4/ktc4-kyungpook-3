# 0003. 실시간 전사는 발화 단위로 자르고, 발화마다 API 로 한 번 전사한다

- 날짜: 2026-09-11
- 상태: 확정

## 배경

회의 중에 전사를 채널에 띄우려면 오디오를 어디선가 잘라 STT 에 보내야 한다.
자르는 방식이 지연·정확도·비용을 한꺼번에 정한다.

골든셋(meeting-01/02, 실제 6인 녹음)에서 발화 길이를 재보니 화자당 평균 7.8~25초였다.
25초짜리는 `MAX_SEGMENT_MS` 상한에 걸린 것이라 실제로는 더 길었다.
다만 이 녹음은 각자 대본을 낭독한 것이라 실제 대화보다 발화가 길다.

## 검토한 선택지

**발화 단위만** - 무음 800ms 면 발화 확정 후 전사.
경계가 자연스럽고 무음에 과금되지 않는다. 종료 후 대기도 0 에 가깝다.
문제는 긴 발화가 끝날 때까지 화면에 아무것도 안 뜬다는 것이다.
25초 발화면 25 + 0.8 + STT 7.5 = 약 33초 뒤에 표시된다.

**고정 윈도우** - 3초마다 자름.
지연 상한이 확실하다. 대신 단어 중간에서 잘려 정확도가 떨어지고,
무음도 함께 보내 비용이 는다. 조각을 이어붙이는 후처리가 따로 필요하다.

**발화 단위 + 장발화 부분 전사** - 기본은 발화 단위. 발화가 6초를 넘으면
그 시점까지를 부분 전사해 먼저 올리고, 이어지면 같은 메시지를 편집한다.
발화가 끝나면 전체를 다시 전사해 최종본으로 덮는다.
복잡도가 올라가는 대신 지연 상한과 자연스러운 경계를 둘 다 얻는다.

## 결정

**발화 단위로 최종 전사만 한다. API 호출은 발화당 정확히 1회.**

부분 전사(로컬 작은 모델 + 버퍼 트리밍)는 설계했다가 구현 단계에서 뺐다 (2026-09-11).

- 로컬 모델을 봇을 돌리는 컴퓨터마다 깔아야 하는데 동료들 환경에서 그게 안 된다
- 체감 지연 차이가 크지 않다. 6초 미만 발화는 어차피 부분 전사가 안 돌고,
  긴 발화도 25초 상한에서 끊겨 확정본이 흐른다
- 데모와 운영 어느 쪽도 로컬 모델 의존이 없는 편이 낫다

빠지면서 파이프라인에서 가장 복잡하던 부분(부분 전사 큐, 워커, LocalAgreement 상태)이
같이 사라진다. 남는 것은 큐 하나, 워커 셋, 발화당 API 1회다.

첫 글자까지 지연은 발화 길이 + 0.8초 + API 시간이다. 5~15초 발화면 7~20초,
25초 상한 독백이면 약 33초. 데모 체감이 문제면 `MAX_SEGMENT_MS` 를 15초로 내리는
선택지가 남는다. 비용은 같고 턴 묶기가 메시지를 하나로 잇는다.

`LocalStt` 는 API 장애 폴백으로 코드만 남기고 기본 경로에는 배선하지 않는다.
faster-whisper 는 설치되지만 모델 가중치가 첫 호출에 내려받히기 때문이다.

유료 오디오가 1배이고 API 호출은 발화당 정확히 1번이다.

같은 오디오를 API 로 반복해 보내는 안(누적 3.4배, 증분+최종 1.82배)은 버렸다.
골든셋에서 실측한 배수이고 크레딧 12만원 대비 최악 12% 라 감당은 되지만,
공짜로 할 수 있는 일에 돈을 쓸 이유가 없다.

호출 수를 발화당 1번으로 묶은 것은 비용 때문만이 아니다. **Elice 의 최소 과금
단위를 확인하지 못했다.** 호출당 60초로 올림한다면 6초짜리 호출 5번이 30초가
아니라 5분으로 청구된다. 잘게 쪼개는 설계는 이 미확인 값에 결과가 좌우된다.

### (폐기) 부분 전사에 버퍼 트리밍을 쓰려 했다

아래는 빼기 전 설계다. 다시 넣게 될 때 참고용으로 남긴다.

whisper_streaming(UFAL) 의 LocalAgreement-2 방식이다. 버퍼 전체를 재전사하되
직전 가설과 연속 2회 일치하는 단어 접두사만 확정하고, **그 지점에서 오디오를
잘라 버린다.** 재전사 길이에 상한이 생겨 발화가 길어져도 연산이 발산하지 않는다.

시계 눈금이 아니라 확정된 단어 끝에서 자르므로 **경계에서 단어가 깨지지 않는다.**
고정 6초 간격으로 자르는 안을 버린 이유가 이것이다.

로컬 연산은 버퍼가 트리밍으로 15초에 묶이고 평균 8초, base-int8 의 RTF 0.14 이면
한 번에 1.1초다. 2초마다 돌리면 코어의 55% 를 쓴다. 회의에서는 보통 한 명씩
말하므로 동시에 도는 것은 1~2 개다. **계산이고 측정이 아니다.** t3.medium 은
서버를 받으면 잰다. 부담이 크면 부분 전사만 끈다. 최종 전사는 그대로 동작한다.

### 발화와 턴을 나눈다

| | 경계 | 쓰는 곳 |
|---|---|---|
| 발화 | VAD. 침묵 800ms · 패킷 끊김 800ms · 상한 25초 · flush | STT 호출 단위, `transcript.jsonl` |
| 턴 | 같은 화자의 연속 발화 묶음 | 디스코드 메시지 1개, `transcript.md` |

800ms 쉬고 이어 말하면 VAD 는 새 발화로 본다. 그대로 두면 한 문장이 메시지 두 개로
쪼개지고, 추출에서 "그럼 그건 제가 할게요" 의 *그건* 이 앞 발화에 남아 문맥이 끊긴다.

턴으로 묶는 조건은 셋을 모두 만족해야 한다.

1. 같은 화자
2. 직전 발화 종료로부터 3초 이내
3. 그 사이에 다른 화자의 메시지가 게시되지 않았을 것

세 번째가 없으면 B 가 말한 뒤에 A 의 옛 메시지가 편집되어 화면 순서가 실제 순서와
어긋난다. 25초 상한에 강제로 끊긴 독백도 같은 턴이라 한 메시지로 이어진다.

3초는 측정값이 아니다. AssemblyAI 의 턴 침묵 상한 1280ms 보다 넉넉하게 잡았다.
설정값으로 빼두고 다음 녹음에서 실제 간격 분포를 보고 조정한다.

## 시간축 권위는 도착 시각이다 (2026-09-11 정정)

처음에는 RTP 타임스탬프를 시간축 권위로 쓰려 했다. 지터가 없다는 이유였다.
멘토가 참고하라고 한 Craig(craig.chat) 소스를 읽고 바꿨다.

**Craig 가 하는 것** (`apps/bot/src/modules/recorder/recording.ts` `onData()`):
`process.hrtime(startTime)` 으로 도착 시각을 잡아 그것을 위치로 쓴다.
RTP 원값은 0바이트 패킷의 granule 로 기록만 해두고 합성에는 쓰지 않는다
(`cook/oggstender.c` 주석 "timestamp references"). SSRC 는 레포 전체에 안 쓴다.

**왜 그게 맞나.** RTP 는 발신자 클럭이다. 여섯 명이면 클럭이 여섯 개고 서로
드리프트한다. 도착 시각은 봇 클럭 하나라 **화자 간 순서 비교에 구조적으로 유리하다.**
우리에게 필요한 정밀도는 초 단위이고 네트워크 지터는 수십 ms 다.

RTP 방식의 실패 모드도 이미 겪었다. 원점이 SSRC 마다 난수라 재접속하면 기준점이
어긋나 시각이 12시간까지 튀었다. 도착 시각에는 그런 실패가 없다.

**그래서 이렇게 한다.**

| 쓰임 | 무엇으로 |
|---|---|
| 발화 위치 (start_ms/end_ms) | **도착 시각** |
| 순서 뒤바뀜 감지 | RTP 타임스탬프 |
| SSRC | 안 쓴다 |

과거를 가리키는 오프셋을 무시하려던 규칙도 버린다. UDP 에서 순서 뒤바뀜은
정상이고, 그 규칙은 회선이 나쁠 때 실제 음성을 조용히 더 버린다.
Craig 처럼 짧은 재정렬 창(16패킷, 320ms)을 두고 RTP 로 정렬만 한다.

## 침묵 프레임을 먼저 걸러야 한다 (2026-09-11 추가)

"말을 멈추면 패킷이 끊긴다" 는 절반만 맞다. 디스코드는 Opus 침묵 프레임
`0xF8 0xFF 0xFE` 을 보내고, Cloudflare 보이스 서버는 한 바이트 빼고 전부 0인
쓰레기 패킷을 보낸다 (Craig `onData:780`, dysnomia `VoiceConnection.js:935`).

**py-cord 는 이걸 걸러주지 않는다.** `voice/receive/reader.py:261` 이
`is_silence()` 로 버리는 건 SSRC 를 모르는 경우뿐이고, 정상 SSRC 면 sink 까지 온다.

에너지 VAD 가 뒷받침하므로 침묵으로 판정되기는 한다. 다만 "패킷 공백 = 침묵"
이라는 전제가 항상 성립하지는 않으므로, 공백 판정 **전에** 이 두 종류를 걸러낸다.

## 근거가 되는 사실

py-cord PR #3159 은 **무음 구간을 채우지 않는다.** `SilencePacket` 클래스가
정의돼 있지만 패키지 어디서도 쓰이지 않는다. 말을 멈추면 패킷이 그냥 끊긴다
(단, 위 "침묵 프레임" 절처럼 잡음 패킷이 오는 경우는 따로 거른다).

그래서 VAD 는 받은 오디오 길이가 아니라 **sink 가 넘겨주는 절대 시각**을 써야 한다.
그 시각은 도착 시각이다. `sink.write` 에 오는 `VoiceData.packet.timestamp` 는
재정렬에만 쓰고 위치 계산에는 쓰지 않는다 (위 "시간축 권위는 도착 시각이다" 절).

## 알려진 한계

짧은 발화 임계 `MIN_SPEECH_MS = 320` 은 기침을 거르지만 "저요", "네" 같은
짧은 유효 발화도 함께 버릴 수 있다. **이 비율은 측정하지 않았다.**
지금 골든셋이 낭독이라 기침도 짧은 응답도 들어 있지 않다.
담당자가 빠지는 문제가 생기면 여기부터 본다.
