# 0003. 실시간 전사는 발화 단위로 자르고, 발화마다 API 로 한 번 전사한다

- 날짜: 2026-09-11 (실측 2026-09-12 추가)
- 상태: 결정됨

## 배경

회의 중에 전사를 채널에 띄우려면 오디오를 어디선가 잘라 STT 에 보내야 한다. 자르는 방식이
지연·정확도·비용을 한꺼번에 정한다.

골든셋(meeting-01/02, 실제 6인 녹음)에서 발화 길이를 재보니 화자당 평균 7.8~25초였다.
25초짜리는 `MAX_SEGMENT_MS` 상한에 걸린 것이라 실제로는 더 길었다. 다만 이 녹음은 각자
대본을 낭독한 것이라 실제 대화보다 발화가 길다.

## 검토한 선택지

- **발화 단위만** (무음 800ms 면 확정 후 전사): 경계가 자연스럽고 무음에 과금되지 않는다.
  종료 후 대기도 0 에 가깝다 / 긴 발화가 끝날 때까지 화면에 아무것도 안 뜬다. 25초 발화면
  25 + 0.8 + STT 약 33초 뒤에 표시된다.
- **고정 윈도우** (3초마다 자름): 지연 상한이 확실하다 / 단어 중간에서 잘려 정확도가
  떨어지고, 무음도 함께 보내 비용이 는다. 조각을 이어붙이는 후처리가 따로 필요하다.
- **발화 단위 + 장발화 부분 전사** (6초를 넘으면 그 시점까지 먼저 올리고 끝나면 덮어씀):
  지연 상한과 자연스러운 경계를 둘 다 얻는다 / 로컬 모델 의존이 생기고 부분 전사 큐·워커·
  LocalAgreement 상태가 붙어 파이프라인에서 가장 복잡한 부분이 된다.

## 결정

**발화 단위로 최종 전사만 한다. API 호출은 발화당 정확히 1회.**

부분 전사는 설계했다가 구현 단계에서 뺐다. 로컬 모델을 봇 돌리는 컴퓨터마다 깔아야 하는데
동료들 환경에서 그게 안 되고, 체감 지연 차이도 크지 않다. 6초 미만 발화는 어차피 부분 전사가
안 돌고 긴 발화도 25초 상한에서 끊겨 확정본이 흐른다. 빠지면서 부분 전사 큐·워커·
LocalAgreement 상태가 같이 사라졌다. 남는 것은 큐 하나, 워커 셋, 발화당 API 1회다.

`LocalStt` 는 API 장애 폴백으로 코드만 남기고 기본 경로에는 배선하지 않는다. faster-whisper 는
설치되지만 모델 가중치가 첫 호출에 내려받히기 때문이다.

**비용.** 유료 오디오가 1배이고 호출이 발화당 1번이다. 같은 오디오를 반복해 보내는 안(누적
3.4배, 증분+최종 1.82배)은 버렸다. 골든셋 실측 배수이고 크레딧 12만원 대비 최악 12% 라 감당은
되지만, 공짜로 할 수 있는 일에 돈을 쓸 이유가 없다. 다만 **Elice 의 최소 과금 단위를 확인하지
못했다.** 호출당 60초로 올림한다면 6초짜리 5번이 30초가 아니라 5분으로 청구된다. 잘게 쪼개는
설계는 이 미확인 값에 결과가 좌우된다.

### 발화와 턴을 나눈다

| | 경계 | 쓰는 곳 |
|---|---|---|
| 발화 | VAD. 침묵 800ms · 패킷 끊김 800ms · 상한 25초 · flush | STT 호출 단위, `transcript.jsonl` |
| 턴 | 같은 화자의 연속 발화 묶음 | 디스코드 메시지 1개, `transcript.md` |

800ms 쉬고 이어 말하면 VAD 는 새 발화로 본다. 그대로 두면 한 문장이 메시지 두 개로 쪼개지고,
추출에서 "그럼 그건 제가 할게요" 의 *그건* 이 앞 발화에 남아 문맥이 끊긴다.

턴으로 묶는 조건은 셋을 모두 만족해야 한다. 같은 화자일 것, 직전 발화 종료로부터 3초 이내일
것, 그 사이에 다른 화자의 발화가 확정되지 않았을 것. 세 번째가 없으면 B 가 말한 뒤에 A 의 옛
메시지가 편집되어 화면 순서가 실제 순서와 어긋난다.

턴은 **VAD 가 발화를 확정하는 시점**에 배정한다. 전사가 끝나는 시점에 배정하면 워커 셋이 같은
화자의 발화를 순서 바꿔 끝낼 때 18초 떨어진 발화가 한 턴으로 합쳐지고 마지막 종료 시각이
되감긴다.

3초는 측정값이 아니다. AssemblyAI 의 턴 침묵 상한 1280ms 보다 넉넉하게 잡았다. 설정값으로
빼두고 다음 녹음에서 실제 간격 분포를 보고 조정한다.

### 시간축 권위는 도착 시각이다

처음에는 RTP 타임스탬프를 쓰려 했다. 지터가 없다는 이유였다. 멘토가 참고하라고 한
Craig(craig.chat) 소스를 읽고 바꿨다. Craig 는 `recording.ts` `onData()` 에서
`process.hrtime(startTime)` 으로 도착 시각을 잡아 그것을 위치로 쓰고, RTP 원값은 기록만 해두고
합성에는 쓰지 않는다.

RTP 는 발신자 클럭이다. 여섯 명이면 클럭이 여섯 개고 서로 드리프트한다. 도착 시각은 봇 클럭
하나라 화자 간 순서 비교에 구조적으로 유리하다. 필요한 정밀도는 초 단위이고 네트워크 지터는
수십 ms 다. RTP 방식의 실패 모드도 이미 겪었다 - 원점이 SSRC 마다 난수라 재접속하면 기준점이
어긋나 시각이 12시간까지 튀었다.

| 쓰임 | 무엇으로 |
|---|---|
| 발화 위치 (start_ms/end_ms) | **도착 시각** |
| 순서 뒤바뀜 감지 | RTP 타임스탬프 |
| SSRC | 안 쓴다 |

과거를 가리키는 오프셋을 무시하려던 규칙도 버렸다. UDP 에서 순서 뒤바뀜은 정상이고, 그 규칙은
회선이 나쁠 때 실제 음성을 조용히 더 버린다. Craig 처럼 짧은 재정렬 창(16패킷, 320ms)을 두고
RTP 로 정렬만 한다.

### 침묵 프레임을 먼저 거른다

"말을 멈추면 패킷이 끊긴다" 는 절반만 맞다. 디스코드는 Opus 침묵 프레임 `0xF8 0xFF 0xFE` 을
보내고, Cloudflare 보이스 서버는 한 바이트 빼고 전부 0인 쓰레기 패킷을 보낸다 (Craig
`onData:780`, dysnomia `VoiceConnection.js:935`). py-cord 는 이걸 걸러주지 않는다 -
`voice/receive/reader.py:261` 이 `is_silence()` 로 버리는 건 SSRC 를 모르는 경우뿐이다.

에너지 VAD 가 뒷받침하므로 침묵으로 판정되기는 한다. 다만 "패킷 공백 = 침묵" 이라는 전제가
항상 성립하지는 않으므로 공백 판정 **전에** 이 두 종류를 걸러낸다.

py-cord PR #3159 은 무음 구간을 채우지 않는다. `SilencePacket` 클래스가 정의돼 있지만 패키지
어디서도 쓰이지 않는다. 그래서 VAD 는 받은 오디오 길이가 아니라 sink 가 넘겨주는 절대 시각을
써야 한다.

## 실측 (2026-09-12)

골든셋 `meeting-01` 6트랙, 합계 209.6초. `--stt fake` 라 무과금이고 전사 시간은 빠져 있다.

```bash
.venv/bin/python stt/eval/realtime_bench.py --tracks "<골든셋 audio 디렉토리>" --pace
```

| | |
|---|---|
| 발화 | 16건 · STT 호출 16건 |
| 말 필터 | 통과 16 · 거름 2 · 오류 0 |
| 발화별 첫 줄 지연 | 중앙값 0.87초 · 최대 1.02초 |
| 종료 후 산출 | 0.08초 |
| 수신 패킷 | 6020 · 잡음 0 · write 오류 0 · 화자 미상 0 |

`--pace` 를 켜야 오디오가 실제 속도로 흐른다. 끄면 순간 주입이라 발화가 실제보다 길게 뭉치고
지연 수치도 체감 지연이 아니다. 발화 수는 실행마다 한두 건 흔들린다 - 침묵 청소가 도는 시점과
패킷이 오는 시점이 맞물리는 자리다.

**임계를 바꾸면 이렇게 갈린다.**

| 바꾼 값 | 발화 | 첫 줄 지연 중앙값 | 거름 |
|---|---|---|---|
| `--silence-hold-ms 300` | 6건 | 0.31초 | 1 |
| 기본 (800) | 16건 | 0.87초 | 2 |
| `--silence-hold-ms 1500` | 8건 | 1.61초 | 0 |
| `--gate-ratio 0.95` | 13건 | 0.89초 | **7** |
| `--no-gate` | 19건 | 0.83초 | 끔 |

`SILENCE_HOLD_MS` 를 내리면 지연이 그만큼 줄지만 발화가 잘게 쪼개지고, 쪼개진 조각이
`MIN_SPEECH_MS = 320` 아래로 떨어지면서 오히려 살아남는 발화가 준다. 300 에서 6건인 이유가
그것이다. `--min-speech-ms` 는 200·320·800 이 같은 결과를 냈다. 골든셋이 낭독이라 그 부근의
짧은 발화가 표본에 없어 **이 값의 효과는 아직 재지 못했다.**

**Elice 응답 시간은 들쭉날쭉하다** (2026-09-12, 실제 회의 오디오 4건).

| 클립 | 길이 | 전사 |
|---|---|---|
| A | 8.70초 | 22.57초 |
| B | 2.04초 | 2.70초 |
| C | 0.96초 | 2.62초 |
| C 재호출 | 0.96초 | 20.58초 |

같은 입력이 2.62초와 20.58초로 갈린다. 길이에 비례하지 않으므로 발화 단위로 쪼개는 설계 자체는
유지된다. 평상시 2.6초 정도이고 가끔 20초 이상으로 튄다.

## 영향받은 파일

- `stt/vad.py` 화자별 스트리밍 VAD, `sweep()` 로 패킷 끊긴 발화 마감
- `stt/session.py` 큐 하나·워커 셋·발화당 1회, 침묵 청소 스레드
- `stt/turns.py` 같은 화자 연속 발화를 턴으로 묶기
- `capture/timeline.py` 침묵 프레임·쓰레기 패킷 필터, RTP 재정렬 창
- `capture/streaming_sink.py` 도착 시각 기준 위치 부여
- `stt/eval/realtime_bench.py` 위 수치를 내는 스크립트

## 다시 볼 조건

Elice 의 최소 과금 단위가 확인되면 다시 본다. 호출당 60초 올림이면 발화 단위로 쪼개는 것이
불리해지고 묶어 보내는 쪽으로 뒤집힌다.

Elice 응답 시간의 꼬리가 계속 20초대로 나오면 종료 대기(`session.close` 10초)를 늘리거나 늦게
온 줄을 회의록에 넣는 구조가 필요하다. 지금은 꼬리에 걸린 줄이 마감 뒤에 도착해 버려진다.

`MAX_SEGMENT_MS` 25초는 데모 체감이 문제가 되면 15초로 내린다. 비용은 같고 턴 묶기가 메시지를
하나로 잇는다.

## 알려진 한계

짧은 발화 임계 `MIN_SPEECH_MS = 320` 은 기침을 거르지만 "저요", "네" 같은 짧은 유효 발화도 함께
버릴 수 있다. **이 비율은 측정하지 않았다.** 지금 골든셋이 낭독이라 기침도 짧은 응답도 들어
있지 않다. 담당자가 빠지는 문제가 생기면 여기부터 본다.
