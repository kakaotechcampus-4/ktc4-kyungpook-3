# 0004. 전사 큐는 봇 안에 하나만 두고, AI-BE 사이에는 큐 서버를 두지 않는다

- 날짜: 2026-09-11
- 상태: 결정됨 (전사 구간). 추출 이후 구간은 범위 밖

## 배경

"큐 구조"가 한 덩어리로 불리는데 실제로는 성격이 다른 두 곳이다. 하나로 설계하면 한쪽에 과한
구조가 들어가고 다른 쪽은 못 막는다.

| | 봇 내부 | AI → BE |
|---|---|---|
| 흐르는 것 | 오디오 조각, 전사 결과 | 확정된 발화 레코드 |
| 주기 | 20ms 패킷, 발화당 수 초 | 회의당 수십 건 |
| 유실 허용 | 부분 전사는 허용, 확정본은 불가 | 불가 |
| 경계 | 한 프로세스 안 | 프로세스를 넘음 |
| 지연 요구 | 초 단위 | 회의 종료 후 10분 |

주기가 세 자릿수 차이다. 같은 도구로 덮으면 한쪽이 반드시 어긋난다.

## 검토한 선택지

**봇 내부 - 큐를 몇 개 둘 것인가** (부분 전사가 있던 시점의 비교다)

- **큐 하나**: 단순하다 / 부분 전사와 확정본이 같은 줄에 서면 부분이 확정본을 밀어낸다. 부분은
  2초마다, 확정본은 발화당 한 번이라 빈도 높은 쪽이 큐를 채운다. 화면에 중간 결과만 계속 뜨고
  확정본이 안 나온다.
- **우선순위 큐 하나**: 밀어내기는 풀린다 / 부분 전사가 쌓여도 안 버려진다. 늦게 도착한
  "말하는 중" 표시는 이미 확정본이 덮어쓴 뒤라 쓸모없는데 그걸 처리하느라 워커 시간을 쓴다.
- **큐 둘**: 성격이 다르니 정책도 다르게 둔다. `final` 은 상한 없이 안 버리고 `partial` 은
  상한 1 로 최신 것만 남긴다 / 관리할 상태가 는다.

**AI → BE 인계**

- **별도 큐 서버를 둔다 (Redis / RabbitMQ + Celery)**: 받는 쪽이 죽어도 일이 안 사라지고
  일꾼을 여러 개 붙여 나눠 처리할 수 있다 / 상시 떠 있어야 하는 프로세스가 하나 늘고, 그게
  죽으면 일이 그 안에 갇히고, 장애가 어디서 났는지 쫓기 어려워진다.
- **HTTP 직접 호출 + 재시도**: 붙일 게 없다 / 받는 쪽이 죽으면 그 호출은 실패한다.

## 결정

**봇 내부는 큐 하나, 워커 셋.** 부분 전사를 빼면서(0003 참고) `partial` 큐가 사라졌다. 남는
것은 확정본 `final` 큐 하나이고 상한 없이 절대 버리지 않는다. 위 "큐 둘" 판단은 부분 전사가
있을 때의 것이라 기록용으로 남긴다.

py-cord 는 소켓 수신 스레드에서 `sink.write(data, user)` 를 부른다. 여기서 무거운 일을 하면
패킷을 흘린다. 그래서 세 겹으로 가른다.

```
[수신 스레드]  PCM 변환 → 화자별 VAD → 발화 확정 시 큐에 put   (20ms 예산)
[STT 워커 x3]  큐 → 전사 → 게시 큐
[asyncio 루프] 게시 큐 → 합치기 → 채널 전송/편집
```

워커를 셋으로 둔 것은 여섯 명이 비슷한 시점에 말을 끝내면 6건이 한꺼번에 들어오기 때문이다.
워커 하나면 순차 처리라 마지막 발화가 14초 밀린다. API 호출은 네트워크 대기라 스레드를 늘려도
GIL 에 안 막힌다. 로컬 모델로 폴백하면 얘기가 다르다 - 그쪽은 CPU 바운드라 워커 수가 코어 수를
넘으면 오히려 느려지므로 백엔드에 따라 다르게 둔다.

**AI → BE 인계에는 별도 큐 서버를 두지 않는다.** 원준님 PR #19 의 `POST /extractions` 가 인계
지점이다. 규모가 안 맞는다 - 회의 한 건이 발화 수십 건이고 동시 회의는 사실상 1건이다.
t3.medium 2 vCPU 에 큐 서버를 얹으면 STT 가 쓸 코어를 뺏는다.

그리고 이미 창고가 있다. 전사가 `transcript.jsonl` 로 먼저 떨어지므로 BE 호출이 실패해도
데이터가 남고, 재시도는 파일을 다시 읽으면 된다. 큐 서버를 넣으면 데이터가 남는 곳이 둘이
되고 어느 쪽이 원본인지가 애매해진다.

필요한 것은 셋뿐이다. 전사 완료 후 `transcript.jsonl` 기록과 `POST /extractions` 호출, 실패 시
지수 백오프 3회(그래도 실패하면 파일만 남기고 로그), 그리고 `meeting_id` 를 멱등 키로 두어
같은 회의를 두 번 보내도 한 번만 반영되게 하는 것.

## 범위 밖

추출·판정·초안 단계는 이 결정이 다루지 않는다. 그쪽은 LLM 호출이 회의당 여러 번이고 실패
비용이 비싸서 작업 큐가 정당할 수 있다. 전사 인계 구간에 큐 서버가 과하다는 것이지 파이프라인
전체에 대한 판단이 아니다.

## 다시 볼 조건

동시 회의가 여러 건이 되어 STT 가 대기열을 타야 할 때 큐 서버를 붙인다. 지금 붙이면 안 쓰는
코드를 운영하게 된다.

워커 3개가 적정한지는 **측정하지 않았다.** 6인 동시 발화 버스트를 오프라인 하니스로 재현해 큐
대기 시간을 재본 뒤 정한다. 지금 3은 계산값이다.
