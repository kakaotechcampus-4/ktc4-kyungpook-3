# 0004. 전사 큐는 둘이고 성격이 다르다. 브로커는 넣지 않는다

- 날짜: 2026-09-11
- 상태: 제안 (김환 확인 필요)

## 배경

"큐 구조"가 팀 안에서 한 덩어리로 불리는데, 실제로는 성격이 완전히 다른 두 곳이다.
하나로 설계하면 한쪽에 과한 구조가 들어가고 다른 쪽은 못 막는다.

| | 봇 내부 | AI → BE |
|---|---|---|
| 무엇이 흐르나 | 오디오 조각, 전사 결과 | 확정된 발화 레코드 |
| 주기 | 20ms 패킷, 발화당 수 초 | 회의당 수십 건 |
| 유실 허용 | 부분 전사는 허용, 확정본은 불가 | 불가 |
| 프로세스 | 한 프로세스 안 | 프로세스 경계를 넘음 |
| 지연 요구 | 초 단위 | 회의 종료 후 10분 |

## 봇 내부 - 스레드 셋과 큐 둘

py-cord 는 소켓 수신 스레드에서 `sink.write(data, user)` 를 부른다. 여기서 무거운
일을 하면 패킷을 흘린다. 그래서 세 겹으로 가른다.

```
[수신 스레드]  PCM 변환 → 화자별 VAD → 발화 확정 시 큐에 put   (20ms 예산)
[STT 워커 x3]  큐 → 전사 → 게시 큐
[asyncio 루프] 게시 큐 → 토큰버킷 → 채널 전송/편집
```

워커가 셋인 이유는 버스트다. 여섯 명이 비슷한 시점에 말을 끝내면 6건이 한꺼번에
들어온다. 워커 하나면 마지막 발화가 14초 밀린다. API 는 네트워크 대기라 스레드를
늘려도 GIL 에 안 막힌다.

**큐를 둘로 나눈다.** 부분 전사와 확정본을 한 큐에 넣으면 부분이 확정본을 밀어낸다.
화면에 중간 결과만 계속 뜨고 확정본이 안 나오는 상태가 된다.

| 큐 | 상한 | 넘칠 때 |
|---|---|---|
| `final` | 없음 | 버리지 않는다. 회의록 자체다 |
| `partial` | 1 | 버린다. 최신 것만 남긴다 |

이게 백프레셔 정책이다. 부분 전사는 "말하는 중" 표시라 늦으면 의미가 없고,
확정본은 버리면 회의 기록이 사라진다. STT 가 밀리면 부분 전사가 먼저 희생된다.

## AI → BE - 브로커를 넣지 않는다

원준님 PR #19 에 `POST /extractions` 가 이미 있다. 여기가 인계 지점이다.
Redis, Celery, RabbitMQ 를 넣자는 얘기가 나올 수 있는데 지금은 반대한다.

**규모가 안 맞는다.** 회의 한 건이 발화 수십 건이고 동시 회의는 사실상 1건이다.
t3.medium 2 vCPU 에 브로커를 얹으면 STT 가 쓸 코어를 뺏는다.

**실패 모드가 늘어난다.** 브로커가 죽으면 회의록이 큐에 갇힌다. 지금 구조에서는
전사가 파일(`transcript.jsonl`)로 먼저 떨어지므로, BE 호출이 실패해도 데이터가 남는다.
재시도는 파일을 다시 읽으면 된다.

**필요한 건 재시도와 멱등성뿐이다.**

- 전사 완료 → `transcript.jsonl` 기록 → `POST /extractions` 호출
- 실패하면 지수 백오프로 3회. 그래도 실패하면 파일만 남기고 로그에 남긴다
- `meeting_id` 를 멱등 키로 둔다. 같은 회의를 두 번 보내도 한 번만 반영되게

브로커가 필요해지는 시점은 **동시 회의가 여러 건이 되어 STT 가 대기열을 타야 할 때**다.
그때 붙이면 되고, 지금 붙이면 안 쓰는 코드를 운영하게 된다.

## 김환님께 확인이 필요한 것

이 문서는 **합의된 것이 아니라 내 제안**이다. `현황.md` 에 "큐 구조는 김환" 으로
적혀 있는데 레포에 코드도 문서도 없어서 내가 먼저 정했다.

물어볼 것 셋.

1. 추출·판정·초안 단계에 별도 작업 큐를 두려고 했는가. 그렇다면 LLM 호출이
   회의당 여러 번이라 거기는 브로커가 정당할 수 있다. 내 반대는 전사 인계 구간에 한정된다
2. `POST /extractions` 를 AI 가 직접 부르는 게 맞는가, 아니면 BE 가 폴링하는가
3. 멱등 키를 `meeting_id` 로 잡아도 되는가. 재전송 시 BE 가 어떻게 처리하는가

## 안 해본 것

워커 3개가 적정한지는 **측정하지 않았다.** 6인 동시 발화 버스트를 오프라인 하니스로
재현해 큐 대기 시간을 재본 뒤 정한다. 지금 3은 계산값이다.
