# 0008. 전사는 회의가 끝난 뒤 배치로 한다. 화자별 클립을 턴으로 묶어 보내고 한 시간축에 놓는다

- 날짜: 2026-09-16 (측정 2026-09-15 ~ 16)
- 상태: 결정됨. 0003(회의 중 발화 단위 전사)을 번복한다. 운영 기본 백엔드(API/로컬)는 t3.medium
  측정(#40) 뒤 확정. "측정 중" 은 2026-09-16 저녁 기준으로 아직 안 끝난 설정이다. 표는 회의마다 한 줄이다

## 배경

회의 중 전사(0003)는 고려할 것이 많고 구현이 복잡한 데 비해 얻는 것이 적었다. 회의가 끝난 뒤
저장된 트랙을 배치로 전사하는 쪽으로 정했다. 실시간을 만들면서 알게 된 것은 그대로 쓴다.
트랙이 회의 시계 위에 쓰인다는 것, VAD 상수, 말 필터, 그리고 아래 API 지연 분포다.

**API 지연은 길이가 아니라 확률의 문제였다.** 같은 1초 클립을 Elice 에 20번 보냈다.

```
2.4초 × 17회 / 22.0 · 25.0 · 27.8초 × 3회       p50 2.62  p95 25.15  max 27.81
```

길이별 3회씩: 1초 2.4초, 3초 2.4~3.0초, 5초 3.2초(1회는 20.95초), 10초 3.8초, 20초 9.8초,
30초 14.3초. 고정비 약 2.4초에 길이의 0.45배가 붙고, 그와 별개로 호출의 15% 가 길이와 무관하게
22~28초 멈춘다. 첫 호출도 아니고(1·4·6번째) 동시 호출도 아니었다(순차). 서버 쪽이라 줄일 수
없다. 실제 회의에서 이 꼬리가 종료 대기를 넘겨 발화를 잃었다. 재시도는 멈춤을 두 배로 늘릴
뿐이라 안 쓴다. 배치에서는 호출을 여럿 겹쳐 꼬리를 흡수하고 호출 수를 줄여 노출을 줄인다.

**트랙을 통째로 넣으면 안 된다.** 이전 `transcribe.py` 는 트랙 wav 를 그대로 모델에 넣었다.
6인 60분이면 무음 포함 360분이 들어간다. 무음 구간에서 위스퍼는 앞 문장을 반복하거나 문장을
지어낸다. 74.7초 파일이 한 문장을 무한 반복해 CER 87% 가 된 사례가 0007 에 있고, 회의 길이
트랙에서는 아래 표 1 처럼 무너진다.

**시간축은 트랙 파일이 이미 갖고 있다.** `TrackWriter` 가 화자별 wav 를 회의 시계 하나 위에 쓴다.
패킷 도착 시각이 위치이고 안 온 구간은 0 이다. 그래서 파일 안의 샘플 위치가 곧 회의 경과 시각이고
트랙별 오프셋이 필요 없다. VAD 가 준 `start_ms` 가 그대로 절대 시각이며, 화자를 섞어 `start` 로
정렬하면 회의록이다. `SyncedWaveSink` 도 앞을 무음으로 채워 같은 모양을 만들지만 `time.time()`
이라 NTP 보정에 흔들린다(#41).

## 검토한 선택지

트랙을 VAD 로 발화 클립으로 자른 뒤 무엇을 모델에 보내느냐로 넷이 갈린다. `stt/batch.py` 에
네 모드로 같이 두어 같은 시간축 위에서 비교했다.

- **whole. 이전 방식 그대로**: 옵션 없이 트랙 통째. 무음 자리 단어도 남긴다. 비교 기준.
- **clip. 클립 하나씩**: 실시간 경로가 보내던 단위 그대로. 무음 0, API 비용 최소 / 앞뒤 문맥이
  없고, 로컬 모델은 클립마다 30초 창을 채우는 고정비(turbo 약 5초)가 들어 호출 수만큼 손해다.
- **chunk. 같은 화자의 클립을 턴으로 묶어 침묵 없이 28초 안으로 이어 붙여 보낸다**: 문맥이 살고
  무음은 안 간다. 호출 수가 화자당 한두 번이라 API 멈춤 노출도 준다. 단어 시각으로 클립에
  되돌리므로 시각은 클립 단위로 남는다 / 단어 시각이 없는 백엔드면 되매핑을 못 한다(Elice 도
  준다, 실측 unmapped 0). 28초는 위스퍼 창 30초 아래로 잡은 값이다.
- **track. 트랙 통째에 반복 억제 옵션**: `condition_on_previous_text=False`,
  `hallucination_silence_threshold=1.0` (treesoop 이 쓰는 두 옵션). VAD 가 말이 없다고 본
  자리의 단어는 버린다. 문맥 최대 / 무음까지 다 계산하고, 옵션이 오히려 진짜 발화를 건너뛰게
  한다(표 4). 로컬 전용이다. API 로 보내면 무음까지 과금이다.

단위는 셋이다. 클립은 VAD 가 침묵(800ms, 8초 넘긴 발화는 400ms)에서 자른 조각이고 STT
되매핑의 최소 단위다. 턴은 같은 화자의 클립이 3초 안에 이어진 묶음이고 회의록 한 줄, seq
하나다. 사이에 다른 화자의 클립이 시작하면 거기서 끊는다. 묶음은 STT 에 한 번에 보내는
오디오로, 턴을 침묵 0.2초로 이어 28초 안으로 채운다. 턴 하나가 28초를 넘으면 그 턴 안의 가장
긴 쉼에서 가른다. 클립 중간은 어디서도 자르지 않고, 28초를 넘는 클립만 15초 이후 가장 조용한
20ms 에서 가른다(실시간의 25초 강제 절단은 배치에서 끈다).

## 결정

**chunk 를 기본으로 한다.** 실제 6인 녹음 두 회의의 정렬본에서 두 백엔드 모두 chunk 가 CER 이
가장 낮고, 호출 수와 CPU 가 clip 의 절반이다. 전 트랙의 묶음을 한 풀에 넣어 로컬은 워커 1, API 는
워커 6 으로 보낸다.

정렬본은 `stt/eval/golden.py align` 이 만든다. 원본 골든셋은 트랙이 각자 0초에서 시작해(김환만
24초) 회의 전체 순서를 복원할 수 없다(`meta.json known_issues`). 그래서 각 화자의 클립을 대본
순서대로 1초 간격으로 놓았다. **목소리는 진짜지만 시간축은 합성이다.** 순서·시각 지표는 그 합성
순서 대비다. 정답은 7턴이고, meeting-01 은 유재환 트랙 맨 앞의 대본 밖 "다시 하겠습니다." 를
정답에 넣었다(1,062자). 모델 셋이 같은 말을 들었고, 정답은 말한 것이어야 한다. 원본의 "네," 는
임계 위 프레임이 100ms 남짓이라 VAD 의 알림음 재시작 규칙에 걸려 클립에 없다. 짧은 대답이
빠지는 첫 실측 표본이다.

CER 은 문자 가중, 공백 제거, 정답과 전사 양쪽에 같은 정규화다. 로컬은 M4 10코어 int8, 설정마다
새 프로세스에서 돌려 최대 RSS 를 따로 쟀다. "무음 자리 단어" 는 VAD 가 말이 없다고 본 자리에
모델이 놓은 단어 수다. track 은 버리고 whole 은 남긴다. 결과 JSON 과 표는
`stt/eval/results/2026-09-16-batch/` 에 있고 `python -m stt.eval.rescore` 로 다시 채점할 수 있다.

### treesoop/whisper_transcription 과 노이즈 필터

treesoop 은 mlx-whisper 로 파일 통째 전사, pyannote 로 화자 분리, 겹침이 가장 큰 화자에 세그먼트
배정, 30분 넘는 파일은 ffmpeg 분할이다. 환각 대응은 위 두 옵션뿐이고 track 모드가 그것이다.
우리는 화자별 트랙이라 pyannote 가 필요 없다. 노이즈 필터는 0007 에서 뺐고 표 3 의 하이패스가
같은 결론이다.

## 영향받은 파일

- `stt/batch.py` 네 모드, 턴 묶음과 병합, 긴 클립 분할, 전 트랙 공용 풀, 통계
- `stt/transcribe.py` 본체를 `stt/batch.py` 로 위임. 출력 형식과 `timing_summary.md` 는 그대로.
  기본 `--mode chunk`, 이전 방식은 `--mode whole`. faster-whisper 직접 의존 없음
- `stt/local.py` 빔·문맥 옵션·환각 임계를 명시. `stt/transcript_writer.py` 대본형 md.
  `stt/elice.py` 타임아웃 180 → 30초. `capture/track_writer.py` 패킷 공백 상한 60초 → 4시간
- `stt/eval/golden.py` 정렬본과 지표, `matrix.py` 비교표, `fleurs.py` 모델 순위, `rescore.py` 재채점
- 실시간 전용 코드는 `capture/realtime/` `stt/realtime/` 로 옮겼다. 지우지 않았다. 0003 은 번복

재현 (ai/ 안에서. 로컬은 무과금, Elice 는 회의당 약 14원, 통째는 약 90원):

```bash
.venv/bin/python -m stt.eval.golden align --golden "<meeting-01>" --out "<meeting-01-aligned>"
.venv/bin/python -m stt.eval.matrix run --golden "<m01-aligned>" "<m02-aligned>" --fleurs "<fleurs_ko>" --out results/ --only local
.venv/bin/python -m stt.eval.matrix run ... --elice --yes
.venv/bin/python -m stt.transcribe recordings/<회의> --mode chunk                      # 운영 경로
```

## 재지 않은 것

- t3.medium 에서의 벽시계·CPU·RSS (#40)
- 실제 교차 발화 녹음의 순서·시각 지표. 정렬본은 합성 순서라 순서 오류 0 이 당연히 나온다
- 짧은 대답 보존율. 표본이 "네," 하나뿐이다. 프리토킹 녹음이 있어야 잰다
- 할 일 추출 F1. #30 추출기가 머지되면 같은 전사본으로 잰다
- Elice 의 최소 과금 단위. 호출당 올림이 있으면 clip 과 chunk 의 비용이 갈린다
- 28초 상한과 클립 사이 0.2초 침묵, 턴 공백 3초의 다른 값. 한 값으로만 쟀다

## 다시 볼 조건

- t3.medium 에서 로컬 turbo 가 1분 오디오당 30초를 넘거나 4GiB 에 안 들어가면 Elice 를 기본으로 한다
- Elice 가 단어 시각을 안 주게 바뀌면 chunk 의 되매핑이 깨진다(`unmapped_chunks` 가 0 이 아니게
  된다). 그때는 clip 으로 돌린다
- 프리토킹 녹음에서 짧은 대답이 사라지면 VAD 의 알림음 재시작 규칙과 말 필터(0005)부터 본다
- 회의가 길어져 화자당 묶음이 수십 개가 되면 워커 수와 메모리(묶음 pcm 을 한꺼번에 들고 있다)를 다시 본다
