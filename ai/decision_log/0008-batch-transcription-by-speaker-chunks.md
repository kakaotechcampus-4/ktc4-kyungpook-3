# 0008. 전사는 회의가 끝난 뒤 배치로 한다. 화자별 클립을 침묵 없이 묶어 보내고 한 시간축에 놓는다

- 날짜: 2026-09-16 (측정 2026-09-15)
- 상태: 결정됨. 0003(회의 중 발화 단위 전사)을 번복한다. 운영 기본 백엔드(API/로컬)는 t3.medium
  측정 뒤 확정

## 배경

회의 중 전사(0003)는 고려할 것이 많고 구현이 복잡한 데 비해 얻는 것이 적었다. 재환님과 상의해
회의가 끝난 뒤 저장된 트랙을 배치로 전사하는 쪽으로 정했다. 실시간을 만들면서 알게 된 것은
그대로 쓴다. 트랙이 회의 시계 위에 쓰인다는 것, VAD 상수, 말 필터, 그리고 아래 API 지연 분포다.

**API 지연은 길이가 아니라 확률의 문제였다.** 실제 회의에서 20초 넘게 걸린 호출이 종료 대기를
넘겨 발화를 잃었다. 같은 1초 클립을 Elice 에 20번 보내 봤다.

```
2.4초 × 17회 / 22.0 · 25.0 · 27.8초 × 3회       p50 2.62  p95 25.15  max 27.81
```

길이별 3회씩: 1초 2.4초, 3초 2.4~3.0초, 5초 3.2초(1회는 20.95초), 10초 3.8초, 20초 9.8초,
30초 14.3초. 고정비 약 2.4초에 길이의 0.45배가 붙고, 그와 별개로 **호출의 15% 가 길이와 무관하게
22~28초 멈춘다.** 첫 호출도 아니고(1·4·6번째) 동시 호출도 아니었다(순차). 서버 쪽이라 우리가
줄일 수 없다. 이전에 본 20.58·22.57·21.24초가 전부 이 분포 안이다. 타임아웃을 두고 재시도하면
멈춤이 두 배가 될 뿐이라 안 한다. 배치에서는 워커 여럿이 벽시계를 흡수하면 되고, 호출 수를
줄이면 멈춤에 노출되는 횟수가 준다. 재현: `stt/eval/` 의 지연 스크립트 (227초, 23원).

**트랙을 통째로 넣으면 안 된다.** 동료 `transcribe.py` 는 트랙 wav 를 그대로 faster-whisper 에
넣었다. 6인 60분이면 무음 포함 360분이 모델에 들어간다. 무음 구간에서 위스퍼는 앞 문장을
반복하거나 문장을 지어낸다. 52초 트랙의 31~36초 완전 무음에 앞 문장이 복사됐고, 74.7초 파일은
한 문장을 무한 반복해 CER 87.55% 가 됐다(0007). 원인은 `condition_on_previous_text=True`
기본값이다. 무음에서 들을 것이 없으면 앞 문맥을 그대로 낸다.

**시간축은 트랙 파일이 이미 갖고 있다.** `TrackWriter` 가 화자별 wav 를 회의 시계 하나 위에 쓴다.
패킷 도착 시각이 위치이고 안 온 구간은 0 이다. 그래서 파일 안의 샘플 위치가 곧 회의 경과 시각이고
트랙별 오프셋이 필요 없다. VAD 가 준 `start_ms` 가 그대로 절대 시각이며, 화자를 섞어 `start` 로
정렬하면 회의록이다. `SyncedWaveSink` 도 앞을 무음으로 채워 같은 모양을 만들지만 `time.time()`
이라 NTP 보정에 흔들린다(멘토 HIGH 1, 재환님 파일이라 별도 이슈).

## 검토한 선택지

트랙을 VAD 로 발화 클립으로 자른 뒤 무엇을 모델에 보내느냐로 셋이 갈린다. `stt/batch.py` 에
세 모드로 같이 두어 같은 시간축 위에서 비교했다.

- **clip. 클립 하나씩 보낸다**: 실시간 경로가 보내던 단위 그대로다. 무음 0, API 비용 최소 /
  앞뒤 문맥이 없어 CER 이 나쁘고, 로컬 모델은 클립마다 30초 창을 채우는 고정비(turbo 약 5초)가
  들어 호출 수만큼 손해다.
- **chunk. 같은 화자의 클립을 침묵 없이 28초 안으로 이어 붙여 보낸다**: 문맥이 살고 무음은 안
  간다. 호출 수가 화자당 한두 번이라 API 멈춤 노출도 준다. 단어 시각으로 클립에 되돌리므로
  시각은 클립 단위로 남는다 / 단어 시각이 없는 백엔드면 되매핑을 못 한다(Elice 도 준다, 실측
  unmapped 0). 28초는 위스퍼 창 30초 아래로 잡은 값이다.
- **track. 트랙 통째. 반복 억제 옵션을 켠다**: `condition_on_previous_text=False`,
  `hallucination_silence_threshold=1.0` (treesoop 이 쓰는 두 옵션). VAD 가 말이 없다고 본
  자리의 단어는 버린다. 문맥 최대 / 무음까지 다 계산하고, 옵션을 켜도 무음에서 문장을 지어내며,
  긴 무음 뒤 진짜 발화를 건너뛴다(아래). 로컬 전용이다. API 로 보내면 무음까지 과금이다.
- **whole. 동료 방식 그대로**: 옵션 없이 트랙 통째. 비교 기준으로 `--mode whole` 에 남긴다.

## 결정

**chunk 를 기본으로 한다.** 실제 6인 녹음 2회차를 대본 순서대로 놓은 정렬본에서 두 백엔드 모두
chunk 가 CER 이 가장 낮고, 호출 수와 CPU 가 clip 의 절반이다.

정렬본은 `stt/eval/golden.py align` 이 만든다. 원본 골든셋은 트랙이 각자 0초에서 시작해
(김환만 24초) 회의 전체 순서를 복원할 수 없다(`meta.json known_issues`). 그래서 각 화자의
클립을 대본 순서대로 1초 간격으로 놓았다. **목소리는 진짜지만 시간축은 합성이다.** 순서·시각
지표는 그 합성 순서 대비다. 정답은 7턴 1,054자(유재환의 시작·마무리가 둘).

버려서 회의록에는 안 들어갔지만, 빠진 말은 되살릴 수 없다. 재현:

```bash
.venv/bin/python -m stt.eval.golden score --session "<meeting-01-aligned>" --mode track --backend local
```

**whole(동료 방식 그대로)은 이 셋에서 39.20% 다.** 여섯 트랙 전부 앞 무음에 "감사합니다." 가 한 번에서
세 번 붙었고, 최진호 트랙은 문장을 반복해 104.1% 가 나왔다(0007 의 74.7초 파일과 같은 현상).
원본 골든셋에서 6.97%(0007) 였던 것이 정렬본에서 이렇게 된 이유는 트랙 길이다. 원본은 트랙마다
자기 발화만 있어 무음이 짧고, 정렬본은 6인 회의처럼 트랙의 85% 가 무음이다. 실제 회의 트랙은
정렬본 쪽에 가깝다. 재현: `python -m stt.transcribe <정렬본> --mode whole --model large-v3-turbo`
뒤 `stt/eval/eval.py` 의 `score` 로 `truth_by_speaker.json` 대비 채점.

**clip 은 로컬에서 특히 손해다.** turbo 는 클립 길이와 무관하게 호출당 약 5~6초가 든다(30초 창을
채운다). 15클립이면 CPU 325초, 7묶음이면 179초다. Elice 는 발화 길이 과금이라 clip 이든 chunk
든 비용이 같고(13.5 대 13.8원), chunk 가 p95 를 25.0초에서 10.8초로 줄였다. 호출 15번 중 하나가
멈춤에 걸린 것이 7번에서는 안 걸린 것이다. 확률 15% 면 7번 중 한 번은 걸릴 수 있다.

### treesoop/whisper_transcription 에서 가져온 것

mlx-whisper 로 파일 통째 전사, pyannote 로 화자 분리, 겹침이 가장 큰 화자에 세그먼트를 배정하는
구조다. 환각 대응은 `--condition-on-previous-text False` 와 `--hallucination-silence-threshold 1`
둘뿐이고, 30분 넘는 파일은 ffmpeg 로 쪼개라고 한다. 우리는 화자별 트랙이라 pyannote 가 필요
없고, 두 옵션은 로컬 track 모드에 그대로 넣었다(`stt/local.py` 의 `track_mode`). 위 표가 보여
주듯 두 옵션은 반복은 막아도 무음의 지어내기와 건너뛰기는 못 막는다. VAD 로 먼저 잘라 무음을
안 보내는 쪽이 옵션보다 확실했다.

## 영향받은 파일

- `stt/batch.py` 세 모드, 한 시간축 정렬, 통계. `stt/lines.py` 로 `Line` 분리
- `stt/transcribe.py` 본체를 `stt/batch.py` 로 위임. 출력 파일 형식과 `timing_summary.md` 는
  그대로. 기본 `--mode chunk`, 동료 방식은 `--mode whole`
- `stt/local.py` `track_mode`. `stt/elice.py` 타임아웃 180 → 30초. `capture/track_writer.py`
  패킷 공백 상한 60초 → 4시간
- `stt/eval/golden.py` 정렬본 생성과 지표. `tests/test_batch.py`, `tests/test_transcribe_batch.py`
- 실시간 전용 코드는 `capture/realtime/` `stt/realtime/` `tests/realtime/` 로 옮겼다. 지우지
  않았다. 0003 은 번복 처리

재현 (ai/ 안에서. 로컬은 무과금, Elice 는 회의당 약 14원):

```bash
.venv/bin/python -m stt.eval.golden align --golden "<meeting-01>" --out "<meeting-01-aligned>"
.venv/bin/python -m stt.eval.golden matrix --session "<meeting-01-aligned>"            # 로컬 세 모드
.venv/bin/python -m stt.eval.golden matrix --session "<meeting-01-aligned>" --elice --yes
.venv/bin/python -m stt.transcribe recordings/<회의> --mode chunk                      # 운영 경로
```

## 재지 않은 것

- t3.medium 에서의 벽시계·CPU·RSS. 운영 백엔드 기본값은 이것 뒤에 정한다
- 실제 교차 발화 녹음의 순서·시각 지표. 정렬본은 합성 순서라 순서 오류 0 이 당연히 나온다
- 짧은 대답("네", "그렇죠")의 보존율과 할 일 추출 F1. 골든셋이 낭독이라 표본이 없다.
  프리토킹 녹음과 추출 정답이 있어야 잰다
- Elice 의 최소 과금 단위. 호출당 올림이 있으면 clip 과 chunk 의 비용 차이가 생긴다
- 28초 상한과 클립 사이 0.2초 침묵의 다른 값. 한 값으로만 쟀다

## 다시 볼 조건

- t3.medium 에서 로컬 turbo 가 1분 오디오당 30초(멘토 기준)를 넘거나 4GiB 에 안 들어가면
  Elice 를 기본으로 한다
- Elice 가 단어 시각을 안 주게 바뀌면 chunk 의 되매핑이 깨진다(`unmapped_chunks` 가 0 이
  아니게 된다). 그때는 clip 으로 돌린다
- 프리토킹 녹음에서 짧은 대답이 사라지면 말 필터(0005)와 VAD 최소 길이부터 본다
- 회의가 길어져 화자당 묶음이 수십 개가 되면 워커 수와 메모리(묶음 pcm 을 한꺼번에 들고 있다)를
  다시 본다
