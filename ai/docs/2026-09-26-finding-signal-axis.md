## 왜

멘토 인라인 코멘트(`judge/semantic_judge.py:41`):

> **고민 🤔 진행상황 공유를 제외하면 상태 갱신은 어디서 할까요?**
> 1단계는 "로그인 API 붙였어요"를 FYI로 제외하지만, 2단계에는 done 판정이 있어요. 직렬로
> 연결하면 실제 완료 소식이 2단계에 도달하지 못할 수 있어요.
> **문서 기록 여부와 Task 생성·상태 변경 여부를 분리해서 판단해보면 어떨까요?**

1단계가 답하던 질문은 하나였다 — "Notion 문서를 갱신할 만큼 의미 있는가". 진척 보고는 그
기준으로 제외가 **맞다**(문서에 쓸 새 내용이 없다). 문제는 축이 하나뿐이라 **"문서 기준 무의미"가
곧 "파이프라인에서 삭제"가 된다**는 것이다. 그래서 `JudgeResult.status` 가 `done` 을 매길 수
있는데도 재료가 도달하지 못한다.

같은 병이 2단계에도 있다. 멘토 리뷰 1번:

> `is_meaningful` 하나로 후보 폐기까지 결정하면 "문서 변경 없음"과 "업무 없음"이 섞여요.

1단계에서는 "제외", 2단계에서는 "`is_meaningful=False`" — 이름만 다르고 **문서 축 하나로 Task
축까지 결정**하는 건 같다. 이 PR 은 그중 1단계 쪽을 연다.

### 왜 "FYI 조항만 빼기"로는 안 되나

`judge()` 는 **finding 하나당 Terra 호출 1회**다. 축 없이 진척 보고를 통과시키면 호출이 40%
가까이 늘고(팀이 1단계를 Terra → Luna 로 내린 이유가 비용이다), 그렇게 올려보내도 2단계가
`is_meaningful=False` 한 줄로 똑같이 버린다. **싼 1단계에서 축을 갈라 라우팅해야** 비용이
줄고 신호도 산다.

## 담당자 호칭 — 왜 4종이 아니라 7종인가

`JudgeFinding.assignee_type` 은 필드만 뚫려 있고 아무도 안 채우고 있었다(항상 `None`).
1단계가 채울 수 있는 값인데도 프롬프트가 물어보지 않아서다 — `status` 는 Notion 후보와
비교해야 알 수 있고 `evidence_status` 는 담당자·마감 필드가 생긴 뒤에야 물을 수 있지만,
**담당자 호칭은 문장 표면만 보면 판정된다.**

어휘를 처음엔 BE 스키마 설명문을 보고 4종(`first/third/group/none`)으로 잡았는데, 멘토가
`ExtractedTask` 의 7종 기준으로 가라고 했다. 이유는 셋이다.

**3인칭을 합치면 BE 처리 경로가 지워진다.** `thirdname`("지민님이")은 alias 완전일치로
찾을 수 있고, `thirdpronoun`("그분이")은 조회 불가라 AI 가 문맥으로 풀어야 하며,
`thirdrole`("백엔드 리더가")은 역할 매핑이라 대체로 PM 확인이다. 성공률도 경로도 다른데
`third` 하나로 뭉치면 BE 가 구분할 수 없고 어느 갈래가 약한지 측정도 못 한다.

**`second` 가 없으면 "너"가 별칭으로 조회된다.** 멘토가 직접 짚은 부분이다:

> `second` 의 "너"를 이름 별칭으로 조회하지 않도록 원문과 해소된 이름도 구분해야 해요.

`resolve_assignee` 는 `MemberAlias.alias_text` **완전일치 한 번**이라 "너"로는 영원히
NOT_FOUND 다. 그래서 `assignee_raw`(원문 그대로)와 `assignee_resolved`(문맥으로 푼 이름)를
따로 둔다. `first/group/none` 은 가리킨 말이 없으므로 `assignee_raw` 를 코드가 지운다 —
특히 `first` 는 BE 가 `evidence_speaker`(화자 uid)로 푸는데 raw 가 같이 오면 분기가
그쪽을 먼저 본다.

**합치더라도 순서가 있다.** 멘토는 "저장할 필요 없는 분류는 **명시적으로** 합쳐주세요"라고
했다. 7종의 의미를 먼저 세우고 그다음 합칠지 정하라는 뜻인데, 4종은 그 판단 없이 미리
합친 것이었다. BE 도 #74 에서 설명문이 `first/second/thirdname/group/none` 으로 바뀌어
같은 방향으로 갔다.

모르는 타입이 오면 셋 다 `None` 으로 둔다. `"none"`(담당자 언급 없음)으로 떨어뜨리면
**판정 실패와 "담당자가 없다"가 구분되지 않는다.**

## 결과

| | 이전 | 이번 |
|---|---|---|
| 축 분류 (decision/progress) | — | **76/76 (100%)** |

**축 분류 76건, 담당자 호칭 11건 전부 맞았다.** Luna 가 "문서에 쓸 새 내용" 과 "기존 작업의 진척" 을 구분하는
데는 문제가 없다는 뜻이다. 규칙 기반이 82% → 70% 로 떨어진 건 정규식이 진척 보고를 잡을
방법이 없어서이고, 예상된 결과다(프로덕션 경로가 아니라 비교용이다).

통과율이 97% → 94% 로 내린 건 **분모의 성격이 바뀌었기 때문**이다. `should_flag=true` 라벨이
36건에서 82건으로 늘었다(잡아야 할 게 2배 이상). 그리고 남은 실패의 대부분이 모델 문제가 아니라 **라벨 경계 문제**다 — 아래 참고.

**라벨을 안 건드린 진척성 문장 (11건)** — 이번 relabel 은 `note` 에 "진행상황" 이 적힌 라벨만
대상으로 삼았다. 그 밖의 note 로 적힌 진척성 문장은 그대로 `false` 라서, Luna 가 `progress` 로

| 문장 | 현재 라벨 note | 보는 사람에 따라 |

| "저는 결제 API 연동 중인데 문서가 좀 헷갈리네요." | 상태 설명 | 연동 중 = `in_progress`, 헷갈림 = `blocked` 에 가깝다 |
| "리뷰 남겨주신 거 확인했습니다." (5곳) | 잡담 | 리뷰 확인이라는 작업의 진척인가, 단순 응답인가 |
| "QA 쪽에서 버그 리포트 몇 개 왔어요." (4곳) | 진행상황 | 본인 작업의 진척이 아니라 외부 이벤트라서 이번엔 뺐다 |
| "오늘 다시 봐야 할 것 같아요." | 진행상황 | 계획에 가깝다고 보고 뺐다 |

**기존부터 열려 있던 라벨 합의 항목 (6건)** — `"네 그거 확인해볼게요"` (5곳),
`"나중에 자료로 공유드릴게요"`. PR #78 에 이미 적어둔 항목이다.

**진짜 놓침 (5건)** — `"저는 오늘 디자인 시스템 정리하고 있어요."`,
`"디자인은 색상 팔레트 다 정했습니다."`, `"저는 어제 계속 디버깅했어요."`,
`"혹시 시간 되면 이번 주까지 해볼게요."`, `"그러니까 이번 주"`(통과율 제외 케이스).

## 이번에 정한 라벨링 규칙

**문장에 "무슨 작업인지" 가리키는 대상이 있으면 `progress`, 없으면 제외.** 상태를 바꿀 Task 를
특정할 수 없으면 2단계가 할 수 있는 게 없기 때문이다.

- `progress` — "로그인 API 붙였고요", "인프라 쪽 로그 정리했어요", "색상 팔레트 다 정했습니다"
- 제외 — "어제 야근했어요", "다른 작업 좀 했어요", "저도 특별한 건 없었어요", "순조롭게 진행 중이에요"

경계에 있는 판단(위 표)은 **재환님과 정해야 한다.** 남의 골든셋이라 애매한 것까지 혼자 뒤집지 않았다.

## 덤으로 드러난 것 — 중복 검사의 한계

#91 이 넣은 중복 앵커 검사가 `short_sentences/case_09` 를 잡았다.

```
"로그인은 내일까지 하고, 회원가입은 담당자를 다시 정하기로 했어요."
  -> 같은 앵커로 2건 (한 결정이 쪼개졌을 수 있음)
```

한 문장에 결정이 **둘** 들어 있는 케이스라(골든셋 설명에도 "한 문장에 결정 2개"로 적혀
있다) Luna 가 둘로 나눈 건 오히려 맞는 동작이다. 중복 검사는 "한 결정이 쪼개진 것"과
"두 결정이 한 문장을 공유하는 것"을 구분할 수 없다. 케이스 하나뿐이라 이번엔 그대로 두고
기록만 남긴다 — 더 흔해지면 finding 에 결정 식별자를 붙이는 쪽을 봐야 한다.
