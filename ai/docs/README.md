# docs/

AI 파트 문서를 모아 두는 곳입니다.

```
docs/
├── README.md
├── api/                    AI·BE 계약, 단계 간 데이터 흐름도 (.excalidraw)
├── request/                다른 파트가 우리 팀에 요청한 것
├── plan/
│   ├── 전체 계획.md
│   └── <phase 번호>/        예: M3/
│       ├── 컨텍스트.md
│       └── 결과물.md
└── basis_for_decision/     진행 로그 + 트레이드오프 결정 기록
    ├── ai/<날짜>-<slug>.md      AI(Claude 등)가 작성
    └── member/<날짜>-<slug>.md  팀원이 직접 작성
```

## basis_for_decision/

진행 로그와 결정 기록을 한곳에 둡니다. `ai/` 와 `member/` 는 **누가 썼는지**로 나눕니다 — AI 가 쓴
문서(커밋에 `Co-Authored-By: Claude` 가 붙는 경우)는 `ai/`, 팀원이 직접 쓴 문서는 `member/`.

| | 진행 로그 | 결정 기록 |
|---|---|---|
| 담는 것 | 한 일의 기록 (무엇을/왜/결과) | 트레이드오프 결정의 근거 |
| 시점 | push 할 때마다 | 여러 선택지 중 하나를 고를 때만 |
| 파일명 | `YYYY-MM-DD-짧은-제목.md` | `YYYY-MM-DD-NNNN-짧은-제목.md` |

트레이드오프가 있던 결정이면 진행 로그에 자세히 적지 말고 결정 기록을 따로 남긴 뒤 링크만 건다 —
같은 내용을 두 곳에 쓰지 않는다. 같은 날 여러 개면 제목 뒤에 `-2`, `-3` 붙인다.

결정 기록의 `NNNN` 은 옛 `decision_log/` 의 번호를 이어 쓴다. 코드 주석이 "0013" 처럼 번호로 가리키므로
번호만으로 찾을 수 있게 남겨 둔다.

### 진행 로그 — 언제

push 할 때마다 하나. 아주 사소한 수정(오타, 포맷팅)까지 남길 필요는 없고, "코드가 실제로 바뀌었다" 싶으면 남긴다.

```markdown
# 제목 (무엇을 했는지 한 줄)

- 날짜: YYYY-MM-DD
- 이슈: #NN
- PR: #NN
- 브랜치: feat/NN-xxx
- 작성자:

## 한 일

- 개조식으로 핵심 변경사항 나열
- 코드 변경이면 파일/함수 단위로

## 왜

배경/동기를 짧게. 트레이드오프가 있는 결정이었으면 자세한 근거는 여기 쓰지 않고
결정 기록(`YYYY-MM-DD-NNNN-xxx.md`) 링크로 대신한다.

## 결과

검증/테스트 결과. 수치 있으면 표로.

| 항목 | 값 |
|---|---|

## 다음

남은 일, 후속 이슈 링크.
```

### 결정 기록 — 언제

- 여러 선택지 중 하나를 골랐고, 그 선택이 나중에 "왜 이렇게 했지?"라고 물을 만한 것일 때
- 특히 비용/시간/정확도 트레이드오프처럼 정답이 없고 팀 합의가 필요한 결정일 때

사소한 리팩터링이나 버그 픽스는 남기지 않는다(git log 로 충분).

```markdown
# NNNN. 제목

- 날짜:
- 상태: 검토중 | 결정됨 | 보류 | 번복됨(→ 번복한 파일 링크)

## 배경
왜 이 결정이 필요했는지, 어떤 제약(비용/시간/인원) 안에서 나온 건지.

## 검토한 선택지
- 선택지 A: 장점 / 단점
- 선택지 B: 장점 / 단점

## 결정
무엇을 선택했는지, 근거는 무엇인지.

## 다시 볼 조건
어떤 상황이 되면 이 결정을 재검토해야 하는지 (예: "large 모델이 실제로 더 빠르게 나오면").
```

## plan/

`전체 계획.md` 에 마일스톤(M0~M6)을 두고, phase 를 시작할 때 `plan/<phase 번호>/` 를 만들어
`컨텍스트.md`(시작 시점의 배경·제약·입력) 와 `결과물.md`(끝났을 때 산출물·검증 결과) 를 남긴다.

## request/

다른 파트(BE·FE 등)가 AI 파트에 요청한 내용을 한 건에 한 파일로 남긴다. 파일명은 `YYYY-MM-DD-짧은-제목.md`.
