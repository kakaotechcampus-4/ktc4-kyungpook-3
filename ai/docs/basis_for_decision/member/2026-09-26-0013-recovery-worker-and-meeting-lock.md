# 0013. 후처리 복구를 자동으로 돌리고 워커 프로세스로 뗄 수 있게 하며, 누가 처리할지는 회의마다의 파일 잠금이 정한다

- 날짜: 2026-09-26
- 상태: 결정됨. 서버에서 어느 모드를 쓸지, 전사 백엔드, 워커 메모리 상한은 #40 측정 뒤 팀이 정한다

## 배경

회의 후처리(전사 → 추출 → BE 인계)가 중간에 실패하거나 봇이 죽으면 사람이 `/recover` 를 쳐야 다시 돌았다. BE 에는 첫 실패에서 바로 fail 을 보냈고 BE 의 failed 는 끝 상태라, 나중에 복구가 성공하면 새 BE 회의를 만드는 우회를 탔다. 후처리가 봇 프로세스 안에서 돌아서 봇을 재시작하거나 배포하면 돌던 단계가 죽었고, 전사가 CPU 를 다 쓰면 디스코드 연결 유지와 명령 응답이 밀릴 수 있었다.

서버는 t3.medium 한 대(2 vCPU, 4GB)이고 BE 와 DB 가 같이 올라간다. 로컬 large-v3-turbo 는 M4 에서 RSS 2.5~2.9GB 였다. wav 가 그 서버 디스크에 있으니 무엇을 먼저 처리할지는 파일이 있는 쪽이 정하고, 매니페스트가 곧 대기열이다.

## 검토한 선택지

어디서 돌릴지. 사람의 `/recover` 만 두면 멈춘 회의를 아무도 모를 때 영원히 남는다. 봇 안의 주기 루프는 봇 메모리로 녹음 중인 회의를 바로 알고 결과를 채널에 올릴 수 있지만 봇과 같이 죽고 CPU 를 나눠 쓴다. 별도 워커 프로세스는 봇 재시작과 후처리가 갈리는 대신 프로세스 사이의 배제와 봇과 말할 길이 필요하다. 둘을 모드로 둘 다 두었다.

대기열. 매니페스트, SQS, Redis, BE DB 를 봤다. 기계가 한 대라 디스크가 곧 공유 저장소이고 단계별 재개가 이미 매니페스트에 있어 매니페스트로 했다. SQS 는 워커 하나에 과하고, Redis 는 4GB 서버에 서비스가 하나 더 늘고, BE DB 는 파일이 BE 에 없어 파트가 얽힌다.

누가 처리할지. 처음에는 매니페스트에 `claimed_by`·`claimed_at` 을 적고 만료가 지나면 누구든 다시 잡게 했다. 읽고 쓰는 사이가 원자적이지 않고, 잡은 프로세스가 죽으면 만료까지 회의가 막혔다. 잠금 파일을 만들고 지우는 방식도 죽으면 같은 문제가 남는다. OS 파일 잠금(flock)은 쥔 프로세스가 죽으면 OS 가 풀고, 같은 프로세스 안에서도 따로 연 파일끼리 부딪혀 봇의 루프와 `/recover` 도 막는다. flock 하나로 했다.

결과 알림. 워커가 봇 토큰으로 채널에 올리기, 워커가 봇에게 넘기기, 워커는 BE 로만 넘기기를 비교했다. 워커의 일은 전사·추출·인계이고 결과는 BE 를 거쳐 웹에서 보면 된다. 워커가 디스코드를 모르면 토큰이 필요 없고 게이트웨이 연결이 겹칠 걱정도 없어서 BE 로만 넘긴다.

BE 상태. 실패마다 fail 을 보내고 BE 에 failed → processing 전이를 만드는 것과, BE 상태 머신은 두고 fail 시점만 늦추는 것을 비교했다. 뒤쪽을 골랐다. 재시도가 남은 동안 BE 회의는 processing 이고 failed 는 재시도가 끝났다는 뜻이 된다.

## 결정

- 두 모드. `MM_PIPELINE_MODE=bot`(기본, 개발용 한 프로세스, 결과를 채널에 올린다)과 `worker`(봇은 저장까지, `python -m capture.worker` 가 처리하고 결과는 BE 로만). 다른 값이면 봇이 시작할 때 멈춘다. 오타로 봇 모드가 되면 4GB 서버에 모델이 올라간다
- 회의 잠금. `session_<회의ID>.lock` 의 OS 파일 잠금을 기다리지 않고 잡는다(POSIX 는 flock, 윈도는 msvcrt.locking 으로 첫 1바이트). 두 모드 모두, 루프와 `/recover` 사이도, 봇과 워커 사이도 이것 하나로 막는다. `/record` 는 잠금을 먼저 잡고 recording 매니페스트를 쓴다. 워커 모드의 `/stop` 은 saved 를 다 쓴 뒤에 놓고, 봇 모드는 스스로 처리하는 동안까지 쥔다. 쥔 쪽이 죽으면 OS 가 풀고 다음 쪽이 마지막 단계 다음부터 잇는다. `claimed_by`·`claimed_at` 은 "누가 몇 분째" 를 보여 주는 표시로만 남기고 만료로 빼앗는 규칙은 없앴다. 두 규칙이 같이 있으면 어긋난다. 같은 초에 시작한 녹음은 다음 초의 회의 ID 를 쓴다(겹치면 앞 회의를 덮어썼다)
- 한 바퀴. `recorder.recover_pass` 를 봇의 루프, `/recover`, 워커가 같이 쓴다. 대상은 바퀴를 시작할 때 정하고 회의마다 잠금을 잡은 뒤 다시 읽는다. #83 의 `/recover` 가 세마포어를 기다리는 사이 시작된 녹음을 집던 것을 이것으로 고쳤다. 먼저 시작한 회의부터 돈다. 모든 서버를 보는 바퀴는 서버가 적히지 않은 옛 매니페스트를 뺀다
- 재시도. 단계를 닫지 못한 실행(failed 또는 partial)을 세어 다음 시도를 두 배씩 미룬다. 단계가 닫히면 0 으로 돌아간다. 상한에서 포기하고 그때 처음 BE 에 fail 을 보낸다. 포기할 때 BE 가 꺼져 있었으면 fail 만 다시 보낸다. 자동 복구 전에 failed 로 끝난 회의는 사람의 `/recover` 에 둔다. 포기한 회의에 사람이 `/recover` 를 치면 한 번 더 돌고(BE 에는 새 회의), 또 실패하면 곧바로 다시 포기해 그 BE 회의도 failed 로 닫는다
- 처리 도중 죽은 실행. 메모리 상한이나 종료 대기 시간에 걸려 처리 도중 죽으면 `process_session` 이 실패를 세지 못한다. 안 세면 다시 뜬 워커가 같은 회의를 곧바로 다시 집고 또 죽어 뒤 회의가 모두 멈춘다. 잠금은 풀렸는데 `claimed_by` 가 남아 있으면 쥔 쪽이 도중에 죽은 것이라, 다음에 잡는 쪽이 실패 한 번으로 먼저 센다. 봇 모드의 `/stop` 뒤 처리는 이 표시를 남기지 않아 첫 번째 죽음은 세지 못하고, 그 뒤부터는 복구가 잡으므로 센다
- 워커. 봇처럼 asyncio 로 돌고 처리는 스레드에서 한 번에 한 회의만 한다(`MM_MAX_CONCURRENT_MEETINGS` 는 보지 않는다). 주기마다 한 바퀴 돌고, 살아 있다는 표시(`recordings/.worker/heartbeat.json`)는 처리와 따로 도는 태스크가 남겨 긴 전사 중에도 끊기지 않는다. 봇의 `/recover` 가 `wake-<서버ID>` 파일을 만들면 그 서버를 사람이 친 `/recover` 처럼(포기한 회의까지) 바로 돈다. 종료 신호를 받으면 새 회의를 집지 않고 하던 회의를 마친다. discord 를 import 하지 않는다
- 워커 모드의 봇. 전사 백엔드를 싣지 않는다. `/stop` 은 "처리되면 웹에서 확인할 수 있습니다(앞에 N건)" 를 올리고 N 은 워커와 같은 목록과 순서로 센다. `/recover` 는 워커를 깨우고 대기·처리 중 건수와 워커 상태를 알린다. 주기의 여섯 배(최소 1분) 넘게 조용하면 "워커가 N분째 응답이 없습니다" 다. `on_session_saved` 는 부르지 않는다
- 재시작 안내. 봇이 뜨기 전에 시작돼 녹음 중에 끊긴 회의(잠금이 풀린 recording, 또는 워커가 먼저 트랙을 되찾은 회의)의 채널에 한 번 올린다. 트랙을 마지막으로 쓴 지 한 시간(잠정)이 넘었으면 회의가 끝났다고 보고 올리지 않는다

기본값과 근거.

| 환경 변수 | 기본값 | 근거 |
|---|---|---|
| `MM_PIPELINE_MODE` | `bot` | 개발 기기에서 지금과 같게 돈다. 서버는 `worker` 를 권하지만 팀이 정한다 |
| `MM_RECOVERY_INTERVAL_S` | 60초. 0 이면 끈다 | 봇 모드 루프의 주기. 워커 모드에서는 재시작 안내만 훑는다. 대상 목록이 매니페스트 100개에 중앙값 3.7ms, 1000개에 41.2ms 였다(M4, 합성 매니페스트, 회의마다 잠금을 확인하는 지금 코드) |
| `MM_RECOVERY_BACKOFF_S` | 60초에서 두 배씩, 한 시간 상한 | 1, 2, 4, 8분 뒤에 다시 한다. 네 번째 재시도까지 약 15분이라 BE 재시작이나 API 일시 장애는 넘긴다 |
| `MM_RECOVERY_MAX_ATTEMPTS` | 5 | `MM_PARTIAL_RETRY_MAX + 1`(기본 4) 이상이어야 재전사에서 살아나는 partial 회의가 포기 전에 빠진 구간을 둔 채 넘어간다 |
| `MM_WORKER_INTERVAL_S` | 10초 | 워커 한 바퀴와 살아 있다는 표시의 주기. 워커가 쉬고 있으면 `/stop` 뒤 10초 안에 집고 `/recover` 의 깨우기는 1초 안에 받는다. 다른 회의를 처리 중이면 그 회의가 끝난 뒤다 |

비용 상한(추정). 한 회의가 전사 단계에서 상한까지 가면 원격 전사를 최대 5번 보낸다. 60분 회의 한 번이 약 290원(0008 추정)이라 최대 약 1,450원이고 자동 재시도로 늘어난 몫은 4번, 약 1,160원이다. 재전사는 실패한 구간만 보내므로 보통은 이보다 적다. 추출 LLM 한 번의 비용은 아직 안 쟀다.

배포 전에. 첫 바퀴(봇 모드의 루프나 워커)는 끝나지 않은 회의 가운데 서버가 적힌 것을 모두 집는다. 원격 전사와 추출 LLM 이 그만큼 과금되고 BE 설정이 있으면 인계까지 간다. 켜기 전에 `recorder.pending_sessions` 로 몇 개인지 본다. 내 개발 기기의 `recordings/` 는 매니페스트 8개가 모두 서버가 적히지 않은 9/12 녹음이라 집는 회의가 0개였다(9/26 확인). 서버 설정 예시는 `ai/deploy/systemd/` 에 두었다(워커는 낮은 우선순위와 메모리 상한, 둘 다 죽으면 다시 뜬다). 예시일 뿐이고 배포는 팀이 정한다.

재현(대상 목록 시간, 무과금):

```bash
.venv/bin/python - <<'PY'
import statistics, tempfile, time
from pathlib import Path
import numpy as np, soundfile as sf
from capture import recorder as R
rec = Path(tempfile.mkdtemp()) / "recordings"
for i in range(100):
    mid = f"77_{1000 + i}"
    (rec / mid).mkdir(parents=True)
    sf.write(str(rec / mid / f"1_{1000 + i}.wav"), np.zeros(1600, dtype=np.float32), 16000, subtype="PCM_16")
    R.write_status(rec, mid, status=R.STATUS_SAVED, entries=[{"user_id": "1", "display_name": "a",
                   "file": f"{mid}/1_{1000 + i}.wav", "duration_sec": 0.1}], guild="g", channel="c", library_version="x",
                   started_at="2026-09-16T00:00:00Z", meeting_dir=mid, extra={"guild_id": "77"})
claims, times = R.Claims(), []
for _ in range(20):
    t = time.perf_counter(); R.recovery_targets(rec, claims=claims); times.append((time.perf_counter() - t) * 1000)
print(f"{statistics.median(times):.1f}ms")
PY
```

## 다시 볼 조건

- flock 은 한 기계의 로컬 파일시스템에서만 서로를 막는다. `recordings/` 를 NFS·EFS·S3 로 옮기거나 두 번째 기계를 쓰면 잠금을 다시 정한다
- 윈도 잠금(msvcrt.locking)은 flock 과 같은 뜻을 내도록 짰지만 윈도에서는 아직 실제로 안 돌렸다. 윈도에서 처음 돌릴 때 잠금 테스트부터 본다
- 워커 수를 늘리거나 다른 기계로 옮길 때. 공유 저장소와 외부 큐가 필요해진다
- #40 에서 서버를 재면 어느 모드를 쓸지, 전사 백엔드, 워커 메모리 상한과 종료 대기 시간을 정한다
- 재시작 안내의 한 시간 기준이 실제 회의에서 너무 짧거나 길 때
- BE 에 failed → processing 전이가 생기면 포기한 회의의 수동 재시도가 새 BE 회의를 만들지 않아도 된다
