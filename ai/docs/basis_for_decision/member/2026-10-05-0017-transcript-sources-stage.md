# 0017. 전사 발화는 전사 직후 단계로 BE 에 저장하고, 저장 완료는 보낸 BE 회의에 묶는다

- 날짜: 2026-10-05
- 상태: 결정됨

## 배경

BE 에 발화 저장 API(`POST /api/v1/meetings/{id}/sources`, #130)가 생겼다. 명세(노션 "[BE] STT 전사문 저장 API 명세", #129)는 "발화 먼저, 추출 나중" 을 요구한다. BE 는 다음 작업에서 근거를 문장 대신 발화 번호(seq)로 잇는다. 후처리는 `recorder.process_session` 하나이고 단계가 닫히거나 실패하며, 실패는 60초부터 두 배씩 미뤄 5회 뒤 포기한다(0013). BE 회의가 failed 로 닫혀 있으면 인계 코드(`Handoff.end`, `register`)가 새 회의를 만들어 바꾼다.

## 검토한 선택지

- 보내는 시점
  - 전사 직후 새 단계: BE 명세가 추천한 시점이다. 판단(LLM)이 실패하거나 길어져도 회의록은 BE 에 남는다. 매니페스트 단계가 하나 는다
  - 인계 단계 안, 추출 등록 직전: 코드가 가장 적다. 판단이 실패하면 회의록도 가지 않는다
- 저장이 실패했을 때
  - 멈추고 기존 백오프로 재시도: 단계가 일자로 이어진다. 판단 경로는 어차피 BE 유사 검색이 있어야 돌아서 BE 장애 때 추출만 앞서가는 이점이 없다
  - 추출은 계속하고 저장만 따로 재시도: 복구 코드가 갈라지고 명세의 순서가 깨질 수 있다
- 바로 포기할 거절을 무엇으로 가리나
  - 오류 코드만: BE 는 경로가 없을 때(#130 전 배포)도 404 에 `INVALID_REQUEST` 를 준다. 코드만 보면 재배포로 풀릴 일을 바로 포기한다
  - (상태, 코드) 쌍: `(400, INVALID_REQUEST)`, `(409, MEETING_FAILED)` 만 바로 포기한다
- 저장 완료를 무엇으로 판정하나
  - 단계 기록만: 추출에서 포기해 BE 회의가 failed 가 되고 /recover 로 새 회의가 생기면, 새 회의에 발화가 하나도 없는 채 추출만 등록된다. 리뷰에서 재현했다
  - 단계 기록과 보낸 BE 회의 ID: 회의가 바뀌면 다시 보낸다

## 결정

- 전사 직후 단계(`sourced`)로 보낸다. 실패는 기존 백오프로 재시도하고, `(400, INVALID_REQUEST)`·`(409, MEETING_FAILED)` 만 바로 포기한다. 400 이 알려 주는 필드(`details.fields`)는 오류 기록에 붙인다
- 저장 완료는 `stages.sourced` 와 `be.sources.meeting_id == be.meeting_id` 둘 다로 판정한다(`recorder.sources_saved`). 회의를 바꾸는 `_fresh` 는 `be.sources` 를 지우고, 인계 중 같은 실행 안에서 회의를 바꾸면 추출 등록 전에 새 회의로 발화를 먼저 보낸다
- 뒤 단계(추출·인계)에서 실패하던 회의는 저장 단계가 닫혀도 실패 횟수를 이어 센다. 지우면 포기한 회의를 /recover 로 다시 돌려 또 실패해도 곧바로 포기하지 않는다
- BE 설정이나 서비스 토큰이 없으면 이 단계만 건너뛰고 추출로 간다. 옛 추출 경로는 토큰 없이 돌았다
- 이미 끝난 회의는 소급 명령(`python -m capture.backfill_sources`)으로 한 번 보낸다. BE 는 done 회의도 받고 같은 seq 는 건너뛴다

## 다시 볼 조건

- BE 가 근거를 seq 로 잇기 시작하면(#124 evidence_seqs) 추출 등록 전에 저장이 끝났는지를 BE 쪽에서도 확인할지
- BE 의 나머지 봇 경로(회의 생성·종료·실패·추출 등록)에도 서비스 토큰이 붙으면(#128 고민 4), 토큰 없이 도는 설정이 사라지므로 "토큰 없으면 건너뜀" 을 지운다
- 409 에서 새 회의를 만들어 다시 보내야 할 경우가 실제로 생기면
