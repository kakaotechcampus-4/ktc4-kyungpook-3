# 0026. 처리 방식은 워커 하나다. 봇은 저장하고 워커의 알림을 채널에 올린다

- 날짜: 2026-10-13
- 상태: 결정됨. [0013](2026-09-26-0013-recovery-worker-and-meeting-lock.md) 의 두 방식(봇 모드, 워커 모드) 가운데 워커 모드만 남긴다. [0021](2026-10-12-0021-guild-workspace.md) 의 "봇 모드는 전사까지 해 채널에 올린다" 를 대신한다

## 배경

0013 뒤로 처리 방식이 둘이었다. 봇 모드는 봇 프로세스가 `/stop` 뒤 전사부터 BE 인계까지 직접 하고 결과를 채널에 올린다. 워커 모드는 봇이 저장까지만 하고 따로 뜬 워커가 처리한다. 운영 서버는 워커 모드(`MM_PIPELINE_MODE=worker`)로 돈다.

두 방식을 같이 두니 세 가지가 걸렸다.

운영에서 사용자가 보는 것이 없었다. 워커는 디스코드를 몰라서 `/stop` 뒤 "저장했습니다" 한 줄 다음에는 채널에 아무것도 오지 않았다. 전사가 끝났는지, 할 일이 웹에 올라갔는지는 웹을 열어 봐야 알았다. 결과를 채널에 올리는 코드는 봇 모드에만 있었다.

같은 처리를 두 길로 돌렸다. 봇 모드의 처리·진행 표시·결과 보고가 어댑터에 있어서 `capture/discord_adapter.py` 가 831줄이었고, 판단 경로나 연결 대기처럼 처리 규칙이 바뀔 때마다 두 방식의 테스트를 같이 고쳤다. 모드 값을 잘못 적으면 봇 프로세스에 전사 모델(약 2.5GB)이 올라가는 것도 테스트로 막아야 했다.

`/recover` 가 디스코드 명령이었다. 서버의 아무나 다시 돌릴 수 있었고(원격 전사는 다시 과금된다), 답에는 대기 수, 처리 중인 회의 ID, 워커의 마지막 신호 같은 운영 정보가 섞였다.

## 검토한 선택지

- 두 방식을 그대로 두고 워커 모드에만 알림을 붙이기: 같은 처리를 두 길로 돌리는 문제가 남는다
- 봇 모드 하나로 가기: 봇 프로세스에 모델이 올라가고, 배포로 봇을 재시작하면 처리 중인 회의가 끊긴다. 0013 에서 분리한 이유가 그대로다. 9/23 배포 특강의 연사도 전사 서버를 따로 두라고 답했다
- 워커가 봇 토큰으로 디스코드에 직접 올리기: 지금 워커는 봇 토큰이 필요 없다. 토큰을 두 프로세스에 두면 키가 퍼지고, 같은 토큰의 요청 한도를 두 프로세스가 서로 모르고 나눠 쓴다
- 큐를 DB 나 Redis 에 두기: 새 인프라가 생기고 DB 는 BE 가 맡고 있다. 봇과 워커는 이미 같은 녹음 폴더를 보고 있다(회의 잠금, 워커의 살아 있다는 표시)
- 파일 우편함(고른 것): 워커는 `recordings/.worker/outbox` 에 알림 한 건을 파일 하나로 쓰고, 봇이 이름 순서대로 읽어 채널에 올린 뒤 지운다. 디스코드에 말하는 프로세스는 봇 하나로 남는다. 회의 잠금처럼 한 기계 안에서만 맞는다는 한계는 0013 과 같다

`/recover` 대신은 둘을 비교했다. `--retry` 가 자기 프로세스에서 바로 처리하면 워커가 꺼져 있어도 돈다. 하지만 워커는 systemd 가 늘 띄워 두므로 둘이 같이 전사하게 되고, 로컬 전사면 메모리가 두 배다. 그래서 `--retry` 는 이미 있던 깨우기 파일(`wake-<서버ID>`)만 남기고 떠 있는 워커가 돈다. 워커가 꺼져 있으면 깨우기가 남아 있다가 워커가 뜰 때 돈다.

## 결정

- 처리는 워커만 한다. 봇은 녹음을 저장하고 회의 잠금을 놓은 뒤 워커를 찌른다(`nudge`). `MM_PIPELINE_MODE` 와 `MM_PROGRESS` 는 더 읽지 않는다
- 워커는 단계가 끝날 때마다 그 회의의 채널에 한 줄을 우편함에 쓴다. 처리 시작, 전사 끝(줄 수), 웹 회의록 저장(줄 수), 할 일 찾음(건수), 웹에 올림(PM 승인 대기 건수). 처음 실패, 자동 재시도 중단, 빠진 구간, 건너뛴 단계, BE·판단 경로의 경고도 쓴다
- 봇은 우편함을 2초마다 비운다. 올리지 못하면 같은 회의의 순서를 지키려고 거기서 멈추고 다음 바퀴에 다시 올린다. 30분이 지난 알림과 봇이 볼 수 없는 채널의 알림은 버린다
- `MM_DEBUG_REPORT=1` 이면 단계 시작, 회의록 파일, 할 일 목록, 처리 시간·대기·최대 메모리 한 줄을 더 쓴다. 개발에서 켜고 운영에서는 비운다
- 아무 단계도 움직이지 않은 바퀴는 알리지 않는다. 설정이 없어 멈춘 회의와 연결을 기다리는 회의를 워커가 바퀴마다 다시 집기 때문이다. 연결 대기는 기다리기 시작할 때 한 번만 알린다
- `/recover` 를 지운다. 자동 재시도를 멈춘 회의는 서버에서 `python -m capture.worker --retry <서버ID>` 로 깨운다
- `/recover` 가 하던 "워커가 살아 있나" 는 저장 알림에 붙인다. 워커 신호가 없거나, 멈췄거나, 주기의 여섯 배(최소 1분) 넘게 조용할 때만 경고 한 줄을 붙이고 정상이면 붙이지 않는다
- 동시 처리는 지금처럼 한 번에 한 회의다. 아래 "동시성" 을 본다

## 동시성

워커는 회의를 하나씩 처리한다. 로컬 전사(large-v3-turbo)는 M4 에서 RSS 2.5 ~ 2.9GB 라 4GB 서버에서 둘을 같이 돌릴 수 없다. Elice 원격 전사는 사정이 다르다. #182 측정에서 6인 정렬본 복사본 5개를 한꺼번에 넣어도 9.58초에 다 끝났고 실패는 0 이었다(`stt/eval/results/2026-10-06-server-capacity/README.md`). 전사가 회의 하나에 수 초라 지금 규모(팀 하나, 회의가 겹치는 일이 드물다)에서는 한 번에 하나로도 대기가 짧다. 저장 알림의 "앞에 N건" 이 대기를 보여 준다. 원격 전사일 때만 동시 처리 수를 늘리는 설정은 아직 만들지 않았다.

## 주기와 비용

워커는 10초마다 한 바퀴를 돌고 1초마다 찌르기와 깨우기를 본다. 봇이 저장하면 찌르므로 새 회의는 주기와 상관없이 1초 안에 시작한다. 주기가 정하는 것은 재시도 시각(1·2·4·8분)을 얼마나 늦게 알아채는지와, 웹에서 연결한 서버의 회의를 얼마나 늦게 집는지다.

한 바퀴의 비용은 매니페스트를 다 읽는 데서 나온다. M4 에서 처리할 회의 없이 쟀다(매니페스트 평균 1.5KB, 중앙값 7회). 운영 서버의 매니페스트는 지금 3개, 평균 1.6KB 다.

| 쌓인 매니페스트 | 대상 고르기 | 재시작 안내 확인 | 워커 한 바퀴 |
|---|---|---|---|
| 100 | 2.1ms | 2.1ms | 2.3ms |
| 1,000 | 22.8ms | 23.1ms | 23.2ms |
| 5,000 | 122.6ms | 123.4ms | 123.1ms |

1,000개면 10초 주기에서 한 코어의 0.23%, 60초면 0.04% 다. 이 차이는 작아서 10초를 그대로 둔다. 서버(t3.medium)에서는 아직 안 쟀다. 매니페스트가 수천 개로 늘면 주기를 늘리기보다 끝난 매니페스트를 옮겨 두는 쪽이 맞다. 봇의 우편함 확인(2초)은 빈 폴더 하나를 보는 일이다.

```
cd ai && .venv/bin/python -m stt.eval.capacity.scan --counts 100 1000 5000
```

## 끝나지 않는 경우

자동 재시도는 1·2·4·8분 간격으로 늘고 다섯 번째 실패에서 멈춘다. 그 밖에 바퀴마다 다시 집히며 끝나지 않는 경우가 셋 있다. 회의 20개로 워커 10바퀴를 1분 안에 돌려 셌고, 셋째는 코드(`recorder._due`, `Handoff.fail`)로 확인했다.

| 경우 | 바퀴마다 하는 일 | 끝나는 때 |
|---|---|---|
| 연결을 기다리는 회의(`workspace_wait`) | BE 조회는 1분에 한 번(1분 안 10바퀴에 0번, `test_recovery.py` 가 지킨다), 처리 표시를 쓰고 지우느라 매니페스트를 다시 쓴다 | 웹에서 연결할 때. 기한이 없다 |
| 설정이 없어 멈춘 회의(LLM, BE 설정) | 외부 호출 없음, 매니페스트를 다시 쓴다 | 설정을 채우고 워커를 다시 띄울 때 |
| 포기했는데 BE 에 fail 이 닿지 않은 회의 | 바퀴마다 `PATCH /meetings/{id}/fail` 을 다시 보낸다 | BE 가 받을 때. BE 회의가 없어 404 `MEETING_NOT_FOUND` 면 끝나지 않는다 |

셋째가 문제다. BE DB 를 다시 만들면 포기한 회의마다 10초에 한 번씩 404 를 받는 요청이 영원히 간다. 404 를 끝 상태로 보거나 fail 재전송에도 재시도 간격을 두는 쪽을 고쳐야 한다. 이 PR 범위 밖이라 따로 다룬다.

## 다시 볼 조건

- 봇과 워커를 다른 기계로 나누게 되면 우편함과 회의 잠금을 같이 옮긴다(공유 폴더로는 안 된다)
- 회의가 자주 겹쳐 "앞에 N건" 대기가 길어지면 원격 전사일 때만 동시 처리 수를 늘린다
- 매니페스트가 수천 개를 넘으면 끝난 것을 옮긴다
- 연결 대기에 기한을 두게 되면 기한이 지난 회의를 포기로 돌리고 채널에 알린다
