# 0007. 전사 앞에 노이즈 필터를 두지 않는다

- 날짜: 2026-09-14
- 상태: 결정됨. 발화 클립을 잘라 보내는 경로에 필터를 두지 않는다. 트랙 통째 전사는 비교 기준으로만 남는다 (0008)

## 배경

로컬 위스퍼 후기 글에 "ffmpeg 로 16kHz 로 맞추고 간단한 노이즈 필터를 걸었더니 정확도가
눈에 띄게 올라갔다" 는 말이 있었다. 수치는 없었다. 우리 파이프라인에는 소음을 빼는 단계가
없고(16kHz 변환, 패킷 필터, 에너지 VAD 로 자르기, 실로로 거르기뿐이다), 넣을 값어치가 있는지
재야 했다.

같은 종류의 필터를 numpy 로 만들어 같은 오디오에 걸고 로컬 large-v3-turbo(int8)로 CER 을
비교했다. ffmpeg 가 없어 값이 블로그의 필터와 같지는 않다.

- 대역 제한: 100~7500Hz 밖을 지운다 (highpass/lowpass 에 해당)
- 스펙트럼 게이팅: 조용한 프레임 10% 의 스펙트럼을 소음 프로필로 삼아 그 아래를 지운다 (afftdn 에 해당)

입력은 골든셋 6트랙(예전 봇으로 녹음, 209.6초)과 오늘 디스코드를 거쳐 낭독한 회의 2건
(정답 대본 있음, 44초·74.7초)이다. 전부 무과금이다.

## 검토한 선택지

- **스펙트럼 게이팅을 건다**: 블로그가 말한 것 / 우리 오디오는 조용한 구간이 디지털 0 이라
  소음 프로필이 0 이고 필터가 아무것도 안 뺀다. 디스코드 클라이언트가 보내기 전에 잡음을
  억제하고 침묵에서 패킷을 끊기 때문이다.
- **100Hz 하이패스를 건다**: 긴 파일 하나에서 디코딩 붕괴를 막았다 / 클립 단위에서는 화자
  셋이 나빠지고 하나가 좋아져 합이 0 에 가깝다.
- **아무것도 안 건다**: 지금 그대로다 / 위 긴 파일 사례를 놓친다. 그 경로는 우리 것이 아니다.

## 결정

발화 클립을 잘라 보내는 경로에는 아무 필터도 넣지 않는다. 처음에는 회의 중 전사가 이 경로였고,
지금은 종료 뒤 배치의 chunk 모드가 같은 클립을 묶어 보낸다 (0008).

**스펙트럼 게이팅은 0.000% 를 바꿨다.** 조용한 프레임 RMS 의 10퍼센타일이 0.00000 이다.
골든셋도 디스코드 녹음도 같다. 뺄 소음이 없다.

**대역 제한은 에너지를 2.8~4.3% 바꿨는데, 클립 단위 CER 은 화자마다 다른 방향으로 움직였다.**

| 화자 (골든, 클립 단위) | 원본 | 100Hz 하이패스 |
|---|---|---|
| 김동우 | 1.60% | 1.60% |
| 김환 | 11.59% | 11.59% |
| 유재환 | 11.30% | 12.43% |
| 윤지민 | 12.90% | 14.84% |
| 장원준 | 1.46% | 2.19% |
| 최진호 | 13.40% | 6.19% |
| 문자 가중 평균 | 8.56% | 8.42% |

원본은 두 번 돌려 두 번 같았다(결정적). 합은 0.14pt 차이인데 셋이 나빠지고 하나가 크게
좋아진 것이라, 넣을 근거가 못 된다.

재현 (ai/ 안에서, 무과금):

```bash
.venv/bin/python -m stt.eval.noise_filter_bench --tracks "<골든셋 audio>" --truth "<truth_by_speaker.json>"
.venv/bin/python -m stt.eval.clip_cer --tracks "<골든셋 audio>" --truth "<truth_by_speaker.json>"
```

## 같이 드러난 것

**긴 파일 통째 전사에서는 100Hz 하이패스가 디코딩 붕괴를 막았다.** 디스코드를 거친 74.7초
낭독(위스퍼의 30초 창을 넘는 길이)을 통째로 넣으면 원본은 "백엔드 API 명세가 나오면 바로
연결할 수 있게 됩니다" 를 무한 반복했다.

| 74.7초 파일, 통째 전사 | temperature 0 | 기본 설정 3회 |
|---|---|---|
| 원본 | 87.55% (반복 루프) | 4.56 / 7.47 / 13.69% |
| 100Hz 하이패스만 | 2.07% | 2.07 / 2.07 / 2.07% |
| 7500Hz 로우패스만 | 104.15% (루프) | |
| 50Hz 하이패스만 | 87.97% (루프) | |

50~100Hz 성분(전체 에너지의 0.6%)이 있는 채로 30초 창을 넘겨 통째로 넣으면 루프에 빠지고,
100Hz 아래를 지우면 안 빠진다. 이 성분의 자리를 재 보면(2026-09-16) 말하는 초에만 있고 조용한
초는 디지털 0 이다. 디스코드가 침묵에서 패킷을 끊기 때문이다. 피크는 84~85Hz 로 60Hz 배수의
전원 험이 아니고, 잡음원이 아니라 목소리의 저역(기본 주파수와 파열음)이다. 그래서 필터로 지울
것이 아니라 무음까지 통째로 넣는 전사 방식의 문제다. 기본 설정에서 실행마다 4.6~13.7% 로
흔들리는 것은 temperature 폴백이 샘플링으로 루프를 빠져나오기 때문이다.

**발화 클립을 묶어 보내는 경로에서는 이 문제가 없다.** 같은 74.7초 파일을 클립 8개, 묶음 2개로
보내면 반복이 없고, 100Hz 하이패스를 걸어도 텍스트가 한 글자도 안 바뀐다. 정렬본 두 회의에서도
하이패스가 chunk 의 CER 을 바꾸지 않았다 (0008 의 변형 표).
`temperature=0` 은 결정적이지만 원본에서 루프에 갇혀 못 쓴다. 골든셋 윤지민 트랙도 통째
전사에서 12.90 → 11.61% 로 3회 재현됐다. 나머지 5트랙은 변화 없음.

**클립 하나씩 전사는 트랙 통째보다 나빴다.** 같은 모델, 같은 골든셋에서 트랙 통째 6.97%,
클립 8.56%. 클립은 앞뒤 문맥이 없다. 이 차이는 클립을 화자별로 묶어 보내는 chunk 모드가
닫았고, 회의 길이 트랙에서는 통째가 오히려 무너진다. 두 값 다 0008 에 있다.

## 영향받은 파일

- `stt/eval/noise_filter_bench.py` 필터 세 조건 비교
- `stt/eval/clip_cer.py` 클립 단위 CER (로컬/Elice)

## 재지 않은 것

Elice 로 잰 클립 CER 이 없다. 골든셋 209.6초면 약 21원이다.

긴 파일에서 하이패스가 살린 것은 파일 하나다. 통째 전사가 비교 기준으로만 남아 더 재지 않는다.

블로그가 쓴 실제 필터와 값을 모른다. 마이크로 직접 녹음한 파일이면 결과가 다를 수 있다.

## 다시 볼 조건

이 결론은 디스코드 녹음(침묵이 0 으로 오는 입력)과 하이패스 필터에서 잰 것이다. 디지털 무음이 0 이라고
말하는 구간에 소음이 없다는 뜻은 아니다. 다른 입력과 다른 필터에는 같은 표로 다시 잰 뒤에야 말할 수 있다.

마이크로 직접 녹음한 파일처럼 조용한 구간이 0 이 아닌 입력이 들어오면 스펙트럼 게이팅을 다시
잰다. 지금 결과는 디스코드가 침묵을 0 으로 보내 주는 조건에서 나온 것이다.

묶음 경로에서 특정 화자의 클립만 나쁘게 나오는 일이 생기면(최진호 13.40 → 6.19 같은 경우)
그 화자의 오디오로 다시 잰다.
