# 0065. 완료 트랙 진행을 처리 소유 스레드에서 보고한다

- 날짜: 2026-11-10
- 상태: 결정됨, #483 AI 구현 선택
- 근거: [#483](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/issues/483), [AI와 BE 계약](../../../../backend/docs/contracts/backend-ai-contract.md)

## 배경

기존 `batch.run`의 네 인자 콜백은 끝난 모델 호출·제출한 호출·읽은 트랙·전체 트랙 수다. 추가 클립 전사와 지연 묶음 때문에 제출한 호출 수는 늘어난다. 읽은 트랙은 전사를 끝낸 트랙이 아니다. 이 값을 그대로 웹의 완료 트랙 수로 보낼 수 없다.

BE는 같은 STT 단계의 수치를 덮어쓰며 재시작을 위해 감소도 허용한다. 따라서 요청을 하나씩 순서대로 보내야 한다. 기존 작업 스레드 콜백은 알림 오류를 삼키므로 회의 삭제의 종결 신호를 전달할 별도 경계도 필요하다.

## 검토한 선택지

- 기존 호출 콜백을 전송한다. 연결은 짧지만 분모가 늘어나며 트랙이라는 단위와 맞지 않는다. 알림 오류 처리도 삭제 신호를 삼킨다.
- 완료량을 모아 별도 스레드가 최신값만 보낸다. HTTP 대기를 결과 수거에서 분리하지만 종료·최종 보고 대기·스레드 합류·삭제 예외 전달·privacy epoch 적용을 새로 소유해야 한다.
- 결과를 수거하는 소유 스레드에서 완료 트랙을 보고한다. HTTP 대기는 추가되지만 요청 순서와 저장 전 삭제 종결을 같은 스레드에서 보장한다.

## 결정

세 번째를 선택했다. [batch.py](../../../stt/batch.py)의 입력 index별 남은 작업 수가 일반 결과 수거와 추가 클립 전사, 지연 묶음 처리가 모두 끝난 트랙만 센다. 같은 화자의 서로 다른 파일도 분리한다. 기존 네 인자 콜백은 그대로 유지한다.

[Handoff](../../../capture/handoff.py)의 시도별 `stt_progress`가 시작·최종값을 보내고 중간 보고는 2초 간격으로 제한한다. 2초는 측정한 최적값이 아니라 요청 제한 정책이다. 별도 타이머·전송 스레드가 없으므로 함수가 돌아온 뒤 늦은 STT 보고가 남지 않는다. 일반 보고 장애는 전사를 막지 않고 삭제 예외는 출력 저장 전에 전파한다.

재시도도 전체 입력 WAV 분모를 유지한다. 작업 없는 트랙은 이미 처리한 것으로 세고, 대상 트랙은 마지막 실패 줄을 처리한 뒤 센다. 기존 중복 화자 파일의 last-wins 재시도 선택 동작은 이번 변경에서 고치지 않는다.

## 감수한 제약

- 긴 단일 트랙은 `0/1`에 오래 머물 수 있다. 수치는 처리량이고 성공률·파일 저장 완료가 아니다.
- 생략된 중간값은 다음 완료 사건 전까지 낮게 남을 수 있다. 최종값은 간격과 관계없이 시도한다.
- HTTP 지연은 소유 스레드와 STT ops 시간에 들어간다. 연결·읽기 각각의 타임아웃으로 전체 대기 상한을 주장하지 않는다.
- 삭제 뒤 대기열 작업은 취소하지만 실행 중인 외부 모델 호출의 즉시 취소는 보장하지 않는다.

## 다시 볼 조건

다트랙·BE 장애에서 보고 대기가 처리 지연의 주요 원인으로 관측되거나, 긴 단일 트랙에 더 세밀한 실제 처리량이 필요하면 단위와 전송 방식을 다시 검토한다. 현재 선택은 성능 개선을 측정한 결과가 아니다.
