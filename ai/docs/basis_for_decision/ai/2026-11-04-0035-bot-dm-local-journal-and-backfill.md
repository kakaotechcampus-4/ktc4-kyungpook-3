# 0035. 봇은 DM 발송 결과와 받은 답장을 파일에 먼저 적고, 게이트웨이에 다시 붙으면 끊긴 동안 온 DM 을 기록에서 메운다

- 날짜: 2026-11-04
- 상태: 결정됨

## 배경

봇이 승인된 리마인드를 DM 으로 보내고 결과를 보고하는 계약은 결정 0034 와 [backend-ai 계약](../../../../backend/docs/contracts/backend-ai-contract.md) §리마인드 DM 에 있다. 가져간 메시지는 다시 나오지 않고, 10분 안에 보고가 없으면 BE 가 못 보냄(`unknown`)으로 닫는다. 늦은 보고는 받아서 실제 결과로 고친다. 봇 쪽에서 남은 문제는 둘이었다.

- 봇이 DM 을 보낸 뒤 보고하기 전에 죽거나 BE 가 내려가 있으면, 실제로 나간 리마인드가 PM 화면에 못 보냄으로 남는다. 받은 답장을 BE 에 넘기지 못한 채 죽으면 그 답장은 사라진다
- 디스코드 게이트웨이는 봇이 꺼진 동안 온 DM 을 다시 주지 않는다. 배포나 재시작 사이에 팀원이 답하면 PM 은 그 답장을 영영 보지 못한다

## 검토한 선택지

보고하지 못한 결과와 넘기지 못한 답장

- 메모리에서만 재시도한다: 코드가 가장 작다 / 재시작하면 잃는다. 나간 DM 이 못 보냄으로 남고 답장이 사라진다
- 녹음 폴더 아래 파일에 먼저 적고, 보고나 전달이 끝나면 지운다(채널 알림 우편함 `FileOutbox` 와 같은 방식): 재시작해도 남는다 / 파일 상태를 관리해야 한다

꺼진 동안 온 DM

- 받아들인다: 코드가 없다 / 재시작 때마다 답장이 조용히 빠질 수 있다
- 게이트웨이에 붙을 때마다 최근에 봇이 DM 을 보낸 사람의 DM 기록을 읽어 넘긴다: 빠진 답장을 되찾는다. BE 가 같은 `discord_message_id` 를 한 번만 저장하므로 다시 넘겨도 안전하다 / 받는 사람마다 디스코드 API 를 한 번씩 부른다

## 결정

둘 다 파일로 한다(`ai/capture/dm.py`). 위치는 `recordings/.bot/dm/` 이다.

- 발송 기록 `sent/<message_id>.json`: 보내기 전에 결과 없이 쓰고, 조각이 나갈 때마다 나간 id 를 더하고, 끝나면 결과를 적는다. 보고가 받아지면(또는 다시 보내도 같은 거절이면) 지운다. 재시작 때 결과 없이 남은 기록은 보내다 죽은 것이라 다시 보내지 않는다. 조각이 다 나갔으면 delivered, 아니면 나간 id 만 실어 `unknown` 으로 보고한다
- 답장 큐 `replies/<discord_message_id>.json`: 받는 즉시 쓰고 넘긴다. 넘기지 못하면 다음 바퀴에 디스코드 id 순서로 다시 넘긴다. `MEMBER_NOT_FOUND` 와 400 은 버린다. BE 는 없는 경로에도 `INVALID_REQUEST` 를 404 로 주므로, 그 코드는 400 일 때만 거절로 읽는다
- 메우기 `recipients.json`: 봇이 DM 을 보낸 사람마다 마지막 DM 시각과 표시(`after_id`)를 둔다. `on_ready` 마다 마지막 DM 이 7일 안인 사람의 기록을 표시 뒤부터 끝까지 읽는다. 표시의 시작값은 처음 보낸 DM 이고, 기록을 끝까지 읽었을 때만 옮긴다. 발송이나 실시간 DM 이 옮기면 읽지 않은 구간의 답장이 영영 빠진다. 겹쳐 읽은 글은 BE 가 한 번만 저장한다
- 메우기 전에 남은 발송 결과부터 보고한다. BE 는 팀원이 어느 DM 에 답했는지 결과 보고로 알아서, 답장이 먼저 가면 같은 팀원이 속한 다른 워크스페이스 대화에 들어갈 수 있다

디스크가 차서 발송 기록을 쓰지 못하면 보내지 않고 `unknown` 으로 보고한다. DM 이 나간 뒤의 쓰기 실패는 결과를 바꾸지 않고, 메모리의 결과로 보고한다. 디스코드가 글을 저장하고 5xx 를 주면 라이브러리의 재시도가 같은 DM 을 또 보내므로, 조각마다 메시지 id 로 만든 nonce 를 `enforce_nonce` 와 함께 싣는다.

메우기 범위는 마지막 봇 DM 이 7일 안인 사람으로 정했다(2026-11-04). 꺼져 있던 시간이 아니라 마지막 DM 에서 잰다. 마지막 DM 이 8일 전인 사람이 쓴 답장은 짧은 재시작 사이에 온 것이어도 메우지 않는다.

로컬 BE 와 테스트 디스코드 서버에서 실제로 확인했다. 봇을 끈 동안 보낸 DM 은 재시작 직후 대화에 들어왔고, 이미 넘긴 답장은 다시 들어오지 않았다. 표시를 읽은 데까지만 옮기도록 바꾼 뒤의 동작은 단위 테스트로 확인했다. nonce 는 실제 디스코드에서 같은 값으로 두 번 보내 같은 메시지 id 가 돌아오는 것을 봤다.

## 다시 볼 조건

- 봇을 여러 대에서 띄우거나 녹음 폴더를 서로 다른 곳에 두게 되면 다시 본다. 지금 파일은 한 호스트의 봇 하나를 가정한다. 같은 폴더를 쓰는 봇이 하나 더, 앞 봇이 보내는 도중에 뜨면, 실제로 나간 메시지를 `unknown` 으로 보고할 수 있다. 같은 DM 이 두 번 나가지는 않는다
- 마지막 DM 이 7일 지난 사람의 답장이 빠졌다는 일이 생기면 범위를 다시 본다
- BE 가 봇의 DM 기록 조회나 웹훅 같은 다른 수신 경로를 갖게 되면 메우기를 그쪽으로 옮긴다
