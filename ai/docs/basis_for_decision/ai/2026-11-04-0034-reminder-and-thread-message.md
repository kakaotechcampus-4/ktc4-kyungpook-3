# 0034. 리마인드는 받는 사람·시각별 보낼 메시지로 묶어 PM 이 그 문구를 승인하고, 봇 DM 은 최대 한 번만 보낸다

- 날짜: 2026-11-04
- 상태: 결정됨

## 배경

PM 이 팀원에게 마감 리마인드를 보내고 답장을 받는 기능의 BE 가 없었다. FE 메시지 정책(D-174)은 재촉을 태스크 하나 × 받는 사람 한 명 단위로 다루고, 같은 받는 사람·발송 시각의 재촉은 한 통으로 합쳐 보내기로 정해 두었다. 상태는 예정·발송됨·취소됨·만료됨 넷이다. 리마인드의 목적은 PM 이 PM 말투로, 부담 없이, 사람이 쓴 것처럼 팀원에게 묻는 것이다. 봇 DM 발송, 스케줄러, 답장 판단 작업이 이 테이블과 API 위에 붙으므로 아래를 여기서 정해야 했다.

- 무엇을 저장하고 승인하는가
- 합친 문구를 누가 쓰는가
- DM 실패를 어떻게 보이는가
- 봇이 결과를 보고하지 못했을 때 어떻게 하는가
- 서버 정보가 없는 DM 답장을 어느 워크스페이스에 넣는가

## 검토한 선택지

승인 단위와 합치기

- 태스크마다 승인하고 나갈 때 BE 가 문구를 이어 붙인다: 단순하다 / 이어 붙인 글은 사람이 쓴 것처럼 읽히지 않고, PM 이 실제로 나갈 한 통을 보지 못한다
- 같은 받는 사람·시각의 리마인드를 승인 전에 보낼 메시지(묶음) 하나로 모으고, PM 이 묶음 문구를 보고 승인한다: PM 이 나갈 글 그대로를 승인한다 / 묶음 구성이 바뀌면 문구를 다시 만들고 승인을 풀어야 한다
- PM 이 처음부터 태스크 여러 개를 고른 리마인드 한 통을 쓴다: 사람이 쓰니 자연스럽다 / 스케줄러가 태스크마다 만든 제안은 다시 합쳐야 한다
- 나갈 때 AI 가 다듬고 PM 은 보지 않는다: 구현이 작다 / PM 이 확인하지 않은 글이 나가고, LLM 이 태스크나 날짜를 빼먹거나 지어낼 수 있다. D-174 설정 문구 "자동 승인을 켜지 않으면 보내기 전에 문구를 확인합니다"와 어긋난다
- 재촉 제안을 기존 승인 요청(`ApprovalRequest` 의 `reminder_dm`)에 둔다: 테이블을 덜 만든다 / 태스크 승인 화면에 섞여 D-174 의 "재촉 검토는 메시지 페이지에서만"과 어긋난다

문구를 쓰는 곳

- BE 에 LLM 을 넣는다: 한 곳에서 끝난다 / BE 에 LLM 키와 실패 처리가 생기고, BE 와 AI 는 HTTP 로만 이야기한다는 레포 규칙과 어긋난다
- AI(Luna)가 BE 의 초안 대기 목록을 가져가 써 넣는다(웹 업로드 가져가기와 같은 방식): 규칙을 지킨다 / 초안 워커가 따로 필요하고, 초안이 오기 전에는 규칙 문구가 보인다

DM 을 못 보낸 경우

- 상태 넷은 그대로 두고, 나간 메시지에 DM 결과(보냄, 못 보냄과 사유)를 따로 단다: 웹 대화에는 들어갔으니 발송됨이 맞다. FE 정책의 상태 값이 바뀌지 않는다
- 발송 실패 상태를 더한다: 상태 하나로 보인다 / D-174 상태 목록을 바꿔야 하고, 웹으로는 전달된 메시지가 실패로 보인다

봇이 가져간 뒤 결과를 보고하지 않을 때

- 최대 한 번: 10분 안에 보고가 없으면 다시 주지 않고 못 보냄(알 수 없음)으로 둔다 / 실제로 못 나간 DM 이 PM 화면에 실패로만 남는다
- 최소 한 번: 10분 뒤 다시 준다 / 봇이 보내고 보고하기 직전에 멈추면 팀원이 같은 DM 을 두 번 받는다

DM 답장의 워크스페이스(디스코드 DM 에는 서버 정보가 없다)

- 봇 DM 의 디스코드 메시지 id 를 저장하고, 답장 기능의 대상 id, 없으면 그 DM 창에서 바로 앞에 나간 봇 DM 으로 찾는다: BE 만으로 된다 / 두 팀 리마인드가 연달아 온 뒤 앞 팀 이야기를 일반 메시지로 쓰면 뒤 팀으로 들어간다
- DM 대신 각 팀 서버의 비공개 스레드로 보낸다: 서버 정보가 붙어 정확하다 / D-174 의 DM 이 바뀌고, 서버 관리자가 스레드를 볼 수 있고, 봇 권한이 더 필요하다
- 헷갈리면 봇이 버튼으로 어느 팀인지 묻는다: 정확하다 / 봇 상호작용을 새로 만들어야 한다. 한 사람이 두 팀에 동시에 있는 일이 드물 것으로 봐서(재 보지 않았다) 지금은 넣지 않는다

## 결정

- 리마인드(태스크 × 받는 사람)와 보낼 메시지(묶음)와 대화 메시지(실제로 나간 DM 한 통, 팀원 답장)를 나눈다. 같은 대화·같은 발송 시각의 예정 묶음은 하나뿐이다(DB 부분 유일 인덱스). PM 은 묶음 문구를 보고 고치고 승인한다. 승인 요청 테이블은 쓰지 않는다
- 묶음 구성이 바뀌면(더하기, 빼기, 태스크 메모 고치기, 시각 옮기기) 규칙 문구로 다시 만들고, AI 초안을 다시 요청하고, 승인을 푼다. PM 이 묶음 문구를 직접 고치면 승인은 그대로이고 AI 가 덮어쓰지 못한다. 문구를 고치면서 다른 묶음과 합쳐지는 시각으로 옮기는 요청은 고친 문구가 갈 곳이 없어 400 으로 막는다
- 문구 출처는 pm·ai·rule 이다. 리마인드가 하나뿐이고 PM 메모가 있으면 메모가 그대로 문구가 된다. 그 밖에는 AI(Luna, `ai/draft/reminder_draft.py`)가 초안을 쓴다. 말투는 PM 이 쓰거나 고쳐 승인한 최근 문구 5개를 따르고, 없으면 기본 페르소나(같은 팀 동료인 PM 이 가볍게 묻는 존댓말, 짧게, 재촉·탓하지 않음)로 쓴다. 결과에 태스크 제목과 마감 날짜가 모두 들어 있지 않거나, 목록 모양이거나, 600자를 넘거나, AI·봇이라는 말이 있으면 버리고 규칙 문구를 둔다. 규칙 문구는 기본 페르소나 틀이다(예: "재환님, API 명세서 마감이 11/14(금)이라 한번 여쭤봐요. 지금 어디까지 됐는지 편하게 알려 주세요!")
- BE 에 LLM 을 넣지 않는다. BE 는 초안 대기 목록과 써 넣기 API 를 열고, 초안을 가져간 뒤 묶음이 바뀌었으면(`draft_version`) 409 로 버린다
- 상태는 예정·발송됨·취소됨·만료됨 넷이다. DM 결과와 사유(DM 막힘, 디스코드 미연결, 알 수 없음)는 봇 메시지에 따로 둔다. 디스코드가 연결되지 않은 팀원의 메시지는 봇에 주지 않고 만드는 순간 디스코드 미연결로 표시한다
- 봇 발송은 최대 한 번이다. 늦게 온 보고는 받아서 실제 결과로 고친다
- 지난 시각으로 만들거나 고치거나 승인하면 "예정 시각이 지났어요" 오류를 낸다
- 봇 DM 창에 온 팀원 글은 리마인드에 대한 답인지와 상관없이 모두 대화에 넣는다. 워크스페이스는 답장 기능의 대상 DM, 바로 앞에 나간 봇 DM, 가장 최근 봇 DM, 가장 나중에 등록된 팀원 순서로 정한다

## 다시 볼 조건

- 같은 DM 이 두 번 가는 것보다 못 나간 DM 이 더 문제가 되면(실패 표시가 자주 보이면) 최소 한 번으로 바꾸고 봇 쪽에서 중복을 막는다
- 묶음이 자주 바뀌어 PM 이 같은 묶음을 여러 번 다시 승인하게 되면, 구성 변경 때 승인을 푸는 규칙을 다시 본다
- AI 초안이 검사에 자주 떨어지면(규칙 문구가 자주 나가면) 프롬프트와 검사 기준을 다시 본다. 실제 Luna 출력은 아직 보지 않았다
- 두 팀에 동시에 든 팀원의 답장이 다른 팀으로 들어간 일이 생기면 봇이 버튼으로 묻는 방법을 넣는다
- 태스크 안내 DM 이나 #회의록 요약처럼 태스크 × 받는 사람 단위가 아닌 메시지를 더할 때 리마인드 테이블에 넣을지 따로 둘지 다시 본다
- 팀원이 봇 DM 을 PM 이 보지 않기를 원하면 답을 기다리는 리마인드가 있을 때만 저장하는 쪽을 다시 본다
