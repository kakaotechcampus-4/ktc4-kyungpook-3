## 한 일

- `capture/chat_poll.py`: 채널의 최근 N분 메시지를 REST 로 한 번 읽어 `Transcript(source="chat")` 로 바꾸고 `judge.pipeline.run` 에 넣는다. 봇 메시지와 본문 없는 메시지는 뺀다. 유사 task 검색은 `judge.eval_pipeline.EmbeddingCandidates` 를 그대로 써서 `--tasks` 의 task 목록을 실제 임베딩으로 검색한다. 결과는 `runs/chat_poll_<시각>.json`. BE 에는 인계하지 않는다
- `to_transcript`: (작성자, 봇 여부, 시각, 본문) 목록 → 시간순 세그먼트. `start` 는 첫 메시지 기준 초, `seq` 는 1부터
- 사람 메시지 본문이 전부 비어 있으면 Message Content Intent 가 꺼진 것으로 보고 멈춘다(본문 없이 빈 결과가 나오는 것을 막는다)
- `shared/config.py`, `.env.example`: `CHAT_POLL_BOT_TOKEN`. 음성 봇과 다른 테스트 봇을 쓴다
- `tests/capture/test_chat_poll.py`: 봇·빈 메시지 제외, 시간순, seq·start

2026-10-14 추가 (fix 커밋):

- 멘션: `m.content` 는 `<@id>` 로 와서 LLM 이 누구를 지목했는지 모른다. 메시지에 같이 오는 `m.mentions` 로 `@이름` 으로 바꾼다(`clean_text`). `clean_content` 는 게이트웨이 없이 읽으면 서버 캐시가 없어 오류가 난다
- 줄바꿈: 공백으로 바꾼다. 남으면 1단계가 번호 매긴 한 줄이 여러 줄로 보인다
- 메시지 단위: `judge/semantic_judge._flatten` 이 `source == "chat"` 이면 문장 부호로 나누지 않고 메시지 하나를 한 줄로 둔다. URL·`v1.2` 가 조각나지 않는다. `source` 로 동작이 갈리는 첫 지점이고, 음성(`meeting`)은 그대로다
- 리액션: 누른 사람의 메시지 한 줄(`👍 (위 메시지에 반응)`)로 원래 메시지 바로 뒤에 넣는다. 1단계가 "네 그렇게 해요" 처럼 합의로 읽는다. 누른 시각은 API 가 주지 않아 원래 메시지와 시각이 같다

## 왜

음성 회의 파이프라인(1단계 Luna → 유사 검색 → Terra → Luna 초안)이 채팅에도 그대로 쓰이는지 보려고 한다. 판단 코어는 `Transcript` 하나만 받고 `source` 에 이미 `chat` 이 있어서 입력만 바꾸면 된다. 수집기(반복 폴링, 대화 묶음 나누기)와 BE 인계는 채팅에서 판단 품질이 나오는지 본 뒤에 만든다.

음성 봇은 Message Content Intent 를 일부러 꺼 두고 있어서(`capture/discord_adapter.py`) 테스트 봇을 따로 만들었다.

> 음성·채팅을 같은 형식으로 같은 판단 파이프라인에 넣는 방향은 유지. 채팅 특유의 실패를 먼저 재고, 차이가 반복되는 곳만 프롬프트·정책으로 보완한다. 단계 순서나 문맥 관리까지 크게 달라질 때 분리를 검토한다
- [ ] 담당자 규칙 고치기(판단 공통, 음성에도 영향): "근거 마지막 줄 화자 = 1인칭 담당자" 대신 실제로 맡겠다고 한 사람. 원준 "제가 할게요" 뒤 지민 "금요일까지요"면 담당은 원준. 👍 리액션이 담당 수락으로 읽히는 문제도 같이 막는다
- [ ] 입력 정리에서 의미를 바꾸지 않기: "제가 할까요?"(질문)가 약속으로, 👍 가 담당 수락으로 해석되지 않게
- [ ] 공통 평가 세트: 회의 대본과 실제 채팅 사례(주제 섞임, 답장, 시간차, 리액션)를 함께 넣고 사람이 정한 기대 결과와 비교. 회의 대본 말투만 바꾼 사례로는 채팅 특성이 빠진다
