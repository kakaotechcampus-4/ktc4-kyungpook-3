# 0032. PM 이 제안 값을 고쳐 승인하면 고친 값은 승인 기록에 두고, 진행률 칼럼은 지운다

- 날짜: 2026-11-04
- 상태: 결정됨

## 배경

PM 은 승인 카드에서 AI 제안을 그대로 승인하거나 반려만 할 수 있었다. 화면 설계의 확인 필요 카드와 리마인드 답장 제안 카드에는 제안 값을 고쳐서 승인하는 칸이 있어, BE 가 고친 값을 받아야 한다. 같은 PR 에서 팀 합의로 쓰지 않기로 한 진행률(progress)을 BE 에서 뺀다. 이어서 할 리마인드 메시지·팀원 초대·알림 스케줄러 작업이 같은 `models.py` 와 마이그레이션 체인 위에서 시작하므로 Task 와 ApprovalRequest 모양을 이 PR 에서 정해야 했다.

정할 것은 셋이었다. 진행률 칼럼을 지울지, PM 이 고친 값을 이력과 승인 기록에 어떻게 남길지, 승인 요청의 출처(회의, 리마인드 답장 등)를 어디에 둘지.

## 검토한 선택지

진행률

- 칼럼을 지우고 응답에서도 뺀다: 모델이 최종 모양이 되고 뒤 PR 이 그 위에서 시작한다 / 남은 값은 사라진다. AI 는 progress 를 보내지 않고 FE 에는 편집 화면이 없어 값은 대부분 비어 있을 것으로 봤다(운영 DB 는 확인하지 않음). 노션의 Progress 값은 그대로 남는다
- 칼럼은 두고 코드와 응답에서만 뺀다: 되돌리기 쉽다 / 쓰지 않는 칼럼이 남아 나중에 다시 정리해야 한다
- 칼럼을 두고 응답에 null 로 싣는다: FE 가 깨지지 않는다 / 쓰지 않는 필드를 계약에 계속 둔다

고친 값의 기록

- 고친 필드만 PM 한 줄: 이력에는 실제로 바뀐 값만 남는다. 수정 제안은 지금 값에서 PM 값으로, 새 태스크는 생성 줄 다음에 제안 값에서 PM 값으로 한 줄. 원래 제안과 근거는 승인 기록 payload 에 그대로 두고, PM 값은 `payload.task_overrides` 에 따로 둔다 / 이력 화면만으로는 AI 가 무엇을 제안했는지 모른다. 승인 기록과 비교해야 한다
- 항상 두 줄(제안 반영 다음에 PM 수정): 이력 화면에서 제안과 수정이 나뉘어 보인다 / 태스크에 들어간 적 없는 제안 값이 이력에 남고, PM 줄을 되돌리면 아무도 고른 적 없는 제안 값으로 돌아간다. 이력 줄에는 근거가 붙지 않으므로 근거를 남기는 데에는 도움이 되지 않는다

출처

- payload 키 `change_source`: 마이그레이션이 없고 `task_overrides` 와 같은 곳에서 읽힌다 / 타입이 없어 POST /approvals 에서 따로 검증해야 한다
- `ApprovalRequest` 칼럼: 타입이 있고 바로 조회할 수 있다 / 마이그레이션이 하나 늘어 뒤 PR 의 리비전 체인에 들어간다

## 결정

- 진행률 칼럼을 마이그레이션으로 지우고 Task 응답과 요청에서 뺀다. 요청 본문에 progress 가 와도 오류 없이 무시한다. 노션 연결 검사는 Progress 속성을 더는 요구하지 않고, 이미 있는 속성은 지우지도 쓰지도 않는다. 옛 진행률 이력 줄은 남고 되돌리기는 400 으로 막힌다
- 고친 필드만 PM 한 줄(출처 manual, 변경자는 승인한 PM)로 남긴다. 고치지 않은 필드는 승인 요청의 출처로 남는다. 제안 값과 같은 값은 `task_overrides` 에 넣지 않아, 값을 건드리지 않은 승인이 고친 승인으로 세지지 않는다. "제안 값을 고쳐 승인한 건수" 같은 지표는 `approval_request` 에서 `task_overrides` 가 있는 승인 건으로 센다
- 고친 값 필드 이름은 FE 가 먼저 정해 둔 요청안(`frontend/docs/contracts/frontend-api-contract.md` 「미합의 요청안」 M6-1)의 `task_overrides` 로 맞춘다. 새 태스크 키는 `task_title`·`assignee_member_id`·`due_date`, 수정 제안은 `status`·`due_date`.
- 마감과 담당자는 "미정"(`task_overrides` 에 null)으로 고를 수 있다. FE 요청안 M6-3(새 태스크 승인에 담당자·마감 필수)은 받지 않는다. 마감 없이 나온 일을 지어낸 날짜로 승인하지 않게 하려는 것이다. 태스크명과 상태의 null 은 400. 새 태스크 승인의 상태는 제안과 상관없이 항상 todo 다(승인 없이 바로 만드는 auto 경로는 AI 가 보낸 상태를 그대로 쓴다. 회의에서 "이미 끝났다" 고 확실히 나온 일을 todo 로 내리지 않기 위해서다)
- 승인 요청의 출처는 payload 키 `change_source` 로 두고, 없으면 회의로 본다. POST /approvals 는 ChangeSource 값이 아닌 출처와, PM 이 고친 것처럼 보이게 하는 `task_overrides` 키를 400 으로 막는다

## 다시 볼 조건

- 이력 화면에서 AI 제안과 PM 수정을 나눠 보여 달라는 요구가 생기면 두 줄 방식이나 이력과 승인 기록을 잇는 칸을 다시 본다
- 승인 지표를 자주 조회해 payload JSON 을 매번 풀어 읽는 것이 느리거나 번거로워지면 `task_overrides` 유무나 `change_source` 를 칼럼으로 옮긴다
- 진행률을 다시 쓰기로 하면 칼럼을 새로 더한다(지운 값은 돌아오지 않는다)
