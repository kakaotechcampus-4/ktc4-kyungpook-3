- 날짜: 2026-09-23

## 한 일

### 1. 근거를 단일 `index` 대신 `indices` 배열로 (`bf23091`)

- Luna 응답 형식을 `{"index": 0, ...}` → `{"indices": [0, 1], ...}` 로 변경
- `JudgeFinding.evidence` 가 근거 문장들을 담게 되고, `seq`/`speaker` 는 그중 **마지막 줄**을 가리킴
- 범위 밖 번호가 섞여 와도 나머지 근거로 항목을 살림 (`_valid_indices`)
- 채점기도 같이 수정 — 근거 문장 중 **앵커(마지막)만** 후보로 셈

### 2. 1단계 프롬프트 기준 조정 (`977ecb9`)

`_LUNA_SYSTEM_PROMPT` 에 포함 규칙 넷을 명시했다. 기존 프롬프트는 제외 규칙만 구체적이고
포함 규칙은 추상어("일정 합의, 담당자 언급, 범위 변경, 결정")뿐이라, 형태가 애매한 발화가
전부 제외 쪽으로 빨려 들어갔다.

- 조건이 붙은 약속("시간 되면 접근성 점검도 해볼게요")
- 이미 정해진 것을 바꾸자는 발화 — 제안 형태여도 포함
- 산출물이 분명한 작업 요청("리뷰 부탁드려요") — 제외 대상인 '발언 요청'과 구분
- 사고 활동에 산출물이 붙은 경우("고민해보고 내일까지 정리해서 공유드릴게요")

### 3. 골든셋 라벨 버그 3건 수정 (`977ecb9`)

`expected[].text` 가 실제 문장 분리 결과와 안 맞는 라벨 3건. 재발 방지 테스트도 추가
(`test_golden_set_labels_match_split_sentences`).

### 4. `JudgeFinding` 을 BE 인계 전 운반 스키마 형태로 (`519a50b`)

| 필드 | 변경 |
|---|---|
| `evidence` | `str` → `list[str]` |
| `indices` | 신규 `list[int]` — 근거 문장의 전사록 내 위치 |
| `assignee_type` | 신규 `str \| None` — `first\|third\|group\|none` |
| `status` | 신규 `str \| None` — `todo\|in_progress\|blocked\|done` |
| `evidence_status` | 신규 `str \| None` — `certain\|inferred\|missing` |

뒤 세 칸의 기본값은 `None` 이고 1단계는 채우지 않는다. `None` 이 "아직 판정 전"을 뜻한다.

## 왜

### 근거가 반쪽이었다

결정은 한 문장으로 끝나지 않는다. "제안 → 합의", "지시 → 수락"처럼 여러 발화에 걸쳐
만들어지는데, index 하나만 받으니 그중 한 줄만 근거로 남았다.

```
summary : API 명세서 작성은 지민님이 담당하기로 했다
evidence: 이건 지민님이 맡아주세요.        <- 무슨 작업인지 근거에 없다
```

같은 이유로 **하나의 결정이 findings 두 건으로 쪼개져** 나오기도 했다(잡음 섞인 8턴 회의
실측). 2단계가 이걸 다시 합칠 방법이 없다. 이 시스템은 근거 문장을 PM 에게 보여주는 게
핵심이라, 근거와 요약이 어긋나면 제품 가치가 무너진다.

### 필터가 조용히 좁았다

골든셋 25케이스를 처음 돌려봤다(`LUNA_API_KEY` 가 이제 있다). `short_sentences/case_06` 은
골든셋 README 가 "조건부 약속 — 애매해도 넉넉하게 포함하는 원칙 확인"이라고 적어둔
케이스인데 실제로는 실패하고 있었다. 프롬프트 마지막 줄이 "애매하면 포함시켜라"인데도,
그 위의 제외 규칙들이 더 구체적이라 모델이 그쪽을 따랐다.

1단계에서 놓치면 2단계가 검토할 기회 자체가 없어진다. 오탐은 뒤에서 걸러지지만 누락은
복구되지 않는다.

### 골든셋 라벨이 조용히 틀려 있었다

`expected[].text` 가 문장 분리 결과와 다르면 그 라벨은 어떤 findings 와도 매칭되지 않아
**늘 같은 답으로 채점된다** — `should_flag=false` 면 공짜 정답, `true` 면 영원한 오답이다.
점수는 나오는데 아무것도 재고 있지 않은 상태였다.

- `"다들 오셨나요? 시작하겠습니다."`, `"바로 본론으로 갈게요. 로그인 마감은~"` — 한 발화가
  문장 둘로 쪼개지는데 라벨은 하나
- `"음... 그건 나중에 다시 얘기해보죠."` — 말줄임표가 종결부호로 잘려 `["음.", "그건~"]` 이 됨

`golden_set/README.md` 에 같은 실수를 한 번 겪었다고 적혀 있어서, 눈으로 지키는 대신
테스트로 막았다.

## 결과

### 골든셋 25케이스 (실제 Luna API)

| | 규칙 기반 | Luna |
|---|---|---|
| 변경 전 | 277/337 (82%) | 314/337 (93%) |
| 변경 후 | 279/340 (82%) | **331/340 (97%)** |

`short_sentences` 는 86% → **100%**. 분모가 337→340 인 것은 라벨 3건을 6건으로 쪼갰기 때문이다.

개선분의 상당 부분은 **채점기 수정**에서 나왔다. `indices` 도입 직후 질문형이 오탐 8건으로
잡혀 확인해보니, 전부 "제안 + 합의"가 한 건으로 묶인 정상 동작이었고 summary 도 정확했다.

```
summary : 로그인 화면 마감을 이번 주 금요일로 앞당기기로 합의했다.
evidence: ["로그인 화면 마감을 이번 주 금요일로 당기는 게 어때요?", "네 그렇게 하시죠."]
```

`should_flag` 는 "이 발화 자체가 후보인가"를 묻는데 근거로 딸려온 앞줄까지 세고 있었다.
앵커만 세도록 고쳤다. 덤으로 이 기준은 정정 발화가 다른 결정에 묶여버리면 놓침으로
잡아준다 — 프롬프트가 "정정 전 발화도 따로 포함하라"고 요구하는 동작이라 그게 맞다.

### 실제 동작 확인

```
입력: A "API 명세서 작성 담당이 필요합니다." / B "이건 지민님이 맡아주세요."

text     : API 명세서 작성은 지민님이 담당한다.
evidence : ["API 명세서 작성 담당이 필요합니다.", "이건 지민님이 맡아주세요."]
indices  : [0, 1]
seq=2 speaker=B
```

잡음 8턴 회의에서는 사이에 낀 잡담을 건너뛴 `indices=[2,5,6]` 으로 한 건에 묶였다
(변경 전에는 두 건으로 쪼개졌다).

## 생각해볼 점

### Terra 2단계가 버린 건 Task 도 될 수 없다

파이프라인이 직렬이라 `is_meaningful=False` 로 걸러진 발화는 BE 로 가지 않는다. 그런데
Terra 2단계의 기준은 "Notion 문서에 기록을 남길 가치가 있나"다. 두 기준이 항상 같지 않다.

| 발화 | Notion 기록 | Task 추적 |
|---|---|---|
| "소셜 로그인은 이번 스프린트에서 빼기로" | O | X |
| "시간 되면 접근성 점검도 해볼게요" | 애매 | **O** |
| "리뷰 부탁드려요" | 애매 | **O** |

아래 두 줄이 Notion 관점에서 버려지면 **Task 도 같이 사라지고 알아챌 방법이 없다.**

### `status` 소유권이 겹친다

`JudgeResult.status`(PR #70)와 `JudgeFinding.status` 가 같은 어휘(`todo|in_progress|blocked|done`)를
쓴다. 의도적으로 맞췄지만(Terra 2단계 값을 옮겨 담는 자리), 누가 최종 소유자인지는 정해야 한다.
#70 이 머지되면 거기 추가된 `TASK_STATUSES` 상수를 공유하면 된다.

### `finding_id` 가 없다

`judge()` 가 finding 하나씩 받는 구조라 호출부가 findings 와 results 를 zip 으로 들고 있으면
대응이 유지된다. 다만 `JudgeInput` 은 `{source, text, candidates}` 만 실어서 `seq`/`speaker`/
`indices` 가 안 넘어가므로, zip 을 놓치면 복구할 방법이 없다. 프로세스가 갈리면 필요해진다.

### 앵커가 항상 마지막이라는 보장은 없다

`seq`/`speaker` 를 근거의 마지막 줄로 잡았다. "제안 → 합의" 구조에선 결론 발화가 뒤에 오고
1인칭 담당자 해소도 그 화자를 봐야 해서지만, 반례가 나오면 LLM 에 `anchor` 번호를 따로
받아야 한다. 코드에 `ponytail:` 주석으로 남겨 뒀다.

### 골든셋 라벨 하나는 재환님과 정해야 한다

남은 오탐 6건 중 6건이 `"네 그거 확인해볼게요"` / `"나중에 자료로 공유드릴게요"` 계열이다.
골든셋은 잡담으로 라벨했지만 확인·공유하겠다는 새 약속에 가깝다. 이 라벨이 정리되면
97% 에서 99%대로 간다. 남의 골든셋이라 이번엔 건드리지 않았다.
