# 0018. 새 항목 중복 방지는 첫 배포 뒤 빈도를 보고 정한다

- 날짜: 2026-10-02 (2026-10-09 정정, #184)
- 상태: 결정됨 (재검토 시점 아래)
- 번호: 처음 `decision_log/0017` 로 머지됐으나 `0017-transcript-sources-stage` 와 겹쳐 0018 로 옮겼다

## 배경

판단 파이프라인은 유사 검색으로 기존 task 를 찾아 Terra 가 "새 항목 / 기존 수정"을 가른다. 유사 검색은
task 테이블만 보는데, 새 항목은 PM 이 승인해야 task 가 된다. 그래서 아직 task 가 아닌 같은 일이 다시
언급되면 또 새 항목이 된다. 두 경우가 있다.

| 경우 | 앞의 것이 있는 곳 | 이슈 |
|---|---|---|
| 같은 회의 안에서 두 번 언급 (1단계가 finding 둘로 나눔) | AI `run()` 메모리 — 아직 BE 로 안 보냄 | #140 |
| 다른 회의에서 언급, 앞의 것이 승인 대기 중 | BE `approval_request` (pending) | #141 |

## 검토한 선택지

- **배포 전에 둘 다 고친다** — AI 하루 안팎 + BE 검색 확장 · 합치기 접수 · 마이그레이션 며칠. 첫 배포가 그만큼 늦어진다
- **배포 전에 #140(같은 회의)만 고친다** — AI 혼자 가능. 다만 빈도를 모르는 채로 먼저 고치게 된다
- **배포 뒤 빈도를 보고 고친다** — 새 항목은 모두 PM 승인을 거치므로 중복 카드가 자동으로 task 가 되지는 않는다.
  다만 PM 이 두 장을 모두 승인하면 task 도 두 개가 된다

## 결정

**배포 뒤 빈도를 보고 고친다.** 새 항목은 자동으로 만들지 않으므로 중복 카드가 그대로 task 가 되지는 않지만,
**"자동 생성하지 않는다"가 "중복이 안 생긴다"는 뜻은 아니다.** PM 이 같은 업무의 카드 두 장을 모두 승인하면 task 가
두 개가 되고, 담당자와 마감이 다른 카드에 나뉘어 있었다면 한 업무의 정보가 두 task 에 쪼개진다(#175 리뷰 고민 5).

| 시각 | 발화 | 결과 |
|---|---|---|
| 14:05 | "로그인 화면은 하은님이 맡아 주세요" | 새 항목 카드 ① (담당 하은) |
| 14:20 | "그 로그인 화면 금요일까지요" | 새 항목 카드 ② (마감 금) — ①은 아직 task 가 아니라 검색에 안 잡힘 |
| 다음 날 | PM 이 둘 다 승인 | task 2개 — 담당은 ①에만, 마감은 ②에만 |

그래도 배포 뒤로 미루는 것은, 제한된 시연 기간에는 PM 이 카드를 직접 확인하고, 실제 빈도를 모른 채 AI · BE 를
함께 바꾸는 비용이 크기 때문이다. 같은 회의 안의 중복은 1단계가 전사록 전체를 보고 같은 일을 묶도록 되어 있어
드물 것으로 예상하고, 회의 사이의 중복은 PM 이 승인을 미뤄 둔 경우에만 생긴다. 해결 설계(합치기 규칙, AI · BE 계약)는 #140 · #141 에 먼저 정리해 두었다.

## 재검토 시점

첫 배포(2026-10-03) 뒤 **2주가 되는 2026-10-17, 또는 실제 회의를 10번 운영한 뒤** 중 먼저 오는 때에 아래 측정값을 보고
#140 · #141 진행 여부를 정한다. #141 은 BE 작업이라 BE 와 같이 본다.

## 다시 볼 조건

- 첫 배포 뒤 같은 회의 안, 또는 승인 대기 중인 요청과 비슷한 제목의 `task_create` 가 자주 보이면 #140 부터 진행
  - 측정: `approval_request` 에서 같은 회의(`meeting_id`)이거나 pending 기간이 겹치는 `task_create` 중 제목이
    비슷한 것의 비율
- 담당자와 마감이 다른 카드로 나뉜 경우, 승인 뒤 한 업무의 정보(담당 · 마감)가 task 하나에 모였는지 확인한다.
  두 task 로 쪼개진 사례가 나오면 카드 수와 상관없이 #140 부터 진행
- PM 이 중복 카드를 거절하는 수고가 사용자 경험을 해친다는 피드백이 나오면
- 새 항목을 PM 승인 없이 바로 만드는 경로(AUTO 게이트)를 다시 쓰게 되면 — 그때는 중복이 바로 task 가 되므로
  먼저 고친다
