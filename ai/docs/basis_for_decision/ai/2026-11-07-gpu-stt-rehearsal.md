# GPU 전사 서버 전환 리허설

- 날짜: 2026-11-07
- 이슈: #393
- PR: #528
- 브랜치: `docs/393-gpu-stt-rehearsal`

## 한 일

운영 워커를 GPU 서버로 옮겨 저장된 6인 회의 하나를 처리하고 Elice 로 되돌렸다. 전환과 복귀 경로는 동작했지만 전사 15구간 중 2구간이 오류 없이 비었다. 같은 음성으로 다시 재서 원인을 이름 프롬프트로 좁혔다. 코드는 바꾸지 않았고 `deploy/gpu-stt/README.md` 에 결과와 주의점을 적었다.

## 왜

[#410](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/pull/410) 은 워커를 쓰지 않는 일회성 호출만 쟀다. drop-in 과 워커 재시작, 복귀가 실제로 통하는지 확인하지 못했고 측정용 합성 회의는 정확도 근거가 아니다.

## 결과

회의는 약 2분 13초(132.66초)이고 음성은 70.6초를 보냈다. 원본은 2026-11-04 에 Elice 로 처리한 같은 회의다.

| 단계 | 값 |
|---|---|
| `on --hours 1` | 22초 |
| `/health`, 키 호출 | 둘 다 200 |
| 전환 워커 재시작 | 1초 |
| 복제부터 `handed_off` | 73초 |
| 복귀 워커 재시작 | 1초 |
| `off` | 396초, `stopped` |

한 번 잰 값이다. 워커가 GPU 주소를 쓴 근거는 프로세스 환경값과 처리 중 GPU 서버로 열린 연결 1개다. 서버 쪽 로그는 볼 수 없다.

| 항목 | 원본 (Elice) | 리허설 (GPU) |
|---|---|---|
| 호출 / 실패 / 재시도 | 15 / 0 / 0 | 15 / 0 / 0 |
| 내용이 있는 구간 | 15 | 13 |
| 전사 글자 수 | 521 | 461 |
| 전사 시간 | 5.25초 | 12.8초 |
| 추출 시간 | 약 60초 | 48.99초 |
| 추출 항목 | 6 | 5 |
| 자동 / 검토 / 보류 | 0 / 5 / 1 | 1 / 3 / 1 |

비어서 돌아온 구간은 5.0초와 2.4초 길이의 두 곳이고 앞쪽은 11.349초가 걸렸다. 다른 1.4초 구간은 문장 뒷부분이 빠졌고, 깨진 문자가 한 곳 나왔다. 응답에 오류가 없어 워커는 실패로 세지 않았고 다시 보내지도 않았다.

## 빈 전사 재현

원인은 이름 프롬프트와 GPU 서버의 조합이다. 같은 회의를 워커와 같은 경로로 다시 돌렸고, 정답은 이 회의의 대본이다. 대본과 실제 발화가 다른 곳이 있어 CER 의 절대값보다 조건 간 차이로 읽는다. 글자 수는 372자, 회의 1건이다.

| 조건 | CER | 빈 구간 | 회차 |
|---|---|---|---|
| Elice, 프롬프트 없음 | 6.72% | 0 | 1 |
| GPU, 프롬프트 없음 | 6.72% | 0 | 1 |
| Elice, 이름 프롬프트 (워커 경로) | 8.33% | 0 | 2 |
| GPU, 이름 프롬프트 (워커 경로) | 19.89% | 2 | 3 |
| GPU, 이름 프롬프트, 순차 호출 | 19.89% | 2 | 1 |

프롬프트가 없으면 두 서버의 전사가 15구간 모두 글자까지 같았다. 프롬프트가 있으면 GPU 만 네 번 모두 같은 두 구간이 비었고, Elice 는 같은 프롬프트로 비지 않았다. 동시 호출 수와 단어 시각 요청은 결과를 바꾸지 않았다. 각 구간을 조건별로 세 번씩 다시 보내도 결과가 같아 무작위 오류가 아니다.

스트림으로 빈 5.0초 구간을 보면 모델이 프롬프트의 이름을 363토큰까지 되풀이하다 길이 제한으로 끝났다(`finish_reason=length`, 5.7초). 2.4초 구간은 8토큰 만에 깨진 문자로 끝났다. `response_format=json` 은 이 출력을 그대로 돌려주고 워커가 쓰는 `verbose_json` 은 빈 응답으로 돌려준다. 어느 쪽이든 발화 내용은 없다. 프롬프트의 이름을 21개에서 3개로 줄이면 두 구간 모두 내용이 나왔고, 10개로 줄이면 2.4초 구간은 여전히 비었다. 온도 0.2 도 해결하지 못했다.

Elice 가 같은 프롬프트로 다르게 동작하는 이유는 확인하지 못했다. GPU 서버는 vLLM 0.19.1, T4, `float16` 이고 Elice 의 버전과 설정은 알 수 없다.

이전 측정에서 GPU 와 Elice 의 CER 이 같았던 것은 그 측정이 프롬프트를 끄고 돌렸기 때문이다. [GPU 서빙 측정](../../../stt/eval/results/2026-11-04-gpu-serving/README.md)의 조건표에 프롬프트 없음이 적혀 있다. 그 결론은 프롬프트 없는 경로에만 해당한다.

저장된 다른 회의 6건을 GPU 로 돌리면 2건에서 1.5초보다 짧은 구간이 하나씩 비었다. 이 길이는 이름 대신 앞 줄을 프롬프트로 보내는 구간이고, 프롬프트 없이는 내용이 나왔다. 이름 프롬프트와 같은 원인인지는 재지 않았다.

빈 구간만 프롬프트 없이 다시 보낸 값으로 바꿔 계산하면 CER 은 9.95% 다. 빈 응답 없이 뜻이 달라진 구간이 남아 프롬프트를 끈 것보다 나쁘다.

## 추출과 정리

추출 항목의 차이는 두 갈래다. 빈 구간에 있던 기한 하나가 항목에서 빠졌다. 다른 항목 하나는 근거 발화가 두 전사에 똑같이 있는데도 나오지 않았다. 전사가 달라져 판단 입력이 바뀐 영향으로 보이지만 추출을 같은 입력으로 다시 돌려 보지 않아 전사 때문인지 추출의 편차인지 가리지 못했다. 자동 항목 1개의 출처도 같은 이유로 단정하지 않는다.

복제한 회의는 실제 회의처럼 처리됐다. BE 회의와 승인 대기 4건이 생겼고, 자동 항목은 실제 태스크가 되어 Notion 까지 동기화됐다. 회의, 발화, 추출 항목, 승인 대기, 복제 파일은 지웠다. BE 에 회의 삭제 API 가 없어 DB 에서 트랜잭션으로 지웠고 원본 회의의 행 수가 그대로인 것을 확인했다. 지운 행과 전사 원자료는 레포 밖 `mm/eval-runs/393-gpu-stt-fallback/2026-11-07-rehearsal/` 에 있다. 자동으로 만들어진 태스크는 BE 의 `delete_task` 로 지웠고 Notion 페이지는 동기화로 보관 처리됐다. 복제가 같은 음성 파일 이름을 쓴 탓에 원본 회의의 트랙별 중간 전사 파일이 덮어써졌다. 원본의 합친 전사와 추출 결과는 그대로다.

서버를 켠 시간은 약 14분이고 비용은 계산값 약 ₩210 이다. 추출은 Terra 6회, Luna 6회를 불렀고 다른 측정의 1회 값으로 약 ₩220 을 장부에 추정으로 적었다. 장부 합은 예약 기준 ₩5,828 이고 PR 당 기준을 넘었다. 재현은 GPU 서버 예약 ₩906 과 Elice 대조 약 ₩57 을 별도로 적었다.

## 다음

GPU 서버로 전환한 동안 이름 프롬프트를 끄는 변경은 #530 에서 다룬다. 그 전에는 전환 중 처리한 회의의 전사를 사람이 확인한다. 빈 구간이 있었던 회의를 다시 전사해 인계를 고치는 경로는 없다.

재처리 경로는 아직 돌리지 않았다. 포기된 `stt` 회의가 없었고 재처리 시간도 재지 못했다. 긴 회의를 워커로 처리한 값도 없어 #393 은 열어 둔다.
