# 0068. BE 는 동시 처리 요청을 30개로 막고 DB 연결 풀을 20+20 으로 늘린다

- 날짜: 2026-11-11
- 상태: 검토중

## 배경

#688 부하테스트에서 동시 요청이 40개를 넘으면 BE 가 30초씩 멈추고 요청이 무더기로 실패했다(#701). 인증 의존성과 엔드포인트가 동기 함수라 요청 하나가 단계마다 스레드풀(40개) 차례를 따로 기다리고, 첫 쿼리에서 받은 연결은 끝날 때까지 쥔다. 연결 15개(기본값 5+10)를 쥔 요청은 스레드를, 스레드를 잡은 새 요청은 연결을 기다려 풀 대기 시간 30초가 끝나야 풀린다. 운영은 `uvicorn --workers 1` 한 프로세스에 vCPU 2개다.

## 검토한 선택지

- 풀만 늘리기(20+20): 한 줄이다 / 로컬에서 20 VU 실패 5%, 30 VU 27%, 50 VU 100% 로 막히는 지점이 뒤로 갈 뿐이다
- 스레드풀을 늘리기: 한 줄이다 / 스레드가 많아질수록 연결을 기다리는 스레드도 늘어 같은 교착이 더 큰 수에서 생긴다
- 동시 처리 요청을 풀보다 작게 막는 ASGI 관문: 30줄 안쪽이고 엔드포인트를 건드리지 않는다. 기다리는 요청은 스레드도 연결도 잡지 않는다 / 몰리면 관문 앞에서 기다리는 시간만큼 응답이 늦어진다. 오래 걸리는 업로드도 한 자리를 쓴다
- 인증 의존성과 엔드포인트를 async 로 바꾸기: 스레드풀 차례를 기다리지 않는다 / DB 접근 코드 전체를 비동기 드라이버로 바꿔야 한다
- uvicorn 워커를 늘리기: CPU 2개를 다 쓴다 / 프로세스마다 백그라운드 워커(리마인드, Notion 동기화 등)가 따로 떠서 중복 발송을 먼저 막아야 하고, 프로세스마다 교착은 그대로다

## 결정

관문 30, 풀 20+20 으로 간다. 관문을 풀(40)보다 10 작게 잡은 것은 같은 프로세스의 백그라운드 워커 6개와 웹소켓도 연결을 쓰기 때문이다. 웹소켓은 오래 열려 있어 관문에 넣지 않는다. 운영 Postgres `max_connections` 는 100 이고 확인할 때 12개를 쓰고 있었다.

## 다시 볼 조건

- 관문 앞 대기로 p95 가 1초를 넘는 부하가 실제로 오면, 인증 쿼리 수(요청마다 약 6개)를 줄이거나 async 전환을 본다
- uvicorn 워커나 서버를 늘리면 프로세스 수 × 40 이 `max_connections` 를 넘지 않는지 본다
- 녹음 업로드가 몰려 관문 자리를 오래 차지하면 업로드 경로를 관문에서 뺀다
