# 0038. 리마인드 스케줄러는 나간 재촉마다 시계 행을 두고, 알림은 outbox 표에서 VAPID 웹 푸시로 보낸다

- 날짜: 2026-11-04
- 상태: 결정됨

## 배경

리마인드 표와 API([0034](2026-11-04-0034-reminder-and-thread-message.md))는 있지만 시간이 되어 스스로 움직이는 부분이 없었다. FE 메시지 정책(D-174)은 재촉 제안, 발송 직전 재확인, 72시간 무응답 막힘, 놓친 일정 처리를 BE 에 맡긴다. 웹 안 알림과 브라우저 푸시도 없어 PM 과 팀원에게 알릴 길이 없었다. 다음을 정해야 했다.

- 72시간 시계를 어떻게 저장하는가
- 무엇을 응답으로 보는가
- 프로세스가 둘 이상일 때 어떻게 중복을 막는가
- 푸시를 어떻게 보내는가

## 검토한 선택지

72시간 시계

- 시계 표를 두고 매 틱 확인한다: 답장을 기다리는 동안 시계를 멈출 자리가 있고, 막기 전 상태를 저장해 되돌릴 수 있다. 0034 의 표를 바꾸지 않는다 / 표가 하나 늘고 상태 전이를 관리해야 한다
- 표 없이 대화·리마인드·이력에서 매번 계산한다: 표가 줄어든다 / 멈춘 시계와 이미 알린 사실을 저장할 곳이 없어 조건이 복잡해진다
- 실행 시각이 있는 작업 큐를 둔다: 시각이 분명하다 / 발송·마감 변경·답장 자리마다 작업을 넣거나 지우는 훅이 필요해 빠뜨리기 쉽다

제안 중복

- 기존 리마인드에서 계산한다: 표가 늘지 않는다 / PM 이 시각을 옮기면 같은 마감으로 다시 제안이 생긴다
- 태스크·마감 쌍을 기록하는 표를 둔다: PM 이 옮기거나 취소한 제안이 다시 생기지 않는다 / 표가 하나 더 는다

푸시 라이브러리

- pywebpush: VAPID 서명과 본문 암호화를 맡긴다 / 의존성이 는다
- 직접 구현: 의존성이 없다 / 웹 푸시 암호화는 몇 줄로 끝나지 않고 틀리기 쉽다

## 결정

- 나간 리마인드 하나에 시계 하나(`reminder_watch`)를 두고 상태는 watching, answered, blocked, released, stopped 다. 태스크마다 최신 시계만 살아 있고, 자동 막힘이 걸린 채 새 재촉이 나가면 새 시계가 되돌릴 값을 이어받는다. 시계는 DM 전달 보고 시각부터 잰다. 메시지 생성 시각부터 재면 봇이 72시간 넘게 꺼졌다 켜질 때 팀원이 받자마자 막히기 때문이다. DM 이 실패했거나 전달 보고 전이면 막지 않는다
- 응답은 대화의 팀원 답장(디스코드, 웹)과 사람이 바꾼 태스크 상태·마감이다. 출처 `scheduler` 인 변경은 세지 않는다. 회의나 카톡으로 알린 뒤 보드만 고친 경우를 막힘으로 만들지 않으려는 것이다. 답장 판정이 붙기 전까지 답장 하나는 그 대화의 모든 태스크에 대한 응답으로 본다
- 제안은 `scheduler_suggestion`(태스크·마감·담당자 유일)으로 한 번만 만든다. 마감이나 담당자가 바뀌면 새로 제안한다
- 담당자 변경은 초기화다. 예정 재촉은 승인된 것까지 취소하고 열린 시계는 막지 않고 닫는다. 옛 담당자의 침묵으로 새 담당자의 태스크가 막히지 않게 하려는 것이다. 변경은 태스크 이력으로 판단한다. PM 은 담당자가 아닌 팀원에게도 재촉을 만들 수 있어 현재 담당자와 비교할 수 없다
- 발송 직전 확인은 `dispatch_due` 안의 한 줄 호출로 넣어 봇 경로도 함께 거친다. 응답이 있는 재촉은 취소하고, 묶음의 나머지는 승인을 풀어 PM 이 새 문구를 보게 한다. PM 이 보지 않은 문구는 나가지 않는다는 0034 의 규칙을 지키려는 것이다
- 카톡이나 회의로 이미 들은 경우가 많으므로 자동 막힘은 PM 이 한 번에 되돌릴 수 있다. 막기 전 상태와 사유는 시계 행에 있고, 그 뒤 태스크가 바뀌었으면 되돌리지 않는다
- 제안과 시계 판정은 항목마다 커밋하고 항목마다 PostgreSQL advisory 잠금을 잡는다. 잠금을 하나만 들고 있어 봇 가져가기·추출 저장과 교착하지 않고, 행 하나의 실패가 다른 워크스페이스의 일을 막지 않는다. 한 트랜잭션으로 묶거나 제안 단계만 먼저 커밋하면 PostgreSQL 에서 교착이 재현됐다. 멱등은 유일 키와 행 잠금으로 보장한다
- 알림은 `notification` 표에 먼저 쓰고 발송 상태를 같이 둔다. 푸시는 대상을 표시해 커밋한 뒤 잠금 밖에서 보내고 결과만 짧게 쓴다. 표시는 5분 뒤 풀려 프로세스가 죽어도 다시 보낸다. 틱 하나가 푸시에 쓰는 시간은 30초까지다. 실패해도 목록에는 남고, 일시 오류는 최대 3번, 404·410 은 구독을 지운다. `dedupe_key` 로 같은 사건의 알림을 한 건으로 만든다
- 서버가 구독 주소로 직접 요청을 보내므로 주소는 브라우저 푸시 서비스(FCM, Apple, Mozilla, Windows)만 받는다. 새 브라우저의 푸시 서비스는 코드에 더해야 한다. 계정마다 최근 10개 기기만 남긴다
- 시간대는 코드 상수 UTC+9 다. 워크스페이스에 시간대 칼럼이 없고 지금 사용자는 모두 한국이다. tzdata 의존을 피하려고 고정 오프셋을 쓴다. 한국은 일광 절약이 없다
- pywebpush 를 쓴다. 푸시 키는 서버 환경 변수로만 받고, 없으면 푸시를 건너뛰고 웹 안 알림만 쌓는다

알려진 한계는 다음과 같다.

- 상태 변경으로 시계가 answered 로 닫힌 뒤 온 답장은, 사람이 건 그 막힘을 풀지 않는다
- 담당자를 A, B, A 로 되돌리면 A 에게는 같은 마감으로 다시 제안하지 않는다
- 답장 하나가 대화의 모든 태스크를 응답으로 처리하므로, 답장 판정이 붙기 전에는 답이 없는 태스크도 응답으로 잡힌다
- 제안은 마지막 재촉 뒤에 응답이 있으면 건너뛴다. 그 뒤 마감이 바뀌면 다시 제안한다
- 알림 설정 저장이 없어 모든 알림이 켜진 것처럼 나간다
- 자동 재작성 문구는 초안 워커가 붙기 전까지 규칙 문구다

## 다시 볼 조건

- 한국 밖 사용자가 생기면 워크스페이스 시간대 칼럼을 더한다
- 답장 판정이 붙으면 대화 전체를 응답으로 보는 규칙을 태스크 단위로 바꾸고, 판정 대기 중 시계 멈춤을 쓴다
- PM 이 자동 막힘을 자주 되돌리면 72시간이나 응답 기준을 다시 본다
- 지원하는 푸시 서비스 밖의 브라우저에서 구독이 거절되면 허용 목록을 더한다
- 워커 프로세스가 늘어 틱이 주기 안에 끝나지 않으면 별도 워커로 뺀다
- 재촉이 PM 알림으로 많아 피로하다는 말이 나오면 제안 알림을 묶거나 설정 저장을 먼저 만든다
