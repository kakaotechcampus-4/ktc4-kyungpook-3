# 0044. GPU 전사 서버는 고정 IP 와 자체 서명 인증서로 부르고 전사 호출에만 CA 를 건다

- 날짜: 2026-11-05
- 상태: 결정됨

## 배경

[0039](2026-11-04-0039-gpu-stt-server.md) 는 GPU 서버를 장애 때만 켜기로 했고, 운영 서버에서 부를 경로와 인증서는 폴백 연결 때 정하기로 남겼다. 운영 서버는 팀 AWS, GPU 서버는 개인 AWS 라 둘 사이는 공인 인터넷을 지난다. API 키와 회의 음성이 함께 가므로 HTTPS 가 필요하고, `stt/elice.py` 도 `http://` 주소를 거절한다.

AMI 의 인증서는 localhost 전용이고 2026-11-07 에 끝난다. AMI 는 다시 만들지 않기로 했으니 새 인증서는 인스턴스에 넣어야 한다. 새로 띄우면 공인 IP 도 바뀐다. 운영 서버의 탄력적 IP 는 고정이어서 보안 그룹은 그 IP 하나만 열면 된다.

AMI 로 새로 띄우면 `on` 부터 첫 200 까지 335초가 걸렸다. 인스턴스를 지우지 않고 꺼 두면 2026-11-06 측정에서 운영 서버의 첫 전사 응답까지 161.8초와 158.6초였다([측정](../../../stt/eval/results/2026-11-05-gpu-fallback-prod/README.md)).

## 검토한 선택지

- 자체 서명 인증서와 고정 IP, 전사 호출에만 `verify` 지정: 외부 서비스에 기대지 않고 유효기간을 길게 잡을 수 있다. `stt/elice.py` 를 고쳐야 해서 배포 전에는 운영 워커로 리허설을 할 수 없다.
- sslip.io 와 Let's Encrypt 의 공인 인증서: 코드를 고치지 않아 머지 전에 리허설할 수 있고 주소와 키만 바꾸면 된다. 대신 장애 때 sslip.io 에 의존하고, 발급할 때 포트 80 을 열어야 하고, 90일마다 만료된다.
- certifi 와 자체 인증서를 합친 번들을 워커의 `REQUESTS_CA_BUNDLE` 로 지정: 코드를 고치지 않는다. 대신 GPU 서버의 키가 새면 워커의 BE 호출까지 위장할 수 있다.
- 고정 IP 없이 켤 때마다 인증서를 만든다: 대기 비용이 없다. 대신 켤 때마다 운영 서버의 주소와 인증서를 바꿔야 해서 장애 때 손이 더 간다.

켜는 방식은 둘을 비교했다.

- 켤 때마다 AMI 로 새로 띄우고 끄면 지운다: 디스크 대기 비용이 없다. 대신 켤 때마다 초기화 약 $0.30 이 들고 첫 응답까지 약 2.9분이 더 걸린다.
- 대기 서버를 꺼 둔다: 켜기가 160초 안팎이고 초기화가 한 번뿐이다. 대신 디스크 75GB 가 월 $6.84 이고, stop 에 약 400초가 걸려 그동안 켤 수 없으며, 켤 때 AWS 용량에 기댄다. 키와 인증서가 디스크에 남는다.

## 결정

자체 서명 인증서를 쓰고 `ELICE_STT_CA_BUNDLE` 로 전사 호출에만 CA 를 지정한다. 고정 IP 는 켜고 끄는 동안 유지하고, 인증서는 그 IP 를 SAN 에 넣어 400일로 만든다. 보안 그룹은 8000 포트를 운영 서버 IP 에만 연다.

장애 대응 경로가 또 다른 외부 서비스에 기대지 않는 쪽을 골랐다. 고정 IP 대기 비용은 시간당 $0.005 로 12월 말까지 약 $6.8 이다. [0039](2026-11-04-0039-gpu-stt-server.md) 의 예산표에 넣었다.

인스턴스는 지우지 않고 꺼 둔다. `setup` 이 대기 서버를 한 번 만들어 고정 IP 를 붙이고 끄며, `on` 은 start, `off` 는 stop 이다. 장애 때 3분이 줄어드는 값이 초안 10분 기준에서 크고, 디스크 비용은 12월 말까지 약 $12.4 로 예산 안에 든다. 지우는 일은 `destroy` 로 나누어, 인증서를 새로 만들 때와 기간이 끝날 때만 쓴다. `setup` 이 첫 부팅을 끝까지 본 서버에만 `Ready` 태그를 붙이고 `on` 은 그 서버만 쓴다.

리허설은 코드가 배포된 뒤에야 할 수 있어 머지 뒤로 미룬다.

인증서 키와 API 키는 AMI 를 다시 만들지 않으려고 user-data 로 넘긴다. 그래서 대기 서버가 있는 2026-12-31 까지 개인 계정 권한으로 평문 조회가 된다. 키가 지키는 대상은 운영 서버 IP 로 막힌 서버 하나이고, 개인 계정에 접근할 수 있으면 이미 서버를 지울 수 있다. 그래서 별도 비밀 저장소를 두지 않는다.

user-data 는 첫 부팅에만 돌고 재부팅은 종료 예약을 지운다. 그래서 첫 부팅이 부팅마다 도는 cloud-init 스크립트를 디스크에 설치하고, 그 스크립트가 vLLM 시작과 종료 예약을 건다. `on --hours` 의 값은 인스턴스 태그 `StopAt` 으로 넘겨 부팅 때 읽는다. 태그를 못 읽으면 3시간으로 건다.

켠 뒤 3시간에 인스턴스가 스스로 stop 하도록 예약한다. 기본값으로 켜고 잊어도 한 번에 약 $1.94 까지만 쓰려는 장치다. 짧은 시각으로 실제 꺼지는 것을 확인했다. 3시간을 넘는 장애 처리는 다시 켜야 하고, 그때 처리 중이던 회의는 빠진 구간을 둔 채 인계될 수 있다.

음성 임시 파일을 위한 tmpfs 는 넣지 않는다. 운영 워커의 묶음이 최대 902,444바이트로 Starlette 가 디스크에 내리는 1MiB 아래다. 근거와 한계는 [측정](../../../stt/eval/results/2026-11-05-gpu-fallback-prod/README.md#음성-임시-파일)에 있다.

## 다시 볼 조건

- 운영 서버 IP 가 바뀌면 보안 그룹을 다시 맞춘다.
- 고정 IP 를 놓으면 인증서를 새로 만들어 운영 서버에 다시 넣는다.
- 2026-12-31 에 장애 대응 기간이 끝나면 `destroy --release-ip` 로 대기 서버를 지우고 고정 IP 를 놓는다. 대기 비용이 그때부터 멈춘다.
- `CHUNK_MAX_S` 를 약 32.5초 넘게 올리거나 `track`, `whole` 모드를 운영에 쓰면 음성 임시 파일을 다시 본다.
- 켤 때 용량 부족이 실제로 나오면 AMI 로 새로 띄우는 경로를 되살릴지 본다.
- 전환을 다른 팀원도 해야 하면 개인 계정 키 없이 켤 방법을 다시 정한다.
- 실제 회의 음성이 개인 계정을 지나는 것을 팀이 허용하지 않으면([#360](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/issues/360)) 이 경로를 쓰지 않는다.
