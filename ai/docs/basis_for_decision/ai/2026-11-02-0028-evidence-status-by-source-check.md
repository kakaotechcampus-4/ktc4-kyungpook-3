# 판단 경로 근거 상태를 판정 API Jev 에 다시 물어 정한다

- 기록일: 2026-11-02 (2026-11-03 B안으로 변경)
- 관련 마일스톤: 확인 필요 (이슈 #232)

## 문제와 제약

- BE 의 judge 새 항목 auto 조건(`task_status`·`due_status` 가 certain, `similar_count` 0 등)은 이미 머지돼 있었지만, AI 판단 경로는 이 값을 만들지 않아 judge 새 항목이 auto 가 될 수 없었다.
- LLM 에게 상태를 직접 매기게 하면 자기가 낸 값을 대체로 확신해 거의 다 certain 이 나오고, auto 조건이 의미를 잃는다(#232 사용자 답글).
- 잘못된 certain 은 PM 확인 없이 Task 가 만들어지는 쪽으로 틀린다. 반대로 잘못된 inferred 는 review 로 가서 사람이 한 번 더 본다.

## 실제 검토한 선택지

#232 답글과 2026-11-02~03 설계 논의(PR #261)에서 검토했다.

- A. 코드로 원문 대조: LLM 은 값과 원문 표현만 내고, 코드가 표현 목록·정규식·날짜 계산기로 확인한다.
- B. 별도 검증 질문: 값을 만든 뒤 근거 원문과 함께 "원문에 명시돼 있나"를 따로 묻는다.
- C. Luna 가 `ambiguous` 를 자기 표시(#232 본문 원안).

## 선택과 이유

처음에는 A 를 구현했다가 B 로 바꿨다(사용자 결정).

- A 는 정해 둔 모양만 알아본다. "14일까지"(월 없는 날짜), "맡아주세요"(목록에 없는 지시)처럼 사람이 보기에 명확한 문장도 inferred 가 되고, "아직 못 했습니다" 같은 부정은 certain 이 됐다. 말의 모양은 끝없이 다양해 규칙 목록이 따라갈 수 없다고 판단했다.
- B 의 질문 상대는 Terra·Luna 대신 Elice MLAPI 의 판정 API Jev(`typesafe/jev-latest`, `POST /v1/decisions`)로 정했다. 문장을 생성하지 않고 정해 준 선택지(yes/no/unclear)마다 확률을 돌려주므로, 응답을 파싱할 필요가 없고 숫자에 근거가 있다. 값을 만든 Luna 와 다른 모델이라 자기 답을 너그럽게 보는 위험도 줄인다.
- certain 기준은 yes 확률 0.8 이상이다. Jev 가 함께 주는 `confidence` 는 계산 공식이 공개되지 않았고 고른 답(no 일 수도 있음)에 대한 값이라, 방향이 분명한 yes 확률을 쓴다. 0.8 은 BE 의 담당자 확정 기준과 맞췄다.
- C 는 거의 certain 이 나온다는 문제를 그대로 가져서 채택하지 않았다.

## 장단점과 감수한 제약

- 새 항목마다 Jev 호출이 1회 늘어난다(할 일·마감을 한 번에 묻는다, 응답 1초 안팎).
- 응답이 실행마다 조금 다르다(같은 대사에서 yes 0.78 ↔ 0.82). 기준 근처 항목은 실행에 따라 certain/inferred 가 바뀔 수 있다.
- Jev 는 달력 계산이 약했다. "금요일까지"인데 토요일 날짜를 yes 0.82 로 통과시켜, 마감 날짜의 요일을 함께 주도록 바꿨다. 이후 같은 평가에서 잘못된 certain 은 0건이었다.
- pytest 로는 가짜 Jev 만 검증한다. 실제 판정 품질은 `judge/eval_evidence.py` 로 잰다.
- 키가 없거나 호출이 실패하면 inferred 다. 운영에 `JEV_API_KEY` 가 없으면 auto 가 열리지 않는다.

## 영향 범위와 재검토 조건

- 판단 경로 새 항목만 해당한다. update 항목과 legacy 경로(`extract/`)는 바꾸지 않았다. 담당자 근거는 BE 매칭이 맡으므로 묻지 않는다.
- 평가(2026-11-03, 대사 19개 × 2회): 잘못된 certain 0건, 할 일 37/38·마감 22/24 정답. 놓친 3건은 yes 0.78~0.79.
- 재검토: 운영의 상태별 PM 반려·수정 비율을 보고, 잘못된 certain 이 나오면 기준값을 올리거나 질문 기준을 고친다. 평가 대사를 늘린 뒤 0.8 을 다시 본다.
