# 이전 회의 5회로 쌓인 용어 목록이 6회차 전사 오류를 잡는지 확인

- 날짜: 2026-11-10
- 브랜치: `feature/643-asr-term-e2e`
- 이슈: #643 (1번 목업 회의, 3번 E2E)

## 한 일

시연·심사에서 "이전 회의에서 쌓인 용어 목록 덕분에 전사 오류를 잡는다"를 보여 줄 수 있는지 확인했다. 워크스페이스 용어 목록은 judge 파이프라인이 회의를 처리할 때만 쌓인다(한 회의에서 두 사람 이상이 말한 명사, PM 이 승인한 확인 카드 제목). 그래서 목업 회의를 DB 에 넣기만 해서는 목록이 비고, 회의를 차례로 파이프라인에 통과시켜야 한다.

- 목업 IT 팀 회의 1~5회차(11-02·05·09·12·16, 회차당 30~38줄)와 6회차 2인 대본 2벌(정확본·오인식본)을 `judge/golden_set_asr_terms/` 에 새로 썼다. 팀원은 지민(PM)·동우·원준·김환·재환·진호. 고유 용어 제브·폴러·루나는 기본 목록 밖이고 형태소 분석기가 한 명사로 자르는 것을 실측해 골랐다. 회의마다 세 용어를 두 사람 이상이 말한다.
- 4회차 "발표 리허설" 카드는 김환 혼자 말하고 PM 이 승인한다. 승인 제목이 다음 회의에서 용어로 흡수되는 경로를 보이기 위해서다.
- 심사위원이 읽을 6회차 대본은 `judge/golden_set_asr_terms/judge-script.md`. 테스트가 fixture 와 대사를 대조한다.
- CI 테스트(`tests/test_asr_terms_e2e.py`): 1단계·Terra·Luna 초안·Jev 만 고정하고, 전사록·두 사람 이상 규칙·형태소 분석·`BeClient`↔가짜 BE 의 용어 GET/POST·승인 큐 흡수는 실제 코드로 돈다.
- 실제 실행(`judge/eval_asr_terms.py`): 1~5회차를 실제 Luna·Terra·임베딩·Jev 로 차례로 돌리고, 5회차 뒤 상태 복사본에서 6회차 정확본·오인식본을, 빈 목록에서 이력 없는 정확본을 돌렸다. BE 는 메모리 흉내다. 실제 서버·테스트 계정에는 아무것도 넣지 않았다.

## 결과 (실제 실행)

실행 1은 끝까지 돌았다. 실행 2는 3회차 1단계에서 Luna 응답을 두 번 연속 파싱하지 못해(`FindingExtractionUnavailableError`, 58문장) 멈췄다. 비용을 이유로 추가 실행은 하지 않았다(#643 설계 확정 Q5 를 조정, 사용자 확인).

**용어 목록**: 1회차 뒤 제브·폴러·루나가 들어갔다(실행 1·2 같음). 4회차 승인 제목 "발표 리허설 진행"은 5회차 실행 때 큐에서 흡수돼 "리허설"이 목록에 들어갔다.

**6회차 폴러 줄 (실행 1)**

| 대본 | 제목 | 의심 단어 (Jev yes) | 근거 상태 (할 일 / 마감) | 기대 |
|---|---|---|---|---|
| 정확본, 이력 있음 | 채팅 폴러 서버 설정 | 없음 | certain(1.0) / certain(0.93) | 반영(auto) 후보 |
| 오인식본, 이력 있음 | 채팅 볼러 서버 설정 | 볼러 (0.18) | certain(1.0) / certain(0.91) | 확인 필요 (`asr_suspect`) |
| 정확본, 이력 없음 | 채팅 폴러 서버 설정 | 폴러 (0.69) | certain(1.0) / certain(0.93) | 확인 필요 |

설계 확정(Q4)은 이력 없는 대조의 통과 기준을 "Jev 에 물었다"로만 두었는데, 실제로도 0.8 미만이라 확인 필요 장면이 나왔다.

## 드러난 문제

1. **형태소 분석기 분할로 생긴 오탐**: "제목"이 제+목, "스플래시"가 스+플래시, "검수"가 검, "최종본"이 최종+본으로 잘려 정상 제목에 의심 단어가 붙었다. 6회차 B 줄(발표 자료 최종본)은 오인식본에서 '최종'(0.78·0.64)으로 의심 단어가 붙었지만 마감이 inferred 라 어차피 확인 필요다. 1~5회차에서도 '실행'(0.56)·'축약'(0.47)·'제작'(0.31~0.57)·'점수'(0.55) 같은 정상 단어가 0.8 미만으로 막혔다. 결정 기록 0051 의 정상 발화 오탐(19%)과 같은 방향이다.
2. **완료 보고가 새 할 일로 추출**: 6회차 C 줄 "루나 제목 검수는 김환님이 어제 끝냈대요"가 새 할 일(task inferred)로 뽑혔다. 시연의 확인 필요에 카드가 하나 더 보인다.
3. **조건부 발언 추출**: "시간 되면 Soniox" 가 할 일로 뽑혔다(task yes 0~0.09 → inferred 라 확인 필요).
4. **1단계 파싱 실패**: 3회차(58문장)에서 Luna 1단계 응답을 재시도까지 두 번 쓰지 못했다. 운영에서는 회의 하나가 통째로 실패하는 경로다.
5. **Luna 가 제목을 원문과 다르게 지으면 할 일이 inferred**: 예 "채팅 폴러 systemd 유닛 파일 준비"(task 0.26), "제브 호출 비용 정리"(0.26). 근거 판정이 제목과 원문의 일치를 본다.

## 시연·시드에 주는 뜻

- 실제 테스트 계정(#606)에는 **1~5회차만** 파이프라인으로 넣는다. 6회차는 미리 돌리지 않고 시연 때 대본을 읽으며 실제 회의로 진행한다(미리 돌리면 그 회의의 명사가 목록에 들어가 상태가 바뀐다).
- 실제 음성은 "폴러"를 맞게 받아 적을 수도 있다. 그러면 이력 덕분에 통과(반영됨)하고, 잘못 받아 적으면 확인 필요로 잡힌다. 오인식 장면을 반드시 보여야 하는 우리 시연 영상은 오인식본을 업로드해 보인다.
- 확인 카드에 의심 단어 사유를 보이는 것은 FE 몫이다(#643 4번).

## 한계

- 실제 실행은 1회 전체 + 1회 부분이다. 의심 단어 확률은 실행마다 흔들린다(예: '실행' 0.56 → 0.54, 오인식본 '최종' 0.78 → 0.64).
- 실제 BE 게이트(auto/review)는 돌리지 않았다. AI 쪽은 `asr_suspects` 와 근거 상태만 본다.
- **승인 경로는 게이트를 흉내 내지 않는다.** `approve_titles` 는 fixture 가 정한 카드를 승인한 것으로 보고 제목을 큐에 넣는다. 실제 BE 는 확인 카드를 승인할 때만 큐에 넣는다. 이 실행 결과를 시드로 재생한 #673 에서 보니(BE 게이트 auto 4·review 24·hold 2) 2회차 시나리오(마감 inferred)와 3회차 프론트 요청 이슈(2인칭 담당자)는 확인 카드였지만, **1회차 루나 프롬프트와 4회차 리허설 카드는 회의의 첫 항목이라 auto 로 갔다.** 그래서 "4회차 리허설 승인 → 5회차 용어 흡수"는 CI 와 이 실행에서만 성립하고 실제 흐름에서는 일어나지 않는다. 실제 실행 스크립트는 승인 대상이 auto 모양이면 경고를 출력한다(#648 리뷰). 시연용 시드(#673)는 용어를 직접 넣어 리허설이 목록에 있으므로 시연에는 영향이 없다.
- 음성·STT 는 거치지 않았다. 전사록부터 시작한다.
- `MM_EXTRACT_PATH=judge` 일 때만 이 경로가 돈다. 운영 값은 저장소로 확인할 수 없다.
