# 0039. 리마인드 답장은 답장 한 통마다 판단 행을 두고, 회의 판단을 이번 답장의 finding 으로만 돌리며, 자동 반영은 BE 가 가른다

- 날짜: 2026-11-04
- 상태: 검토중

## 배경

팀원 답장은 대화에 저장될 뿐 태스크로 이어지지 않았다. 웹 답장은 봇이 보지 못하므로 답장 이벤트로 판단을 시작할 수 없고, `/extractions` 는 `meeting_id` 가 필수라 답장 결과를 받을 곳이 없다. `judge/pipeline.py` 의 수정 항목에는 근거 상태가 없고, 스케줄러 `_settle` 은 답장이 오면 내용과 상관없이 시계를 닫고 막힘을 푼다. 다음을 정해야 했다.

- 답장을 어떻게 맡기고, 재시작과 재시도에서 한 번만 반영할 것인가
- 판단 코드를 어디까지 고칠 것인가
- 자동 반영과 PM 확인을 어디서 가를 것인가
- 시계와 막힘을 언제 처리할 것인가

## 검토한 선택지

맡기는 방식

- 답장 저장과 같은 트랜잭션에서 판단 행을 만들고 봇이 가져간다: 웹과 디스코드가 같은 길을 타고, 행이 없으면 리마인드 답장이 아니라는 뜻 하나로 읽힌다 / 저장 함수 두 곳을 고친다
- 맡길 때 행을 만든다: 저장 코드를 안 고친다 / 행이 없는 것이 대기와 무관을 함께 뜻해 스케줄러가 시간을 재야 한다

맡긴 뒤 봇이 죽을 때

- 3분 뒤 다시 맡기고 attempt 로 늦은 결과를 거른다: 배포로 재시작해도 PM 에게 판단 실패 알림이 가지 않는다 / LLM 비용이 한 번 더 들 수 있다
- 한 번만 맡기고 10분 뒤 알린다: 코드가 준다 / 재시작마다 판단 못 함 알림이 간다

앞 답장을 문맥으로 줄 때 이번 답장 변경만 남기기

- `pipeline.run` 에 `judge_seq` 를 더해 이번 답장의 finding 만 판단한다: 앞 줄에 Terra·Luna 호출을 쓰지 않는다 / 재환 코드를 고친다
- 판단 코드를 안 고치고 `evidence_at_ms` 로 뒤에서 거른다: 고칠 곳이 없다 / `_merge_into` 가 근거를 앞 카드 것으로 두므로, 앞 답장과 같은 태스크를 이번 답장이 바꾸면 이번 변경까지 버린다

자동 반영을 가르는 곳

- AI 는 근거 상태를 보내고 BE 가 지금 값과 대조해 가른다: 회의 경로와 같고 판단 사이 PM 이 고친 값을 덮지 않는다 / 와이어에 기준 값을 실어야 한다
- AI 가 정해서 보낸다: BE 가 단순하다 / BE 가 지금 값 확인을 어차피 해야 해서 정책이 두 곳에 나뉜다

상태 근거 평가

- `judge/evidence.py` 에 답장용 질문을 더한다: Jev 질문이 한 곳에 모인다 / 재환 코드 파일을 고친다
- 새 파일에 둔다: 재환 코드를 안 건드린다 / `pipeline.py` 를 어차피 고치므로 나눠 얻는 것이 없다

이력 연결

- `task_history.reply_change_id` 를 더한다: 변경 하나에 이력이 둘이어도(막힘과 사유) 묶이고 타임라인 제외가 쿼리로 된다 / 기존 표에 칸이 는다
- `reply_change.history_id` 하나: 기존 표를 안 고친다 / 이력 하나만 담는다

## 결정

답장 한 통에 `reply_judgment` 행 하나, 필드 하나에 `reply_change` 줄 하나를 둔다. 저장과 같은 트랜잭션에서 행을 만들고 후보가 없으면 만들지 않는다. 후보는 마지막 리마인드 묶음의 태스크와 열린 시계의 태스크다. 시간 창을 두면 창 밖 답장을 PM 이 볼 길이 없다.

맡기기는 리스 3분과 attempt 로 다시 맡기고, 대화마다 가장 오래된 답장만 맡겨 이어 쓴 답장이 앞 반영값을 본다. 결과 접수는 반영, 승인 요청, 기록, 알림을 한 트랜잭션으로 묶는다.

판단 코드는 세 곳을 고친다. `pipeline.run` 의 `judge_seq`, 마감 지움 사유 상수 `DUE_CLEARED_REASON`, `evidence.py` 의 `verify_reply` 다. 회의 경로는 `judge_seq` 를 넘기지 않으므로 동작이 그대로다.

게이트는 BE 다. 상태 변경이고 근거가 certain 이며 판단 때 본 값이 지금 값과 같고 담당이 대화 주인일 때만 자동 반영한다. 그 밖은 태스크당 승인 요청 한 장이다. 후보에 안 맞는 말은 새 태스크를 만들지 않고 PM 이 고르게 한다.

시계는 `_settle` 만 쓴다. `replies.clock_effect` 가 판단 상태를 읽어 기다림, 멈춤, 응답, 막힘 유지를 정한다. 판단이 10분 안에 끝나지 않으면 PM 에게 한 번 알리고 답장을 응답으로 친다.

## 다시 볼 조건

- 측정에서 잘못된 certain 이 나오면 자동 반영 범위와 Jev 질문을 다시 본다
- 답장 사례에서 finding 이 이번 답장 줄로 잡히지 않아 변경을 놓치면 `judge_seq` 조건을 다시 본다
- 회의 판단에도 근거 상태가 필요해지면 `verify_reply` 를 합칠지 본다
- 답장 판단이 몰려 대화별 차례가 늦어지면 맡기는 단위를 다시 본다
