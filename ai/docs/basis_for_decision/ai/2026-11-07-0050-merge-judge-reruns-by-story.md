# 0050. 다시 돌린 판단 결과는 실행 하나를 고르지 않고 얘기 단위로 합친다

- 날짜: 2026-11-07
- 상태: 결정됨. [0016](../member/2026-09-30-0016-judge-path-flag-and-unjudged-findings.md) 의 "다시 돌린 결과는 항목이 더 많을 때만 바꿔 끼운다" 를 바꾼다(#217)

## 배경

판단하지 못한 finding 이 남으면 파이프라인을 다시 돌리고(0016), 결과가 여러 벌이 되면 항목 수가 많은 실행 하나를 통째로 남겼다. #128 멘토 리뷰가 이 규칙이 다시 돌려서 성공한 finding 을 버린다고 짚었다. 1회차가 A 얘기에서 항목 2개와 B 실패, 2회차가 A 는 바꿀 것 없음과 B 항목 1개면 1회차가 남아 B 는 끝까지 실패로 남는다. A 처럼 실행마다 판단이 엇갈린 얘기도 항목 수로 한쪽이 조용히 이긴다.

## 검토한 선택지

실행끼리 합치는 방법은 셋을 봤다.

- 실패가 적은 실행을 고르고 빈 결과만 따로 막기: 봇 코드만 바꾸면 되고 B 는 산다. 대신 A 의 엇갈린 판단은 이번엔 "바꿀 것 없음" 쪽이 이겨 A 카드가 사라진다. 멘토가 요구한 "충돌하면 검토 대상으로 보존" 을 맞추지 못한다
- 모든 실행의 항목을 다 보내기: 성공한 것은 사라지지 않지만 같은 얘기의 카드가 실행 수만큼 선다([0018](2026-10-02-0018-duplicate-new-items-after-first-deploy.md))
- 요약 문장으로 실행끼리 짝짓기: 1단계가 실행마다 문장을 다시 써서 같은 얘기도 글자가 다르다

파이프라인 결과를 어떻게 담을지는 둘을 봤다.

- finding 하나에 결과 하나, 항목은 위치 정수로 가리키기(처음 안): 회의 안 카드 합치기(#140)가 들어오면서 맞지 않게 됐다. finding 이 앞 카드에 합쳐지면 자기 카드가 없고, 되돌린 카드는 `items` 에서 빠져 뒤 카드의 위치가 밀린다
- 나간 카드와 실패마다 결과 하나, 그 객체를 직접 가리키기: 채택했다. 합쳐진 finding 의 번호는 카드의 결과에 더하고, 되돌린 카드의 결과는 건너뜀으로 바꾼다

엇갈린 얘기의 새 항목이 auto 게이트(#232)를 지나는 경계는 셋을 봤다.

| 안 | 사용자 | 데이터 | 계약 |
|---|---|---|---|
| 그대로 두고 게이트에 맡긴다(채택) | 틀린 Task 가 PM 검토 없이 설 수 있고, PM 이 되돌린다 | auto 되돌리기로 복구한다 | 변경 없음 |
| `task_status` 를 낮춰 review 로 보낸다 | PM 이 카드로 본다 | 근거가 명시됐다는 값의 뜻이 틀어진다 | 변경 없음 |
| BE 에 엇갈림 표시 필드를 더한다 | PM 이 이유까지 본다 | 정확하다 | 변경, BE 작업 필요 |

## 결정

- 실행마다 결과를 `transcripts/session_<회의ID>.judge_runs.json` 에 쌓는다. 근거 문장 번호는 같은 전사를 가리켜서 실행이 달라도 견줄 수 있다
- 번호가 하나라도 겹치는 결과는 실행이 달라도 같은 얘기로 묶는다. 1단계가 실행마다 얘기를 다르게 쪼개도(`[3, 4]` 와 `[5]`, `[3, 4, 5]`) 한 얘기가 된다
- 얘기마다 이렇게 정한다(`capture.judge_path.merge_runs`)
  - 한 번이라도 항목이 나왔으면 항목을 남긴다. 같은 카드가 두 장 서지 않게 실행 하나의 것만 쓴다. 실패 없이 끝난 실행, 항목이 많은 실행, 먼저 돈 실행 순으로 고른다
  - 어느 실행에서든 실패 없이 끝났으면 실패로 세지 않는다. 모든 실행이 실패한 얘기만 실패로 남긴다
- 엇갈린 얘기의 항목도 다른 항목과 똑같이 BE 게이트를 지난다. 새 항목은 조건을 모두 채우면 PM 검토 없이 Task 가 되고, 틀리면 PM 이 auto 되돌리기로 처리한다. 고른 실행 하나를 남기던 옛 규칙에서도 같은 게이트를 지났다. BE 에 따로 표시를 보내지 않는다
- finding 이 하나도 없는 실행은 아무것도 바꾸지 않는다. 항목 수를 먼저 보던 이유(빈 결과가 가진 결과를 밀어냄)가 따로 규칙 없이 막힌다
- 1단계 탈락 기록 `extract_dropped`(#186)는 실행마다 하나씩 리스트로 남긴다. 항목이 여러 실행에서 오므로 한 실행 것만 남기면 다른 실행에서 버려진 것을 찾지 못한다
- `PipelineResult.outcomes` 는 이 변경과 같은 PR 에서 넣는다. 합치는 쪽만 먼저 들어가면 판단 경로 회의가 추출에서 실패해서 머지 순서가 묶인다. 한 PR 에 두면 그 의존이 없어지고, 카드 합치기까지 포함한 불변식을 `test_pipeline.py` 전체에서 함께 검사할 수 있다. 답장 경로는 `items`, `failures` 만 읽어 영향이 없다

## 다시 볼 조건

- 실행끼리 근거 문장이 겹치지 않으면 같은 일의 새 카드가 두 장 설 수 있다. 1회차가 3번 문장 카드와 9번 실패, 2회차가 3번을 놓치고 9번 카드를 낸 경우다. 한 추출 요청에서 앞 항목이 auto 로 Task 를 만들면 뒤 새 항목은 auto 가 되지 않아(`test_second_auto_candidate_in_same_meeting_goes_to_review`) 둘 다 자동으로 서지는 않는다. 이런 카드가 실제로 보이면 묶는 기준을 넓힌다
- 엇갈린 얘기의 항목이 auto 로 만들어진 뒤 PM 이 되돌리는 일이 보이면 BE 와 표시 필드를 정한다. 엇갈린 빈도는 아직 재지 않았다
- 다시 돌린 실행에서 얘기가 아예 안 나오면(1단계가 놓침) 그 얘기의 앞선 실패가 남는다. 이 때문에 "일부 실패" 로 닫히는 회의가 잦으면, 놓친 것과 판단하지 못한 것을 나눠 센다
- 항목 없이 실패만 남은 실행(`JudgeAllFailed`)은 기록되지 않아, 그 실행의 건너뜀도 합치는 데 쓰이지 않는다. 이 때문에 닫히지 않는 회의가 보이면 실패 실행도 쌓는다
- 같은 문장에 서로 다른 결정이 둘 있는데 실행마다 다르게 묶여 한 얘기로 합쳐지는 일이 보이면, 묶는 기준을 번호 겹침보다 좁힌다
