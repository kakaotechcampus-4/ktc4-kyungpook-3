# GPU 전사 자동 전환

- 날짜: 2026-11-08
- 이슈: #530
- PR:
- 브랜치: `feature/530-gpu-stt-autostart`

## 한 일

Elice 전사가 계속 실패하면 운영 워커가 개인 AWS 의 GPU 대기 서버를 켜서 전사를 넘기고, Elice 가 돌아오면 되돌리고 끄게 했다. 서버는 개인 AWS 의 Lambda 스위치로 켜고 끈다. 팀원은 비공개 운영 채널의 `/gpu on|off|status` 로 직접 조작한다. GPU 로 가는 호출에는 이름과 문맥 프롬프트를 싣지 않는다. 운영 절차는 `deploy/gpu-stt/README.md` 를 고쳤다.

## 왜

담당자 한 명만 서버를 켤 수 있어 담당자가 없으면 장애 대응이 시작되지 않았다. 설계와 값의 근거는 [0056](2026-11-08-0056-gpu-stt-auto-failover.md) 에 있다.

## 결과

| 항목 | 값 |
|---|---|
| 전체 pytest | 2241 passed |
| 실제 워커 프로세스, 가짜 HTTPS 서버 | `manual` 로 띄워 `--gpu on` 에서 normal → starting → on_gpu, `--gpu off` 에서 stopping → normal. 운영 채널 알림 4건, 켜기 알림에만 `@everyone` |
| 실제 Lambda, 운영 서버, GPU 서버 | 아직 안 했다 |
| 비용 | 0원. 실제 Elice, AWS 를 부르지 않았다 |

가짜 서버 실행은 `.env` 가 없는 코드 사본에서 했다. 사본에 `.env` 가 없으니 워커가 실제 BE 주소를 읽지 않는다.

리뷰에서 비용과 알림을 틀리게 하는 결함 14건을 재현해 고쳤다. 대표 장면의 전후는 아래와 같다(가짜 시계와 가짜 서버로 돌린 값).

| 장면 | 고치기 전 | 고친 뒤 |
|---|---|---|
| GPU 실제 호출 3번 실패 뒤 일이 없음 | 175분 켜짐, 알림 1,036건 | 16분, 알림 6건 |
| 부팅 뒤 8분만 응답하는 서버 | 하루 23번 켬 | 2번 켜고 멈춤 |
| 확인은 통과하고 실제 호출은 모두 503 | 시간당 알림 360건 | 2번 켜고 멈춤, 알림 4건 |
| GPU 확인이 한 번씩 실패하는 멀쩡한 서버 | 두 번째에 멈춤 | 같은 서버로 알림 없이 돌아옴 |

## 다음

- 관리자 자격 증명으로 `deploy/gpu-stt/switch.sh setup` 을 돌리고 운영 서버에 env 파일과 drop-in 을 둔다(담당자 확인)
- 비공개 운영 채널을 만들고 채널 ID 를 운영 `.env` 에 넣는다
- `manual` 로 배포해 저장 회의로 리허설하고, 포기 회의 재처리를 한 번 실제로 돌린 뒤 `auto` 로 올린다
