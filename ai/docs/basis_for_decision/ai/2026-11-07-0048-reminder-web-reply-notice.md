# 0048. 리마인드 DM 은 안내만 보내고 답장은 웹에서만 받는다

- 날짜: 2026-11-07
- 상태: 검토중

## 배경

DM 에는 디스코드 서버 정보가 없다. 같은 계정이 여러 워크스페이스의 팀원이면 BE 는 디스코드 답장 대상과 DM 순서로 답장이 어느 대화의 것인지 추측한다([backend-ai 계약](../../../../backend/docs/contracts/backend-ai-contract.md)의 `POST /bot/replies`). [결정 0035](2026-11-04-0035-bot-dm-local-journal-and-backfill.md)의 답장 큐와 DM 기록 메우기는 이 경로를 지키려고 있다.

웹 대화는 대화가 정해져 있어 추측이 필요 없고, 웹 답장은 이미 답장 판단으로 이어진다(`add_web_reply` 에서 `open_judgment`). 답장 받는 곳을 웹 하나로 모으면 DM 은 알림 역할만 남는다.

## 검토한 선택지

DM 에 싣는 것

- 승인 문구를 그대로 보내고 DM 답장도 받는다: 바꿀 코드가 없다 / 추측이 남고 여러 워크스페이스 팀원의 답장이 다른 대화에 들어갈 수 있다
- 승인 문구 뒤에 대화 링크를 붙인다: DM 에서 내용을 바로 읽는다 / 본문이 있으면 팀원은 그 자리에서 답한다
- 워크스페이스 이름, 답장을 기다리는 리마인드 수, 대화 링크만 보낸다: 답장 받는 곳이 하나가 된다 / 내용을 보려면 웹을 열어야 한다

봇 DM 창에 온 글

- 지금처럼 저장해 PM 에게 보인다: 글을 잃지 않는다 / 어느 대화인지 다시 추측해야 한다
- 저장하지 않고 웹 안내를 돌려준다: 추측이 없다 / 안내를 놓치면 글이 PM 에게 닿지 않는다

웹 계정이 없는 팀원

- 대화 링크를 그대로 준다: 문구가 한 가지다 / 초대를 수락하기 전까지 403 이다
- 가입 링크만 준다: 안내가 짧다 / 가입만으로는 `Member.user_id` 가 이어지지 않아 가입한 뒤에도 403 이다
- PM 에게 초대를 요청하라는 문구와 가입 링크를 준다: 실제로 답장에 닿는 길이다 / 문구가 길고 PM 의 조치가 필요하다

## 결정

DM 은 안내만 보낸다. 봇 계약은 그대로이고 BE 가 claim 때 `body` 를 안내로 만들며 저장하지 않는다. 저장된 메시지 본문은 PM 이 승인한 문구 그대로이고 웹 푸시 미리보기도 그 문구를 쓴다. 워크스페이스마다 안내 한 통이 나가므로 여러 워크스페이스 팀원은 공간마다 맞는 이름, 수, 링크를 받는다.

리마인드 수는 그 대화의 열린 시계와 이번 묶음의 리마인드를 합쳐 태스크로 중복을 뺀 값이다. 시계는 claim 뒤에 열릴 수 있어 이번 묶음을 직접 합친다. 막힌 시계는 태스크가 끝나거나 풀리거나 담당이 바뀌어도 열려 있으므로, 시계 쪽에서 지운 태스크, 끝난 태스크, 담당이 대화 주인이 아닌 태스크, 사람이 막힘을 푼 태스크를 뺀다. 이번 묶음은 방금 나가는 글이라 그대로 세어 수가 0 이 되지 않는다. 태스크 없는 리마인드는 하나씩 센다.

봇 DM 창에 온 글은 저장하지 않고 웹 안내를 돌려준다. 같은 사람에게 1시간에 한 번이고 횟수는 봇 로컬 파일 하나로 센다. 웹 주소는 claim 응답의 `web_url` 로 받아 봇 환경 변수가 늘지 않는다.

웹 계정이 없는 팀원에게는 대화 링크 대신 초대 요청 문구와 가입 링크를 준다. 연결을 끊은 팀원도 `user_id` 가 비므로 같다. PM 화면에 표시할 수 있게 대화 응답에 `web_reply_available` 을 더한다. 읽는 시점에 판정해 마이그레이션이 없다.

#470 의 PM 글도 DM 에는 안내만 보낸다. 첫 줄은 공간 이름과 PM 이름이고 그다음이 대화 링크다. 이 작업은 메시지 종류를 나누지 않고, #470 이 자기 첫 줄을 더한다. 첫 줄 아래 문구는 `_reply_guide` 하나를 같이 쓴다.

결정 0035 는 일부를 대체한다. 답장 큐(`replies/`), DM 기록 메우기, 메우기 대상(`recipients.json`)을 봇에서 지운다. 발송 기록(`sent/`)과 결과 보고는 그대로다. 이 기록이 결정됨이 되면 0035 의 상태를 고친다.

BE 쪽 경로는 남긴다. `/bot/replies`, `BotDmPart`, 워크스페이스 추측 코드를 지우면 갱신 전 봇이 없는 경로를 부른다. 그 404 는 `INVALID_REQUEST` 인데 봇의 `_is_final` 은 이 코드를 400 일 때만 영구 거절로 읽어, 재시도하며 파일이 쌓인다. 경로를 남겨 배포 순서를 타지 않게 하고 삭제는 후속으로 미룬다.

감수하는 손실이 둘 있다. 배포 전 봇이 꺼진 동안 쓴 DM 은 메우기가 없어져 더 읽지 않는다. 남은 `replies/` 큐도 옮기지 않는다. 그 글들은 PM 에게 닿지 않고, 파일은 디스크에 그대로 둔다. 되돌릴 때는 봇과 BE 를 함께 되돌린다. 새 봇과 옛 BE 가 붙으면 DM 은 옛 문구("여기로 답장하시면")로 나가는데 봇은 답장을 넘기지 않는다.

바뀌지 않은 것도 있다. 첫 메시지 틀 문구(`framed_body`)의 "이 봇으로" 는 이제 웹에만 보이고 이 문구는 후속으로 고친다. 화면의 답장 칸 안내와 웹 답장 불가 표시는 FE 요청으로 따로 고치므로, 그 전까지 틀린 문구가 화면에 남는다.

## 다시 볼 조건

- 갱신 전 봇이 모두 내려가면 `/bot/replies`, `BotDmPart`, 워크스페이스 추측 코드를 지운다
- 안내를 받은 팀원의 답장이 DM 시절보다 줄면 DM 에 내용을 다시 싣는 쪽을 본다. 아직 재지 않았다
- 팀원이 DM 창에 글을 계속 쓰면 안내 간격과 문구를 다시 본다
