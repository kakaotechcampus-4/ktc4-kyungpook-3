## 한 일

- `recorder.Claims`: 복구가 잡은 회의를 매니페스트 `claimed_by`·`claimed_at` 에 적는다. 만료(`MM_RECOVERY_CLAIM_TTL_S`, 기본 2시간)가 지나면 누구든 다시 잡는다. 같은 프로세스 안에서는 잠금과 보유 목록으로 두 번 잡지 못한다 (b2e5e6e)
- `recorder.process_session`: 복구가 잡은 회의면 단계를 저장할 때마다 `claimed_at` 을 새로 적는다 (1e91cba)
- 같은 함수: 단계를 닫지 못한 실행(failed, partial)을 `recovery.attempts` 로 센다. 다음 시도는 60초에서 두 배씩 미루고 한 시간에서 멈춘다. 단계가 닫히면 0 으로 돌아간다. 상한(`MM_RECOVERY_MAX_ATTEMPTS`, 기본 5)에 닿으면 포기하고 그때 처음 BE 에 fail 을 보낸다. 전에는 첫 실패에서 바로 보냈다 (2ccad69)
- `recorder.recovery_targets`, `recover_one`: 한 바퀴의 대상 고르기와 회의 하나 돌리기. 선점을 먼저 잡고 매니페스트를 다시 읽어 아직 할 일인지 본다. `recover()` 는 이 둘을 잇는다 (edae588)
- 포기할 때 BE 가 꺼져 있어 fail 이 안 닿았으면 루프가 fail 만 다시 보낸다 (c4c6ed8)
- `discord_adapter._recover_pass`: 루프와 `/recover` 가 같이 쓰는 한 바퀴. 대상을 바퀴 시작에 정하고 후처리 세마포어를 회의마다 잡는다. `/recover` 는 남이 잡은 회의를 건너뛰고 누가 언제까지 잡았는지 알린다 (b8964ca)
- 루프는 `on_ready` 에서 뜨고 첫 바퀴를 바로 돈다. 주기는 `MM_RECOVERY_INTERVAL_S`(기본 60초, 0 이면 끔). `cog_unload` 가 취소한다 (589b9e4)
- 봇이 뜨기 전에 시작돼 recording 으로 남은 회의는 처리 전에 그 회의 채널에 재시작 안내를 한 번 올린다 (2a0fa30)
- 실패와 partial 알림이 "N분 뒤 자동으로 다시" 또는 포기를 알린다. 루프가 떠 있지 않으면 전처럼 `/recover` 를 안내한다 (012c6ef, 11bee79)
- 첫 바퀴가 옛 회의를 쓸어 가지 않게 했다. 서버가 적히지 않은 옛 매니페스트는 건너뛰고(f9128aa), 자동 복구 전에 failed 로 끝난 회의는 포기한 회의처럼 사람의 `/recover` 에 둔다(e6c42e4)
- 재시작 안내는 트랙을 마지막으로 쓴 지 한 시간 안일 때만 올린다 (ebfc02c). 봇이 준비된 뒤에 붙은 Cog 도 루프를 띄운다 (051f48b)
- 모듈 설명과 `decision_log/0013` (37c3e2b, deee0bf, dd16320)

## 왜

- 결정과 기본값의 근거는 `decision_log/0013` 에 있다
- 코드를 읽다 #83 의 `/recover` 에서 경쟁을 찾았다. 보유 회의 집합은 세마포어를 기다리기 전에 만들고 목록은 기다린 뒤 스레드에서 만들어서, 기다리는 사이 시작된 녹음의 wav 를 집었다. 테스트로 재현하니 새 녹음이 `recording` 에서 `transcribed` 로 바뀌었다. 루프가 60초마다 돌면 이 창이 늘 열려 있게 된다. 대상을 바퀴 시작에 정해 막았다
- 세마포어를 바퀴 전체에 거는 것과 회의마다 거는 것을 비교했다. 바퀴 전체면 밀린 회의가 여럿일 때 새 `/stop` 이 그 전부를 기다린다. 회의마다를 골랐다
- 루프가 예약된 재시도의 실패까지 채널에 올리면 한 회의에 경고가 다섯 번 쌓인다. 루프는 단계가 움직였거나 포기했을 때만 올리고, 첫 실패는 `/stop` 뒤 보고가 "N분 뒤 자동으로 다시 시도" 라고 알린다
- 내 개발 기기의 `recordings/` 를 읽어 보니 끝나지 않은 매니페스트가 8개였고 모두 서버가 적히지 않은 9/12 녹음이었다. 서버별 `/recover` 는 이것들을 못 집는데 모든 서버를 보는 루프는 첫 바퀴에 전부 전사하고 인계하려 했다. 서버가 적힌 회의만 집게 해 0개가 됐다

## 남은 것

- 워커를 별도 프로세스로 떼기와 프로세스 사이 원자적 선점
- 끊긴 회의 뒤 새 녹음을 같은 회의로 묶기
- 죽은 선점을 만료 전에 푸는 방법(같은 호스트 pid 확인, 강제 해제). 지금은 복구 바퀴 도중 봇이 죽으면 그 회의가 최대 2시간 기다린다
- t3.medium 전사 시간으로 선점 만료 다시 정하기 (#40)
- `discord_adapter.py` 의 기존 import 줄에 이제 안 쓰는 `recover` 가 남아 있다. 수신 공용 계층 작업이 같은 import 줄을 바꾸는 중이라 그 머지 뒤 지운다
- `ai/README.md` 의 `/recover` 설명. README 를 고치는 다른 작업과 겹쳐 이 PR 에서 뺐다
- 루프와 `/recover` 가 되살린 회의에는 `on_session_saved` 훅이 불리지 않는다. 전부터 `/recover` 가 그랬고, 이제 복구가 자주 도니 훅을 BE 연결 지점으로 쓰려면 같이 불러야 한다

## 생각해볼 점

- 봇이 영영 안 뜨면 BE 회의는 processing 에 남는다. 언제부터 그랬는지 보이려면 BE Meeting 에 갱신 시각이 필요하다(회의 안건)
- 포기한 회의의 수동 재시도는 한 번이다. 또 실패하면 곧바로 다시 포기한다. 상한을 새로 줄지는 운영해 보고 정한다
- 설정이 없어 멈춘 회의도 루프가 매 바퀴 잡았다 놓는다(매니페스트 쓰기 세 번). 설정이 생길 때까지 건너뛸지
- 루프가 채널에 올리는 조건(단계가 움직였거나 포기)이 사용자에게 충분한지는 실서버 녹음 검증에서 본다
- 배포 전에 첫 바퀴가 집을 회의 수를 `recorder.pending_sessions` 로 먼저 본다(0013 "배포 전에")
- 재시작 안내의 한 시간 기준은 잠정값이다
