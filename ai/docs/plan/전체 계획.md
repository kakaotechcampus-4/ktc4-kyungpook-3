# AI 파트 전체 계획

기준일: **2026-10-02**

## 1. 목표와 범위

회의 음성에서 할일과 변경 사항을 찾아, 원문·화자·시각 근거가 포함된 승인용 초안을 BE에 전달하는 AI 파이프라인을 완성한다. 신규 할일뿐 아니라 기존 task의 일정·담당자·상태·범위 변경을 다루고, 변경이 없는 발화는 승인 후보에서 제외한다.

이 문서의 근거는 `ai/` 내부 코드, 테스트, 작업 기록, 결정 기록이다. 현재 상태는 코드를 우선하며, 과거 평가 결과는 당시 조건의 결과로만 사용한다. **구현됨은 운영 검증 완료를 뜻하지 않는다.** BE의 실제 구현·배포 상태는 이 문서에서 판단하지 않는다. PM 승인과 Notion 반영은 AI가 전달한 결과를 사용하는 외부 연계 범위다.

일정과 담당자는 별도 합의 대상으로 두고 단계 순서와 완료 조건을 정의한다. 이번 산출물은 이 문서 하나이며 코드·API·타입 변경은 포함하지 않는다.

## 2. 현재 구조와 책임 경계

목표 흐름이자 선택 가능한 `judge` 경로는 다음과 같다.

```text
음성 캡처 → 화자별 전사 → Luna 후보 발화 추출 → 기존 task 유사 검색(BE)
          → Terra 변경 판단 → Luna 초안 생성 → BE 인계
          → [외부 연계: PM 승인 → Notion 반영]
```

현재 기본값은 `MM_EXTRACT_PATH=legacy`다. `MM_PIPELINE_MODE=bot|worker`는 후처리를 실행하는 위치이고, 추출 경로와는 독립적인 설정이다. 두 모드는 같은 `process_session`을 사용한다. [추출 경로 선택](../../capture/judge_path.py), [후처리](../../capture/recorder.py), [결정 기록 0016](../basis_for_decision/member/2026-09-30-0016-judge-path-flag-and-unjudged-findings.md)

| 구분 | 현재 동작 | 경계와 주의점 |
|---|---|---|
| 음성 수집·전사 | 화자별 트랙·매니페스트 저장 후 chunk 배치 전사. 회의 기준 시각과 발화 순번을 보존 | 화자별 수신 트랙을 사용한다. 실제 크로스토크·유실 품질은 별도 측정 필요 |
| `legacy` 기본 경로 | `extract_tasks`가 `ExtractedTask`를 만들고 인계기가 BE 항목으로 변환 | 기존 task 유사 검색·Terra 비교·Luna 변경 초안의 전체 흐름을 실행하지 않음 |
| `judge` 선택 경로 | Luna가 finding을 고르고, finding마다 유사 검색 → Terra → 의미 있는 결과에 Luna 초안 실행 | 설정 누락 시 옛 경로로 자동 전환하지 않음. 잘못된 경로 값은 시작 시 오류 |
| BE 인계 | 회의 생성·종료·실패 및 `/extractions` 등록용 클라이언트 구현. 유사 검색은 서비스 토큰 사용 | 실제 BE와의 계약·등록 결과는 M3에서 확인 |
| 실행 모드 | `bot`은 봇 안에서 후처리·채널 알림, `worker`는 저장된 회의를 별도 프로세스에서 처리 | 워커의 미판단 finding은 현재 매니페스트·로그에 남음 |

근거: [화자 트랙 저장](../../capture/track_writer.py), [배치 전사](../../stt/batch.py), [기존 추출기](../../extract/llm.py), [인계기](../../capture/handoff.py), [워커](../../capture/worker.py).

### 단계별 입출력

| 단계 | 주요 입력 → 출력 | 책임 |
|---|---|---|
| 전사 | 화자별 음성·매니페스트 → `Transcript` / `TranscriptSegment` | `speaker`, 회의 시작 기준 `start/end`, 근거 식별자 `seq` 보존 |
| 후보 추출 | `Transcript` → `JudgeFinding` | 후보 요약, 여러 줄의 근거·인덱스, 담당자 표현과 해소된 이름 추출 |
| 유사 검색 | 워크스페이스·finding 요약 → `NotionCandidate[]` | 외부 검색 결과 수신. 검색 오류를 후보 없음으로 바꾸지 않음 |
| 변경 판단 | `JudgeInput` → `JudgeResult` | 신규/수정/무변경, 수정 대상, 분류, 상태 결정 |
| 초안 생성 | finding·판단·현재 후보·회의 날짜 → `DraftResult` | 새 제목·마감일과 승인 화면용 설명 생성. update에서 제목을 새로 덮어쓰지 않음 |
| 인계 조립 | 위 결과 → `PipelineResult(items, failures)` → BE 요청 | 각 단계 값을 합침. 동일 마감·상태 제거, 변경 없는 update 제외. 범위 변경은 설명만 있어도 유지 |

[공통 스키마](../../shared/schemas.py)는 단계 간 순수 dataclass 계약이며 DB 테이블 정의가 아니다. `to_dict/from_dict`와 [스키마 테스트](../../tests/shared/test_schemas.py)가 있다. 플랫폼 객체는 capture 경계에서 처리하고 판단·초안에는 데이터만 전달한다. `judge` 인계 어댑터는 LLM에 화자 이름을 보여 준 뒤 결과의 화자를 uid로 복원한다. [파이프라인](../../judge/pipeline.py), [화자 변환](../../capture/judge_path.py)

현재 `JudgeFinding.signal`은 제거돼 있다. 진척 보고는 프롬프트에서 후보로 포함하고 `JudgeResult.status`로 변경을 판단한다. `judge`의 세 LLM 단계는 키·응답 실패 시 오류를 내며 규칙 기반으로 대체하지 않는다. 오래된 주석이나 README의 폴백 설명을 현재 동작으로 해석하지 않는다. [signal 제거 기록](../basis_for_decision/ai/2026-09-30-remove-finding-signal.md), [후보 추출](../../judge/semantic_judge.py), [최종 판단](../../judge/final_judge.py), [초안](../../draft/doc_draft.py)

## 3. 전체 마일스톤

M0~M2의 기존 구현을 출발점으로 M3~M5를 진행한다. M4의 재현 가능한 결함 점검은 M3와 병행한다. M6는 MVP 완료의 필수 조건에서 제외한다.

### M0. 공통 계약과 구조

- **목표:** 단계별 데이터와 플랫폼·AI·BE의 책임 경계를 일치시킨다.
- **현재 상태:** 단계별 dataclass, 중첩 타입의 직렬화, 플랫폼 인계 어댑터 구현. 스키마 왕복 테스트 존재. 이번 문서 작업에서 테스트를 다시 실행한 것은 아니다.
- **남은 작업:** 실제 요청·응답 예시로 필수/선택 필드, `None` 의미, uid·이름 변환, 오류와 빈 결과의 차이를 점검한다. 계약 변경이 필요하면 BE와 합의한다.
- **산출물:** 단계별 계약표, JSON 예시, 호환성·왕복 검증 기록.
- **완료 기준:** 사용하는 계약의 JSON 왕복과 중첩 객체 복원이 확인되고, 실제 인계 필드의 출처·책임이 문서와 일치한다.
- **선행 조건:** 현재 스키마와 양쪽 연계 요구사항 확인.

근거: [스키마](../../shared/schemas.py), [왕복 테스트](../../tests/shared/test_schemas.py), [인계 변환](../../capture/handoff.py).

### M1. 음성 수집·전사

- **목표:** 화자와 시각 근거를 보존한 회의 전사록을 만든다.
- **현재 상태:** 화자별 녹음, chunk 배치 STT, 실패 구간 재전사, CER·처리 시간·메모리 평가 도구 구현. 과거 정렬 회의 데이터의 측정 결과 존재.
- **남은 작업:** 정독·자연 대화 시나리오를 실제 사용할 환경에서 확보하고, 전사 정확도·크로스토크·동시 발화·시작/종료 유실·처리 시간을 확인한다.
- **산출물:** 화자별 음성·매니페스트, 정답 전사, 전사 JSON/회의록, 설정별 평가표와 정성 체크리스트.
- **완료 기준:** 두 시나리오의 정확도·화자 분리·처리 시간 결과를 확보하고 기존 STT 1차 목표 대비 충족 여부를 명시한다. 미달은 원인과 조치 후 재검증한다.
- **선행 조건:** 녹음 가능한 환경, 2명 이상 화자, 사람이 검수한 정답과 측정 설정.

근거: [STT 검증 계획](../../stt_diarization_validation_plan.md), [전사 실행](../../stt/transcribe.py), [전사 방식 결정](../basis_for_decision/member/2026-09-16-0008-batch-transcription-by-speaker-chunks.md).

### M2. 추출·판단·초안

- **목표:** 신규 할일과 기존 task 변경을 근거 있는 승인 초안으로 변환한다.
- **현재 상태:** 후보 추출·검색 인터페이스·Terra 판단·Luna 초안·item 조립 구현. 무변경 update 제거와 범위 변경 보존 구현. 실제 LLM 평가 기록은 있으나 최신 signal 제거 후 재평가는 남아 있다.
- **남은 작업:** 신규·일정·담당자·상태·범위 변경과 무변경 제외를 최신 코드로 평가하고, STT 오류·짧은 응답·여러 줄 합의·애매한 담당자 사례를 확대한다.
- **산출물:** 라벨 기준, 골든셋별 평가 결과, 실패 사례와 프롬프트·계약 수정 근거.
- **완료 기준:** 핵심 시나리오의 기대 item과 근거가 일치하고, 무변경·언급 없는 task의 오수정이 제외된다. 관찰 전용·라벨 미합의 사례는 채점 대상과 분리한다.
- **선행 조건:** M0 계약, 검수된 전사·후보 task 데이터, 평가 시 사용할 LLM·임베딩 설정.

근거: [파이프라인](../../judge/pipeline.py), [초안](../../draft/doc_draft.py), [파이프라인 테스트](../../tests/test_pipeline.py), [통합 골든셋](../../judge/golden_set_pipeline/meeting_01.json).

### M3. BE 통합 검증

- **목표:** 실제 회의 결과가 BE에 등록되고 승인에 필요한 데이터로 전달되는지 확인한다.
- **현재 상태:** 봇·워커 배선과 로컬 HTTP/가짜 BE 테스트 구현. 2026-09-30 작업 기록상 실제 BE와 실제 LLM을 함께 사용한 실행은 미검증이다.
- **남은 작업:** `judge`를 `bot`·`worker` 두 실행 모드에서 실제 회의로 검증하고, 기본 `legacy` 인계도 회귀 확인한다. 등록 응답, 설명·담당자·날짜·근거, 누락/미수신 항목을 대조한다.
- **산출물:** 실행 설정과 회의 식별자, 송수신 payload, 등록·승인용 데이터 확인 기록, 실패 시나리오 결과.
- **완료 기준:** 두 실행 모드에서 결과와 승인용 데이터가 일치한다. 인증·검색·LLM 실패가 정상 후보 0건으로 오등록되지 않으며, 재시도·재시작에도 중복 인계를 방지한다. 정상적인 무변경 0건과 실패 0건을 구별한다.
- **선행 조건:** 실제 BE 주소·워크스페이스·서비스 토큰, 양쪽 임베딩/LLM 설정, 기존 task·참여자 데이터, M0~M2의 검증 가능한 입력.

근거: [연결 작업 기록](../basis_for_decision/member/2026-09-30-judge-handoff.md), [배선 테스트](../../tests/capture/test_judge_wiring.py), [가짜 BE](../../tests/capture/fake_be.py), [환경 예시](../../.env.example).

### M4. 정확성·복구 안정화

- **목표:** 불완전한 입력과 외부 실패에도 잘못된 승인 데이터나 무한 재시도를 만들지 않는다.
- **현재 상태:** 회의별 OS 파일 잠금, 단계별 복구·백오프·포기 처리, 부분 전사 및 미판단 finding 재시도 구현. 재시도 상한과 담당자 근거 등에 알려진 보완점이 있다.
- **남은 작업:** 4절의 우선 과제를 재현하고 수정한다. 특히 부분 전사 후 후속 단계 실패의 횟수 초기화, 장기 LLM 대기, 1인칭 담당자 불일치, 동일 회의 중복 항목을 회귀 사례로 고정한다.
- **산출물:** 결함별 재현·수정·회귀 결과, 실패/부분 성공 처리 규칙, 실패 finding 재처리 설계.
- **완료 기준:** 부분 전사 뒤에도 실패 상한이 지켜지고, 호출 시간 제한 후 복구가 가능하다. 담당자 근거·중복 후보·상대 날짜 회귀를 통과하며, 누락은 숨기지 않고 추적된다.
- **선행 조건:** 저장된 매니페스트·테스트 fixture와 실패 주입 환경. 외부 필드·표시 변경은 BE와 합의. 코드 결함 점검은 M3 완료 전에도 진행한다.

근거: [복구 결정](../basis_for_decision/member/2026-09-26-0013-recovery-worker-and-meeting-lock.md), [후처리 코드](../../capture/recorder.py), [복구 테스트](../../tests/capture/test_recovery_loop.py), [판단 단계 테스트](../../tests/capture/test_judge_stage.py).

### M5. 운영 준비·전환

- **목표:** 측정 결과로 운영 설정과 `judge` 기본 전환 여부를 결정한다.
- **현재 상태:** 독립 워커와 systemd 예시 존재. 예시의 메모리·종료 대기 값은 운영 확정값이 아니다. 서버에서 전체 파이프라인 지연·비용·메모리 측정이 필요하다.
- **남은 작업:** 단계별 지연과 전체 완료 시간, 실제 API 요청 수·비용, 최대 메모리, 적체·재시작·강제 종료 복구를 측정한다. STT 백엔드와 실행 모드·재시도 상한을 결정한다.
- **산출물:** 운영 측정표, 설정·배포·장애 대응 절차, 전환 및 복귀 체크리스트.
- **완료 기준:** M3·M4 결과와 운영 측정치를 검토해 허용 기준을 합의하고, `judge` 전환 또는 `legacy` 유지 이유를 기록한다. 설정 복귀와 미처리 회의 재개 절차를 검증한다.
- **선행 조건:** M3 실제 연계, M4 핵심 결함 해소, 실제 운영 환경과 측정 가능한 비용 자료.

전환은 `MM_EXTRACT_PATH=judge`의 명시 설정으로 검증한 뒤 기본값 변경을 별도로 결정한다. 복귀 절차에는 `legacy` 설정 복원·프로세스 재시작뿐 아니라 진행 중/등록 완료 회의의 매니페스트·결과 보존과 재처리 대상 확인을 포함한다. 경로 변경만으로 이미 등록한 추출이 교체된다고 가정하지 않는다. ### M6. 후속 확장

- **목표:** MVP 결과와 실제 요구사항에 근거해 실시간 처리·reminder·confidence 확장을 결정한다.
- **현재 상태:** 실시간 수신·전사·지연 측정 경로는 실험용으로 존재한다. reminder와 독립 confidence 영역은 후속 범위이며 운영 완료로 보지 않는다.
- **남은 작업:** 실시간 사용 목적·비용·지연 요구와 알림·확신도 표현 요구를 정리하고, 기존 필드별 근거 상태 및 BE 승인 정책과의 관계를 정한다.
- **산출물:** 확장별 범위, 별도 착수 조건, 검증 계획과 계약 변경안.
- **완료 기준:** MVP 측정 결과와 사용자 요구를 바탕으로 각 확장의 착수/보류 조건이 정의된다. 구현 완료는 별도 계획에서 관리한다.
- **선행 조건:** MVP 결과와 확장 요구 합의. M6 완료를 MVP 출시 조건으로 두지 않는다.

## 4. 우선 과제와 증거 구분

아래의 **코드 확인**은 읽어서 확인한 동작이며 이번 작업에서 새로 재현한 테스트 결과가 아니다. **기록상 문제**는 당시 기록의 관찰이다. **외부 협의**는 AI 코드만으로 확정할 수 없는 계약·정책이다.

### 골든셋 평가

- [후보 추출 평가](../../judge/eval_golden_set.py): signal 제거 후 신규·변경·진척 후보의 누락/오탐, 담당자 분류, 근거 묶음을 재평가한다. [골든셋 설명](../../judge/golden_set/README.md)의 라벨·관찰 조건을 함께 기록한다.
- [Terra 평가](../../judge/eval_final_judge.py): 신규/수정 대상, 상태 변경, 무변경 제외를 [단계2 케이스](../../judge/golden_set_stage2/cases.json)로 확인한다.
- [통합 평가](../../judge/eval_pipeline.py): 최종 item 기준으로 확인한다. 이 도구는 **BE만 가짜이며 LLM·임베딩은 실제 호출**하므로 실제 BE 통합 검증을 대체하지 않는다.
- [legacy 평가](../../extract/eval_golden_set.py): 담당자·마감일·필드별 상태와 상대 날짜를 확인하고 judge 결과와 비교한다.

평가 기록에는 실행 날짜·코드 버전·모델/프롬프트·fixture·기준일·반복 횟수·실패·관찰 전용 사례를 남긴다. 합의되지 않은 전체 품질 목표 수치는 새로 확정하지 않는다.

### 실제 회의 통합 검증

동일한 기대 결과를 정의한 회의 데이터로 `bot`과 `worker`를 확인하되, 비교 실행은 등록 충돌이 없도록 별도 테스트 회의로 구분한다. 신규 생성, 기존 항목 변경, 무변경 제외, 인증 실패, 일부 STT/LLM 실패, 처리 중 재시작, 동일 회의 재처리를 포함한다. 최종 item뿐 아니라 근거 원문·uid·시각, 수정 대상, BE 수신/누락 수, 승인용 설명을 대조한다. 실제 승인·Notion 반영 확인이 필요하면 외부 연계 담당과 검증 범위를 합의한다.

STT 목표는 [기존 검증 계획](../../stt_diarization_validation_plan.md)의 **1차 목표**를 인용한다. 공백 제거 CER 기준 정독 5% 이하, 대화 10% 이하, 화자 분리 체크리스트 충족, 오프라인 1분 오디오당 전사 30초 이내다. 이는 최종 제품 품질 합의나 현재 달성 선언이 아니다. 실시간 지연 목표는 M6 검토 대상으로 분리한다. 전체 AI 처리 지연·비용·운영 메모리는 측정 후 합의한다.

## 7. MVP 완료 판단

M0~M2의 계약·핵심 시나리오 검증 결과를 최신 상태로 확보하고, M3 실제 연계와 M4 정확성·복구 기준을 충족한 뒤 M5 운영 측정으로 설정을 결정한다. 정상적인 변경 없음, 부분 성공, 전체 실패를 구분하고 누락을 추적할 수 있어야 한다. 미해결 외부 계약은 영향과 합의 여부를 기록하며, AI 코드만으로 PM 승인·Notion 반영의 구현 완료를 선언하지 않는다.
