# 서버 처리 용량 측정 (2026-10-06)

#154 의 결과다. 팀 서버 한 대에서 회의 전사가 얼마나 걸리고 자원을 얼마나 쓰는지 쟀다. 전사 차이가 판단 경로의 할 일 추출에 주는 영향도 같이 쟀다([extract-6p/](extract-6p/)). 숫자는 [summary.json](summary.json), 식이 붙은 전체 표는 [tables.md](tables.md) 에 있다. 이 문서는 그 두 파일의 값에 세 가지를 더했다. 거기서 식으로 푼 "계산값", summary 에 없어 1초 표본에서 따로 뽑은 "원자료" 값, 레포 밖 원자료 폴더의 cloudwatch.json 에 남긴 CloudWatch 조회값이다. 계산값과 원자료 값은 숫자 옆에 그렇게 적었다.

## 결론

지금 서버(t3.medium, 2 vCPU, 메모리 3.74GiB)에서 로컬 large-v3-turbo(int8, beam 5)로 62.42분짜리 반복 합성 회의를 전사하는 데 84.93분 걸렸다. 회의 길이 기준 RTF 는 1.36 이다. 60분으로 환산하면 회의 1시간당 전사 81.63분이다(계산값).

메모리에는 turbo 전사 프로세스가 하나만 들어간다(계산값). 워커 2개를 띄우자 두 프로세스가 모델을 올리던 10초 무렵 남은 메모리가 481MiB 까지 내려갔고 그때부터 스왑이 초당 약 90MiB 씩 늘었다(원자료). 18초에 측정의 안전 기준(스왑이 기록 시작보다 768MiB 증가)에 걸려 꺼졌다. 스왑 없이 둘은 들어가지 않는다. 스왑을 쓰며 끝까지 도는지와 그때 속도는 재지 않았다.

한 프로세스에서 회의 2개를 같이 돌리면 메모리는 들어갔다. 두 결과가 423.53초와 424.14초에 함께 나와, 하나씩 돌린 전사 시간 합 423.5초보다 빠르지 않았다(정렬본).

워커 1개가 쉬지 않고 돌면 하루에 회의 17.64시간 분량을 처리한다(계산값). CPU 크레딧 안에서 추가 요금 없이 전사하는 시간은 하루 6.38시간, 회의로는 4.69시간 분량이다. 이를 넘는 전사 1시간마다 0.06달러가 붙는다(둘 다 계산값).

전사 중에도 BE /health 실패는 0건이었다. p95 는 상시 3.44ms 에서 turbo 실행 중 6.14~7.09ms 로 늘었다. 봇 방식에서 50ms 타이머는 전사 중 p95 1.40ms, 최대 52.5ms 늦게 깼다.

small(int8, beam 1)은 6인 정렬본에서 turbo 보다 3.2~3.5배 빨랐다. CER 은 8.20%, 8.68% 로 turbo(5.33%, 4.99%)보다 2.87pt, 3.69pt 높았다.

판단 경로로 6인 정렬본에서 할 일을 뽑아 보니, small 전사에서 뽑은 항목이 turbo 전사에서 뽑은 것보다 나쁘지 않았다(전사마다 3번). 같은 정답 대본을 여러 번 넣어도 항목이 0~2개 빠지고 0~3개 더해져, 이 흔들림 안에서 turbo 가 낫다는 차이는 보이지 않았다. 추출 한 번(2.4~2.6분 회의)은 평균 53.01초, LLM 호출 13.93번이었다.

62.42분 회의는 전사만으로 초안 10분 기준을 74.93분 넘는다(60분 환산 71.63분, 계산값). 0008 의 다시 볼 조건인 오디오 1분당 30초도 넘는다(회의 1분당 81.63초, 계산값).

## 측정 조건

서버는 ktc4-team-server(t3.medium, 2 vCPU, MemTotal 4018429952 바이트 = 3832.27MiB, 스왑 4GiB, CPU 크레딧 unlimited)다. 스왑 크기와 크레딧 방식은 측정 전에 서버와 EC2 설정에서 확인했고 원자료 기록기는 남기지 않는다. 같은 서버에서 BE·DB 도커와 봇이 같이 돈다. 봇은 봇 모드로 켜 두었고 시작 때 모델을 올리지 않은 상태였다(45MiB). 측정 시각은 2026-10-06 00:00~01:57(한국 시각)이다.

코드는 커밋 bc9dc35 다. 서버에는 .git 이 없는 사본을 두어 COMMIT 파일로 커밋을 남겼다. faster-whisper 1.2.1, ctranslate2 4.8.2, Python 3.12.3, int8 이고 cpu_threads 는 지정하지 않아 기본값으로 돌았다. 전사는 운영 경로(stt.batch.run, chunk 모드, 말 필터 켬, 호출은 한 번에 하나)로만 했다. 평가 도구의 결과 캐시는 쓰지 않았다.

실녹음은 10/2 실제 디스코드 2인 회의(회의 65.1초, 말 48.7초)이고 같은 회의를 3번 줄 세웠다. 6인 정렬본은 m01(회의 146.87초, 말 133.5초)과 m02(회의 155.68초, 말 140.4초)이고, 목소리는 진짜지만 시간축이 합성이며 대본 낭독이라 짧은 대답과 겹침이 없다. 60분 회의는 m01 과 m02 를 5초 간격으로 번갈아 12번씩 이어 붙인 62.42분 반복 합성 회의(트랙 3745.48초)라 시간과 자원만 보고 정확도 근거로 쓰지 않는다. 말한 시간 3286.8초는 12 × (133.5 + 140.4) 와 정확히 같다.

켜 둔 봇과 측정을 떼어 놓았다. 측정은 서버 임시 폴더의 별도 ai/ 사본과 그 안의 recordings 폴더로 돌렸다. 사본의 .env 에는 MM_STT_BACKEND=local, PM_AGENT_LLM=off 두 줄만 넣었다. 그래서 LLM 호출과 BE 회의 생성이 일어나지 않는다. 켜 둔 봇의 cgroup 메모리는 측정 내내 14~54MiB 였다(원자료). 봇이 모델을 올린 흔적이 없어 측정 중 실제 회의는 들어오지 않았다고 본다. 운영 워커(mm-worker)도 켜져 있었지만 모델 없이 10초마다 녹음 폴더만 보며 기다렸다(systemd 기준 26~28MiB). 01:31~01:32 에 develop 배포가 봇과 워커를 다시 시작했다. seq-long60 도중이었고, 봇 cgroup 메모리는 14MiB 에서 47MiB 로 올라왔다(원자료).

시나리오는 운영 워커와 같게 nice -n 10 으로 돌렸다. 봇 방식(botlag)만 봇처럼 nice 없이 돌렸다. 서버 기록기와 BE 측정기도 nice 없이 두었다. 각 시나리오는 모델을 먼저 올리고 1초 무음을 한 번 전사한 뒤 회의를 쟀다. 그래서 회의 처리 시간에 모델 로드가 섞이지 않는다. 서버 기록기는 1초마다 서버 사용 메모리, 스왑, 바쁜 vCPU, steal, 측정 프로세스의 PSS, 봇과 측정 단위의 cgroup 메모리를 남겼다. BE 측정기는 1초마다 http://127.0.0.1:8000/health 응답 시간을 남겼다. CloudWatch 는 조회만 했다. 전체는 systemd-run 으로 띄운 단위(mm-capacity-1006.service) 안에서 돌았다.

## 안 한 것과 한계

- 추출 비교는 전사마다 3번, 정답 대본 9번이다. LLM 흔들림(놓침 0~2)과 견줄 만큼 크지 않다. 2.4~2.6분 낭독 회의라 실제 회의의 할 일 수와 다르다.
- 호출별 temperature 와 compression_ratio 를 남기지 않았다. 반복 합성 회의에서 압축률 폴백(같은 묶음을 다시 디코딩)이 돌았는지 모른다. 말 기준 RTF 는 6인 원본 범위 안이었다.
- 준비 단계(트랙 읽기, 묶기)와 실행 단계(전사 호출)의 메모리를 나누지 못했다.
- cpu_threads 를 지정하지 않아 기본값으로 돌았다. 전사 중 바쁜 vCPU 는 1.29(상시 0.08 포함)로 2 에 못 미친다. 스레드 수를 바꿔 다시 재야 두 번째 vCPU 를 더 쓸 수 있는지 안다. 워커 2개를 워커당 1스레드로 돌리는 비교도 아직 안 했다.
- 10분, 30분 회의는 재지 않았다. 60분 합성은 한 번 돌렸다.
- 같은 설정의 반복이 적다. 2인 회의 3번, 6인 m01 turbo 2번(워커, 봇 방식), 나머지는 1번씩이다. 호출 p95 는 호출 단위 값이고 회의 단위 p95 가 아니다. 호출 3개, 7개인 실행에서는 최댓값과 같다. 호출 길이 구간별 p95 도 내지 않았다.
- 상시 값(바쁜 vCPU 0.08, 메모리 961.55MiB)은 자정 무렵 2분 표본 하나다. 낮 시간 BE·DB 부하와, 봇 방식에서 모델을 쥔 상시값은 다를 수 있다. 하루 6.38시간과 프로세스 1개 계산이 이 값을 그대로 쓴다.
- 대기열 N=2, 3, 5 는 계산값이다. 대기열 실측은 2인 1분 회의 3개뿐이다.
- BE 는 /health 응답만 쟀다. DB 를 거치는 API 에 주는 영향은 모른다.
- BE p95 는 0부터 센 round((n−1)×0.95) 번째 값이다. 표본이 적은 small 두 실행(n=71, 74)과 workers2(n=19)는 규칙에 따라 값이 크게 달라진다. 1부터 센 ceil(0.95n) 번째로 계산하면 golden-m02-small 은 9.33ms, workers2 는 10.43ms 다(원자료). 결론의 6.14~7.09ms 는 표본 250개 이상인 turbo 실행만 쓴 범위다.
- 실제 녹음 중 봇의 CPU 와 메모리, 회의 1시간당 디스크 사용량은 아직 안 했다.
- 워커 유닛 설정 그대로 돌린 cgroup memory.peak 는 내지 않았다. 측정 단위 전체의 memory.peak(2732.61MiB)에는 기록기, BE 측정기, 페이지 캐시가 섞여 있다.
- 실제 회의마다 남는 처리 기록은 #153 이 들어간 뒤 쌓인다. 추출·인계 시간과 LLM 비용은 그때 나온다.
- 6인 정렬본은 대본 낭독이라 짧은 대답과 겹침이 없다. 대화 CER 10% 기준과는 견줄 수 없다. 60분 합성은 정확도 근거로 쓰지 않는다.
- steal 최대값(seq-long60 69.95%)은 1초 표본 가운데 가장 큰 값이다. 시나리오 구간 평균은 1.12~1.58% 였다.
- 봇 cgroup 메모리가 45MiB 에서 14MiB 로 줄어든 것은 전사 중 메모리 압박에 봇 페이지가 밀려난 흔적일 수 있다(추정).
- CloudWatch 대조는 5분 기본 지표라 서버 기록과 시각이 딱 맞지 않는다.
