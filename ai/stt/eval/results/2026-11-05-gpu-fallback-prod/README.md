# 운영 서버에서 부른 GPU 전사 서버 시간

- 날짜: 2026-11-05, 대기 서버 방식 측정 2026-11-06
- 이슈: [#393](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/issues/393)
- 데이터: 정렬본을 이어 붙인 62.42분 합성 회의. 시간과 자원만 본다. 정확도 근거로 쓰지 않는다

운영 서버(t3.medium)에서 개인 AWS 의 g4dn.xlarge(vLLM, whisper-large-v3)를 공인 인터넷과 TLS 로 불렀다. 꺼 둔 대기 서버를 켜면 `on` 부터 운영 서버의 첫 전사 응답까지 161.8초와 158.6초다. 62.42분 전사 166.2초를 더하면 약 326초(5.4분)로, 따로 잰 값을 더한 계산값이다. AMI 로 새로 띄우던 때의 501초(8.35분)보다 175초 짧다.

이 합계는 장애를 알아채는 시간, 워커 재시작, 추출과 인계를 넣지 않았다. 남는 시간은 약 4.6분이고 워커 재시작은 처리 중인 회의가 있으면 20분까지 걸릴 수 있다. 그래서 회의 하나가 끝날 때까지 전체가 10분 안에 든다는 뜻은 아니다.

이 값은 처음 전사하는 회의의 경로다. 장애에 걸려 포기된 회의를 다시 돌리는 경로는 회의를 하나씩, 클립을 하나씩 보내며 재지 않았다.

## 꺼 둔 서버 켜기

2026-11-06 측정이다. 시작과 끝을 Mac 시계로 재서 시계 차이가 없고 공인 인터넷 왕복이 들어 있다. 첫 전사는 합성음 20초 WAV 다.

| 항목 | 1회 | 2회 |
|---|---|---|
| `on` 부터 운영 서버의 첫 전사 응답 | 161.8초 | 158.6초 |
| `on` 명령이 끝날 때까지 | 30.5초 | 23.0초 |
| 첫 전사 호출 | 1.57초 | 0.77초 |
| `off` | 403.7초 | 402.0초 |

앞서 인스턴스 안에서 같은 방식을 잰 값도 있다. 부팅 시작부터 첫 전사 응답까지 156.2초와 155.8초다. 이 값은 네트워크 왕복이 빠져 있고, 시계가 Mac 과 달라 start 호출 뒤 부팅 시작까지의 시간도 빠져 있다. 그래서 위 표를 기준으로 쓴다. 같은 측정에서 새로 띄운 첫 부팅은 부팅 시작부터 333.2초였다. 측정용 음성을 만드는 시간이 들어 있어 단순 비교는 하지 않는다.

`setup` 은 709.6초 걸렸다. 첫 부팅이 모델을 올린 뒤 스스로 꺼질 때까지 기다린 값이다.

자동 stop 도 실제로 돌렸다. 종료 시각 태그를 240초 뒤로 두고 켜자 시작 346.8초에 `stopping` 이 되고 710.2초에 `stopped` 가 됐다. 꺼지기 시작한 시각은 태그보다 약 107초 늦다. 스크립트가 분 단위로 올려 잡고, 운영체제 종료 처리가 더해진다.

운영 서버에는 아무것도 쓰지 않았다. `/etc/mm` 의 설정을 읽어 호출만 했고 음성은 표준 입력으로 넘겼으며 워커는 재시작하지 않았다. drop-in 도 두지 않아 워커 전환 경로는 확인되지 않았다. 측정 뒤 대기 서버는 `stopped`, 볼륨은 gp3 75GB, 다른 작업의 g5 인스턴스는 전후 시작 시각이 같다.

## 음성 임시 파일

운영 워커가 보내는 음성은 Starlette 가 임시 파일로 내리는 기준 아래다. 그래서 tmpfs 같은 장치는 더하지 않았다.

Starlette 1.10.0 은 업로드가 1MiB(1,048,576바이트)를 넘으면 `/tmp` 에 쓴다(`formparsers.py` `spool_max_size`). `/tmp` 는 EBS 의 ext4 다. 합성음으로 확인한 결과는 아래와 같다.

| 업로드 | 요청 중 관측 |
|---|---|
| 640,044바이트 (20초) | 임시 파일 없음 |
| 1,920,044바이트 (60초) | `/tmp/#번호 (deleted)`, 같은 크기, 3회 모두 |

워커의 두 경로(`transcribe_session`, `retry_failed_lines`)는 모두 `mode="chunk"` 다. 묶음은 `CHUNK_MAX_S` 28초, `TARGET_SR` 16kHz, `PCM_16` 이라 WAV 가 최대 896,044바이트이고 기준까지 152,532바이트 남는다. 1MiB 는 약 32.8초에 해당한다. vLLM 0.19.1 의 `speech_to_text.py` 는 받은 바이트를 `BytesIO` 로 읽는다.

한계가 있다. 관측은 50ms 간격 표본이고 합성음으로만 했다. 요청 뒤 찾은 새 파일에 음성은 없었지만 `/var/log` 는 찾지 않았고 `vllm.log` 의 내용도 보지 못했다. 지워진 임시 파일의 블록이 디스크에 남는지는 보지 않았다. 운영 경로 밖의 `track`, `whole` 모드나 `CHUNK_MAX_S` 를 약 32.8초 넘게 올리는 변경은 이 판단을 다시 봐야 한다.

60초 WAV 는 3회 모두 200 이지만 응답이 78바이트, 0.74초였다. 본문을 저장하지 않아 내용을 모른다. 운영 경로 밖이라 재측정하지 않았고 미확인으로 남긴다.

디스크 삭제는 terminate 측정 인스턴스로 확인했다. `DeleteOnTermination=True` 였고 뒤에 볼륨 조회가 `NotFound` 였다. 대기 서버는 이 삭제가 일어나지 않아 `destroy` 때까지 디스크가 남는다.

## AMI 로 새로 띄운 측정

아래는 2026-11-05 값이다. 각각 한 번 잰 값이고 지금 쓰지 않는 켜는 경로다. 전사 시간은 서버가 같아 위 계산에 그대로 썼다.

| 항목 | 값 |
|---|---|
| `on` 부터 첫 `/health` 200 | 335초 |
| 62.42분 합성 전사 | 166.2초 |
| 합계 | 501초 (8.35분) |
| 호출 / 실패 / 재시도 | 168 / 0 / 0 |
| 보낸 오디오 | 3402초 |
| 호출 p50 / p95 / 최대 | 5.03 / 6.39 / 6.66초 |
| 측정 프로세스 CPU / 최대 메모리 | 50.0초 / 약 483MiB |
| 측정 중 최대 동시 호출 | 6 |

[GPU 서버 안에서 부른 측정](../2026-11-04-gpu-serving/README.md)은 같은 회의가 159.8초였다. 호출 수와 보낸 오디오는 같고 차이는 6.4초(4%)다. 한 번씩 잰 값이라 전송 비용으로 단정하지 않는다. 콜드 스타트는 지난번 5.0분보다 0.6분 길다. 이번 값은 `on` 호출 21초와 운영 서버의 10초 간격 확인을 포함한다.

키 없는 `/v1/models` 는 401, 키가 있으면 200 이었다. 측정은 운영 워커를 쓰지 않았다. 코드를 임시 폴더에 복사해 일회성으로 돌렸고 워커는 재시작하지 않았으며 운영 `.env` 도 바꾸지 않았다. 그래서 워커 전환 경로는 이 측정으로 확인되지 않았다. 측정 뒤 인스턴스 0대를 확인했다.

## 재현

대기 서버 측정은 커밋 `76690f32` 의 스크립트로 돌렸다. 절차와 원자료는 레포 밖 `mm/eval-runs/393-gpu-stt-fallback/2026-11-06-standby/`(`verify.sh`)와 `2026-11-06-stop-start/` 에 있다. 운영 서버에서 `/etc/mm/gpu-stt.env` 를 읽어 `/health` 를 기다린 뒤 표준 입력의 WAV 를 `/v1/audio/transcriptions` 로 보낸다.

```bash
deploy/gpu-stt/gpu-stt.sh setup <운영 서버 공인 IP>
deploy/gpu-stt/gpu-stt.sh on --hours 1
deploy/gpu-stt/gpu-stt.sh off
```

아래는 2026-11-05 전사 측정이다. 커밋 `83e1672c` 의 `ai/` 와 같은 코드로 돌렸다. 임시 폴더라 결과 JSON 의 `git_commit` 은 비어 있다. 원자료는 레포 밖 `mm/eval-runs/393-gpu-stt-fallback/2026-11-05-prod-long-60/` 에 있다.

Mac 에서 합성하고 GPU 서버를 켠다.

```bash
python -m stt.eval.capacity.synth --source $DATA/m01 --source $DATA/m02 --out $DATA/long-60 --minutes 60 --gap 5
deploy/gpu-stt/gpu-stt.sh on
```

`.env` 가 없는 임시 폴더로 코드와 `long-60` 을 옮겨, 운영 서버에서 돌린다. `--spend-file` 은 Elice 측정과 옵션을 맞춘 것이고 실제 과금이 아니다.

```bash
set -a; . <(sudo cat /etc/mm/gpu-stt.env); set +a
/opt/mm/ai/.venv/bin/python -m stt.eval.capacity.runner seq --tracks-dir $DATA/long-60 --label long-60 \
  --backend elice --spend-file $RUN/spend.jsonl --cap-krw 1000000 --out-dir $RUN --pids-file $RUN/pids
```
