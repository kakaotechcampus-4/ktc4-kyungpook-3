# judge/golden_set/

Terra 1단계(`judge/semantic_judge.py`) 검증용 골든셋. `extract/golden_set/`(지민님, Phase 1)과
같은 패턴이되, 여기서 보는 건 "누가/뭘/언제까지"가 아니라 **"이 발화가 2단계까지 갈 가치가
있는가"**(`should_flag`) 하나뿐입니다.

## 디렉토리

- `short_sentences/` — 발화 1~2개짜리 최소 케이스. 특정 규칙/문제 하나를 정확히 짚어보는 용도.
- `long_sentences/` — 실제 회의처럼 잡담/진행상황 보고/여러 주제가 섞인 10턴 이상짜리(대략
  10분 안팎 분량) 케이스. 청크로 안 쪼개고 전체를 한 번에 넣었을 때도 신호를 놓치거나
  잡음을 오탐하지 않는지 보는 스트레스 테스트.

각 디렉토리 안에 `case_01.json`부터 케이스 하나당 파일 하나.

## case_*.json 형식

```jsonc
{
  "case_id": "case_01",
  "scenario": "짧은 영문 식별자",
  "description": "이 케이스가 뭘 검증하는지",
  "turns": [{"speaker": "A", "text": "..."}],   // 화자는 실명 대신 A/B/C 같은 익명 라벨
  "expected": [
    {"text": "...", "should_flag": true, "note": "왜 이렇게 기대하는지"}
  ],
  "counts_toward_pass_rate": true   // false면 정답률 계산에서 제외(참고/스트레스용)
}
```

`expected`의 `text`는 `judge.semantic_judge.split_sentences()`가 뽑아낼 문장과 정확히 일치해야
채점됩니다. 채점은 `JudgeFinding.evidence`(항상 원문 그대로)와 비교합니다 — `JudgeFinding.text`는
LLM 경로에서 문맥을 반영한 요약으로 바뀔 수 있어서 원문 기준 채점엔 안 맞습니다.

## `short_sentences/`가 특별히 겨냥하는 것

- **case_01, 02**: 명확한 일정 합의/범위 변경 — 규칙 기반도 Luna도 다 잡아야 하는 기본기
- **case_03, 04**: 잡담/회의 진행 멘트 — 오탐하면 안 됨
- **case_05**: 질문 vs 결정 — 규칙 기반은 `까지` 키워드로 오탐 예상, Luna는 걸러야 함
- **case_06**: 조건부 약속 — 애매해도 넉넉하게 포함하는 원칙 확인
- **case_07**: 같은 회의 안에서 번복 — 모순 해결은 2단계 몫이라, 1단계는 둘 다 후보로 남기면 됨
- **case_08**: STT로 잘린 문장 (참고용, 통과율 계산 제외) — 정확도보다 크래시 없이 처리되는지가 목적
- **case_09**: 한 문장에 결정 2개(쉼표로만 구분) — 문장 분리가 안 돼서 하나의 `JudgeFinding`으로
  뭉뚱그려지는 게 알려진 한계
- **case_10**: 패턴 없는 문맥적 합의("그럼 그렇게 갑시다") — 애초에 Luna를 도입한 이유 그 자체.
  규칙 기반은 못 잡을 것으로 예상
- **case_11**: 날짜 키워드만 있는 잡담 — 규칙 기반은 오탐, Luna는 걸러야 함

case_05/10/11은 **규칙 기반과 Luna의 정답률이 갈리는 걸 보여주기 위한 케이스**입니다 —
둘 다 100% 맞히면 오히려 Luna를 도입한 의미가 약해지는 케이스이니, 결과 해석 시 참고하세요.

## `long_sentences/`가 특별히 겨냥하는 것

짧은 케이스에서 100%가 나와도, 실제 회의처럼 잡음(진행상황 보고/잡담/여러 주제)이 잔뜩 섞인
긴 전사록에서는 새로운 실패 패턴이 나올 수 있다는 걸 실제로 검증하려고 만들었습니다.

- **case_01**: 신호 4개가 잡음 사이에 흩어진 일반적인 스탠드업 (~13분)
- **case_02**: 신호가 아예 없음 — 오탐 방지 확인
- **case_03 / 04**: 신호가 맨 앞 / 맨 뒤에 몰림 — 위치와 무관하게 잘 잡는지("lost in the
  middle" 문제 확인)
- **case_05**: 질문-답변 형태의 문맥적 합의가 여러 개
- **case_06**: 같은 주제가 세 번 정정됨 — 전부 후보로 남기는지
- **case_07**: 여러 화자가 같은 결정을 반복 확인 — 새 정보 없는 재확인은 제외해야 함
- **case_08**: 세 가지 주제가 번갈아 나옴 — 섞여도 각 결정을 놓치지 않는지
- **case_09**: 잡음 대비 신호가 1개뿐인 극단적 케이스
- **case_10**: 회의가 아니라 텍스트 채팅(`source="chat"`, 캐주얼한 말투)
- **case_11**: 의견 대립 후 최종 합의 — 대립 발화 자체는 제외
- **case_12**: 한 발화 안에 문장 여러 개가 섞여 있고 그중 하나만 결정 (문장 분리 후 채점되므로
  `expected`도 분리된 문장 기준으로 적어야 함 — 안 그러면 매칭 자체가 안 됨, 실제로 한 번
  겪은 실수)
- **case_13**: 개발 용어 없는 마케팅/일정 조율 회의 — 특정 도메인 패턴에 과적합 안 됐는지

이 그룹은 실행할 때마다 결과가 살짝 다를 수 있습니다(LLM 비결정성) — 한 번 100%가 안 나왔다고
바로 프롬프트를 고치기보다는, 같은 실패가 반복되는지 몇 번 더 돌려보고 판단하세요.
