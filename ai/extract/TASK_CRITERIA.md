# 무엇을 "할일"로 볼 것인가 (판단 기준)

추출기가 어떤 발화를 할일로 잡을지 정한 기준. **LLM 프롬프트(`extract/prompts.py`)와 골든셋 정답이
둘 다 이 문서를 따른다** — 기준이 흔들리면 프롬프트도 채점도 같이 흔들리므로, 바꿀 땐 여기부터 고치고
프롬프트·골든셋을 맞춘다.

이건 모델 성능 문제가 아니라 **제품 결정**이다. "검토해볼게요"를 PM 승인 목록에 띄울지 말지는 팀이
정하는 것이고, 모델은 정해진 기준을 따라할 뿐이다.

## 3원칙 — 셋 다 만족해야 할일

1. **행동** — 구체적인 동작이나 산출물이 있다. (누가 무엇을 한다)
2. **미완료** — 아직 안 끝났다. 이미 끝난 일의 보고는 할일이 아니다.
3. **의지 또는 요청** — 하겠다는 의지, 또는 해달라는 요청이 있다. 단순 가능성·희망·추측은 아니다.

## 애매한 구간을 가르는 기준

실제 회의에서 자주 나오는데 3원칙만으로는 안 갈리는 것들. **애매하다고 버리지 않는다** — 할일로
잡되 "추론 필요" 상태로 내려서 PM이 확인하게 한다(놓치는 것보다 확인 한 번이 싸다).

| 상황 | 판단 | 이유 |
|---|---|---|
| 조건부 — "시간 되면 해볼게요", "필요하면 도와드릴게요" | **할일 O** (추론 필요) | 조건이 붙었다고 버리면 진짜 할일을 놓친다. PM이 확인 |
| 사고 활동만 — "고민해볼게요", "생각해볼게요" | **할일 X** | 산출물이 없다. 3원칙 1번 불충족 |
| 사고 + 산출물 — "고민해보고 내일 공유드릴게요" | **할일 O** | 공유라는 산출물이 붙었다 |
| 모호한 동사 + 구체적 대상 — "이 PR 검토해볼게요" | **할일 O** | 대상이 구체적이면 행동이 특정된다 |
| 질문형 — "이거 누가 하죠?" | **할일 X** | 아직 아무것도 결정 안 됐다 (BE 문서의 "무기재/암묵적 결정") |
| 제3자 추측 — "그건 환이가 할 것 같은데요" | **할일 X** | 결정이 아니라 추측이다 |
| 미완료 보고 — "그거 아직 못 했어요" | **할일 X** | 할일이 있다는 신호지만 새 할일 선언은 아니다. 뒤에 "오늘까지 할게요"가 붙으면 **그 문장**이 할일 |
| 진행 계속 선언 — "계속 진행하겠습니다" | 마감이 붙으면 **O**, 없으면 **X** | 마감 없는 계속 선언은 상태 보고에 가깝다 |
| 보류 — "그건 다음에 얘기하죠" | **할일 X** | 논의 연기이지 실행 약속이 아니다 |
| 회의 진행 — "오늘 스탠드업 시작할게요", "여기까지 하죠" | **할일 X** | 회의 운영 발언 |
| 전원 대상 — "다 같이 검토하죠" | **할일 O**, 담당자 `all` | 담당자 불명이 아니라 **참석자 전원**이라는 결정이다. BE 가 멤버 전원으로 펼친다 |
| 전원 지칭 없는 청유 — "이번 주 안으로 한번 손보죠" | **할일 O**, 담당자 `none` | "다 같이"·"우리 모두" 같은 전원 지칭이 없으면 `all` 이 아니라 미지정이다 |

## 마감일 해석 규칙

날짜 "해석"은 LLM 이 하지만, 애매한 표현을 어떻게 읽을지는 팀이 정한다. 아래는 확정된 규칙이다.

| 표현 | 해석 |
|---|---|
| "월요일까지"(요일 단독) | 오늘 기준 가장 가까운 다음 해당 요일 |
| "이번 주 안으로" | **이번 주 일요일** |
| "다음 주까지" | 다음 주 일요일 |
| "월말까지" | 그 달 마지막 날 |
| 마감 표현 없음 | null (지어내지 않는다) |

기간 표현을 "그 기간의 마지막 날"로 **확정**하기로 한 결정이다. 비워두고 PM 이 채우게 하는 안도
있었지만, 그러면 "이번 주 안으로"라고 분명히 말한 정보가 버려져 PM 이 원문을 다시 찾아야 한다.

다만 "이번 주"의 끝을 일요일로 볼지 금요일(업무 주)로 볼지는 팀 관행에 달렸다 — 지금은 달력 기준
일요일로 정했고, 주말에 일하지 않는 팀이라면 금요일로 바꾸는 게 맞을 수 있다. 바꾸려면 이 표와
extract/prompts.py 의 7번 항목, 골든셋 정답을 같이 고친다.

## 담당자 타입 (BE alias 설계와 1:1)

| 타입 | 예시 | 이후 처리 |
|---|---|---|
| `first` | "제가 하겠습니다" | BE — 발화자를 이미 알고 있음. **AI는 이름을 채우지 않는다** |
| `second` | "이건 너가 하는 걸로" | AI가 문맥으로 해소 시도 → 실패 시 PM |
| `thirdname` | "환 님이 맡아주세요" | BE — alias 테이블 조회 |
| `thirdpronoun` | "그분이 하시기로" | AI가 문맥으로 해소 시도 → 실패 시 PM |
| `thirdrole` | "백엔드 리더가 담당" | BE — 매핑 기록 활용, 대체로 PM 확인 |
| `all` | "다 같이", "전체", "각자" | BE — 참석자 전원을 담당자로 채운다 (BE 문서엔 없던 타입 — 추가 필요) |
| `none` | 담당자 언급 없음 | PM 확인 |

## 필드별 상태

정확도 %를 사용자에게 보여주는 대신, 필드마다 아래 3단계를 매긴다. **숫자는 내부 로그로만 남긴다**
(PM 승인/반려 기록이 쌓이면 나중에 보정 검증에 쓴다).

| 상태 | 언제 | PM이 할 일 |
|---|---|---|
| `certain` | 원문에 명시적으로 있음 | 바로 승인 |
| `inferred` | 문맥으로 유추했거나 반복 호출 시 답이 흔들림 | 근거 문장 확인 |
| `missing` | 그 필드가 발화에 없음 | 직접 입력 |
