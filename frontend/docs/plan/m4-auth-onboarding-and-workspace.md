- 근거: `frontend-development-plan.md`, `m3-routing-and-data-layer.md`, `../decision/frontend-decisions.md`, `../api/frontend-api-contract-draft.md`, `../design/canvas/`

## 1. 목표와 범위

**MSW 환경에서 회원가입·로그인 → 온보딩 → 대시보드 진입과 워크스페이스 전환을 완성한다.** Storybook과 브라우저 E2E를 포함한다.

- M3의 라우터·접근 가드·Query·이탈 확인, M2의 디자인 토큰·공통 UI를 재사용한다.
- 랜딩, 로그인, 회원가입, 워크스페이스 선택, 온보딩 4단계, 앱 헤더·5개 탭, 대시보드 빈 상태를 구현한다.
- 실제 OAuth·백엔드 보완, 대시보드 집계·업무 목록, 회의·태스크·설정 본문은 후속 범위로 둔다.
- 화면은 기존 HTML 캔버스와 확정 결정문을 기준으로 구현한다. 데스크톱 1024px 이상을 지원한다.

## 2. 데이터 흐름과 개발 기반

### API와 캐시

- `entities`에 로그인·가입·로그아웃, 워크스페이스 생성·상세·온보딩 갱신, 연동 상태·Discord 사용자 조회, 팀원 생성·수정 함수를 추가한다.
- 기존 DTO·매퍼·`request`를 사용하고, 생성 요청과 온보딩 `{ step, action }` 등 누락된 요청 타입을 명시한다. 백엔드 API 형식은 변경하지 않는다.
- `features`가 제출·캐시 갱신·단계 진행을 담당하고, `widgets`가 헤더·워크스페이스 메뉴·팀원 연결 화면을 조립한다.
- 온보딩 PATCH는 빈 객체를 반환하므로 **갱신 성공 → 상세 재조회 → 목록 캐시 반영 → 다음 화면 이동** 순서를 지킨다.
- 서로 독립적인 조회는 병렬로 실행하며, 워크스페이스별 데이터는 기존 ID 기반 Query key로 분리한다.

### MSW 보완

현재 MSW는 로그인된 상태로 시작하고, 새로고침하면 모든 변경이 초기화된다. 이를 다음과 같이 보완한다.

- 브라우저에서는 최초 비로그인으로 시작한다. 기존 Vitest 픽스처와 초기화 방식은 유지한다.
- 브라우저 MSW에만 버전이 있는 `sessionStorage` 저장·복원을 추가해 가입 계정, 세션, 워크스페이스, 온보딩, 연동·팀원 상태가 같은 탭의 새로고침과 OAuth 왕복 후에도 유지되게 한다.
- E2E마다 저장소와 픽스처를 초기화하고, 비로그인·워크스페이스 0/1/복수·미완료 공간 시나리오를 독립적으로 준비한다.
- 새 워크스페이스에서도 Discord 연결 후 사용자 목록이 반환되도록 현재 `ws_01` 전용 픽스처를 확장한다.
- OAuth 모의 화면은 개발·MSW 모드에서만 등록한다. 현재 탭으로 이동해 성공·취소·실패를 재현하고 원래 온보딩 단계로 복귀한다. 복귀 후 연동 상태를 다시 조회한다.

## 3. 화면과 동작 구현 순서

### ① 랜딩·인증

- 랜딩의 `시작하기`는 로그인으로 연결하고, 로그인에서 회원가입으로 이동한다.
- React Hook Form과 Zod resolver를 추가한다. `onTouched`, 변경 시 재검증, 첫 오류 포커스, 제출 중 중복 실행 방지를 공통 적용한다.
- 회원가입은 이름·이메일·비밀번호와 보기 토글을 구현한다. 이름 필수·이메일 형식·비밀번호 8자 이상 및 숫자 포함을 검증한다. 로그인은 이메일 형식과 비밀번호 필수만 검증한다.
- 사용자 선택에 따라 비밀번호 강도 표시와 약관 동의는 이번 범위에서 제외하고 결정 문서에 기록한다.
- 필드 오류는 입력 아래, 비필드 오류는 공통 `FormErrorPanel`(신규)에 표시한다.
- Google 로그인과 비밀번호 재설정은 비활성으로 표시한다.
- 인증 성공 시 이전 사용자 요청·캐시를 정리하고 새 워크스페이스 목록을 확보한다. **로그인 직후에는 `postLoginPath`, 인증 화면 재방문에는 `authRevisitPath`**(`entities/workspace/lib/entryPath.ts`)를 사용하도록 가드와 이동 처리를 조정한다.
- 로그아웃은 서버 성공 후 사용자 캐시를 정리하고 로그인으로 이동한다. 미저장 변경은 기존 이탈 확인을 거친다.

### ② 워크스페이스 생성·온보딩

- 공통 온보딩 레이아웃에 단계 표시, 본문, 진행·건너뛰기 버튼을 배치한다.
- 생성 이름은 M3의 공백 정규화·1~20자·계정 내 중복 검증을 재사용하며 대소문자를 구분한다.
- 생성 성공 후 생성 단계 완료를 저장한다. 단계 저장에 실패해도 생성된 ID를 유지하고 재시도하여 공간을 중복 생성하지 않는다.
- Discord·Notion 연결은 현재 탭 이동 방식으로 구성한다. 모의 OAuth 성공 여부만으로 완료 처리하지 않고, 연동 상태가 `connected`인지 조회한 뒤 단계를 완료한다.
- Notion 데이터베이스 선택 화면은 추가하지 않는다.
- Discord 건너뛰기 시 팀원 연결도 건너뜀으로 저장한다. 중간 요청 실패 시 이미 저장된 상태를 재조회해 남은 처리만 재시도한다.
- 단계 완료·건너뛰기가 모두 저장되면 새 공간의 대시보드로 이동한다. 새로고침·재로그인·직접 URL 진입은 저장된 미완료 단계로 복귀한다.
- 일반 팀원은 PM 설정 대기 안내를 보고, 온보딩 수정 요청을 보낼 수 없다.
- 기존 공간에서 새 공간 만들기를 시작할 때 복귀할 공간 ID를 보관한다. 온보딩의 뒤로가기는 입력 중인 팀원 매핑을 저장한 뒤 기존 대시보드로 복귀하며, 저장 실패 시 화면에 남는다. 최초 가입자는 워크스페이스 선택 화면으로 복귀한다.

### ③ 팀원 연결

- Discord 사용자와 기존 팀원을 함께 조회하고 기존 `linkDiscordUsers`(`entities/member/lib/linkDiscordUsers.ts`)로 목록을 구성한다. 봇은 제외하고 기존 매핑을 채워 보여준다.
- Discord 사용자와 팀원 이름의 1:1 제약을 검사한다. 빈 행을 제외한 부분 매핑도 저장·완료할 수 있다.
- 기존 매핑은 PATCH, 입력한 이름과 일치하는 미연결 팀원이 있으면 해당 팀원에 연결, 없으면 POST한다. 생성자인 PM도 기존 팀원으로 재사용한다.
- 일괄 API가 없으므로 변경 행을 순서대로 저장한다. 성공 행의 ID와 값을 반영해 재시도 때 중복 생성하지 않는다.
- 일부 저장 실패 시 실패 행과 남은 입력을 유지한다. 모든 저장 성공 후에만 온보딩 완료 요청을 보낸다.
- 일반 링크·워크스페이스 전환·브라우저 이탈에는 기존 미저장 변경 확인을 적용한다.

### ④ 워크스페이스 선택·앱 셸·대시보드

- 별도 선택 화면과 헤더 메뉴는 같은 목록·진입 정책을 사용한다. 미완료 공간에 `설정 미완료`를 표시한다.
- 완료 공간 선택은 해당 대시보드로, 미완료 공간 선택은 온보딩 재개 지점으로 이동한다.
- `Main` 캔버스를 기준으로 헤더와 5개 탭을 구현하고 설정은 별도 메뉴로 연결한다.
- 메뉴는 Radix Dropdown Menu를 사용해 키보드 이동·Esc 닫기·포커스 복귀를 지원한다. 아이콘은 기존 캔버스 SVG를 공통 컴포넌트로 추출한다.
- 대시보드는 빈 상태와 다음 행동 안내만 제공한다. 집계·목록 API는 요청하지 않는다.
- 다른 마일스톤의 본문은 기존 임시 화면을 유지하되 실제 앱 셸 안에서 이동할 수 있게 한다.

## 4. 검증과 완료 기준

- **인증:** 가입 성공, 중복 이메일, 잘못된 자격 증명, 중복 제출 방지, 0/1/복수 공간 분기, 재방문 이동 정책.
- **온보딩:** 전 단계 연결, 전 단계 건너뛰기, Discord 건너뛰기의 팀원 단계 연쇄 처리(2026-09-29 D-173 개정 — 연쇄 없이 팀원 연결 단계가 온다), 중간 저장 실패·재시도, 생성 중복 방지.
- **팀원:** 기존 PM 연결, 중복 매핑 차단, 부분 저장·완료, 일부 요청 실패 후 재시도.
- **복귀·권한:** 새로고침·재로그인·OAuth 왕복 후 재개, 기존 공간으로 복귀, 미완료 대시보드 차단, 일반 팀원 수정 차단.
- **전환:** 미저장 변경 시 취소·이동, 전환 후 이전 공간 데이터 비노출.
- Playwright Chromium E2E로 가입부터 대시보드까지, 기존 사용자 선택·전환, 진행 상태 복원을 검증한다. MSW가 개발 모드에서만 동작하므로 E2E는 Vite 개발 서버로 실행한다.
- Storybook에 M2 공통 UI와 M4 폼·메뉴·온보딩의 기본·로딩·오류·비활성 상태를 추가한다.
- 기존 검사에 `build-storybook`과 `test:e2e`를 추가한다. CI에서 기존 검사 통과 후 앱·Storybook 빌드와 E2E를 실행하고 실패 시 브라우저 trace를 보관한다.
- 1024·1280·1440px에서 레이아웃과 키보드 조작을 확인한다.

## 5. 문서와 구현 단위

구현은 **① API·MSW 기반 → ② 인증 → ③ 온보딩·팀원 연결 → ④ 선택·앱 셸 → ⑤ Storybook·E2E** 순서로 나눈다. 각 단위에서 관련 통합 테스트를 함께 추가한다.

- 가입 폼 범위 조정(비밀번호 강도·약관 동의 제외)과 MSW 저장·OAuth 모의 처리 방식을 `../impl-decision/`에 구현 결정 문서로 남긴다.
- 실제 API 제약 표를 현재 백엔드 소스 기준으로 갱신한다.
- 완료 판정은 **MSW 환경의 전체 흐름과 CI 통과**이며 실제 OAuth 연동 완료와는 구분해 기록한다.

## 6. 완료 판정 (2026-09-29)

**완료 판정은 MSW 환경의 전체 흐름과 CI 통과다.** 실제 OAuth 연동 완료와 구분한다.

### 완료된 것 — MSW 환경 + CI

- 흐름: 랜딩 → 로그인·회원가입 → 온보딩 4단계(모의 OAuth 포함) → 새 공간 대시보드, 워크스페이스 선택·전환(미저장 변경 확인),
  새로고침·OAuth 왕복 뒤 진행 상태 복원. 모두 브라우저 MSW(비로그인 시작, sessionStorage 버전 키 영속)로 동작한다.
- 검사: `typecheck` · `lint` · `format:check` · `test`(Vitest, MSW + 실제 `request` 경로) · `build` · `build-storybook` · `test:e2e`.
- E2E(Playwright Chromium, Vite 개발 서버 + MSW — `e2e/`):
  - `signup-onboarding.e2e.ts` — ① 가입 → 전 단계(Discord·Notion 모의 OAuth) → 대시보드, OAuth 취소 → 건너뛰기 연쇄(2026-09-29 D-173 개정 — Notion 뒤 팀원 연결 미연결 안내 → `건너뛰기`)
  - `select-switch.e2e.ts` — ② 로그인 → 선택 화면 → 진입 → 미저장 변경이 있는 전환(계속 작성하기·버리고 나가기), 키보드만으로 메뉴 조작
  - `restore.e2e.ts` — ③ 가입·생성·단계가 새로고침 뒤 복원, OAuth 왕복 뒤 복원, 손상된 저장값은 비로그인 시작
  - `layout.e2e.ts` — 1024·1280·1440px 에서 랜딩·로그인·회원가입·선택·온보딩·대시보드의 가로 스크롤 없음, 헤더 76px 한 줄(스크린샷 첨부)
- CI(`.github/workflows/frontend-ci.yml`): `check` 통과 뒤 앱 빌드·Storybook 빌드·E2E 를 병렬로 돌리고, E2E 실패 시 trace·HTML 리포트를 올린다.
- 구현 결정 기록: `../impl-decision/` 의 2026-09-28 `landing-scope` · `onboarding-layout`, 2026-09-29 `signup-scope` ·
  `msw-storage-oauth-mock` · `app-shell-scope` · `modal-inset-zero` · `storybook-e2e-setup`.

### 완료되지 않은 것 — 실 API

- **실제 OAuth 는 연동하지 않았다.** 백엔드에 Google 로그인과 Discord·Notion 연동의 `start`·`callback` 이 없다(`backend/app/main.py` 라우터 목록).
  Google 버튼은 비활성이고, Discord·Notion 은 개발·MSW 모드의 모의 OAuth 화면(`/__mock/oauth/:workspaceId/:provider`)으로만 연결된다.
  복귀 파라미터 `?oauth=&oauth_result=` 는 실 콜백이 없어 둔 프론트엔드 가정이다.
- 온보딩 단계 저장은 실 백엔드에서 스텁이다 — 단계별 상태·건너뛰기·재개는 MSW 로만 검증됐다. Discord 사용자 목록도 스텁이다.
  제약 표는 `frontend-development-plan.md` M4 절 "실 API 제약"(2026-09-29 갱신)에 있다.
- 대시보드는 빈 상태·다음 행동 안내만이다. 집계·목록·되돌리기는 M7 이다.
