# M6 계획 — 태스크 목록·상세·확인 필요 승인

- 작성일: 2026-10-08
- 상태: 구현 전 계획. 완료 판정과 테스트 성공 기록은 포함하지 않는다.
- 계획 근거: 사용자가 지정한 M6 범위와 기본값, 현재 작업 트리의 코드·계약, M5 인수인계.

## 목표와 배경

PM이 확인 필요 항목의 근거를 읽고, 누락 정보를 보완한 뒤 승인·반려할 수 있게 한다. 승인으로 생성·변경된 태스크와 실제 응답에 따른 Notion `반영됨` 상태까지 확인한다. 일반 팀원에게는 태스크 목록·상세를 읽기 전용으로 제공한다.

현재 태스크 목록·상세는 같은 자리표시자 화면을 사용한다. 확인 필요 상세에는 PM 가드와 조회가 있지만 보완·승인·반려는 없다. 기존 태스크·승인 도메인 모델, DTO 매퍼, 날짜 판정, PM 가드와 M5 회의록 링크를 활용한다.

[전체 계획](../frontend-plan.md)의 M6를 구체화한다. 전체 계획과 과거 결정에 남은 오래된 표현은 후속 결정과 현재 코드로 보완한다. 특히 D-162에 따라 확인 필요 항목은 태스크 상태가 아닌 별도 승인 리소스이며, `approval_id`로 식별하고 `/workspaces/:workspaceId/approvals/:approvalId`에서 처리한다. 전체 계획 원문은 수정하지 않는다.

## 구현 범위와 제외 범위

### 구현 범위

- 역할별 태스크 목록·상세, 대기 승인과 태스크의 병합·정렬, URL 탭·날짜 조건.
- 태스크 상세의 담당자·상태·마감·진행률·막힌 사유·연결 회의·변경 이력 조회와 PM의 상태 변경.
- 생성 승인의 근거 확인과 제목·담당자·마감 보완, 변경 승인의 현재값·제안값 비교, 승인·반려·충돌 재확인.
- 버전·Notion 상태·세션 기반 처리자·PM 쓰기 권한에 대한 프론트 계약·타입·MSW 정비.
- 실제 `notion_sync_status`에 따른 표기, 열린 상세의 polling, PM의 반영 실패 재시도.
- Storybook·통합 테스트·E2E, M4·M5 회귀, 구현 후 결과·계약·실제 선택 기록.

생성 승인에는 **제목·담당자·마감 모두 필수**다. 이 규칙은 이번 사용자 선택이며, 기존 일반 태스크에는 담당자·마감 필수를 소급 적용하지 않는다. 승인 보완은 **프론트 계약·MSW를 먼저 구현**하고 백엔드 지원을 별도 연동 조건으로 남긴다.

### 제외 범위

- 일반 태스크의 제목·담당자·마감·진행률·막힌 사유 편집과 시작일 편집.
- 보드·간트·캘린더, 일반 필터·검색·페이지네이션과 사용자가 고르는 정렬.
- 수동 태스크 생성·삭제, 하위 태스크 분할, 되돌리기, 대시보드 완성.
- 백엔드 코드 수정. 보완 API 지원과 승인 조회의 PM 제한은 요청·연동 조건으로 기록한다.

## 구현 순서

### 1. 계약·데이터 계층 정비

1. `entities/task`에 목록·상세·이력 Query 옵션과 상태 변경·Notion 재시도 API를 추가한다. 목록과 상세는 workspace 범위의 공통 캐시 규약을 공유하고, DTO 변환은 엔티티 내부에서 수행한다. 공간이 없는 단건 API 응답도 요청한 workspace와 일치하는지 확인한다.
2. Task DTO·모델에 서버의 `version`, `notion_sync_status`를 반영한다. Notion 상태는 `pending | synced | failed | null`로 다루며, `notion_page_id` 존재만으로 완료를 판단하지 않는다.
3. 승인 처리 API에 `confirm_task_version`과 409 `APPROVAL_CONFLICT`의 `details.task_version`, `conflicts` 처리를 반영한다. 처리자·변경자 ID는 서버처럼 현재 세션에서 결정하며 프론트가 생성해 보내지 않는다.
4. 생성 승인 보완의 **미합의 요청안**은 기존 `PATCH /approvals/{approval_id}`에 다음 입력을 추가하는 방식으로 고정한다. `approved`·`task_create`에만 사용하며, 보완값 적용·승인·태스크 생성·추출 연결은 한 번의 원자적 처리로 요구한다.

   ```json
   {
     "status": "approved",
     "task_overrides": {
       "task_title": "확정할 제목",
       "assignee_member_id": "현재 공간의 팀원 ID",
       "due_date": "2026-10-15"
     }
   }
   ```

5. 대표 계약에 현재 서버 구현과 보완 요청안을 구분해 기록한다. 보완 지원·원자성·필수값 검증 및 승인 목록·상세 조회의 PM 제한을 백엔드 요청으로 남긴다. 실제 요청·합의·실행 검증 상태를 추정하지 않는다.
6. 보완 API 지원은 개발 MSW에서만 활성화한다. 실 API에서는 수정 입력을 제공하지 않고, 기존 값이 필수조건을 충족하는 승인·반려만 사용한다. 미지원 필드가 조용히 무시된 채 승인되는 요청을 보내지 않는다. 누락 정보 때문에 승인할 수 없는 항목에는 연동 한계를 안내한다.

**산출물:** 엔티티 API·Query 옵션, DTO·매퍼·오류 타입, 대표 계약의 코드 대조·미합의 요청안·연동 조건. **대응:** AC-01, AC-05, AC-06.

### 2. MSW 수직 흐름 구성

1. Task 버전·Notion 상태, 세션 기반 변경자·처리자, PM 쓰기 권한, 승인 중복 처리·충돌을 현재 백엔드 의미에 맞춘다. 버전 증가와 충돌의 필드 비교는 서버 구현을 기준으로 한다.
2. 생성 승인 보완은 위 요청안으로 구현한다. 최종 제목·담당자·마감의 필수값, 같은 공간의 담당자, 연결 회의·추출 항목의 소속 및 해당 승인과의 연결을 검증한 뒤 전체 변경을 적용한다. 실패하면 승인·태스크·이력·추출 연결에 부분 변경을 남기지 않는다.
3. 승인 후 추출 항목에는 `task_id`를 채운다. 서버처럼 `approval_id`는 남을 수 있으므로, PM의 확인 필요 판정은 열린 승인 목록과 조인한다. 링크는 `task_id`를 우선한다. 반려는 태스크를 만들지 않는다.
4. 정상·빈 목록·누락 정보·반려·이미 처리됨·충돌·Notion 대기/실패/재시도·일반 팀원 시나리오를 추가한다. 테스트에서는 전이를 명시적으로 제어한다. 브라우저 데모는 기존 sessionStorage 영속 방식에 통합하고 저장 구조 변경 시 기존 복원 정책과 회귀를 확인한다.

**산출물:** handler·상태·픽스처·시나리오·영속 흐름, 권한·중복·원자성·충돌·Notion 전이 테스트. **대응:** AC-01, AC-02, AC-05, AC-06, AC-07.

### 3. 태스크 목록·상세 구현

1. 목록과 상세 라우트를 분리하되 `/workspaces/:workspaceId/tasks`와 `/workspaces/:workspaceId/tasks/:taskId` URL은 유지한다.
2. PM은 `전체/확인 필요/진행 중/완료`, 일반 팀원은 `전체/진행 중/완료` 탭을 본다. `todo/in_progress/blocked`는 진행 중에 포함한다. 일반 팀원은 승인 API를 호출하지 않는다.
3. PM의 전체 목록은 대기 승인을 먼저 표시하고 태스크를 이어 붙인다. 승인은 대기 시작 오래된 순, 태스크는 마감 오름차순·마감 없는 항목 마지막·동률 생성시각 내림차순으로 정렬한다. 역할과 조건에 맞는 개수를 표시하며, 목록·탭 개수 판정을 공통 로직으로 검증한다.
4. 탭은 URL의 `tab`에 기존 `all/needs_review/in_progress/done` 값을 사용한다. D-046의 날짜 조합은 `due=overdue,soon`으로 표현한다. 날짜 조건은 미완료 태스크에 적용하고 승인 항목에는 적용하지 않는다. 서울 오늘부터 6일 뒤까지, 오늘 포함 7개 날짜를 `soon`으로 판정한다. 새로고침·뒤로가기에서도 복원하고 해제 액션을 제공한다. 최초 탭은 `전체`다.
5. 상세에는 담당자·상태·마감·진행률·막힌 사유·연결 회의·변경 이력을 표시한다. 담당자·마감이 없는 기존 태스크도 읽을 수 있어야 한다. PM만 상태를 변경하며 다른 필드 편집은 제공하지 않는다.
6. 상태 변경만 낙관적으로 목록·상세에 적용한다. 같은 태스크의 요청 중 중복 변경을 막는다. 실패 시 해당 태스크만 복구하고 오류 안내 후 재조회한다. 목록 전체 스냅샷 복원으로 다른 태스크의 동시 변경을 되돌리지 않는다. 성공·실패 뒤 목록·상세·이력을 서버와 맞춘다.
7. 공간 전환·로그아웃·권한 변경 이후 늦은 조회·mutation 응답이 이전 화면, 캐시, 알림을 복원하지 않도록 기존 요청 취소·세션 경계를 적용한다.

**산출물:** 목록·상세 페이지, 역할별 탭·개수·정렬, URL 조건, 상태 변경 기능과 경합 검증. **대응:** AC-02, AC-03, AC-04, AC-10.

### 4. 확인 필요 상세·Notion 상태 구현

1. 최초 진입은 읽기 상태다. 개발 MSW에서 PM이 `보완하기`를 눌러 생성 승인의 제목·담당자·마감을 수정한다. 자동 편집 열기는 사용하지 않는다. 미저장 변경에는 기존 이탈 확인을 적용한다.
2. 제목은 앞뒤 공백 제거 후 1~300자, 담당자는 현재 공간의 등록 팀원, 마감은 유효한 `YYYY-MM-DD` 날짜여야 한다. 원문 담당자·마감과 인용·화자·시각은 확정값과 구분해 표시한다. 누락·유효하지 않은 입력은 필드에 연결된 오류로 안내한다.
3. `task_update`는 현재값과 제안값을 비교해 승인·반려한다. `APPROVAL_CONFLICT`에서는 기준값·현재값·제안값과 충돌 필드를 보여 준다. PM이 명시적으로 재승인할 때만 서버가 반환한 버전을 `confirm_task_version`으로 보낸다. 그 뒤 다시 바뀌면 새 충돌을 표시하고 다시 확인한다. 충돌 확인을 자동 재시도로 대신하지 않는다.
4. 지원하지 않는 승인 종류는 읽기 전용으로 표시하고 승인 액션을 제공하지 않는다. 이미 처리된 승인은 재처리하지 않고 현재 결과를 보여 준다.
5. 승인·반려는 서버 성공 후 반영한다. 승인 성공 시 같은 상세에 처리 결과와 생성·변경된 태스크 링크를 남긴다. 반려는 태스크를 만들지 않는다. 요청 중 승인·반려의 중복 클릭과 자동 mutation 재시도를 막는다.
6. 성공 후 승인 목록·상세, 태스크 목록·상세·이력, 관련 추출 캐시를 무효화해 회의록과 목록을 갱신한다. `approval_id`가 남아 있어도 닫힌 승인은 확인 필요로 남지 않아야 한다.
7. Notion은 `pending → 반영 중`, `synced → 반영됨`, `failed → 반영 실패`, `null → 반영 상태 없음`으로 표시한다. 승인 성공이나 `notion_page_id` 존재만으로 `반영됨`을 표시하지 않는다.
8. 열린 태스크 상세 또는 승인 결과에서 `pending`인 동안 3초 간격으로 태스크를 조회한다. 종료 상태·화면 이탈·접근 상실에는 polling을 멈춘다. `failed`이면 PM에게 기존 `POST /tasks/{task_id}/notion-sync/retry` API를 연결한다. 재시도 성공으로 반환된 상태를 표시하고 실제 `synced` 응답까지 기다린다.
9. 일반 팀원의 승인 URL 직접 접근은 목록으로 이동하고 `접근 권한이 없어요`를 표시한다. 승인 상세 조회가 시작되기 전에 가드가 차단해야 한다.

**산출물:** 근거·보완 폼, 승인·반려·충돌 확인·결과 화면, 캐시 무효화, Notion 상태·polling·재시도. **대응:** AC-05, AC-06, AC-07, AC-08, AC-09.

### 경계·경합 검증

- 날짜: 서울 자정 전후, 과거·오늘·기간 끝(오늘+6일)·다음 날(오늘+7일), 마감 없음·완료 상태를 포함한다. 시간대에 따라 날짜 조건이 달라지지 않는지 확인한다.
- 목록: PM 대기 승인 우선, 승인 대기 오래된 순, 태스크 마감 없는 항목 마지막·동률 생성시각 내림차순, 일반 팀원의 승인 요청 0회와 승인 제외를 확인한다.
- 상태 변경: 같은 태스크의 중복 요청, 서로 다른 태스크의 동시 변경 중 한 요청 실패, 진행 중 조회와의 경합을 확인한다.
- 승인: 필수값 누락·잘못된 날짜·다른 공간 담당자·잘못된 추출 연결·중복 클릭·이미 처리됨·연속 충돌에 대해 데이터와 요청 횟수를 단언한다.
- Notion: `pending → synced`, `pending → failed → 재시도 → pending → synced`, `null`을 명시적으로 제어한다. 화면 이탈·종료 상태 뒤 추가 polling이 없는지 확인한다.
- 세션·공간·권한: 전환·로그아웃·권한 변경 이후 늦은 응답이 이전 화면이나 캐시를 복원하지 않는지 확인한다. M5의 늦은 비동기 응답 회귀를 함께 유지한다.

### 최종 게이트

Node 24 환경에서 깨끗한 의존성 설치 후, `frontend/`에서 아래 명령을 **순차 실행**한다. 각 명령의 실제 결과를 따로 기록하고 테스트 단언을 통과시키기 위한 임의 완화는 하지 않는다.

```bash
npm ci
npm run typecheck
npm run lint
npm run format:check
npm run test
npm run build
npm run build-storybook
npm run test:e2e
npm run test:storybook
```

M4·M5 회귀를 포함하고 production 앱 번들에 MSW 시나리오·픽스처·등록 코드가 없는지 점검한다. 기존 `mockServiceWorker.js` 정적 파일 포함 정책은 M5 인수인계를 따른다. 실제 Notion 데이터 반영은 테스트 계정으로 별도 수동 검증하며, 자동 E2E 성공으로 대체하지 않는다.

## 위험 및 미결 사항

- **보완 API 미지원:** `task_overrides`는 미합의 요청안이며 현재 서버가 받는 입력이 아니다. 보완 후 승인 완료 판정은 MSW 기준으로 한정한다. 백엔드 지원·원자성·필수값 검증의 합의와 실제 연동 검증은 별도 상태로 남긴다.
- **승인 조회 권한 차이:** 현재 서버 목록·상세 조회는 공간 소속 검사이며 PM 제한이 없다. 프론트 가드와 요청 차단을 구현하더라도 서버의 PM 조회 제한 지원 여부는 별도로 기록한다.
- **Notion 비동기 반영:** 승인 성공과 Notion 완료는 다르다. 서버 상태·재시도 API에 맞추되 실제 외부 반영은 수동 검증 전까지 성공으로 선언하지 않는다.
- **기존 계약의 과거 상태:** 대표 계약의 과거 스텁·권한·요청 기록을 현재 구현 사실로 읽지 않는다. 최신 코드 대조와 미합의 요청을 구분한다.
- **캐시·요청 경합:** 상태 변경의 복구 범위를 해당 태스크로 제한하고, 세션·workspace·권한이 바뀐 이후 응답 처리를 검증한다. 같은 문제가 M5에서 반복된 근거를 회귀에 활용한다.

이번 계획의 기본값은 최초 `전체` 탭, 승인 상세 읽기 진입, 자동 편집 열기 없음, 서울 오늘 포함 7개 날짜다. 사용자 범위 선택은 확정됐으며, 남은 연동 조건은 백엔드 보완 지원·승인 조회 PM 제한과 실제 Notion 검증이다.
