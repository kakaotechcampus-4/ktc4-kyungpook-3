# Notion 반영 polling은 조회 오류 뒤 화면 재진입까지 멈춘다

- 기록일: 2026-10-11
- 관련 마일스톤: M6 (구현 순서 4-8 — 열린 상세의 polling. 선택은 S4 구현 커밋 `8a8784a`에 들어 있다)

## 문제와 제약

승인 성공과 Notion 반영 완료는 다르다. 태스크의 `notion_sync_status`가 `pending`인 동안 열린 태스크 상세나 승인 결과에서 3초마다 그 태스크를 다시 조회해 `synced`·`failed`를 기다린다.

- [계획](../plan.md) §4-8은 종료 상태·화면 이탈·**접근 상실**에 polling을 멈추게 한다.
- 조회는 서버의 접근 거절(403, 404)뿐 아니라 일시적 네트워크 오류로도 실패할 수 있다. 앱 공통 Query 정책은 네트워크 오류·408·5xx를 1초 뒤 한 번만 다시 묻는다([queryClient](../../../../src/shared/api/queryClient.ts)).

## 실제 검토한 선택지

S4 구현 보고서(감독 보관, 2026-10-11)는 이 선택을 「조회 오류 시 멈추는 선택(일시적 네트워크 오류 뒤에도 멈춘다 — 화면 재진입·새로고침으로 다시 시작)」으로 S5 기록 후보에 올렸다. 오류 종류별로 다르게 처리하는 방식 등을 비교한 기록은 없다 — **대안 검토 기록 없음**.

## 선택과 이유

`notionSyncRefetchInterval`은 조회 상태가 `error`면 오류 종류와 무관하게 `false`를 돌려 polling을 멈춘다. 다시 시작하는 것은 화면을 다시 열거나 새로고침해 조회가 성공하고 그 결과가 `pending`일 때다.

- 계획의 「접근 상실 시 중단」을 오류 코드 판별 없이 지킨다. 권한을 잃은 화면이 3초마다 거절 요청을 계속 보내지 않는다.
- 일시적 오류에는 공통 Query 정책의 1회 재요청이 먼저 적용된다. 그것까지 실패한 뒤에만 멈춘다.

코드 근거:

- [useTaskNotionSync](../../../../src/features/task-notion-sync/model/useTaskNotionSync.ts)의 `notionSyncRefetchInterval` — `query.state.status === 'error'`이면 `false`, `pending`이면 `NOTION_SYNC_POLL_MS`(3초), 그 밖에는 `false`.
- polling은 상세 Query key에 붙은 추가 관찰자라 화면을 떠나 컴포넌트가 사라지면 간격도 함께 사라진다.

감독의 S4 승인 기록(2026-10-11)은 이 선택이 계획의 중단 조건을 깨지 않는다고 적었다.

## 장단점과 감수한 제약

- 장점: 접근을 잃었거나 서버가 계속 실패할 때 요청이 쌓이지 않는다. 오류 판별 규칙을 따로 두지 않아 단순하다.
- 감수한 제약: 일시적 네트워크 오류가 공통 재요청 1회까지 실패하면, 네트워크가 돌아와도 화면은 마지막으로 받은 상태(`반영 중`)에 머문다. 사용자가 화면을 다시 열거나 새로고침해야 다시 확인한다.

## 영향 범위와 재검토 조건

- 영향: 태스크 상세의 Notion 칸, 확인 필요 상세의 처리 결과(생성·변경된 태스크의 Notion 상태).
- 재검토: 일시적 오류 뒤 `반영 중`에 머무는 문제가 실제 사용에서 보고되거나, 서버가 반영 완료를 알리는 다른 수단(푸시 등)을 제공하면 다시 본다.
