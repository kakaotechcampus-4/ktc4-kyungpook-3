# 생성 승인 보완값을 승인 요청 때까지 화면에 둔다

- 기록일: 2026-10-11
- 관련 마일스톤: M6 (구현 순서 4 — 확인 필요 상세. 선택은 S4 구현 커밋 `8a8784a`에 들어 있다)

## 문제와 제약

생성 승인(`task_create`)은 제목·담당자·마감이 모두 있어야 승인할 수 있다. 회의에서 나온 승인은 담당자나 마감이 빠진 경우가 많아, PM이 `보완하기`로 값을 고친 뒤 승인한다.

- [계획](../plan.md) §1-4는 보완값 적용·승인·태스크 생성·추출 연결을 **한 번의 원자적 처리**로 요구한다. §2-2는 실패하면 승인·태스크·이력·추출 연결에 부분 변경을 남기지 않게 한다.
- 현재 서버에는 승인 payload를 미리 고치는 API가 없다. 보완 입력 `task_overrides`는 프론트가 고정한 미합의 요청안이며 기존 `PATCH /approvals/{approval_id}` 본문에 붙는다([대표 계약](../../../contracts/frontend-api-contract.md) 「M6 태스크·승인 처리 경계」).
- 실 API(transport `live`)에는 보완 입력을 보내지 않는다(§1-6).

## 실제 검토한 선택지

S4 구현 보고서(감독 보관, 2026-10-11)는 이 선택을 「보완값을 서버 저장 없이 화면 상태로 확정해 승인 한 번에 싣는 선택」으로 S5 기록 후보에 올렸다. 다른 대안(예: 보완값을 먼저 서버에 저장하는 별도 요청)을 비교한 기록은 없다 — **대안 검토 기록 없음**.

## 선택과 이유

`보완 완료`는 서버로 아무것도 보내지 않는다. 검사를 통과한 값을 확인 필요 상세의 화면 상태로 확정만 하고, PM이 `승인`을 누를 때 그 값을 `task_overrides`로 승인 요청 한 번에 함께 싣는다.

- 계획이 요구한 원자성을 요청 하나로 지킨다. 보완값만 저장되고 승인이 실패해 데이터가 어긋나는 중간 상태가 생기지 않는다.
- 보완값을 받는 별도 서버 API가 없다. 요청안도 승인 본문에 붙는 형태다.

코드 근거:

- [ApprovalReview](../../../../src/widgets/approval-review/ui/ApprovalReview.tsx)의 `TaskCreateReview`가 `overrides`를 상태로 들고, 승인 때 `transport === 'msw'`일 때만 `resolver.resolve(..., { overrides })`로 넘긴다. 반려는 보완값을 싣지 않는다.
- [TaskCreateOverridesForm](../../../../src/features/approval-resolve/ui/TaskCreateOverridesForm.tsx)의 `confirm`은 `onConfirm`만 부른다(「서버로 보내지 않는다」 주석).
- 확정한 보완값 아래에 `보완한 값이에요. 승인해야 저장돼요.`를 보이고, 승인 전까지 `useUnsavedChanges(pending && overrides !== null)`로 기존 이탈 확인을 건다. 폼이 열려 있는 동안 바꾼 값도 `useUnsavedChanges(isDirty)`로 같다.

## 장단점과 감수한 제약

- 장점: 부분 저장이 없다. 서버가 승인을 거절해도(예: 다른 공간 담당자, 추출 항목 미연결) 보완값은 화면에 남아 다시 고칠 수 있다. 이 동작은 S4 통합 테스트가 승인·태스크·이력·추출 스냅샷 동일과 보완값 유지로 확인했다.
- 감수한 제약: 승인하지 않고 화면을 떠나면 보완값이 사라진다. 이탈 확인으로 알리지만 다른 PM과 보완값을 공유하거나 나중에 이어 쓸 수 없다.
- 실 API에서는 보완 자체가 없다. 필수값이 빠진 생성 승인은 `승인`이 꺼지고 사유를 보인다.

## 영향 범위와 재검토 조건

- 영향: 확인 필요 상세 화면, 승인 처리 기능, MSW 승인 handler(보완값 적용과 승인을 함께 처리).
- 재검토: 백엔드가 `task_overrides`(계약 요청 M6-1·M6-2)를 다른 형태로 합의하거나, 보완값을 먼저 저장하는 API를 제공하면 다시 본다.
