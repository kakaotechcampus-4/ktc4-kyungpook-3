# 확인 필요를 태스크 목록과 나란한 카드 구역으로 둔다

- 기록일: 2026-10-11
- 관련 마일스톤: M6 (태스크 목록. 완료 검증이 미충족으로 본 뒤, 현재 목록 UI에 맞춰 다시 구현)

## 문제와 제약

목록 UI를 보드·캘린더·간트와 확인 필요 카드로 바꾼 뒤, 완료 검증은 AC-02·AC-05·AC-07·AC-09를 미충족으로 봤다. 사용자는 확인 필요 카드와 넓은 보기(보드·캘린더·간트)를 되돌리지 말고, AC-02·AC-05·AC-07은 그 화면에 맞게 다시 맞추고, 나머지 지적은 검증이 적은 대로 구현하라고 했다.

- [계획](../plan.md) §3-3은 PM 전체 목록에서 대기 승인을 태스크보다 먼저 보이게 한다. AC-02는 역할별 탭·개수·정렬과 팀원의 승인 조회 0회다.
- §1-6과 AC-05는 실 API에서 필수값이 빠진 생성 승인의 `승인`을 끄고, 버튼 가까이에 미지원 사유를 보이며, `반려`는 누를 수 있게 한다. 보완 입력은 보내지 않는다.
- §4-5·§4-8과 AC-07은 승인 성공 뒤 처리 결과와 생성된 태스크 링크를 남기고, `반영됨`은 조회가 `synced`일 때만 보이게 한다. 목록과 회의록은 같이 갱신된다.
- AC-09의 기존 E2E는 승인 제목 링크로 상세에 들어가고, `마감 조건` 그룹을 찾고, 목록 `main` 너비를 960px 이하·가운데로 본다.

## 실제 검토한 선택지

이번 구현에서 아래를 비교했다.

1. 새 보기 묶음을 빼고 승인을 태스크 목록의 `li[data-kind=approval]`로 되돌린다. 완료 검증이 완료 커밋에서 빼라고 한 쪽이다.
2. 확인 필요 카드 구역을 유지하고, 개수·정렬·승인 후 목록 일치는 그 구역과 그 아래 태스크 목록으로 확인한다.
3. 실 API 보류 카드는 접힌 모습을 유지하되 `승인`을 숨기고 반려 이름을 `제외`로 둔다. 또는 접힌 카드에도 비활성 `승인`·미지원 사유·`반려`를 둔다.
4. 목록 `main`만 960px로 좁힌다. 또는 보드·캘린더·간트까지 같은 폭으로 좁힌다.

1은 사용자가 현재 UI를 유지하라고 해서 선택하지 않았다.

## 선택과 이유

- 대기 승인은 `확인 필요 목록` 카드로 태스크 행보다 위에 둔다. 태스크 행은 `태스크 목록`에만 있다. 탭 개수·오래된 승인 순·마감 정렬·팀원 승인 조회 0회는 그대로다. 승인으로 닫힌 항목은 확인 필요에서 빠지고, 만들어진 태스크는 태스크 목록 링크로 나타난다.
- 생성 승인 카드의 제목은 승인 상세 링크다. 키보드로 그 링크에 들어가 상세에서 보완·승인한다.
- 실 API에서 필수값이 없으면 카드가 접혀 있어도 `승인`은 비활성이고, 사유는 `지금 서버는 승인 전 보완을 지원하지 않아요.`로 끝나며, 버튼 이름은 `반려`다. 개발 MSW의 접힌 보류 카드만 `직접 채우기`로 입력을 연다. 반려 본문에는 보완값을 싣지 않는다.
- 처리 결과·생성된 태스크 링크·`pending` polling은 승인 상세와 태스크 상세에 둔다. 목록 카드는 대기 줄이라, 승인에 성공하면 카드가 빠지고 태스크 목록이 갱신된다. `반영됨`은 `synced` 행과 상세에만 쓴다.
- 리스트 `main`은 `max-w-[960px]`로 가운데에 둔다. 마감 조건 드롭다운은 `role=group` 이름 `마감 조건`으로 감싼다. 보드·캘린더·간트의 `main`은 셸 폭(1360px)을 유지한다. AC-09가 측정하는 화면은 리스트·태스크 상세·승인 상세다.

## 장단점과 감수한 제약

확인 필요를 태스크 행 안에 다시 끼우지 않아도 개수와 승인 후 일치 여부를 확인할 수 있다. 실 API 보류 카드는 접힌 시안을 유지하면서 승인 비활성 계약을 지킨다.

보드·캘린더·간트 `main`은 960px를 넘는다. 그 보기에서 같은 너비 단언을 하면 실패한다. 목록에서 바로 승인한 뒤의 처리 결과 문장과 polling은 상세로 가야 본다.
