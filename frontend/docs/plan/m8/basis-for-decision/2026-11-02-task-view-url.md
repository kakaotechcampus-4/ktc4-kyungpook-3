# 태스크 보기 URL을 한 경로의 `?view=`로 유지하는 선택

- 기록일: 2026-11-02
- 관련 마일스톤: M8-A(#243), [계획](../plan.md) A 절 AC-A-01·구현 순서 1~2

## 문제와 제약

- [전체 계획](../../frontend-plan.md) M8은 보드·간트·캘린더에 대해 「보기 종류는 별도 경로로 표현하고 URL 파라미터에 중복하지 않음(D-132)」이라고 적었다.
- [결정 문서](../../../decision/frontend-decisions.md)의 D-132 원문(결정 요약)은 「별도 경로로 표현된 보기 종류는 URL 파라미터에 중복하지 않고」이다. 같은 결정은 새로고침·뒤로가기·URL 공유로 복원할 상태를 URL 검색 파라미터로 관리하고, 페이지 경계에서 한 번 검증·해석하라고 적는다.
- develop의 코드는 한 경로 `/workspaces/:workspaceId/tasks`에서 `?view=list|board|calendar|gantt`로 보기를 고른다. 이 브랜치도 그 해석을 바꾸지 않았다.
- M8 계획은 이 차이를 「확인 필요」로 두었다. 사용자 확인 전까지 AC-A-01을 미해결로 두었다([결과 A](../result-a.md)).

## 실제 검토한 선택지

M8 계획의 질문에 적힌 두 선택지다.

1. 현재 `?view=` 방식을 유지하고 결정 근거를 보완한다.
2. 전체 계획 M8대로 별도 경로로 옮긴다. 이 경우 구체 경로와 기존 `?view=` 링크 처리 방침도 함께 정한다.

## 선택과 이유

1을 택했다. 사용자 결정이다(2026-11-02, 코디네이터 전달). 별도 경로로 옮기지 않으며 코드는 바꾸지 않는다. 사용자가 밝힌 선택 이유는 전달받지 않았다. 아래는 유지했을 때의 현재 동작을 코드·테스트에서 확인한 사실이다.

**코드에서 확인한 것**

- [taskViews](../../../../src/widgets/task-board/lib/taskViews.ts)의 `readViewQuery`는 `view`·`assignee`·`month`·`from`·`period`를 URL에서 읽는다. 모르는 값은 기본값(`list`, 담당자 전체, 전체 기간)이 된다. `viewSearch`는 기본값을 적지 않고, 탭·날짜 조건(`tab`·`due`) 등 다른 파라미터는 그대로 둔다.
- [TasksPage](../../../../src/pages/tasks/ui/TasksPage.tsx)는 렌더할 때마다 `readViewQuery(searchParams)`로 보기를 정한다. 보기를 따로 담는 저장소는 없다. 그래서 같은 주소로 다시 열면 URL의 보기로 그린다.
- 보기를 바꾸면 `onViewChange`가 `replace` 없이 `navigate({ pathname, search })`를 부른다. 같은 경로 안의 이동이라 이탈 확인 없이 새 기록 항목이 생긴다(`useGuardedNavigate`).

**테스트에서 확인한 것**

- URL 읽기·쓰기: [taskViews.test.ts](../../../../src/widgets/task-board/lib/taskViews.test.ts)의 「보기 조건 URL」 3건. 기본값과 모르는 값, 쓴 값 되읽기와 탭·날짜 조건 보존, 기본값 복귀 때 파라미터 제거를 확인한다.
- 직접 진입: [task-views.e2e.ts](../../../../e2e/task-views.e2e.ts)는 `?view=board|calendar|gantt&month=2026-09&from=2026-09-14` 주소로 바로 들어간다(V3 9/9 통과, 결과 A 기록). Vitest의 [taskViewsCodeSplit.test.tsx](../../../../src/app/taskViewsCodeSplit.test.tsx) 「캘린더 주소로 바로 들어오면」, [taskViews.test.tsx](../../../../src/app/taskViews.test.tsx)·`taskViewsRender.test.tsx`·`taskViewsCreate.test.tsx`도 `?view=` 주소로 시작한다.
- 새로고침·뒤로가기: [tasks.test.tsx](../../../../src/app/tasks.test.tsx)에 같은 페이지의 새로고침·`history.back()` 테스트가 있다. 그러나 이 테스트는 탭·날짜 조건(`tab`·`due`)만 단언하고 `view`는 단언하지 않는다. **보기(`view`) 파라미터의 새로고침·뒤로가기 복원을 단언하는 테스트는 찾지 못했다.** 위 코드 구조로 같은 방식이라고 볼 수 있지만, 테스트로 확인한 사실은 아니다.
- 이 기록 작업에서는 테스트를 다시 실행하지 않았다. 통과 이력은 결과 A의 게이트 기록이다.

## D-132와의 관계

- D-132의 「중복하지 않는다」는 보기 종류를 별도 경로로 표현한 경우의 조건이다. 이번 선택은 별도 경로를 쓰지 않는다. 보기 종류는 `?view=` 한 곳에만 표현되므로 그 조건의 중복에는 해당하지 않는다고 판단한다.
- 보기를 URL 검색 파라미터로 두고 페이지 경계(`TasksPage`)에서 한 번 해석하는 방식은 D-132의 다른 문구(복원할 상태는 URL로, 페이지 경계에서 한 번 검증·해석)와 어긋나지 않는다.
- 다만 전체 계획 M8의 「보기 종류는 별도 경로로 표현」 문구는 이 선택과 다르다. 전체 계획과 결정 문서 D-132의 문구 갱신은 사람이 할 일로 남긴다. 이 기록은 두 문서를 수정하지 않는다.

## 장단점과 감수한 제약

- 코드·라우트·기존 링크를 바꾸지 않는다. 별도 경로 이전에 따른 기존 링크 처리 방침이 필요 없다.
- 전체 계획·결정 문서의 문구가 갱신되기 전까지는 문서와 구현이 다르게 읽힌다.
- 보기 파라미터만의 새로고침·뒤로가기 회귀 테스트가 없다. 지금은 코드 구조와 탭·날짜 조건 테스트에 기대고 있다.

## 영향 범위와 재검토 조건

- 영향: 기존 `/workspaces/:id/tasks?view=…` 링크는 그대로 동작한다. 바뀌는 링크는 없다. 코드 변경 없음.
- 재검토: 보기마다 다른 라우트 단위 기능(별도 권한·로더·메타 정보 등)이 필요해지거나, 사람이 전체 계획·D-132 문구를 별도 경로 쪽으로 확정하면 다시 정한다. 그때는 기존 `?view=` 링크 처리 방침을 함께 정한다.
