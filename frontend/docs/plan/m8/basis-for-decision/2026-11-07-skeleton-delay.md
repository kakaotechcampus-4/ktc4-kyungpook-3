# 화면 안 로딩 스켈레톤의 지연·최소 표시 규칙 (D-129 보완, #508)

- 기록일: 2026-11-07
- 관련 마일스톤: 마일스톤 밖 작업(#508). 결과는 [#508 결과](../../../issues/508-skeleton-delay/result.md)

## 문제와 제약

- D-129 는 API 로딩을 화면 안에서 `isPending` 으로 처리한다고만 정했다. 그래서 화면마다 `isPending` 이면 바로 스켈레톤을 그렸다.
- 사용자 말(2026-11-07): 네트워크가 빨라서 스켈레톤이 잠깐 나왔다 사라지며 깜빡인다. 150ms 응답도 스켈레톤 → 내용으로 두 번 바뀌고, 뼈대가 한두 프레임만 번쩍인다.
- 값은 사용자가 정했다(이슈 #508 본문): 200ms 까지는 같은 높이의 빈 자리, 넘으면 스켈레톤을 보이고 한 번 보이면 400ms 유지, 내용은 150ms 불투명도 전환(`prefers-reduced-motion` 이면 끔), 빈 자리 구간에도 컨테이너 `aria-busy`.
- 제약: 화면 코드·가드를 기다리는 라우트 뼈대(`RouteSkeleton`)에는 넣지 않는다. 스플래시가 그 뼈대를 잡기 신호(`useSplashHold`)로 쓴다. 저장 표시용 `useShownAfter`(지연만, 최소 표시 없음)는 바꾸지 않는다.

## 실제 검토한 선택지

규칙 값과 적용 범위는 사용자가 정했다. 구현에서 견준 것은 아래와 같다.

- 빈 자리: 뼈대를 그리지 않고 높이만 잡은 빈 상자 / 뼈대를 그리되 `visibility: hidden`.
- 최소 표시: 데이터가 와도 붙잡는 동안 내용을 그리지 않는다 / 내용 위에 뼈대를 겹친다.
- 전환: 내용 바깥에 감싸는 상자를 둔다 / `display: contents` 상자로 감싸고 자식에 애니메이션을 건다 / 자리마다 바깥 요소에 클래스를 붙인다.
- 라우트 뼈대에서 넘어올 때: 규칙 그대로(뼈대 → 빈 자리 → 뼈대) / 라우트 뼈대가 그려진 채 로딩으로 시작하면 뼈대를 이어받는다.

## 선택과 이유

| 결정 | 고른 길 | 버린 대안과 이유 |
|---|---|---|
| 시간 규칙 | `shared/lib/loading-indicator` 의 `useLoadingIndicator(loading)` 하나가 `pending`(내용 대신 로딩 자리) · `skeletonVisible` · `reveal` 을 돌려준다. 지연·최소 시간은 `LOADING_DELAY_MS`(200) · `LOADING_MIN_MS`(400) | 자리마다 타이머: 같은 규칙을 25곳에서 다시 쓴다 |
| 빈 자리 | `DeferredSkeleton` 이 뼈대를 그리고 `data-skeleton="blank"` 동안 자식을 `visibility: hidden` 으로 숨긴다. 컨테이너는 보이는 채라 `aria-busy` 가 남는다 | 높이만 잡은 빈 상자: 뼈대마다 높이를 따로 적어야 하고 어긋나면 레이아웃이 밀린다 |
| 최소 표시 | 붙잡는 동안(`pending`) 내용 대신 로딩 자리를 그린다. 자리마다 조건을 `loading \|\| indicator.pending` 으로 쓴다 | 내용 위 겹치기: 겹친 자리의 크기를 맞출 수 없고 스크린리더가 둘을 함께 읽는다 |
| 전환 | `Reveal` 이 `display: contents` 상자로 감싸 자식에 150ms 불투명도 애니메이션을 건다. 상자는 늘 같고, 로딩을 거친 자리만 `data-reveal` 로 전환한다. 바깥 요소를 직접 쥔 곳은 `revealClass` | 보통 상자: flex·grid 부모의 간격이 깨진다. 로딩을 거친 자리만 감싸기: 감싸기가 생길 때 안의 컴포넌트가 다시 마운트돼 조회를 다시 시작한다(회의록 404 에서 실패 → 다시 받기가 끝없이 돌았다). 늘 전환: 캐시로 바로 그린 내용까지 깜빡인다 |
| 라우트 뼈대 이어받기 | 로딩 중으로 처음 그려질 때 스플래시 잡기 수(`getSplashHoldCount`)가 0보다 크면 — 화면 코드를 받고 라우트 뼈대가 막 바뀌는 커밋이다 — 뼈대를 보인 채 시작하고 그때부터 최소 시간을 잰다 | 규칙 그대로: 앱 안에서 처음 가는 화면마다 라우트 뼈대 → 빈 자리 200ms → 뼈대로 깜빡인다. 이슈의 문제를 새로 만든다 |
| 회의록 회의 바꾸기 | 기존 시간 규칙(들고 있기 → 본문 뼈대 → 최소 시간)을 두고 값만 맞춘다. `MINUTES_HOLD_MS` = `LOADING_DELAY_MS`(250 → 200), `MINUTES_SKELETON_MIN_MS` = `LOADING_MIN_MS`(300 → 400). 첫 진입(목록 → 기본 회의 → 회의록)은 한 지표로 잰다 | 들고 있기를 빈 자리로 바꾸기: 고른 회의 머리와 이전 본문을 보이는 UX1-M02 를 버린다. 단계마다 지표: 단계가 바뀔 때 뼈대 → 빈 자리 → 뼈대로 깜빡인다 |
| 보기 코드 대기 | 태스크 보기의 `Suspense` 대기(`보드 화면을 불러오는 중`)는 바로 보인다 | 지연: `Suspense` 가 대기를 내리는 때를 정해 최소 표시를 둘 수 없다. 화면 코드 대기라 라우트 뼈대와 같은 쪽이다 |

## 장단점과 감수한 제약

- 붙잡는 400ms 동안은 데이터가 와 있어도 뼈대다. 지연을 막 넘긴 응답은 내용이 최대 400ms 늦게 보인다.
- 데이터가 이어서 오는 자리(대시보드 최근 반영 → 연동 → 추출)는 안쪽 자리가 새로 그려지면 지연부터 다시 잰다. 조회가 함께 시작해 보통은 함께 끝난다.
- 정해진 글자와 막대가 섞인 뼈대의 모양(빈 자리의 높이)은 이번 규칙이 바꾸지 않는다. 뼈대가 실제 화면과 같은 틀인지는 #508 의 두 번째 일이다.

## 영향 범위와 재검토 조건

- 적용: 대시보드(영역 본문·요약 숫자·회의 안내 줄), 태스크(리스트·보기·상세·변경 이력), 확인 필요 상세, 회의록(목록·본문 첫 진입·확인이 필요한 일·추출된 일), 회의 올리기·화자 지정, 메시지(목록·대화·검토), 팀(목록·연결되지 않은 계정·팀원 연결 창), 설정 알림, 워크스페이스 선택, 온보딩 팀원 잇기.
- 적용 대기: 회의 처리 화면(#483 B), 설정 연결 영역(#507·버튼 삭제)이 develop 에 들어온 뒤 같은 래퍼를 적용한다.
- 재검토: 스플래시를 새로고침마다 띄우지 않게 바꾸면(논의 중) 라우트 뼈대가 새로고침 때 보인다. 이어받기가 그 경우에도 맞는지 다시 본다.
