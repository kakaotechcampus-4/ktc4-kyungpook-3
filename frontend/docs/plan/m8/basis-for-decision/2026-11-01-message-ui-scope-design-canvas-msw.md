# 결정 4의 UI 범위를 디자인 캔버스 기준·MSW 목으로 정한 사용자 결정

- 기록일: 2026-11-01
- 관련 마일스톤: M8-C 메시지(#245)

## 문제와 제약

- 2026-10-31까지의 구현은 [M8 계획](../plan.md) C-3의 결정 4(메시지 화면 정책)가 열려 있어 「결정 전 부분」만 만들었다. 보내기 전 확인은 읽기 전용 미리보기였고, 발송 시점·`고쳐 쓰기`·`이대로 발송`·`보내지 않음`·대화의 `승인`·`반려`, `Discord에서 열기`, `알림 규칙 보기`, 답장 며칠째 표시, 봇 메시지의 `자동 발송`·`지훈 승인` 줄은 「결정 4 뒤로 보류」하거나 「의도적으로 뺐다」고 주석에 적었다([이전 결과](../result-c.md) 「계획 대비 변경」의 당시 기록).
- 사용자가 메시지 화면을 디자인 캔버스([Messages](../../../design/canvas/Messages.dc.html)·[MessagesThread](../../../design/canvas/MessagesThread.dc.html)·[EmptyMessages](../../../design/canvas/EmptyMessages.dc.html))와 비교했고, 상세 영역이 많이 비어 있다고 보고 디자인대로 재작업하라고 했다.
- 메시지 API는 없다. 사용자의 앞선 결정(2026-10-30)으로 UI/UX만 MSW로 만들고 서버 연동·계약 문서는 만들지 않는다.
- 발송은 서버 성공 뒤 반영한다(D-137). 낙관적 갱신을 하지 않는다.

## 실제 검토한 선택지

이 기록은 기술 선택이 아니라 **사용자 결정**을 옮긴 것이다. 코디네이터가 전달한 사용자 지시(2026-11-01)는 다음과 같다.

- 서버가 지켜야 할 정책이 아닌 UI는 MSW 목으로 디자인대로 만든다.
- 이전에 결정 4 뒤로 보류했거나 의도적으로 뺀 항목도 디자인대로 구현하고, 주석·결과 문서의 「보류」를 현재 상태로 고친다.
- 발송 정책의 세부(권한 등)는 MSW 목 동작으로 두고 그 한계를 결과 문서에 적는다.
- 이것을 결정 4의 UI 범위에 대한 사용자 결정(「디자인 캔버스 기준, MSW 목」)으로 결정 기록에 남긴다.

다른 선택지(결정 4가 닫힐 때까지 보류 유지)는 2026-10-31 구현이 택했던 방식이며, 사용자가 이번 지시로 바꿨다.

## 선택과 이유

결정 4 가운데 **화면에 보이는 항목·문구·상태(UI 범위)는 디자인 캔버스를 기준으로** 하고, 그 동작은 **MSW 목**으로 만든다.

- 화면: 보내기 전 확인 전체(미리보기 머리 Discord 표식·매스 아바타·`예정` 시각, `문구는 그대로 고칠 수 있어요`·`고쳐 쓰기`, `왜 보내려 하나요`·`마지막 메시지 보기`, `언제 보낼까요?` 세 카드, `보내지 않음`·`이대로 발송`, 하단 안내), 대화 머리(역할 · Discord 개인 메시지 · ○○ 봇으로 보냄, `답장 N일째 없음` 강조 배지, `Discord에서 열기`), 봇 말풍선 시각 줄, 답장 없음 칩, 승인 대기 점선 말풍선과 `반려`·`승인`, 아래 안내 바와 `확인하기`, 목록의 `09/24 마감`·`3일 전`, `/messages`로 들어오면 첫 확인 항목 선택, 빈 상태의 `알림 규칙 보기`.
- 데이터: 며칠째 답장 없음(답장 대기 시작 시각), 승인자, 사유·근거 링크, 예정 시각·발송 시점, 역할, Discord 주소를 임시 DTO·픽스처 필드로 더했다([임시 DTO](../../../../src/shared/types/api/message.ts), [픽스처](../../../../src/shared/mock/fixtures/message.ts)). 계약이 아니다.
- 동작: 발송·보내지 않음·고쳐 쓰기·발송 시점은 MSW handler가 성공 응답을 낼 때만 db를 바꾸고, 화면은 성공 뒤 메시지 캐시를 다시 받아 그린다([handler](../../../../src/shared/mock/handlers/message.ts), [행동 훅](../../../../src/features/message-review/model/useMessageReviewAction.ts)). 요청 중에는 행동을 잠가 중복 제출을 막고, 실패하면 그 자리에 role=alert와 다시 시도를 둔다(D-137).
- 선택 표현: 보내기 전 확인 항목은 계속 검색 파라미터 `review`로 고른다([이전 기록](2026-10-31-message-review-selection-search-param.md)). 다만 파라미터가 **없으면** Messages 시안처럼 첫 항목을 고른다. 파라미터가 있는데 목록에 없거나 모양이 틀리면 이전처럼 선택 없음이다.

## 장단점과 감수한 제약

- 발송 정책은 MSW 목 동작이며 확정 정책이 아니다. 목에서는 소속 팀원이면 누구나 보내고 반려할 수 있고(PM 전용 여부 미정), 예약 시각이 지나도 메시지가 스스로 나가지 않으며, 「며칠째」는 서버가 준 답장 대기 시작 시각에서 화면이 보낸 날을 1일째로 센다. 실제 서버 정책이 다르면 handler·DTO와 이 화면을 함께 바꾼다.
- 보내기 전 확인 화면(`이대로 발송`·`보내지 않음`)과 대화의 승인 대기(`승인`·`반려`)가 같은 요청을 부른다. 시안 두 장의 행동을 모두 살렸고, 「어느 쪽이 검토 장소인가」는 정하지 않았다([계획](../plan.md) C-10의 상충).
- 상대 표기(`3일 전`, `답장 3일째 없음`, `지금 바로` 카드의 `금요일 아침`)는 기기의 오늘로 계산한다. 픽스처가 2026-09 기준이라 개발 서버를 실제 날짜로 열면 숫자가 시안과 다르다. 테스트와 시각 비교는 시계를 MOCK_NOW로 고정했다.
- `알림 규칙 보기`와 `Discord에서 열기`·`마지막 메시지 보기`의 목적지 화면은 없다. 앞의 것은 가장 가까운 팀 설정으로, 뒤의 둘은 목 Discord 주소(새 창)로 보낸다.

## 영향 범위와 재검토 조건

- 결정 4의 나머지(검토 단위, 발송 권한, 상태 전이·동기화(D-136), 자동 발송 유무)와 실제 메시지 API가 정해지면 임시 DTO·handler·행동 훅과 [결과](../result-c.md)의 한계 목록을 다시 본다.
