# 태스크 보기의 디자인 차이 보완 — 보드 직접 추가와 기간 필터 기본값

- 기록일: 2026-11-01
- 관련 마일스톤: M8-A(#243)
- 결정 주체: **기간 필터 기본값과 직접 추가의 실제 동작은 사용자 결정이다(코디네이터 전달).** 입력 방식·노출 대상·담당자 처리는 시안에 정해진 것이 없어 구현 워커가 고른 기본값이며, 사용자 결정이 아니다.

## 문제와 제약

- 코디네이터가 보드·캘린더·간트를 시안([TasksBoard](../../../design/canvas/TasksBoard.dc.html)·[TasksCalendar](../../../design/canvas/TasksCalendar.dc.html)·[TasksGantt](../../../design/canvas/TasksGantt.dc.html))과 비교해 차이를 찾았다. 보드 칸 아래 「직접 추가」 점선 버튼이 없었고, 보드 기간 필터의 기본값이 시안(「이번 달」)과 달랐다(구현은 「전체 기간」).
- 시안의 「직접 추가」는 버튼 모양(높이 38px, 1px 점선, 12px 600, 더하기 아이콘)뿐이다. 누른 뒤의 입력 방식·상태·문구는 캔버스에 없다.
- 계획 A 절은 새 API를 추가하지 않는다. 대표 계약 §2.6에는 `POST /tasks`가 이미 있고([계약](../../../contracts/frontend-api-contract.md)), MSW handler도 있다. 서버 구현(`backend/app/api/tasks.py`)은 PM 전용(`require_pm`)이다.

## 사용자 결정

1. **보드 기간 필터 기본값은 「전체 기간」을 유지한다.** 시안의 「이번 달」과 다르지만 바꾸지 않는다.
2. **「직접 추가」는 눌러도 아무 일 없는 모양만 두지 않고 실제로 태스크를 만든다.** 계약에 있는 API를 재사용하고, 계약에 없으면 새 API를 만들지 않고 MSW 전용으로 둔다(D-146). 서버 성공 뒤에만 반영하고 낙관적으로 그리지 않는다.

## 실제 검토한 선택지와 구현 워커의 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| API | 계약 §2.6 `POST /tasks` 재사용. 계약 문서는 바꾸지 않았다 | 계약에 이미 있어 MSW 전용 경로를 새로 만들 필요가 없다 |
| 입력 방식 | 버튼 자리에서 시안 카드 틀(둥글기 12, 패딩 12·13)의 한 줄 제목 입력으로 펼친다. Enter·「추가」로 보내고 Esc·「취소」로 닫는다 | 시안에 입력 방식이 없다. 모달·상세 화면 이동보다 보드 맥락을 유지하는 가장 작은 형태로 골랐다 |
| 칸별 상태 | 시작 전 `todo`, 진행 중 `in_progress`, 완료 `done` | 진행 중 칸은 `in_progress`·`blocked`를 함께 담는다. 새로 만든 일은 막힘이 아니므로 `in_progress`다 |
| 노출 대상 | PM에게만 버튼을 둔다 | 서버가 PM 전용이다. 팀원에게 두면 항상 403이다 |
| 담당자 | 담당자 조건으로 걸러 보는 중이면 그 팀원을 담당자로 보낸다. 아니면 담당자 없이 만든다 | 담당자 없이 만들면 걸러 보는 보드에서 만들자마자 사라진다 |
| 반영 | 서버가 돌려준 태스크를 목록 캐시 끝에 넣고 목록을 다시 받는다 | 낙관적 반영 금지. 다른 카드는 같은 객체를 유지해 `memo` 카드가 다시 그려지지 않는다 |
| 빈 제목·중복·실패 | 앞뒤 공백을 뺀 제목이 비면 보내지 않는다(「추가」 비활성). 같은 칸의 요청은 mutation 캐시로 세어 한 번만 보낸다. 실패하면 입력을 남기고 칸 안 `role="alert"`로 알린다 | 사용자 지시의 처리 항목이다 |

## 장단점과 감수한 제약

- 실제 서버로 만든 결과는 확인하지 않았다. 동작 근거는 MSW handler다.
- MSW `POST /tasks` handler는 서버와 달리 인증·PM 검사를 하지 않고, 생성자를 세션 팀원이 아니라 본문 `created_by`로 적는다. 프론트는 `created_by`를 보내지 않으므로 MSW 이력의 생성자는 비어 있다. 이 차이를 고치면 기존 MSW 테스트(`taskApprovalFlow.test.ts`의 ws_02 생성)의 전제가 바뀌어 이번 범위에서 고치지 않았다.
- 태스크도 확인 필요도 없는 공간은 보드 대신 빈 상태를 그리므로 「직접 추가」가 보이지 않는다.
- 기간 필터를 「이번 달」로 둔 경우에도 새 태스크는 마감이 없어 보인다(마감 없는 일은 이번 달 보기에도 남는다).

## 영향 범위와 재검토 조건

- 영향: 보드 세 칸, `entities/task`의 `createTask`, `features/task-create`.
- 재검토: 서버 연동 검증 때 MSW handler의 권한·생성자 기록 차이를 맞춘다. 직접 추가에 마감·담당자 입력이 필요하다는 제품 결정이 나오면 입력 방식을 다시 본다. 기간 필터 기본값은 사용자가 다시 정할 때만 바꾼다.
