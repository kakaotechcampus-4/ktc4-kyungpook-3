# 태스크 보기의 부분 조회 실패 방침

- 기록일: 2026-10-31 (방침 확인 2026-10-30)
- 관련 마일스톤: M8-A(#243)
- 결정 주체: **코디네이터 승인이며 사용자 결정이 아니다.** 구현 워커가 질문했고, 코디네이터가 M7 대시보드의 영역별 실패 선례를 근거로 승인했다.

## 문제와 제약

- 보드·간트·캘린더는 [TaskBoard](../../../../src/widgets/task-board/ui/TaskBoard.tsx)에서 여러 조회를 함께 쓴다. 태스크·팀원 조회는 모든 보기가 쓰고, 확인 필요(승인) 조회는 PM일 때, 회의 조회는 PM이거나 캘린더일 때 켠다.
- 변경 전 코드에서는 PM이 태스크와 확인 필요를 모두 받아야 본문이 보였다. 팀원·회의 실패는 빈 배열과 대체 이름으로 그려 실패가 드러나지 않았다. 데이터가 있는 상태의 재조회 실패도 표시하지 않았다([계획](../plan.md) A 절 「로딩·빈 상태·조회 실패」).
- 계획 AC-A-05는 부분 조회 실패를 실제 빈 데이터로 오인시키지 않고 재시도할 수 있어야 한다고 요구한다. 어떤 실패가 보기 전체를 막을지는 계획이 정하지 않았다(위험과 열린 질문 4).

## 실제 검토한 선택지

구현 워커가 방침을 질문하며 제안을 올렸고, 코디네이터가 「제안 A」를 승인했다. 구현 워커 보고에는 제안 A의 내용만 남아 있고 다른 제안의 내용은 없다. **대안 검토 기록 없음.**

## 선택과 이유

- 처음부터 태스크를 받지 못한 경우만 보기 전체를 오류(`QueryErrorState`)로 그린다.
- 확인 필요(PM)·팀원·회의(캘린더)의 실패는 받은 데이터로 보기를 그린다. 그 위에 `role="alert"` 안내 「○○ 정보를 불러오지 못했어요. 보이는 내용이 전부가 아닐 수 있어요.」와 `다시 시도`를 둔다. 다시 시도는 실패한 조회만 `cancelRefetch: false`로 다시 부른다.
- 데이터가 있는 상태에서 재조회가 실패하면 데이터를 유지하고 같은 안내를 둔다(`queryView`의 `refreshFailed`).
- 실패한 값을 `담당자 없음`·`미지정`·0으로 그리지 않는다. 받지 못한 담당자는 `알 수 없는 담당자`로 쓰고, 간트에서는 별도 묶음으로 둔다.
- 리스트 보기는 기존 분기를 유지한다.

코디네이터가 든 승인 근거는 M7 대시보드의 영역별 실패 선례다. 대시보드도 영역마다 실패를 따로 그리고, 실패한 집계는 숫자 대신 `–`로 두며, 재조회 실패는 기존 값을 둔 채 안내한다([M7 결과](../../m7/result.md) AC-05). 이 밖의 선택 이유는 기록되지 않았다.

## 장단점과 감수한 제약

- 확인 필요나 회의 하나가 실패해도 태스크 보기를 계속 쓸 수 있다. 대신 보이는 내용이 일부일 수 있어 안내 문장에 그렇게 적었다.
- 받은 데이터로 그린 빈 기간·합계가 미확인 항목을 빠뜨린 확정 값처럼 보일 수 있다. 이 문제는 V2 리뷰가 지적했고 별도 결정으로 다뤘다([합계 숨김 결정](2026-10-31-task-views-unconfirmed-approval-totals.md)).
- 보드의 확인 필요 수(`pendingApprovals`)는 미조회일 때 0을 쓰지 않고 안내만 숨긴다.

## 영향 범위와 재검토 조건

- 영향: `TaskBoard`의 상태 분기와 안내, 세 보기의 담당자 표시, 간트 담당자 묶음.
- 재검토: 사용자가 보기의 실패 표시 정책을 따로 정하거나, 조회 실패 표시를 앱 전체에서 공통화할 때(예: #236의 `shared` 이동) 다시 본다.
