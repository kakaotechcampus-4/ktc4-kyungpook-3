# 정책 공개 상태와 계정 범위로 동의 화면을 연결한다

- 기록일: 2026-11-09
- 관련 영역: M4 인증 흐름의 후속 이슈 #566. 기존 M4 계획의 완료 범위를 변경하지 않는다.

## 문제와 제약

동의 API가 있어도 공개 승인된 본문이 없으면 사용자가 무엇에 동의했는지 확인할 수 없다. 가입은 이미 계정을 생성하고 쿠키를 발급하므로, 그 뒤 동의 저장 실패를 가입 실패로 표시하면 재가입·이메일 충돌이 생긴다. 두 탭이 쿠키를 공유하는 동안 A 계정의 폼이 B 계정의 동의를 기록할 위험도 있다.

## 실제 검토한 선택지

별도 동의 경로로 이동하는 방식과 인증 가드 안에서 원래 주소를 유지하는 방식을 비교했다. 별도 경로는 돌아갈 주소를 새로 검증하고 전달해야 한다. 가입 요청에 동의를 원자적으로 포함하는 방식도 기존 API 변경과 계정 생성 정책 변경이 필요하다. 이번 지시는 동의 화면 연결이며 정책 승인이나 모든 서버 API의 접근 제어를 새로 결정하는 작업이 아니다.

## 선택과 이유

- 문서 본문·판본·시행일을 함께 가진 `published`와 `preparing`의 판별 합집합을 사용한다. 현재 제품 값은 `preparing`이다. 환경 변수나 URL로 공개하지 않는다. 문서 페이지와 체크 영역은 같은 문서 쌍을 읽는다.
- `RequireAuth` 다음, `AuthenticatedLayout` 앞에 인라인 동의 가드를 둔다. 원래 주소·쿼리와 기존 안전한 복귀 검증을 유지한다. 공개 문서와 계정 탈퇴는 밖에 둔다.
- 가입 뒤 이전 사용자 범위를 정리하고 새 세션 범위를 잡아 동의를 POST한 후 세션 Query를 반영한다. 동의 응답을 잃어도 생성된 계정은 유지하고 가드의 GET으로 복구한다. 가입 POST를 다시 실행하지 않는다.
- Query 키는 사용자 ID와 표시한 두 판본을 포함한다. FE는 GET·POST에 `X-Consent-Account-ID`를 항상 보내고 BE는 실제 쿠키 계정과 다르면 읽기·저장 전에 409로 거절한다. 계정 불일치 화면에서 새 쿠키 계정을 임의로 로그아웃하지 않는다.

## 감수한 제약과 재검토 조건

선택 헤더가 없는 기존 호출자는 계속 동작하며, 그 호출에는 기대 계정 검증이 적용되지 않는다. 이 가드는 화면 흐름을 막는 장치다. 동의가 없는 사용자의 모든 서버 API를 차단하지 않으며 가입과 동의는 별도 트랜잭션이다. 공개 전 법률 검토·공급사 확인과 최종 본문·새 판본의 동시 반영이 필요하다. 현재 BE 초안 판본 `2026-11-08`을 공개 동의로 재사용하지 않는다.
