# M4 완료 조건 (루프 판정 기준)

- 계획: `m4-auth-onboarding-and-workspace.md` (이하 "계획")
- 판정자: 구현자와 분리된 검증 에이전트(이번 루프는 Claude Opus 5.5 high). 구현 에이전트의 자기 보고는 근거로 인정하지 않는다. 명령은 검증자가 직접 실행한다.
- 구현·검증 루프의 판정 기준이다. 인수인계 현황은 `m4-handoff.md`.

## 판정 규칙

1. 단위(U1~U5)마다 **구현 → 검증 → (FAIL이면) 수정 → 재검증** 루프를 돈다.
2. 검증자는 검증 보고서에 기준 ID별 `PASS | FAIL`과 근거(명령 출력 요약, 파일:줄, 테스트 이름)를 적는다. 기준 밖에서 발견한 결함은 `blocker | major | minor`로 분류해 따로 적는다.
3. 단위 통과 = 해당 단위 기준 + 공통 게이트 G 전부 PASS, `blocker`·`major` 0건. `minor`는 다음 단위 구현 시 함께 처리하거나 사유를 남기고 넘긴다.
4. 같은 단위에서 4회차까지 통과하지 못하거나, 계획과 코드·백엔드가 충돌해 결정이 필요한 경우 사용자에게 올린다.
5. 이전 단위에서 PASS한 기준이 뒤 단위에서 깨지면 그 단위의 FAIL로 본다(회귀).
6. 마지막에 최종 게이트 F를 전체 기준으로 한 번 더 검증한다.

## G. 공통 게이트 (모든 단위에서 매번 확인)

- **G1** `frontend/`에서 `npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run test`, `npm run build`가 모두 통과한다. (U5부터 `build-storybook`, `test:e2e` 추가)
- **G2** 변경 범위는 `frontend/**`와 `.github/workflows/frontend-ci.yml`뿐이다. `backend/`, `ai/`는 건드리지 않는다. 백엔드 API 형식(경로·요청·응답 봉투)을 바꾸지 않는다.
- **G3** 기존 테스트를 삭제·`skip`·약화해 통과시키지 않는다. 동작이 바뀌어 기대값을 고친 경우 검증 보고서에 사유가 있어야 한다.
- **G4** FSD 경계(`eslint-plugin-boundaries`)를 우회하지 않는다. `eslint-disable`을 새로 쓰면 줄마다 사유 주석이 있어야 한다.
- **G5** 서버 데이터는 Query에만 둔다. Zustand·Web Storage에 사용자·워크스페이스 객체나 인증 여부를 저장하지 않는다(예외: 브라우저 MSW의 `sessionStorage` 영속, 복귀할 워크스페이스 ID 같은 UI 상태).
- **G6** 새 화면은 캔버스(`frontend/docs/design/canvas/*.dc.html`)의 문구·구성과 M2 토큰·공통 UI를 따른다. 임의 색상·크기 값을 하드코딩하지 않는다.
- **G7** 새 기능마다 통합 테스트가 있다(MSW + 실제 `request` 경로). 테스트 없이 추가된 동작은 FAIL.

## U1. API·MSW 기반

- **U1-1** `entities`에 로그인·가입·로그아웃, 워크스페이스 생성·상세·온보딩 갱신, 연동 상태·Discord 사용자 조회, 팀원 생성·수정 함수가 있고, 각각 기존 DTO·매퍼·`request`를 쓴다. 생성 요청·온보딩 `{ step, action }` 요청 타입이 명시돼 있다.
- **U1-2** 워크스페이스별 Query key에 `workspaceId`가 들어간다. 온보딩 PATCH 뒤 **상세 재조회 → 목록 캐시 반영** 순서를 보장하는 공통 경로가 있고 테스트로 순서가 검증된다.
- **U1-3** 브라우저 MSW는 비로그인으로 시작한다. Vitest(`server.ts`) 픽스처·초기화 동작은 바뀌지 않는다(기존 테스트 무수정 통과).
- **U1-4** 브라우저 MSW에만 버전 키가 붙은 `sessionStorage` 영속이 있어 가입 계정·세션·워크스페이스·온보딩·연동·팀원 상태가 새로고침 후 복원된다. 버전 불일치·손상 데이터는 초기 상태로 복구된다(단위 테스트).
- **U1-5** 새로 만든 워크스페이스에서도 Discord 연결 후 사용자 목록이 반환된다(`ws_01` 전용 제거, 테스트).
- **U1-6** OAuth 모의 화면은 개발·MSW 모드에서만 등록되고(프로덕션 번들에 포함되지 않음을 확인), 현재 탭 이동으로 성공·취소·실패를 재현해 `state`에 담긴 원래 온보딩 단계로 복귀한다.
- **U1-7** E2E용 시나리오 초기화 수단(비로그인, 공간 0/1/복수, 미완료 공간)이 있고 서로 독립적이다.

## U2. 랜딩·인증

- **U2-1** 랜딩 `시작하기` → 로그인, 로그인 → 회원가입 링크. 랜딩에 회원가입 직접 링크·데모 버튼 없음.
- **U2-2** React Hook Form + Zod resolver. `mode: 'onTouched'`, `reValidateMode: 'onChange'`, `shouldFocusError: true`, 제출 중 중복 제출 방지가 공통 적용된다.
- **U2-3** 회원가입: 이름 필수, 이메일 형식, 비밀번호 8자 이상 + 숫자 포함, 비밀번호 보기 토글. 로그인: 이메일 형식, 비밀번호 필수. 강도 표시·약관 동의 없음.
- **U2-4** 필드 오류는 입력 아래에 있고 `aria-describedby`·`aria-invalid`로 연결된다. 비필드 오류는 공통 `FormErrorPanel`에 표시된다. 서버 필드 오류는 `setError`로 반영된다.
- **U2-5** Google 로그인·`비밀번호를 잊으셨나요?`가 비활성으로 보인다.
- **U2-6** 인증 성공 시 이전 사용자 캐시·요청을 정리하고 워크스페이스 목록을 확보한 뒤 `postLoginPath`로 이동한다. 로그인 상태의 인증 화면 재방문은 `authRevisitPath`. 0/1/복수 공간 분기 테스트.
- **U2-7** 로그아웃: 서버 성공 후 캐시 정리 → 로그인 이동. 실패 시 캐시 유지. 미저장 변경이 있으면 이탈 확인을 거친다.
- **U2-8** 테스트: 가입 성공, 중복 이메일, 잘못된 자격 증명, 중복 제출 방지, 재방문 이동.

## U3. 온보딩·팀원 연결

- **U3-1** 공통 온보딩 레이아웃(단계 표시·본문·진행/건너뛰기). 캔버스 `SetupTeam`/`SetupDiscord`/`SetupNotion`/`SetupMembers` 기준.
- **U3-2** 생성: M3 정규화·1~20자·계정 내 중복(대소문자 구분) 검증 재사용. 생성 후 단계 저장이 실패해도 재시도 시 **워크스페이스 POST가 다시 나가지 않는다**(요청 횟수 테스트).
- **U3-3** Discord·Notion: 모의 OAuth 복귀 후 연동 상태를 재조회해 `connected`일 때만 단계 완료. 취소·실패 시 단계 미완료 + 안내. Notion DB 선택 화면 없음.
- **U3-4** Discord 건너뛰기 → 팀원 연결도 건너뜀으로 저장. 중간 실패 시 저장된 상태를 재조회해 남은 요청만 재시도(요청 횟수 테스트).
  - 2026-09-29 개정(D-173): 팀원 연결은 함께 건너뛰지 않는다 — Discord 건너뜀 하나만 저장하고 Notion 뒤에는 팀원 연결이 온다(Discord 미연결 안내 + `건너뛰기`). 중간 실패·재시도(요청 횟수 테스트)는 한 단계 저장의 재시도로 본다.
- **U3-5** 모든 단계가 완료·건너뜀이면 새 공간 대시보드로 이동. 새로고침·재로그인·직접 URL 진입은 저장된 미완료 단계로 복귀.
- **U3-6** 일반 팀원: PM 설정 대기 안내, 온보딩 PATCH 요청 0회.
- **U3-7** 기존 공간에서 새 공간 만들기 시 복귀 공간 ID를 보관. 뒤로가기는 입력 중 매핑을 저장 후 기존 대시보드로, 저장 실패 시 화면 유지. 최초 가입자는 워크스페이스 선택 화면으로.
- **U3-8** 팀원 연결: Discord 사용자 + 팀원 동시 조회, `linkDiscordUsers`로 구성, 봇 제외, 기존 매핑 채움. 1:1 중복 차단, 빈 행 제외 부분 저장·완료.
- **U3-9** 저장 규칙: 기존 매핑 PATCH / 이름 일치 미연결 팀원(생성자 PM 포함)에 연결 / 없으면 POST. 순차 저장, 성공 행 반영으로 재시도 시 중복 생성 없음. 일부 실패 시 실패 행·남은 입력 유지, 전부 성공 후에만 온보딩 완료 요청.
- **U3-10** 팀원 연결 화면에 미저장 변경 확인(링크·전환·브라우저 이탈) 적용.
- **U3-11** 테스트: 전 단계 연결, 전 단계 건너뛰기, Discord 건너뛰기 연쇄(2026-09-29 D-173 로 "연쇄 없음 · 팀원 연결 단계 표시" 로 바뀜), 중간 실패·재시도, 생성 중복 방지, 기존 PM 연결, 중복 매핑 차단, 부분 저장, 일부 실패 후 재시도, 일반 팀원 차단.

## U4. 워크스페이스 선택·앱 셸·대시보드

- **U4-1** 선택 화면과 헤더 메뉴가 같은 목록·진입 정책 함수를 쓴다. 미완료 공간에 `설정 미완료` 표시, 선택 시 온보딩 재개 지점으로, 완료 공간은 대시보드로.
- **U4-2** `Main` 캔버스 기준 헤더 + 5개 탭, 설정은 별도 메뉴. 다른 마일스톤 임시 화면도 앱 셸 안에서 이동 가능.
- **U4-3** 메뉴는 Radix Dropdown Menu. 키보드 이동·Esc 닫기·포커스 복귀 테스트. 아이콘은 캔버스 SVG를 공통 컴포넌트로 추출.
- **U4-4** 대시보드는 빈 상태 + 다음 행동 안내만. 집계·목록 API 요청 0회(테스트).
- **U4-5** 전환: 미저장 변경 시 취소·이동 모두 테스트, 전환 후 이전 공간 데이터 비노출. 미완료 공간 대시보드 직접 진입 차단.

## U5. Storybook·E2E·CI·문서

- **U5-1** Storybook 도입. M2 공통 UI와 M4 폼·메뉴·온보딩의 기본·로딩·오류·비활성 스토리. `npm run build-storybook` 통과.
- **U5-2** Playwright Chromium E2E가 Vite 개발 서버(MSW)로 실행된다. 시나리오: ① 가입 → 온보딩 전 단계 → 대시보드 ② 기존 사용자 선택·전환(미저장 변경 확인 포함) ③ 새로고침·OAuth 왕복 후 진행 상태 복원. 각 테스트는 독립 초기화. `npm run test:e2e` 통과.
- **U5-3** CI: 기존 검사 통과 후 앱·Storybook 빌드와 E2E 실행, 실패 시 trace 아티팩트 업로드.
- **U5-4** 1024·1280·1440px 레이아웃 확인(E2E 뷰포트 또는 스크린샷 근거)과 키보드 조작 확인.
- **U5-5** 문서: 구현 결정 문서(가입 폼 범위 조정, MSW 저장·OAuth 모의 처리)가 `frontend/docs/impl-decision/`에 README 형식대로 있다. 개발 계획의 실 API 제약 표가 현재 `backend/` 소스 기준으로 갱신돼 있다(검증자가 백엔드 라우트와 대조). 계획 문서에 완료 판정(MSW 흐름·CI)과 실제 OAuth 미완료가 구분돼 기록돼 있다.
