# M6-API 계획 — 배포 백엔드 실제 API 연동 전환

- 작성일: 2026-10-12
- 상태: 구현 전 계획. 완료 판정과 테스트 성공 기록은 포함하지 않는다.
- 계획 근거: 사용자가 지정한 연동 전환 계획(2026-10-12)과 범위, 현재 작업 트리의 코드·대표 계약, M4~M6 결과·인수인계.
- 위치: [전체 계획](../frontend-plan.md)의 M0~M8 번호에 없는 마일스톤이다. M6 완료 뒤 M7 착수 전에 배포 백엔드 연결을 수행하도록 사용자가 `m6-api`로 지정했다. 전체 계획은 수정하지 않는다.

## 목표와 배경

M6까지 구현한 프론트엔드의 앱 기본 실행을 **실제 API**로 전환한다. 로컬 프론트엔드에서 배포 백엔드로 요청을 보내 검증하며, 백엔드가 지원하는 기능부터 연결한다. MSW는 단위 테스트·Storybook·기존 E2E에서 계속 사용한다.

M4·M5·M6의 완료 기록은 MSW 기준이다. [M6 결과](../m6/result.md)는 실 API 보완 승인·승인 조회 PM 제한·실제 Notion 반영을 미검증 연동 과제로 남겼고, [M5 인수인계](../m5/m5-handoff.md)도 실 백엔드 흐름을 미검증으로 구분한다. 이번 마일스톤은 이 미검증 항목을 실제 서버로 확인하고, 지원되지 않는 기능을 명시적으로 제한한다.

현재 실행 환경은 다음과 같다(2026-10-12 정적 확인).

| 경계 | 현재 근거 | 이번에 필요한 변경 |
|---|---|---|
| 환경 예시 | [.env.example](../../../.env.example): `VITE_ENABLE_MSW=true`, `VITE_API_BASE_URL` 비움 | 기본값을 `VITE_ENABLE_MSW=false`로 전환 |
| 환경 해석 | [env.ts](../../../src/shared/config/env.ts): 개발 서버이고 값이 `true`일 때만 MSW 사용. 값이 없으면 `false` | 동작 유지. 명시적으로 켠 경로만 MSW 사용 확인 |
| 프록시 | [vite.config.ts](../../../vite.config.ts): `/api` → `http://localhost:8000` 고정 | 서버 전용 `API_PROXY_TARGET`으로 대상 지정, 경로·쿠키 보존 |
| MSW 등록 | [main.tsx](../../../src/main.tsx), [browser.ts](../../../src/shared/mock/browser.ts): 활성 시에만 worker 시작. 비활성 시 기존 등록 해제 없음 | 이전 service worker가 요청을 가로채지 않게 하는 전환 절차 |
| E2E | [playwright.config.ts](../../../playwright.config.ts): webServer에 `VITE_ENABLE_MSW: 'true'` 명시 | 유지. 프록시 설정과 독립. 실 API용 설정은 별도 추가 |

## 구현 범위와 제외 범위

### 구현 범위

- 배포 백엔드의 OpenAPI·배포 버전과 프론트 요청·응답 타입 대조, 기능별 연동 가능 여부 분류.
- 실 API 기본 실행 환경: 환경 예시, 프록시 대상 변수, 쿠키·HTTPS 확인, MSW worker 전환 절차.
- 인증 → 워크스페이스·팀원 → Discord·Notion → 회의·회의록·추출 → 태스크 → 승인·Notion 반영 순서의 실제 연결과 차이 수정.
- 미지원 기능의 명시적 제한과 남은 백엔드 의존성 정리.
- 실제 API용 Playwright 설정과 smoke 테스트, 기존 MSW 회귀, 대표 계약·실행 안내·결과 기록.

### 제외 범위

- 백엔드 코드 수정과 배포, 배포 프론트엔드 검증·배포 실행(후속 단계).
- 전체 개발 계획 변경, M7 이후 기능 구현.
- 백엔드가 지원하지 않는 기능을 프론트에서 우회하는 구현. MSW 분기만 바꿔 미지원 필드를 실 API로 보내지 않는다.
- 실 API 실패 시 앱이 자동으로 모의 응답으로 전환하는 동작. 테스트용 MSW 실행은 명시적 설정으로만 사용한다.

## 의존 사항과 관련 문서

- **배포 주소:** 실행 시 입력받는 환경값으로 둔다. 주소 확인 전에도 단계 1의 코드·계약 대조와 단계 2의 설정 준비는 진행할 수 있다. 실제 연동 검증은 주소 확보 후 시작한다.
- **테스트 계정:** 전용 테스트 계정·워크스페이스와 PM·일반 팀원 계정이 필요하다. 비밀번호와 세션은 저장소·로그에 남기지 않는다.
- **Node 24:** 최종 게이트 실행에 필요하다. [M6 결과](../m6/result.md)에 따르면 기존 작업 기계에는 Node v22.17.1만 있었다.
- 관련 문서: [대표 계약](../../contracts/frontend-api-contract.md)(특히 「M6 태스크·승인 처리 경계」, 「백엔드 요청 (합의 여부 확인 필요)」 M6-1~M6-4, 「4. 백엔드 요청」), [M4 계획](../m4/plan.md), [M5 계획](../m5/plan.md), [M6 계획](../m6/plan.md), [M6 결과](../m6/result.md), [M5 인수인계](../m5/m5-handoff.md), [M4 인수인계](../m4/m4-handoff.md), [파트 README](../../../README.md), [MSW 안내](../../msw-guide.md).
- 관련 이슈: [#211](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/issues/211) 추출 API의 승인 상태 구분(2026-10-12 기준 OPEN). 응답 필드 `approval_status`는 이슈의 제안이며 합의된 계약이 아니다.

## 구현 순서

### 1. 배포 계약과 연동 범위 확인

1. 구현 시작 시 최신 `develop`과 작업 트리 상태를 확인하고 사용자 변경을 보존한다.
2. M4~M6에서 사용하는 API를 **인증 / 공간·팀원 / 외부 연결 / 회의·추출 / 태스크·승인**으로 묶어 목록화한다. 근거는 엔티티 API 모듈과 대표 계약이다.
3. 배포 백엔드의 OpenAPI 문서와 배포 버전(커밋·태그 등 확인 가능한 식별자)을 확보해 프론트 DTO와 대조한다. 저장소의 백엔드 코드만으로 배포 서버의 지원 여부를 단정하지 않는다.
4. 각 기능을 `연동 가능 / FE 수정 필요 / BE 보완 필요`로 분류하고 근거(OpenAPI 경로·필드, 실제 응답)를 기록한다.
5. 우선 확인할 차이: 생성 승인 보완값(`task_overrides`, M6-1~M6-3), 승인 목록·상세 조회의 PM 제한(M6-4), 추출 승인 상태(#211), Notion 연결 상태.

**산출물:** 기능별 API 목록과 분류표, 배포 버전·OpenAPI 확인 근거, 미지원 기능 목록. **대응:** AC-01.

### 2. 실제 API 실행 환경 구성

1. `.env.example`의 기본값을 `VITE_ENABLE_MSW=false`로 바꾼다. E2E·Storybook·테스트처럼 명시적으로 켠 경로는 유지한다.
2. Vite 프록시 대상을 서버 전용 환경 변수 `API_PROXY_TARGET`으로 지정할 수 있게 한다. `VITE_` 접두사를 쓰지 않아 브라우저 번들에 들어가지 않게 한다. 로컬 프론트는 `VITE_API_BASE_URL`을 비워 `/api/v1`을 동일 출처로 호출한다. 값이 없을 때의 기본 대상은 기존 `http://localhost:8000`을 유지한다.
3. 프록시가 경로(`/api/v1` prefix)와 쿠키를 보존하는지 확인한다. 실제 응답의 `Set-Cookie` Domain·Secure·SameSite 속성을 확인하고, 로컬 출처에서 저장·재전송되지 않으면 쿠키 도메인 재작성 또는 로컬 HTTPS를 구성한다.
4. 이전 MSW service worker가 실 API 실행에서 요청을 가로채지 않는지 확인한다. 최초 전환 절차에 해당 worker 해제와 페이지 재로딩을 포함하고 실행 안내에 기록한다.
5. 실 API 실행에서 픽스처 계정·모의 OAuth 경로(`/__mock/oauth/...`)·`?msw-scenario=` 초기화가 동작하지 않는지 확인한다.
6. 기존 E2E·Vitest·Storybook 설정이 `API_PROXY_TARGET`과 무관하게 동작하고, 기존 E2E가 계속 `VITE_ENABLE_MSW=true`를 명시하는지 확인한다.

**산출물:** 환경 예시·Vite 설정 변경, 쿠키·HTTPS 확인 결과, MSW worker 전환 절차, 실행 안내 초안. **대응:** AC-02, AC-03.

### 3. 기능별 순차 연결

각 단계는 정상 흐름과 대표 오류를 실제 서버로 확인한 뒤 다음 단계로 넘어간다. 응답 형식 차이는 API 계층·DTO·매퍼에서 처리하고, 제품 동작 차이는 화면과 도메인 판정에 반영한다.

| 순서 | 대상 | 확인·수정할 내용 |
|---|---|---|
| 1 | 인증 | 로그인, `/auth/me`, 새로고침 후 세션 복원, 로그아웃, 401 처리. 쿠키 저장과 다음 요청 전송을 먼저 확인 |
| 2 | 워크스페이스·팀원 | 목록·상세·생성, 공간 선택, 온보딩, 팀원 관리. 실제 ID·빈 목록·역할·오류 응답 처리 |
| 3 | Discord·Notion | 실제 OAuth 시작·callback·프론트 복귀, 연결 상태 재조회, 준비 중·실패 처리 |
| 4 | 회의·회의록·추출 | 목록·상세, 업로드 지원 여부, 처리 상태 polling, 완료·실패, 회의록·추출 응답 매핑 |
| 5 | 태스크 | 목록·상세·이력, 상태 변경, 실패 복구, 변경 후 캐시 갱신 |
| 6 | 승인·Notion 반영 | 생성·수정 승인, 반려, 충돌, 이미 처리됨, 승인 후 관련 목록 갱신, 실제 Notion 상태 polling·재시도 |

- OAuth는 시작과 callback에서 같은 세션이 유지되는 구성이 확인되어야 한다. 배포 callback 주소가 로컬 검증과 맞지 않으면 백엔드 개발용 설정을 요청하고 해당 단계만 보류한다.
- 업로드 이후 처리는 API 접수뿐 아니라 AI 워커의 실제 완료까지 확인한다. 서버 파이프라인이 미지원이면 이미 완료된 회의 조회부터 검증한다.
- 단계마다 실제 동작, 수정 내용, 보류 사유를 기록한다.

**산출물:** 단계별 API·DTO·매퍼·화면 수정, 단계별 실제 검증·보류 기록. **대응:** AC-04, AC-05.

### 4. 미지원 기능과 계약 차이 처리

1. **보완 승인:** 배포 서버가 `task_overrides`를 지원하지 않으면 현재 실 API 제한(보완이 필요한 생성 승인의 `승인` 비활성화·사유 표시·`반려` 가능)을 유지한다. 지원이 확인되면 확인된 계약에 따라 실 API에서도 입력·검증·전송을 활성화한다.
2. **추출 승인 상태(#211):** 완료되면 확정된 상태 필드로 대기·승인·반려를 분류한다. 미완료이면 상태를 확인할 수 없는 승인 연결 항목을 반영 완료로 표시하지 않고, PM은 대기 승인 목록으로 확인 경로를 유지한다.
3. **승인 조회 권한(M6-4):** 서버가 PM 제한을 지원하지 않으면 기존 프론트 가드를 유지하되 백엔드 권한 검증 완료로 기록하지 않는다.
4. 백엔드 보완 사항은 기존 관련 이슈·계약 요청에 연결한다. 새로운 독립 문제가 있을 때만 별도로 요청한다. 미지원 항목은 실제 연동 성공 목록에서 제외한다.

**산출물:** 미지원 기능 제한 코드·테스트, 남은 백엔드 의존성 목록과 이슈 연결. **대응:** AC-06.

### 5. 검증·문서화

1. 전용 테스트 계정·워크스페이스에서 PM과 일반 팀원 흐름을 검증한다.
2. 실제 API용 Playwright 설정과 smoke 테스트를 기존 MSW E2E와 분리해 추가한다. 기본 `npm run test:e2e`에 포함하지 않는다. 데이터 변경 테스트는 직렬로 실행하고, 실패한 mutation을 자동 재시도하지 않는다(retries 0). 계정 정보는 실행 시 환경 변수로 받는다.
3. smoke 범위는 로그인·세션 복원, 공간 진입, 회의록 조회, 태스크 조회·상태 변경, 지원되는 승인·반려 후 재조회다. OAuth와 실제 Notion 반영은 수동 검증 결과를 남긴다.
4. Node 24에서 아래 최종 게이트를 순차 실행한다.
5. 대표 계약과 실행 안내(파트 README)에 확정된 설정·서버 지원 범위·실제 검증 결과를 반영한다. 결과는 이 마일스톤 `result.md`에 기록하고 관련 M4~M6 기록에 연결하며, 모의 검증과 실제 검증을 구분한다. 계약은 `contract-update`, 중요한 실제 선택은 `decision-record`, 결과는 `milestone-result` 스킬로 기록한다. 지금은 결과나 과거 선택을 미리 작성하지 않는다.

**산출물:** 실 API Playwright 설정·smoke 테스트, 수동 검증 기록, 최종 게이트 근거, 계약·실행 안내·결과 기록. **대응:** AC-07, AC-08, AC-09.

### 최종 게이트

Node 24 환경에서 깨끗한 의존성 설치 후, `frontend/`에서 아래 명령을 **순차 실행**한다. 각 명령의 실제 결과를 따로 기록하고 테스트 단언을 통과시키기 위한 임의 완화는 하지 않는다. 실 API smoke는 배포 주소·테스트 계정이 주어진 경우 별도로 실행한다.

```bash
npm ci
npm run typecheck
npm run lint
npm run format:check
npm run test
npm run build
npm run build-storybook
npm run test:e2e
npm run test:storybook
```

production 앱 번들에 MSW 시나리오·픽스처·등록 코드와 `API_PROXY_TARGET` 값이 없는지 점검한다.

### 완료 판정

앱 기본 실행이 실 API를 사용하고, 지원 기능의 실제 검증이 통과하며, 미지원 기능이 명시적으로 제한된 상태를 완료로 본다. 배포 프론트엔드 검증과 배포 실행은 후속 단계로 남긴다.

## 위험 및 미결 사항

- **배포 주소·버전 미확보:** 배포 주소와 배포 버전은 아직 확인되지 않았다. 확보 전에는 실제 연동 검증을 시작하지 않는다.
- **쿠키 속성:** 배포 응답의 쿠키가 `Secure`·특정 Domain이면 로컬 HTTP 프록시에서 저장되지 않을 수 있다. 실제 응답을 확인하기 전까지 HTTPS·쿠키 재작성 필요 여부를 정하지 않는다.
- **OAuth callback:** 배포 백엔드의 OAuth callback·복귀 주소가 로컬 프론트와 맞지 않을 수 있다. 맞지 않으면 해당 단계만 보류하고 백엔드 개발용 설정을 요청한다.
- **업로드 파이프라인:** 배포 환경의 AI 워커 동작 여부는 확인되지 않았다. 미지원이면 완료된 회의 조회로 범위를 좁힌다.
- **백엔드 미합의 요청:** `task_overrides`(M6-1~M6-3)·승인 조회 PM 제한(M6-4)·#211은 합의·구현 여부가 확인되지 않았다. 확인 전까지 지원으로 간주하지 않는다.
- **실데이터 변경:** smoke·수동 검증은 배포 데이터를 바꾼다. 전용 계정·워크스페이스에서만 실행하고 실패한 mutation을 자동 재시도하지 않는다.
- **기존 로컬 환경 파일:** 이미 만든 로컬 `.env` 파일이 `VITE_ENABLE_MSW=true`를 유지하면 예시 변경만으로는 전환되지 않는다. 실행 안내에 확인 절차를 포함한다.
- **Node 24 환경:** 작업 기계에 Node 24가 없으면 최종 게이트를 완료할 수 없다. 다른 Node 결과로 대체하지 않는다.
