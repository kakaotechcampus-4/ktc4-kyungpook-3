# 결과 — TaskBoard 보기별 파생 연산과 탭 집계 줄이기 (#351)

- 기록일: 2026-11-05
- 대상: [계획](plan.md) 작업 순서 1~3과 5
- 상태: **확인한 범위에서는 파생 계산이 동작 비용의 작은 부분이라 이번 PR에서는 코드 변경을 보류했다.** 프로덕션 화면에서의 체감 효과는 재지 않았다. 작업 순서 4는 실행하지 않았다.

## 작업 근거와 요약

확인한 범위는 두 가지다.

- 프로덕션 모양 번들(Chromium 153, 15라운드 중앙값, 두 번 실행)에서 잰 파생값의 독립 비용. 모든 memo가 다시 돌 때 보드·간트에서 버리는 계산은 태스크 50건 0.2ms 이하, 500건 1~1.8ms, 2,000건 5.3~8.7ms다.
- 개발 빌드 화면에서 파생 함수가 동작 CPU 시간에서 차지하는 비중. 담당자 바꾸기, 캘린더 달 이동, 간트 주 이동, 보기 전환에서 최대 약 5%(2,000건 간트 다음 3주, 53~68ms 중 2.5~3.1ms)였다.

`TasksPage`가 렌더마다 새 `due` 배열을 만들어, `board`(`buildTaskBoard`)는 보기 전환과 달·주 이동처럼 URL이 바뀔 때마다 다시 돈다. 임시 Vitest로 이동마다 1번씩 더 불리는 것을 확인했다. 그때 버리는 계산은 2,000건에서 3.9~7.7ms다.

이 범위에서 파생 계산은 동작 비용의 작은 부분이라 이번 PR에서는 코드 변경을 보류했다. 프로덕션 빌드 화면에서 이 계산을 없앤 효과는 재지 않았으므로 체감 효과가 없다고 단정하지 않는다. 측정 조건과 표는 [측정 문서](../../../../performance/2026-11-05-taskboard-derived.md)에 있다.

## 측정 결과

| 태스크 | 보드·간트에서 버리는 계산 | 캘린더 | 리스트 | 탭 개수(리스트, 마감 조건 있음) |
|---|---|---|---|---|
| 50 | 0.05~0.21ms | 0.02~0.18ms | 0.00~0.06ms | 0.12ms |
| 500 | 0.95~1.78ms | 0.70~1.48ms | 0.17~0.40ms | 1.05~1.18ms |
| 2,000 | 5.27~8.66ms | 4.22~7.38ms | 0.45~1.79ms | 4.25~5.26ms |

모든 memo가 다시 돌 때(화면 진입, 태스크 변경)의 값이다. 범위는 마감 조건 없음과 있음, 두 번의 실행을 합친 것이다. 버리는 계산의 대부분은 리스트에서만 쓰는 `board`의 정렬이다. 탭 개수는 마감 조건이 없으면 2,000건에서 0.17ms 이하다. URL 변경 때는 `board`만 다시 돌고, 그 비용은 500건 0.64~1.65ms, 2,000건 3.91~7.69ms다.

실제 화면(개발 빌드, MSW)에서 보드의 담당자 바꾸기는 Event Timing 중앙값 500건 88ms, 2,000건 144ms였다. 표본은 각 10개이고 중앙값은 가운데 두 값의 평균이다.

## 계획 대비 변경

- 이슈와 작업 지시는 `calendarMeetings`를 캘린더·간트가 쓴다고 적었다. 코드를 확인하니 캘린더만 쓴다. 측정은 코드 기준으로 했다.
- 처음에는 Vitest(jsdom)로 쟀으나 Chromium보다 5~9배 느린 값이 나왔다. 사용자가 쓰는 곳이 아니라서 버리고, 같은 함수를 minify한 번들로 Chromium에서 다시 쟀다. 원인은 확인하지 못했다.

## 함께 확인한 것

보드 보기로 바꾸는 동안 막힌 카드마다 태스크 상세와 이력 조회가 나갔다. 태스크 500건에서 `GET /api/v1/tasks/:id` 127회, `GET /api/v1/tasks/:id/history` 254회다. 이 문제는 [#365](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/issues/365)와 BE PR [#373](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/pull/373)이 다루므로 새 작업으로 만들지 않았다.

## 검증 내역

코드를 바꾸지 않았으므로 동작 회귀 테스트는 실행하지 않았다. 아래는 문서와 측정 도구를 더한 뒤의 검사다.

| 명령 (`frontend/`, Node v24.11.0) | exit | 결과 |
|---|---|---|
| `npm.cmd run typecheck` | 0 | 오류 없음 |
| `npm.cmd run lint` | 0 | 오류 없음 |
| `npm.cmd run format:check` | 0 | 모든 파일 통과 |
| `npm.cmd run build` | 0 | 빌드 성공 |

측정 도구는 `docs/` 아래라 lint·format 대상이 아니다. 도구를 문서 폴더로 옮긴 뒤 `build.sh`와 `run.cjs`로 Chromium 측정을 다시 돌려 같은 크기의 값이 나오는 것을 확인했다(`results/rerun-chromium.json`).

## 남은 작업과 제한 사항

- 화면 비중은 개발 빌드에서만 쟀다. MSW가 개발 서버에서만 켜져 프로덕션 빌드에 같은 데이터를 넣을 수 없었다. 프로덕션의 React 렌더가 더 빨라 비중은 더 클 수 있다(추정). 한 동작의 다른 작업과 합쳐 프레임 예산을 넘는지는 이 계산의 크기만으로 정할 수 없어, 프로덕션 체감 효과는 미검증이다.
- `board` memo가 URL 변경마다 다시 도는 것은 코드 변경 후보로 측정 문서의 「고칠 거리」에 적었다. 이번 PR에서는 고치지 않았다.
- 측정 데이터는 생성한 데이터다. 실제 워크스페이스의 태스크 수와 상태 분포는 확인하지 않았다.
- 다시 잴 조건과 고칠 방법은 [측정 문서](../../../../performance/2026-11-05-taskboard-derived.md)의 「고칠 거리」와 「고칠 때 확인할 것」에 있다.
