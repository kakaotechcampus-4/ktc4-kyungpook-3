- 상태: 측정을 먼저 하고, 그 결과로 코드 변경 여부를 정하는 계획이다. 실행 결과는 [결과](result.md)에 있다.
- 근거: 이슈 #351, 현재 작업 트리의 코드(기준 `bb29989a`, #347 초점 수정 반영 후), 사용자 지시(2026-11-05: 바꾸기 전에 비용을 재고, 체감할 수 없으면 바꾸지 않는다).
- 위치: [전체 계획](../../../frontend-plan.md)의 M0~M8 번호에 속하지 않는 수정 계획이다. 전체 계획과 기존 마일스톤 계획은 수정하지 않는다.

## 목표와 배경

2026-11-04 선행 조사는 `TaskBoard`가 보기와 관계없이 `board`, `createList`, `calendarMeetings`를 계산하고, `buildTaskBoard`가 탭 개수를 세려고 `selectTab`을 탭마다 다시 부른다고 기록했다. 비용은 재지 않았다.

이 작업의 목표는 그 비용이 사용자가 느낄 크기인지 먼저 재고, 느낄 크기일 때만 줄이는 것이다. 이미 적용된 route lazy와 view lazy는 새 개선으로 세지 않는다.

## 현재 구현 확인

이슈의 코드 링크는 등록 시점(`eede45a`) 기준이다. 그 뒤 #347이 `TaskBoard.tsx`의 탭 패널 초점을 바꿨지만 파생값 계산은 바뀌지 않았다. 최신 코드에서 보기마다 읽는 파생값은 다음과 같다.

| 파생값 | 읽는 보기 |
|---|---|
| `names`, `overlaid` | 모두 |
| `meetingTitles`, `board` | 리스트 |
| `filtered` | 리스트, 보드 |
| `createList` | 캘린더, 간트 |
| `calendarMeetings` | 캘린더 |

이슈와 작업 지시는 `calendarMeetings`를 캘린더·간트가 쓴다고 적었지만, 간트는 회의를 받지 않는다. 보드 보기는 `board`가 아니라 `filtered`를 받아 직접 정렬한다.

## 작업 순서

1. **비용 측정.** 보기마다 지금 계산하는 파생값 전부와 그 보기가 읽는 것만의 비용을 태스크 50 / 500 / 2,000건에서 잰다. 프로덕션 모양 번들을 Chromium에서 돌리고, 반복 횟수와 빌드 종류를 함께 적는다.
2. **화면 전체 비중.** 같은 크기의 데이터를 넣은 실제 화면에서 파생값이 다시 계산되는 동작(보드의 담당자 바꾸기)을 재고, CPU 프로파일로 파생 함수가 차지하는 시간을 본다.
3. **판정.** 줄어들 시간이 한 동작의 화면 비용 앞에서 느낄 수 없는 크기면 코드를 바꾸지 않고 측정 기록만 남긴다.
4. **바꾼다면.**
   - 보기에 필요한 파생값만 계산한다. React Hook 호출 순서는 바꾸지 않는다.
   - 탭 개수는 한 번 훑어 센다. 목록과 탭 개수가 같은 판정을 쓴다는 `taskBoard.ts`의 불변식을 지키지 못하면 바꾸지 않는다.
   - 보기 전환, 검색·필터, 담당자 필터, 탭 개수, 정렬 결과, 확인 필요 탭이 같은지 테스트로 확인한다.
5. **기록.** 측정 문서는 `docs/performance/`, 결과는 이 폴더의 결과 문서에 둔다.
