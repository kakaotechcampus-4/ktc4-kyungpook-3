## 작업 근거와 요약

간트 보기의 `groupRows`는 팀원마다 태스크와 확인 필요 생성 승인을 처음부터 다시 걸렀다. 팀원 M명, 항목 N건이면 비교가 약 M×N번이다. 이제 팀원 ID별 묶음을 `Map`으로 먼저 만들고 태스크·승인을 한 번씩 훑어 넣는다. 화면의 묶음·순서·문구는 같다.

## 실제 구현 및 관련 코드

- **위치 이동** — [ganttGroups.ts](../../../../../src/widgets/task-board/lib/ganttGroups.ts)
  - `groupRows`와 `Group` 타입을 [GanttView.tsx](../../../../../src/widgets/task-board/ui/GanttView.tsx)에서 글자 그대로 옮겼다. 옮긴 본문과 원본은 `diff`로 같음을 확인했다. `GanttView`는 이 함수를 가져다 쓰고 `useMemo(() => groupRows(members, tasks, approvals), [members, tasks, approvals])`는 그대로다.
- **분류** — 같은 파일
  - 팀원 ID → `{ tasks, approvals }` `Map`과 `알 수 없는 담당자`·`미지정` 묶음 둘을 만든다. 항목이 어느 묶음으로 가는지는 `itemsOf` 하나가 정한다(담당자 없음 → 미지정, 팀원 목록에 있음 → 그 팀원, 그 밖 → 알 수 없는 담당자).
  - 태스크·승인을 한 번씩 훑으며 마감이 없으면 `일정이 없는 일`로, 있으면 `itemsOf`가 정한 묶음에 받은 순서대로 넣는다. 이전에는 이 규칙이 `=== member.id`, 알 수 없는 담당자 판정, `=== null` 세 곳에 태스크·승인 몫으로 두 번씩 있었다.
  - 상태 표식·색 클래스·렌더링 마크업은 바꾸지 않았다.
- **테스트** — [ganttGroups.test.ts](../../../../../src/widgets/task-board/lib/ganttGroups.test.ts) 9건
  - 팀원 순서와 알 수 없는 담당자·미지정 위치, 묶음 문구, 알 수 없는 담당자 여럿의 순서, 일이 없는 팀원과 팀원 조회 실패, 빈 목록, 승인 포함, 일정이 없는 일, 담당자 변경, 받은 객체를 그대로 담는지.
  - 옮긴 직후(변경 전 코드)에 먼저 통과시키고, 분류를 바꾼 뒤 그대로 통과했다.
  - 테스트가 동작 변화를 잡는지 확인하려고 코드를 일부러 두 가지로 바꿔 봤다. 알 수 없는 담당자를 미지정으로 보내면 5건, 일정이 없는 태스크 순서를 뒤집으면 1건이 실패했다. 확인 후 원래 코드로 되돌렸다.

## 비용 측정

- 조건: Node v24.11.0, Intel Core Ultra 7 258V(논리 8코어), Windows 11. React production 빌드(`NODE_ENV=production`, esbuild 압축 번들). 측정 중 다른 작업 트리 검사로 CPU 사용률이 약 52%였다. 변경 전·후를 번갈아 재어 같은 잡음을 받게 했다.
- 방법: 크기마다 예열 3회 후 7회 번갈아 쟀다. 한 회는 150ms 동안 반복 호출한 평균이다. 아래 수치는 중앙값 [최소–최대]이고, 같은 측정을 두 번 돌려 둘 다 적었다. 데이터는 담당자 85%가 팀원, 5%가 팀원 목록에 없는 ID, 10%가 미지정이고 마감 없음이 10%다. 승인은 태스크 수의 1/10이다.
- 잡음 확인: 변경 전 코드를 양쪽에 두고 같은 방법으로 쟀을 때 모든 크기에서 ×1.0, 회별 범위는 중앙값의 약 ±10~20%였다.

| 팀원×태스크 (승인) | 변경 전 (1차 / 2차) | 변경 후 (1차 / 2차) | 배수 | 간트 `renderToString` 대비 분류 몫 (전 → 후) |
|---|---|---|---|---|
| 5×50 (5) | 3.19µs [3.04–3.36] / 3.55µs | 2.06µs [1.90–3.06] / 2.31µs | ×1.5 | 0.23% → 0.15% |
| 5×200 (20) | 11.7µs / 12.7µs | 4.77µs / 5.69µs | ×2.2~2.5 | 0.28% → 0.11% |
| 10×500 (50) | 39.6µs / 52.1µs | 8.42µs / 11.7µs | ×4.5~4.7 | 0.45% → 0.10% |
| 20×2,000 (200) | 632µs [542–783] / 565µs | 50.5µs [47.8–62.6] / 51.8µs | ×10.9~12.5 | 1.15~1.31% → 0.09~0.12% |
| 50×5,000 (500) | 3,535µs / 3,113µs | 225µs / 204µs | ×15.3~15.7 | 1.91~2.27% → 0.12~0.15% |

- 무엇이 비용을 정하는지: 변경 전은 5×50에서 50×5,000으로 갈 때(팀원 ×10, 항목 ×100) 약 1,000배, 변경 후는 약 100배 늘었다. 변경 전은 팀원 수×항목 수, 변경 후는 항목 수에 비례한다는 해석과 맞는다. 프로파일러로 확인하지는 않았고, 크기별 증가율에서 추론한 것이다.
- 체감: 같은 데이터로 간트 전체를 `renderToString`한 시간(1.2ms~185ms) 대비 변경 전 분류 몫은 2.3% 이하였다. 브라우저 렌더는 DOM 반영까지 더해지므로 실제 몫은 이보다 작을 것으로 추정한다(측정하지 않음). 분류는 `useMemo` 안에 있어 데이터가 바뀔 때만 돈다. 지금 MSW fixture 규모(팀원 4명)에서는 1회 몇 µs 차이라 사용자가 느낄 개선은 없다. 큰 공간(20명×2,000건)에서 데이터 변경 1회당 약 0.5ms가 줄었다.
- 유지 판단: 출력이 같고, 항목이 어느 묶음으로 가는지 정하는 규칙이 여섯 개의 걸러내기에서 `itemsOf` 하나로 모였다. 읽을 때 따라갈 규칙이 줄어서 유지했다. 성능 개선만으로 유지를 주장하지 않는다.
- 측정 스크립트는 작업 트리의 git 무시 경로 `.verify/bench/`에 두었다(커밋하지 않음).

## 남은 작업과 제한 사항

- 전체 Vitest(`npm run test`)와 E2E는 여러 작업 트리가 같은 머신에서 동시에 돌아 이 작업에서 실행하지 않았다. 간트를 그리는 앱 통합 테스트 3개 파일은 위와 같이 통과했다.
