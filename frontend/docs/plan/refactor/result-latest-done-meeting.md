## 작업 근거와 요약

대시보드의 `latestDoneMeeting`은 회의 하나를 고르려고 `toMinutesList`로 전체 목록을 복사·정렬하고 세 번 걸렀다. 이제 완료 회의만 보며 한 번 훑어 고른다. 선택 결과와 동률 처리는 바뀌지 않았다.

## 실제 구현 및 관련 코드

- **선택 함수** — [dashboard.ts](../../../src/widgets/dashboard/lib/dashboard.ts)의 `latestDoneMeeting`
  - `status === 'done'`인 회의만 본다. `Date.parse(startedAt)`가 지금 후보보다 클 때만 후보를 바꾼다. 같은 시점이면 바꾸지 않아 받은 순서에서 앞의 회의가 남는다.
  - 시작 시각을 읽을 수 없으면(`NaN`) `-Infinity`로 친다. [minutesList.ts](../../../src/entities/meeting/lib/minutesList.ts)의 `startedAtOf`와 같은 규칙이다.
  - `toMinutesList` import를 지웠다. 반환값은 입력 배열의 원소 그대로라 참조가 이전과 같다.
- **바꾸지 않은 것**
  - [minutesList.ts](../../../src/entities/meeting/lib/minutesList.ts). 회의록 화면은 세 목록을 모두 그리므로 정렬이 필요하다. #256이 같이 고칠 수 있는 파일이라 날짜 규칙을 공유하려고 손대지 않았다.
  - [useDashboardData.ts](../../../src/widgets/dashboard/model/useDashboardData.ts). 아래 측정에서 30건 기준 호출 1회가 약 3~4µs라 `useMemo`를 더하지 않았다.
- **테스트** — [dashboard.test.ts](../../../src/widgets/dashboard/lib/dashboard.test.ts) 「최신 완료 회의 선택 기준 (#350)」 7건
  - 빈 목록은 null이다.
  - 받은 순서와 상관없이 가장 늦은 완료 회의를 고르고, 더 늦은 `processing`·`failed`는 건너뛴다.
  - `+09:00`과 `Z` 시각을 문자열이 아니라 시점으로 비교한다.
  - 같은 시점이면 받은 순서에서 앞의 회의다.
  - 날짜를 읽을 수 없는 완료 회의는 날짜가 있는 회의보다 뒤다.
  - 모든 완료 회의의 날짜를 읽을 수 없으면 받은 순서의 첫 완료 회의다.
  - 고정 시드 임의 입력 200개에서 회의록 기본 진입(`latestMinutesId`)과 같은 회의를 고른다.

## 검증 내역

### 테스트가 잘못된 구현을 잡는지 (변형 검사)

`dashboard.ts`를 잠시 바꿔 `dashboard.test.ts`를 돌린 뒤 되돌렸다.

| 변형 | 결과 |
|---|---|
| 동률이면 뒤의 회의를 고른다(`>` → `>=`) | 3건 실패(동률 2건, 대조 1건) |
| 읽을 수 없는 날짜를 `-Infinity`로 바꾸지 않는다 | 2건 실패(날짜 누락 1건, 대조 1건) |

처음 쓴 대조 테스트의 난수 생성기는 2의 거듭제곱 나머지의 하위 비트를 써서 주기가 짧았고, 동률 변형을 놓쳤다. MINSTD(`seed * 48271 % 2147483647`)로 바꾼 뒤 위 결과가 나왔다.

### 측정

- 방법: 실제 `toMinutesList(...).minutes[0]`(변경 전)와 새 `latestDoneMeeting`을 esbuild로 한 파일에 묶어(minify) Node v24.11.0에서 돌렸다. 크기마다 두 쪽을 7회씩 번갈아(A, B, B, A …) 재고, 한 표본은 약 200ms 동안 반복 호출한다. 결과의 `id` 길이를 합산해 계산이 버려지지 않게 했고, 크기마다 두 쪽의 결과가 같은 객체인지 먼저 확인했다.
- 데이터: 고정 시드로 만든 회의 목록. 상태는 `done` 4/7, 나머지 3/7. 시작 시각은 2026년 안의 무작위 분 단위 ISO 문자열이고 정렬하지 않았다.
- 환경: Windows 11, 논리 코어 8개. 다른 워크트리 작업이 함께 돌아 CPU 사용률이 39~65%였다.

호출 1회 시간, 2회 실행(run 1 / run 2) 각각의 7회 중앙값과 범위다.

| 크기(완료 수) | 변경 전 | 변경 후 | 배율 |
|---|---|---|---|
| 30 (17) | 49.2µs [35.8–69.7] / 53.4µs [48.8–60.0] | 3.27µs [2.44–4.34] / 3.82µs [3.60–4.13] | 15.0× / 14.0× |
| 1,000 (587) | 4.05ms [3.90–5.55] / 4.19ms [3.99–4.44] | 0.141ms [0.138–0.149] / 0.143ms [0.139–0.152] | 28.7× / 29.4× |
| 10,000 (5,717) | 61.4ms [56.4–71.7] / 61.8ms [59.0–69.4] | 1.59ms [1.43–1.72] / 1.50ms [1.46–1.58] | 38.7× / 41.3× |

- 모든 크기에서 두 쪽의 범위가 겹치지 않는다.
- 제한 요인은 두 쪽 모두 `Date.parse`다. 측정에 쓰지 않은 별도 실행의 CPU 프로파일에서 자체 시간은 `startedAtOf` 43.3%, 새 `latestDoneMeeting` 47.8%였고, 정렬(`byStartedAtDesc`)과 비교 함수는 합쳐 3.8%다. 변경 전은 정렬 비교마다 날짜를 두 번 읽어 O(n log n)번, 변경 후는 완료 회의마다 한 번 읽는다. 1,000건이면 비교 약 1만 번 × 2회 × 약 200ns ≈ 4ms로 측정과 맞다. 크기가 커질수록 배율이 커지는 것도 이 차이(log n)와 맞다.
- 사용자 체감: 실제 규모(수십 건)에서 줄어든 시간은 렌더 1회당 약 45~50µs다. 60Hz 한 프레임(16.7ms)의 0.3% 정도라 체감 개선은 주장하지 않는다. 대시보드 렌더 전체 시간은 재지 않았다. 1만 건에서는 렌더 1회당 약 60ms가 빠지므로 목록이 커지면 프레임 하나 이상을 아낀다(추정, 화면에서 재지 않음).

## 계획 대비 변경

- 대조 테스트의 난수 생성기를 바꿨다(위 「변형 검사」). 계획의 작업 순서는 그대로다.
- 작업 순서 3의 `useMemo`는 측정 결과에 따라 더하지 않았다.

## 남은 작업과 제한 사항

- 날짜 해석 규칙이 `dashboard.ts`와 `minutesList.ts` 두 곳에 있다. 대조 테스트가 어긋남을 잡는다. #256 병합 뒤 `minutesList.ts`에서 고르는 함수를 공개해 한 곳으로 모을 수 있다.
- 측정은 Node 기준이다. 브라우저에서 대시보드 렌더 시간은 재지 않았다.
- 전체 Vitest·E2E는 병합 담당이 돌린다.
