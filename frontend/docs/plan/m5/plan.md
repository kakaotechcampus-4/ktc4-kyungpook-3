# M5 구현 계획 — 회의 업로드 → 정리 → 회의록

## 1. 목표와 확정 범위

MSW 환경에서 음성 파일 업로드부터 정리 완료·실패, 회의록 확인까지 완결한다. 현재 회의·회의록 모델과 MSW API를 재사용하고, 자리표시자인 회의 화면과 업로드 후 상태 전이를 구현한다.

- **PM만 업로드**한다. 처리 중 다시 `회의 올리기`에 접근하면 현재 처리 화면으로 이동한다.
- Discord는 자동 수집된 회의의 상태·참석자·회의록 조회만 지원한다.
- 원본 재생과 텍스트 업로드는 제외한다.
- 파일은 **MP3·WAV·M4A·OGG·WebM, 최대 200 MiB·2시간**으로 제한한다.
- 상단 회의록 내비게이션 옆에 모든 팀원이 접근할 수 있는 `정리 중` 링크를 표시한다.
- 승인·반려·태스크 수정은 M6에 둔다. M5는 반영 항목과 확인 필요 항목을 표시하고 기존 상세 경로로 연결한다.
- Notion 연결 복귀에 필요한 **설정 화면의 Notion 연결 영역만** M8에서 앞당긴다.

디자인은 `Upload`·`Processing`·`Meetings`·`EmptyMeetings` 캔버스를 따르되, 위 정책과 기존 디자인 토큰을 우선한다.

## 2. 데이터·라우팅 기반

### 경로와 API

- 기존 `/workspaces/:workspaceId/meetings/:meetingId?`를 목록·상세 화면으로 유지한다.
- `/workspaces/:workspaceId/meetings/upload`와 `/workspaces/:workspaceId/meetings/:meetingId/processing`을 추가한다. `upload`가 회의 ID로 해석되지 않도록 별도 라우트로 등록한다.
- 업로드 경로에는 기존 PM 가드를 적용한다. 처리·회의록 경로는 워크스페이스 팀원에게 허용한다.
- `entities`에 회의 목록·상세·업로드, 회의록 본문, 추출 결과, 대기 승인 목록의 API 함수와 Query 옵션을 추가한다. DTO 변환은 해당 엔티티 내부에 유지한다.
- 업로드 입력은 `File`, 제목, 회의 시각, 참석자 ID 목록으로 정의한다. 기존 multipart 계약을 유지하고 `attendee_member_ids`는 동일 이름 필드를 반복 전송한다.
- 공통 요청 옵션에 Axios 타입을 노출하지 않는 업로드 진행 콜백을 추가한다. 전체 크기를 모르면 불확정 진행 표시를 사용한다.

### 캐시와 구성

- 모든 업무 Query Key에 `workspaceId`를 포함한다. 목록·추출·승인 목록은 기본 30초, 완료 회의록 본문은 5분의 최신 시간을 사용한다.
- 페이지는 라우트 조립, feature는 업로드·연결·처리 추적 행동, widget은 회의록과 여러 엔티티의 조합을 담당한다.
- 앱 계층에서 처리 추적과 헤더를 조립한다. 헤더에는 처리 중 회의 링크를 props로 전달해 widget 간 직접 참조를 피한다.
- 회의 상세의 `workspaceId`가 URL과 일치하는지 확인한 뒤 본문·추출 조회를 시작한다.

## 3. 사용자 흐름

### 업로드와 Notion 연결

- 진입 시 회의 목록·연동 상태를 확인한다. 처리 중 회의가 있으면 해당 처리 화면으로 이동하고, 없으면 Notion 연결을 검사한다.
- `not_connected`와 `revoked`는 각각 문서에 정해진 차단 모달을 표시한다. 조회 실패는 미연결로 간주하지 않고 재시도 UI를 제공한다.
- 연결 버튼은 설정의 Notion 영역으로 이동한다. 복귀 목적은 현재 워크스페이스의 업로드 경로로 제한한다.
- 기존 현재 탭 OAuth 방식과 결과 파서를 재사용한다. 성공 콜백 뒤 연동 상태를 다시 조회해 `connected`일 때만 업로드로 복귀한다. 취소·실패는 설정에 머문다.
- 설정의 연결·재연결 액션은 PM에게만 제공한다. 일반 팀원에게는 상태와 PM에게 연결을 요청하는 안내를 표시한다.

### 파일 입력과 제출

- 파일 선택기와 드래그앤드롭을 제공하고 여러 파일을 한 번에 넣으면 오류를 표시한다.
- 제목 기본값은 확장자를 포함한 파일명이다. 날짜는 `lastModified`의 서울 날짜로 표시한다. 수정하지 않으면 원래 시각을 전송하고, 날짜를 수정하면 선택 날짜의 서울 자정에 해당하는 ISO 시각을 전송한다.
- 등록 팀원만 참석자로 선택할 수 있으며, 공백뿐인 제목과 참석자 0명은 제출을 막는다.
- 빈 파일, 허용하지 않는 형식, 용량·길이 초과를 검사한다. 브라우저에서 길이를 읽을 수 없는 파일은 형식 확인 안내와 함께 제출을 막는다. 메타데이터 조회에 사용한 object URL은 해제한다.
- 파일 교체 시 제목·날짜 기본값을 새 파일 기준으로 갱신하고 참석자 선택은 유지한다.
- 전송률과 서버 정리 단계를 구분한다. 전송률 100%만으로 완료 처리하지 않고, 서버의 202 응답 후 처리 화면으로 이동한다.
- 제출 연타와 자동 재전송을 막는다. 응답을 잃은 경우 회의 목록을 재조회해 처리 중 회의가 있는지 먼저 확인한다.
- 파일 선택 이후 이탈은 기존 미저장 변경 확인을 사용한다. 202 수신 후에는 입력·파일 참조를 해제하고 앱 내부 이동을 허용한다.
- 동시 업로드 경쟁은 서버의 409와 `details.meeting_id`로 처리 화면에 연결한다. 413·검증 오류는 폼에 표시하고, 연동 오류는 차단 흐름으로 전환한다.

### 처리 추적

- 인증된 앱 영역에 처리 추적기를 두어 페이지 이동으로 polling이 끊기지 않게 한다. 현재 공간의 목록에서 처리 중 회의를 발견하고, 업로드 응답으로 받은 회의도 즉시 등록한다.
- 발견한 회의는 워크스페이스 전환 후에도 종료까지 추적한다. 새로고침 시에는 현재 공간의 목록으로 복원한다. 전체 공간을 순회 조회하지 않는다.
- 상세 상태는 **3초 간격**, 처리 중에만 polling한다. 완료·실패·접근 권한 상실 시 중단하고 로그아웃 시 추적 상태를 정리한다.
- 서버의 세 가지 `progress` 값을 단계 표시로 사용한다. 임의의 처리 백분율·남은 시간을 만들지 않는다.
- 완료 시 관련 회의·회의록·태스크·승인 캐시를 무효화하고, 회의별 한 번만 `회의 정리가 끝났어요`와 `회의록 보기` 토스트를 표시한다. 처리 화면을 보고 있으면 해당 회의록으로 이동한다.
- 일반 실패는 실패 회의를 목록에서 제외하고 지정된 재업로드 토스트를 표시한다. 해당 처리 화면을 보고 있을 때 회의록 목록으로 이동하며, 다른 화면이나 공간의 사용자를 강제로 이동시키지 않는다.
- 실패 시 연동 상태를 다시 확인해 `revoked`이면 재연결 모달로 분기한다. 실패 원본과 결과를 재사용하지 않는다.
- 일시적인 네트워크 조회 오류를 회의 정리 실패로 처리하지 않는다. 연결 복귀 시 다시 조회한다.

### 회의록

- 목록은 회의 날짜 최신순으로 표시한다. 기본 진입에서는 가장 최근 완료 회의를 선택하고 URL을 `replace`한다. 명시적으로 선택한 회의는 재조회 후에도 유지한다.
- 처리 중 회의는 별도 상태 항목으로 표시해 처리 화면으로 연결한다. 완료 회의가 없으면 빈 상태를 표시하며 업로드 CTA는 PM에게만 제공한다.
- 제목·날짜·참석자·출처·요약·전사문·반영 태스크를 표시한다. `summary: null`, 빈 전사문, 누락된 추출 결과는 각각 빈 상태로 처리한다.
- 반영 태스크는 기존 `appliedItems`, 확인 필요 항목은 `pendingItems`와 대기 승인 ID 집합으로 구성한다. 승인 후 중복 노출과 반려 항목 노출을 방지한다.
- 일반 팀원은 승인 목록을 요청하지 않으며 확인 필요 영역·개수·변경 액션을 표시하지 않는다. PM도 서버의 회의록 권한 값을 함께 확인한다.
- 승인 필요 항목은 기존 승인 상세 경로, 반영 태스크는 기존 태스크 상세 경로로 연결한다. 원본 재생·검색·편집 등 범위 밖의 캔버스 액션은 추가하지 않는다.
- Notion 설명은 “회의록과 확실한 태스크는 즉시 반영, 확인 필요 항목은 승인 후 반영”으로 수정한다. 긴 전사문 블록에는 `content-visibility`를 적용한다.

## 4. MSW와 구현 순서

1. **계약·기반:** 이번 권한·한도·경로 결정을 구현 결정 문서에 기록하고 API 함수, Query 옵션, 업로드 진행 콜백을 추가한다.
2. **MSW 수직 흐름:** 업로드된 회의의 완료·실패 전이와 회의록·추출·태스크·승인 데이터를 일관되게 생성하는 공통 도우미를 만든다.
3. **업로드·연결:** 파일 폼, 진입 가드, 최소 Notion 설정 영역과 OAuth 복귀를 완성한다.
4. **처리 추적:** 처리 화면, 앱 수준 polling, 상단 상태 링크와 전역 알림을 연결한다.
5. **회의록·검증:** 목록·상세·권한 분기를 구현하고 Storybook·통합·E2E 검증을 마친다.

MSW 기본 계약 테스트는 현재처럼 상태를 명시적으로 제어한다. 브라우저 데모에는 단계가 보이는 시나리오를, E2E에는 인위적 지연 없이 완료하는 시나리오를 추가한다. 원본 `File`은 영속 저장하지 않고 생성된 데이터와 처리 시나리오만 기존 저장 체계에 통합한다.

실 백엔드는 여전히 파일 저장·큐 전송이 TODO이며 PM 전용 업로드도 강제하지 않는다. 백엔드 수정은 M5에 포함하지 않고 계약의 백엔드 요청 목록에 권한 강제를 추가한다. 실제 STT·Notion 연동 성공은 M5 완료 조건으로 삼지 않는다.

## 5. 검증과 완료 기준

- **단위:** 파일 한도 경계, 길이 판독 실패, 제목·참석자 검증, 날짜 변환, 진행 상태·권한 판정.
- **통합:** multipart 참석자 복수 전송, 제출 중복 방지, 409·413·401, Notion 미연결·끊김과 OAuth 성공·취소·실패, polling 종료·알림 중복 방지, 워크스페이스 전환과 새로고침 복원.
- **회의록:** 최신 자동 선택, 직접 링크 유지, 실패 회의 제외, 빈 본문, 승인·반려 항목 분리, 일반 팀원의 승인 API 미호출과 영역 비노출.
- **Playwright:** 유효한 짧은 음원으로 업로드 → 정리 완료 → 해당 회의록 확인, 다른 페이지에서 완료 토스트로 이동, 일반 팀원의 업로드 직접 접근 차단.
- **Storybook·수동:** 업로드·처리·완료·빈 상태·오류·권한별 화면, 1024/1440/1920px 레이아웃, 키보드 파일 선택·참석자 선택·모달 포커스, 전역 토스트와 동적 상태 안내.
- 기존 `typecheck`, `lint`, `format:check`, `test`, `build`, `build-storybook`, `test:e2e`를 통과한다. 프로덕션 번들에 MSW 시나리오가 포함되지 않는지 확인한다.

완료 기준은 **MSW에서 핵심 흐름과 실패 복구가 동작하고, PM·팀원 권한 및 기존 M4 흐름의 회귀가 없는 것**이다.
