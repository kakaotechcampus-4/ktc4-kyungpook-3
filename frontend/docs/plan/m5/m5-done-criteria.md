## 판정 규칙

1. 단위(U1~U6)마다 **구현 → 검증 → (FAIL이면) 수정 → 재검증** 루프를 돈다.
2. 검증자는 보고서에 기준 ID별 `PASS | FAIL`과 근거(명령 출력 요약, 파일:줄, 테스트 이름)를 적는다. 기준 밖 결함은 `blocker | major | minor`로 분류해 따로 적는다.
3. 단위 통과 = 해당 단위 기준 + 공통 게이트 G 전부 PASS, `blocker`·`major` 0건. `minor`는 다음 단위에서 함께 처리하거나 사유를 남기고 넘긴다.
4. 같은 단위에서 4회차까지 통과하지 못하거나, 계획과 코드·결정·백엔드가 충돌해 결정이 필요하면 사용자에게 올린다.
   - 2026-10-05: U4가 4회차(M06)에서 미통과. 사용자가 "연동 상태 캐시 쓰기 경로를 공유 Query 하나로 단일화"하는 5회차를 승인했다.
5. 앞 단위에서 PASS한 기준이 뒤 단위에서 깨지면 그 단위의 FAIL로 본다(회귀).
6. 마지막에 최종 게이트 F를 전체 기준으로 한 번 더 검증한다.

## U3. 업로드·Notion 연결 (계획 §3 업로드와 Notion 연결, 파일 입력과 제출)

- **U3-1** 진입: 처리 중 회의가 있으면 그 처리 화면으로 `replace` 이동, 없으면 Notion 연동 상태를 검사한다. `not_connected`·`revoked`는 결정 문서(D-097·D-100)에 정해진 각각의 차단 모달, 조회 실패는 미연결로 취급하지 않고 재시도 UI.
- **U3-2** 연결 버튼은 설정의 Notion 영역으로 이동하고 복귀 목적지는 현재 워크스페이스의 업로드 경로로만 제한된다(외부·다른 공간 경로 거부 테스트). 기존 현재 탭 OAuth와 결과 파서를 재사용하고, 성공 콜백 뒤 연동 상태를 재조회해 `connected`일 때만 업로드로 복귀한다. 취소·실패는 설정에 머무르며 안내를 보인다.
- **U3-3** 설정 화면에는 Notion 연결 영역만 추가된다. 연결·재연결 액션은 PM에게만, 일반 팀원은 상태와 "PM에게 연결 요청" 안내만 본다.
- **U3-4** 파일 선택기·드래그앤드롭. 여러 파일 동시 투입, 빈 파일, 허용하지 않는 형식(MP3·WAV·M4A·OGG·WebM 외), 200 MiB 초과(경계: 정확히 200 MiB는 통과, 1바이트 초과는 차단), 2시간 초과(경계 동일), 길이 판독 실패(형식 확인 안내와 함께 제출 차단)를 검사한다. 메타데이터용 object URL은 성공·실패 모두에서 해제된다(단위 테스트).
- **U3-5** 제목 기본값 = 확장자 포함 파일명, 날짜 표시 = `lastModified`의 서울 날짜. 날짜를 수정하지 않으면 원래 시각, 수정하면 선택 날짜 서울 자정의 ISO 시각을 전송한다(단위 테스트, 자정 경계 포함). 파일 교체 시 제목·날짜는 새 파일 기준으로 갱신되고 참석자 선택은 유지된다.
- **U3-6** 등록 팀원만 참석자 후보다. 공백뿐인 제목·참석자 0명은 제출이 막힌다.
- **U3-7** 전송률과 서버 정리 단계를 구분해 표시한다. 전송률 100%만으로 완료 처리하지 않고 202 응답 뒤 처리 화면으로 이동한다. 전체 크기를 모르면 불확정 진행 표시.
- **U3-8** 제출 연타·자동 재전송이 없다(업로드 POST 정확히 1회 테스트, Query/Mutation retry 0). 응답을 잃은 경우(네트워크 오류) 회의 목록을 재조회해 처리 중 회의가 있으면 그 처리 화면으로 연결한다.
- **U3-9** 파일 선택 뒤 이탈은 기존 미저장 변경 확인을 쓴다. 202 수신 뒤에는 입력·파일 참조를 해제하고 확인 없이 이동한다.
- **U3-10** 409 `MEETING_PROCESSING_IN_PROGRESS` + `details.meeting_id` → 해당 처리 화면. 413·400 검증 오류 → 폼에 표시. 연동 오류(`INTEGRATION_NOT_CONNECTED`·`INTEGRATION_REVOKED`) → 차단 흐름. 401 → 기존 세션 만료 처리.
- **U3-11** 일반 팀원의 업로드 경로 직접 진입은 기존 PM 가드로 차단되고 업로드 관련 요청은 0회다.

## U4. 처리 추적 (계획 §3 처리 추적)

- **U4-1** 처리 추적기가 인증된 앱 영역(앱 계층)에 있어 페이지 이동으로 polling이 끊기지 않는다. 현재 공간 목록에서 처리 중 회의를 발견하고, 업로드 202 응답의 회의도 즉시 등록한다.
- **U4-2** 발견한 회의는 워크스페이스 전환 뒤에도 종료까지 추적된다. 새로고침 시 현재 공간 목록으로 복원된다. 다른 공간 목록을 순회 조회하지 않는다(요청 경로 단언).
- **U4-3** 상세 상태 polling은 3초 간격, 처리 중에만 동작한다. 완료·실패·접근 권한 상실(403·404)에 중단, 로그아웃 시 추적 상태가 정리된다(fake timer 또는 요청 횟수 테스트).
- **U4-4** 처리 화면은 서버의 세 `progress` 값을 단계 표시로만 쓴다. 임의 백분율·남은 시간 문구가 없다.
- **U4-5** 완료 시 관련 회의·회의록·태스크·승인 캐시를 무효화하고, 회의별 정확히 한 번 `회의 정리가 끝났어요` + `회의록 보기` 토스트를 띄운다(재렌더·재발견·탭 이동에도 중복 없음 테스트). 처리 화면을 보고 있으면 해당 회의록으로 이동한다.
- **U4-6** 일반 실패: 실패 회의는 목록에서 빠지고 결정 문서(D-092)의 재업로드 토스트가 뜬다. 해당 처리 화면을 보고 있을 때만 회의록 목록으로 이동하고, 다른 화면·공간의 사용자는 이동시키지 않는다.
- **U4-7** 실패 시 연동 상태를 재조회해 `revoked`면 재연결 모달로 분기한다(D-100). 실패 원본·결과를 재사용하지 않는다.
- **U4-8** 일시적 네트워크 조회 오류는 정리 실패로 처리하지 않고(토스트·이동 없음), 연결 복귀(온라인·포커스) 시 다시 조회한다.
- **U4-9** 헤더의 회의록 내비게이션 옆에 모든 팀원이 보는 `정리 중` 링크가 처리 중일 때만 나타나 처리 화면으로 연결된다. 링크 데이터는 앱 계층이 props로 전달하고 widget 간 직접 참조가 없다.
- **U4-10** PM이 처리 중 `회의 올리기`에 접근하면 현재 처리 화면으로 이동한다(D-090). 처리 상태 변화는 스크린리더용 동적 안내(`role="status"` 등)로 전달된다.

## U5. 회의록 (계획 §3 회의록)

- **U5-1** 목록은 회의 날짜 최신순. 기본 진입은 가장 최근 완료 회의를 선택하고 URL을 `replace`한다. 명시적으로 고른 회의(직접 링크 포함)는 재조회 뒤에도 유지된다.
- **U5-2** 처리 중 회의는 별도 상태 항목으로 보이고 처리 화면으로 연결된다. 실패 회의는 목록에 없다. 완료 회의가 없으면 `EmptyMeetings` 빈 상태, 업로드 CTA는 PM에게만.
- **U5-3** 상세: 제목·날짜·참석자·출처·요약·전사문·반영 태스크. `summary: null`, 빈 전사문, 누락된 추출 결과는 각각 빈 상태로 그린다.
- **U5-4** 회의 상세의 `workspaceId`가 URL과 일치하는지 확인한 뒤에만 본문·추출을 조회한다(불일치 시 본문·추출 요청 0회 테스트).
- **U5-5** 반영 태스크 = 기존 `appliedItems`, 확인 필요 = `pendingItems` ∩ 대기 승인 ID 집합. 승인된 항목이 확인 필요에 중복으로 남지 않고 반려 항목은 보이지 않는다(테스트).
- **U5-6** 일반 팀원은 승인 목록을 요청하지 않고(요청 0회) 확인 필요 영역·개수·변경 액션이 DOM에 없다. PM도 서버의 회의록 `permissions` 값을 함께 확인해 노출한다.
- **U5-7** 확인 필요 항목은 기존 승인 상세 경로, 반영 태스크는 기존 태스크 상세 경로로 연결된다. 원본 재생·검색·편집 등 범위 밖 액션이 없다.
- **U5-8** Notion 설명 문구는 "회의록과 확실한 태스크는 즉시 반영, 확인 필요 항목은 승인 후 반영" 취지로 바뀌어 있다. 긴 전사문 블록에 `content-visibility`가 적용돼 있다.
- **U5-9** Discord 자동 수집 회의는 상태·참석자·회의록 조회만 되고 업로드 관련 액션이 없다.

## U6. Storybook·E2E·문서 (계획 §5)

- **U6-1** Storybook: 업로드(기본·드래그 중·오류·전송 중·불확정)·처리(단계별)·회의록(완료·빈 본문·빈 목록·PM/팀원)·차단 모달·설정 Notion 영역(PM/팀원)·`정리 중` 링크 스토리. `npm run build-storybook`, `npm run test:storybook` 통과.
- **U6-2** Playwright E2E(독립 초기화): ① 유효한 짧은 음원으로 업로드 → 정리 완료 → 해당 회의록 확인 ② 업로드 후 다른 페이지로 이동 → 완료 토스트의 `회의록 보기`로 이동 ③ 일반 팀원의 업로드 직접 접근 차단 ④ 정리 실패 → 재업로드 토스트·목록 제외. `npm run test:e2e` 통과(기존 M4 E2E 포함).
- **U6-3** 1024·1440·1920px 레이아웃(E2E 뷰포트 또는 스크린샷 근거), 키보드만으로 파일 선택·참석자 선택·모달 포커스 가두기·복귀 확인.
- **U6-4** CI 워크플로가 새 E2E·Storybook 검사를 그대로 실행한다(필요하면 `frontend-ci.yml` 갱신).
- **U6-5** 문서: 구현 결정 문서, 계약의 백엔드 요청 추가, 계획 문서에 완료 판정(MSW 흐름)과 실 백엔드 미완료(파일 저장·큐·PM 강제·STT·Notion)가 구분돼 기록. `m5-handoff.md`에 루프 이력과 남은 minor.
