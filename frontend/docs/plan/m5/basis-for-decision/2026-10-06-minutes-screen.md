# 회의록 화면 — 기본 선택, 공간 확인, 확인 필요의 조인, 캔버스에서 뺀 것

- 날짜: 2026-10-06
- 상태: 결정

## 고민

M5 U5 에서 자리표시자였던 회의 화면(`/workspaces/:workspaceId/meetings/:meetingId?`)을 회의록 목록·상세로 바꿨다. 갈린 곳이 다섯이었다.

- **기본 선택.** D-106 은 「처음 진입하면 가장 최근 회의록을 자동 선택」이다. 화면 안에서만 고르면 주소가 회의를 가리키지 않아 공유·새로고침에서 다른 회의가 열린다. 주소를 바꾸면 목록이 늦게 올 때 앞 단위의 결함(U3 r1 M02, U4 r1 M01 — 늦게 끝난 작업이 떠난 사용자를 끌고 옴)과 같은 모양이 생긴다.
- **공간 확인.** 회의 상세(`GET /meetings/{id}`)는 봇 경로라 경로에 공간이 없다(계약 §2.3). 다른 공간의 회의 ID 를 URL 에 넣어도 답이 온다. 회의록 본문(`/minutes`)에는 `workspace_id` 가 없어 응답만으로는 어느 공간 것인지 모른다.
- **확인 필요.** 추출 응답만으로는 대기와 반려가 구분되지 않는다(계약 §3.1, §4.0-②-12). 승인 뒤에도 `approval_id` 가 남는다.
- **권한.** D-104 는 일반 팀원에게 확인 필요 영역·개수를 숨긴다. 서버는 회의록 응답의 `permissions.can_review` 로 같은 판정을 준다. 역할(소속 목록)과 서버 권한 중 무엇을 따를지.
- **캔버스.** `Meetings` 캔버스에는 원본 듣기·Notion에서 보기·검색·되돌리기가 있고, `EmptyMeetings` 에는 텍스트 붙여넣기가 있다. 계획 §1 은 원본 재생·텍스트 업로드·검색·편집을 뺐다. 반대로 캔버스에는 PM 이 업로드로 가는 길이 목록 화면에 없다.

## 고른 길

**기본 선택 — 페이지가 주소를 `replace` 한다. 기록의 지금 경로가 아직 그 목록일 때만.**

```
pages/meetings  useDefaultMinutesSelection(ws, requested)
  목록 Query(select: latestMinutesId) → 회의가 URL 에 없고, useLivePathname() 이 /workspaces/ws/meetings 이면
  useGuardedNavigate()(paths.meetings(ws, latest), { replace: true })
widgets/meeting-minutes  MeetingMinutes — 고른 회의는 URL 의 meetingId 로만 정한다
```

- 고른 회의는 주소가 정한다. 목록을 다시 받아도, 더 최근 회의가 정리돼도 명시적으로 고른 회의(목록 클릭·직접 링크·완료 토스트)는 그대로다 — 주소에 회의가 있으면 기본 선택 훅은 아무것도 하지 않는다.
- 늦게 온 목록의 이동은 U4 r5 구조를 그대로 쓴다(`shared/lib/live-pathname`). 지연 로드 화면을 기다리는 동안에도 기록은 이미 새 경로라 끌고 오지 않는다. 로그아웃·공간 전환도 경로가 바뀌어 같은 검사로 걸린다. 공간 전환은 레이아웃이 화면을 공간 key 로 다시 마운트하고, 로그아웃은 캐시를 비워 답이 화면에 닿지 않는다.
- 기본 선택은 「정리 끝난(`done`) 회의 중 가장 최근」이다. 더 최근이라도 정리 중인 회의는 고르지 않는다.
- 캐시에 직접 쓰지 않는다. 목록·상세·본문·추출·승인 모두 엔티티의 Query 옵션을 `useQuery` 로 읽기만 한다.

**공간 확인 — 상세의 `workspaceId` 가 URL 과 같을 때만 본문·추출을 부른다.**

- 상세 Query 는 URL 공간을 key 에 넣는다(U1). 응답의 `workspaceId` 가 다르면 `이 회의를 볼 수 없어요` 로 그리고 본문·추출·승인 요청을 0회로 둔다. 회의록 본문·추출 조회는 상세가 일치하고 `done` 인 경우에만 마운트되는 컴포넌트가 시작한다.
- 추출 응답의 `meeting_id` 가 그 회의가 아니면 그 회의의 결과로 쓰지 않는다(빈 상태).

**확인 필요 — `pendingItems` ∩ 대기 승인 ID, 조인은 widget.**

- 반영 = `appliedItems`(task_id 우선). 승인으로 태스크가 생긴 항목은 반영에만 한 번 있다.
- 확인 필요 = `pendingItems(extraction, approvalIds(GET /approvals?status=pending))`. 반려·승인으로 닫힌 승인은 대기 목록에서 빠져 자동으로 제외된다.
- 확인 사유(담당자·마감)는 대기 승인 payload 의 `missing` 으로 만든다. 같은 조인에서 함께 나온다(`widgets/meeting-minutes/lib/extractedTasks.ts`).

**권한 — 역할과 서버 권한을 모두 본다.**

- 확인 필요 영역과 승인 목록 조회는 `role === 'pm'` **이고** 회의록 `permissions.can_review` 가 true 일 때만이다. 승인 목록 Query 는 `enabled` 로 막아 일반 팀원은 요청 0회다.
- 일반 팀원의 `추출된 일` 개수는 반영된 것만 센다. Notion 안내도 확인 필요를 언급하지 않는 앞 문장만 보인다(D-104).

**캔버스 — 뺀 것과 더한 것.**

- 뺀 것: 원본 듣기, Notion에서 보기, 검색, 되돌리기(M6), 텍스트로 붙여넣기, `태스크에서 전부 보기`(확인 필요 탭의 태스크 화면이 M6). 목록 행의 확인 필요 개수 배지도 뺐다 — 회의마다 추출을 불러야 한다.
- 더한 것: 목록 머리의 `회의 올리기`(PM 만, 캔버스의 검색 자리). 업로드로 가는 다른 길이 없다. 회의 상세 안에는 업로드 관련 행동이 없다 — Discord 회의는 상태·참석자·회의록 조회만이다(U5-9).
- 탭 세 개(요약 · 전사문 · 추출된 일 N)는 캔버스대로 둔다. 캔버스의 `요약` 탭이 반영·확인 필요 목록을 보이지만, 요약 본문(개요·핵심 내용·결정)을 둘 자리가 따로 없어 `요약` 은 요약, `추출된 일` 은 반영·확인 필요로 나눴다.
- 정리 중 회의는 목록 위 `진행 중` 묶음의 상태 항목이고 처리 화면으로 잇는다. 봇이 기록 중인 회의(`created`·`recording`)는 갈 곳이 없어 상태만 보인다.
- 긴 전사문은 줄마다 `content-visibility: auto` 와 크기 짐작(`contain-intrinsic-size: auto 64px`)을 준다. 짐작값은 화면 밖 줄의 레이아웃 계산용이고 보이는 크기가 아니다.

## 왜

- 화면 안에서만 고르기는 주소가 회의를 가리키지 않아 직접 링크 유지(U5-1)와 같은 판정을 두 가지로 만든다. `replace` 는 기록에 빈 목록 항목을 남기지 않는다 — 뒤로 가기가 다시 기본 선택으로 튕기지 않는다.
- 목록이 오기 전 경로 검사를 `useLocation` 으로 하면 U4 r1 M01 이 그대로 돌아온다. 같은 문제를 이미 푼 공용 도구를 쓴다.
- 서버 권한만 보면 실 API 가 역할 없이 `can_review` 를 줄 때(지금은 role 을 그대로 넣는다, 계약 §4.4) 화면이 그 값에 묶이고, 역할만 보면 서버가 회의별로 권한을 좁혀도 따라가지 못한다. 둘 다 보는 것이 둘 중 하나가 바뀌어도 안전하다.

## 다시 고민할 때

- 백엔드가 승인·반려 시 `extraction_item.approval_id` 를 비우면(§4.0-②-12) — 조인은 그대로 맞지만, 일반 팀원 쪽 판정을 `visibleItems` 로 단순화할 수 있다.
- 회의록 응답에 `workspace_id` 가 생기면 상세를 거치지 않고 본문에서 공간을 확인할 수 있다.
- 실 API 가 요약을 채우면(§4.7-4) 요약 탭의 빈 상태가 기본이 아니게 된다. 요약 탭의 구성(캔버스와의 차이)을 다시 본다.
- 목록 행의 확인 필요 개수 배지가 필요해지면 회의별 대기 개수를 주는 API 를 요청한다(회의마다 추출을 부르지 않는다).
