# 회의록 로딩 자리 — 2단 스켈레톤 하나, 회의를 고를 때는 미리 받기 + 250ms 들고 있기

- 날짜: 2026-10-06
- 상태: 결정 · 같은 날 개정(UX1 2회차) — 맨 아래 「개정」 절이 「흐리게 하지 않는다」와 「다시 고민할 때」의 가드 단계 항목을 대신한다 · 같은 날 두 번째 개정(UX1 3회차, 사용자 결정) — 「개정 2」 절이 2회차 「다시 고민할 때」의 두 줄 참석자 항목을 대신한다 · 10-07 세 번째 개정(UX1 4회차, 사용자 결정) — 「개정 3」 절이 개정 2 「다시 고민할 때」의 긴 제목 항목과 「검증 (개정)」의 실제 시간 Vitest 항목을 대신한다

## 고민

M5 완료 뒤 사용자가 MSW 개발 서버로 회의록 화면을 보고 두 가지를 짚었다(UX1).

1. **첫 진입의 스켈레톤이 화면과 자리가 다르다.** 지연 로드 화면을 기다리는 동안 `RouteSkeleton` 이 범용 `PageSkeleton`(가운데 한 열 `max-w-column`)을 그렸다. 1440px 에서 뼈대 제목이 (244, 124)에 앉는데 실제 회의록 제목은 (344, 120)이고, 왼쪽 308px 목록 자리는 없었다. 화면 코드가 오면 위젯의 목록·본문 로딩 뼈대로 한 번 더 바뀌었고, 그 본문 뼈대(제목 블록 34px + 6줄)에는 탭 줄이 없어 실제 탭 줄(y 229.8)과도 맞지 않았다. 목록 머리 줄도 PM(버튼 32px, 64)과 팀원(제목 줄 26.35px, 58.35)의 높이가 달랐다.
2. **회의를 고를 때마다 스켈레톤이 번쩍인다.** `MinutesDetail` 이 `key={meetingId}` 로 다시 마운트되며 상세·본문을 새로 묻고, 그동안 위 본문 뼈대를 그렸다. MSW 응답은 몇 ms 라 뼈대가 한두 프레임만 보였다 사라졌다 — 그 짧은 깜빡임이 문제였다.

선택 깜빡임에는 길이 셋 있었다. ① 목록 항목의 가리키기·포커스에서 미리 받기, ② 스켈레톤을 늦게 보이기, ③ 새 회의가 올 때까지 이전 본문을 유지. ①만으로는 가리키기 없이 누르는 경로(터치, Playwright 의 `click` 처럼 가리키자마자 누르기)에서 답이 늦으면 그대로 번쩍인다. ②만으로는 그 사이에 빈 칸이 보여 「내용 → 빈 칸 → 내용」으로 또 깜빡인다. ③만으로는 답이 오래 늦으면 이전 회의 내용이 새 회의 것처럼 남는다.

## 고른 길

**자리 — 2단 뼈대 컴포넌트를 `shared/ui/page-skeleton/MinutesSkeleton.tsx` 에 하나 둔다.**

- `MinutesListSkeleton`(정리된 회의 행 높이의 세 줄) · `MinutesDetailSkeleton`(제목 26px 줄 · 메타와 출처 칩 22px · 참석자 칩 22px · 탭 줄 38px + 아래 선 · 본문) · 둘을 왼쪽 308 + 오른쪽으로 놓은 `MinutesPageSkeleton`.
- `RouteSkeleton` 은 회의록 경로(`/workspaces/:id/meetings/:meetingId?`, `upload` 제외)에서 `MinutesPageSkeleton` 을 그린다. 가드가 캐시를 기다리는 단계도 같은 `RouteSkeleton` 이라 2단이다.
- 위젯(`MeetingMinutes` 의 목록·본문 대기, `MinutesDetail` 의 상세·본문 대기)이 같은 `MinutesListSkeleton` · `MinutesDetailSkeleton` 을 쓴다. 단계가 바뀌어도 모양이 같다.
- 글 한 줄 자리는 그 글자 크기의 줄 높이(`h-lh`) 칸 안에 뼈대를 앉혀, 그려질 때 아래 줄이 밀리지 않게 했다.
- 목록 머리 줄을 PM 버튼 높이로 고정했다(`min-h-64` = 위 18 + 32 + 아래 14). 역할을 모르는 라우트 뼈대와 팀원 화면이 어긋나지 않는다. 캔버스도 이 자리에 컨트롤(검색)을 둔다.
- shared 는 widgets 를 가져올 수 없어 치수를 옮겨 적었다(OnboardingSkeleton 과 같은 방식). 어긋나면 `e2e/meeting-skeleton.e2e.ts` 가 잡는다.

**선택 — ①과 ③을 함께, ③에는 250ms 상한을 둔다.**

```
widgets/meeting-minutes
  lib/prefetchMinutes.ts   정리된 회의 행의 pointerenter · focus 에서
                           상세 ensureQueryData → (같은 공간 · done 이면) 추출 prefetch + 본문 ensureQueryData
                           → (PM 이고 canReview 면) 승인 목록 prefetch. 실패는 삼킨다
  model/useShownMeeting.ts URL 회의의 상세·본문 Query 를 MinutesDetail 과 같은 조건으로 지켜보고,
                           아직 없으면 이전 회의를 MINUTES_HOLD_MS(250) 동안만 계속 그린다.
                           회의를 연달아 바꿔도 처음 바꾼 때부터 잰다
  ui/MeetingMinutes.tsx    들고 있는 동안 본문을 aria-busy · inert 로 묶는다. MinutesDetail 의 key 는 그리는 회의다
```

- 빠른 답(미리 받았거나 250ms 안의 응답)은 이전 회의록에서 새 회의록으로 바로 바뀐다. 스켈레톤이 붙지 않는다.
- 250ms 를 넘기면 새 회의로 넘어가 본문 모양의 스켈레톤을 그린다. 이전 회의의 제목·탭이 남지 않는다.
- 주소와 목록의 `aria-current` 는 누른 순간 새 회의다. 들고 있는 이전 회의록은 `inert` 라 누르거나 포커스할 수 없고 보조 기술에도 읽히지 않으며, 감싼 칸이 `aria-busy` 다.
- 탭은 그리는 회의가 바뀔 때 처음 탭(요약)으로 돌아간다(U5). 들고 있는 동안 이전 회의의 탭은 그대로다 — 다시 마운트하면 그 자체가 깜빡임이다.
- 처음 고를 때(이전 회의가 없는 기본 선택·직접 링크)는 들고 있을 것이 없어 바로 스켈레톤이다. 라우트 뼈대와 같은 모양이라 튀지 않는다.

## 왜

- **같은 Query 를 쓴다.** 미리 받기와 `useShownMeeting` 모두 엔티티의 query options 그대로다. 캐시에 쓰는 길은 그 공유 Query 하나다(`setQueryData`·직접 요청 없음, U4 r5). MinutesDetail 이 마운트되면 같은 key 의 조회에 합쳐져 따로 요청하지 않는다.
- **화면 규칙을 미리 받기에도 그대로 건다.** 다른 공간의 회의(상세의 `workspaceId` ≠ URL)는 본문·추출을 받지 않고(U5-4), 승인 목록은 PM 이고 서버가 그 회의록에 `canReview` 를 줬을 때만 받는다(U5-6). `useShownMeeting` 의 본문 조회도 같은 조건으로만 켜진다.
- **`ensureQueryData` 로 묻는다.** 이미 받은 값이면 요청하지 않고(오래됐으면 그 값을 쓰고 뒤에서 새로 받는다 — `revalidateIfStale`), 목록을 훑으며 가리켜도 회의마다 한 번이다. 가리키기 지연(hover intent)은 두지 않았다 — 앞서 받을 시간이 줄고, 회의 목록은 짧다.
- **250ms.** 그보다 짧은 기다림은 「바뀌는 중」으로 느껴지지 않는다는 흔한 기준(스켈레톤·스피너를 200~300ms 늦게 보이기)에 맞췄다. 실제 서버에서 상세 → 본문 두 번의 왕복이 대개 이 안이다. 길게 잡을수록 이전 회의가 보이는 시간이 길어진다.
- **흐리게 하지 않는다.** 들고 있는 동안 이전 본문의 불투명도를 바꾸면 짧은 기다림마다 그 자체가 깜빡임이 된다. 전환(`transition-*`)으로 부드럽게 하는 길은 토큰이 애니메이션 스케일을 비웠고 시안에 근거가 없어(Toast·Modal 과 같은 원칙) 쓰지 않았다. 250ms 상한과 `inert` · `aria-busy` 로 오인을 막는다.
- **`placeholderData: keepPreviousData` 로 하지 않았다.** 상세 → 본문 → 추출이 이어진 조회라 Query 마다 이전 값이 섞여(상세는 새 회의, 본문은 이전 회의) 한 화면에 두 회의가 보일 수 있다. 「그리는 회의 ID」 하나를 들고 있으면 한 회의의 캐시만 읽는다.
- **Suspense + transition 으로 하지 않았다.** 라우터 이동은 transition 이라 새 화면이 suspend 하면 이전 화면이 남지만 상한이 없다 — 답이 늦으면 이전 회의가 계속 보인다.

## 다시 고민할 때

- 실제 서버에서 상세 → 본문 왕복이 250ms 를 자주 넘기면 상세와 본문을 한 번에 주는 API 나 목록 응답에 본문 일부를 싣는 쪽을 본다. 상한을 늘리는 것보다 낫다.
- 가드 단계(세션·소속 대기)는 앱 헤더가 아직 없어, 헤더가 그려질 때 화면 전체가 헤더 높이(76px)만큼 내려간다. 회의록만의 문제가 아니라 모든 제품 화면이 같다 — 고치려면 가드 뼈대에 헤더 자리를 넣어야 한다.
- 회의록 틀(목록 폭·머리·본문 머리·탭 줄)을 바꾸면 `MinutesSkeleton.tsx` 의 옮겨 적은 치수도 함께 바꾼다.

## 개정 — 가드 단계의 헤더 자리, 고른 회의의 머리 (UX1 2회차)

1회차 검증(실제 Chromium 1440px, 연속 캡처)이 두 가지를 짚었다.

- **M01.** 가드(`RequireAuth`·`RequireTeamMember`)가 세션·소속을 기다리는 동안 `RouteSkeleton` 이 앱 셸 바깥에서 헤더 없이 그려졌다. 셸이 뜨면 헤더(76px)가 생기며 목록·본문 뼈대가 통째로 76px 내려갔다(콜드 직접 진입·기본 진입 모두). 사용자가 짚은 「첫 진입 자리 어긋남」이 바로 이것이다. 1회차는 「모든 제품 화면 공통」이라 범위 밖으로 두었고, 1회차 E2E 는 헤더 이전 샘플을 걸러 내 이 이동을 보지 못했다.
- **M02.** 들고 있는 250ms 동안 주소·목록 선택 표시는 새 회의인데 본문 제목·내용은 이전 회의 그대로였고 시각 표시가 없었다(`aria-busy`·`inert` 뿐). 180ms 지연에서 약 217ms, 650ms 지연에서 약 262ms, 지연 없는 첫 선택에서도 약 26ms 어긋났다.

### 고른 길 — M01: 가드 대기에도 셸 틀과 헤더 뼈대

- `widgets/app-shell` 의 `AppHeaderSkeleton` — 진짜 헤더와 **같은 `HEADER` 상수**(`h-header` 76px · 아래 선 · `px-40`)에 마크 24 · 탭 다섯(36px 칸) · 워크스페이스 메뉴 36 · 아바타 29 자리를 둔다. 장식이라 통째로 `aria-hidden` 이고 `header` 랜드마크가 아니다(진짜 banner 와 겹쳐 읽히지 않는다. E2E `start()` 가 `#root header` 로 앱 시작을 기다리는 것과도 섞이지 않는다).
- `app/router/layouts/WorkspaceLayout.tsx` 의 `WorkspaceShellSkeleton` — 진짜 셸과 **같은 `SHELL` 틀**(`flex min-h-dvh flex-col bg-surface`)에 헤더 뼈대 + 자식. 틀 클래스를 한 곳에 둬 두 셸이 어긋날 수 없다.
- `app/router/RouteSkeleton.tsx` 의 `GuardSkeleton` — `/workspaces/:workspaceId/*`(ID 모양이 맞을 때)면 `WorkspaceShellSkeleton` 안에 `RouteSkeleton`, 아니면 `RouteSkeleton` 그대로. `RequireAuth`·`RequireTeamMember` 의 대기 자리만 이것으로 바꿨다. 화면 코드 대기(`lazyPage` 의 Suspense)는 이미 셸 안이라 `RouteSkeleton` 그대로다.

버린 길: **셸 틀을 가드 바깥으로 올리기.** 헤더는 공간 메뉴·계정 메뉴·`정리 중` 링크 때문에 세션·소속 목록이 있어야 그릴 수 있고, 소속 가드가 `NoAccessPage`·404(셸 없음)나 온보딩(셸 없음)으로 보낼 수도 있다. 셸을 가드 밖으로 올리면 이 화면들에도 헤더가 붙거나, 셸이 가드 판단을 다시 해야 한다. 대기 자리만 셸 모양으로 그리면 가드 순서(인증 → 소속 → 온보딩 완료 → 역할, routes.tsx)를 건드리지 않는다.

영향 범위:

- **같은 이득** — 대시보드·태스크·메시지·팀·설정·승인 상세 등 셸 안의 모든 경로. 가드 단계에도 헤더 자리가 있어 셸이 뜰 때 화면이 내려가지 않는다(E2E 대시보드 검사). 화면 몸통 뼈대는 1회차대로 경로별(`RouteSkeleton`)이다.
- **그대로** — 랜딩·로그인·회원가입(`RedirectIfAuthed`, `RouteSkeleton` 그대로), 공간 선택(`/workspaces`), 온보딩(`/onboarding/...`, 가운데 열 뼈대), ID 모양이 틀린 공간 경로(셸 없는 404). `RouteSkeleton.test.tsx` · `guards.test.tsx` 가 확인한다.
- **남는 짧은 바뀜** — 셸 안 경로로 들어왔지만 가드가 셸 없는 화면으로 보내는 경우(비소속 `NoAccessPage`, 미완료 공간의 온보딩 이동, 비로그인 로그인 이동)는 헤더 뼈대가 잠깐 보였다가 셸 없는 화면이 된다. 원래 다른 화면으로 옮겨 가는 경우라 자리 맞추기 대상이 아니다.

### 고른 길 — M02: 머리는 고른 회의, 이전 본문만 지연 흐림

- `MeetingMinutes` 가 이미 받은 목록에서 고른 회의의 요약(`MeetingSummary`: 제목·시작 시각·길이·출처·참석자 수)을 찾아 `MinutesDetail` 에 `selected` 로 넘긴다. 들고 있는 동안(`holding`) `MinutesContent` 는 **머리(제목·메타·출처 칩·참석자 줄)를 요약으로 그리고**, 탭·본문은 이전 회의록 그대로 둔 채 감싼 칸(`data-testid="minutes-body"`)을 흐리게 · `aria-busy` · `inert` 로 묶는다. 참석자는 이름 대신 `참석자 N명` 칩 하나다(같은 22px 줄이라 회의록이 와도 탭 줄이 제자리다).
- 요약이 없으면(목록에 없는 회의) **들고 있지 않는다**(`useShownMeeting` 의 `canHold`). 머리를 바꿀 수 없는데 이전 회의를 들고 있으면 어긋남이 그대로 남는다. 이전 회의가 회의록 본문이 아닌 상태(안내·오류)면 들고 있는 대신 본문 뼈대를 그린다 — 이전 회의의 안내 문구를 새 회의 머리 아래 두지 않는다.
- 250ms 를 넘기면 새 회의로 넘어가 본문 모양 스켈레톤이다. 이때 **스켈레톤의 머리도 같은 요약**이다(`MinutesDetailSkeleton` 의 `head` 칸). 머리가 「요약 → 머리 뼈대 → 회의록」으로 깜빡이지 않는다. 회의를 한 번이라도 바꾼 뒤(`switched`)에만 그렇다 — 첫 진입은 이전 회의가 없어 오인될 것이 없고, 머리 뼈대가 라우트 스켈레톤과 같은 모양이라 그대로 둔다(기존 테스트의 「제목 = 다 받음」 동기점도 그대로다).
- **흐림 — `opacity-55`, 전환 길이 0, 지연 `MINUTES_DIM_DELAY_MS`(100ms).** 들고 있기 시작하고 100ms 안에 답이 오면 흐림이 한 번도 보이지 않는다. 넘기면 그 순간 한 번에 흐려지고, 답이 오면(또는 250ms 에 스켈레톤으로 넘어가면) 새 칸으로 바뀐다.
  - 0.55 는 `Skeleton` 숨쉬기의 낮은 점(m2-design-tokens §7-11)이다 — 「기다리는 중」을 같은 말로 쓴다. 새 색·새 값을 만들지 않았다.
  - 애니메이션 토큰이 비어 있고 Toast·Modal 이 전환을 두지 않는 원칙을 지켜 **움직임(페이드)은 없다.** CSS `transition-delay` 만으로 「100ms 뒤 한 번에」를 만든다 — 타이머·상태를 더 두지 않고, 들고 있기가 100ms 전에 끝나면 브라우저가 전환을 시작하지도 않는다. 줄이기 설정(`global.css` 는 `transition-duration` 만 0.01ms 로 줄인다)과 상관없이 같은 모양이다.
  - 100ms 는 바뀜을 즉시로 느끼는 한계로 흔히 쓰는 값이다. 실측: 지연 없는 MSW 에서 미리 받기 없이 누르면 들고 있기가 26~45ms 생긴다 — 지연을 0 으로 바꾼 변이에서 E2E 3회 중 3회 흐린 프레임이 잡혔다(아래). 1회차가 「흐리면 그것이 깜빡임」이라 흐림을 버린 까닭이 바로 이 짧은 들고 있기였고, 지연으로 그 둘을 함께 푼다.

1회차 「흐리게 하지 않는다」의 근거(짧은 기다림마다 깜빡임, 전환 토큰 없음)는 지연·전환 길이 0 으로 그대로 지킨다. 흐림을 더한 까닭은 머리가 새 회의로 바뀐 뒤 그 아래 이전 본문이 새 회의 내용으로 읽히지 않게 하는 것이다.

## 개정 2 — 참석자 줄은 칩 한 줄, 남는 사람은 `+N` (UX1 3회차, 사용자 결정)

2회차 검증(실제 Chromium, 연속 캡처)이 남긴 것:

- **M03.** 지원 폭 1024px 에서 정상 길이 표시명(`김서연(기획)` 꼴) 10명이 참석한 회의는 이름 칩이 두 줄(22 + 6 + 22)로 접혔다. 뼈대(칩 한 줄)와 목록 요약 머리(`참석자 10명` 칩 하나)는 한 줄이라, 첫 진입에서 탭 줄과 본문이 **28px** 내려가고 회의를 고르면 28px 올라갔다가(요약 머리 · 본문 뼈대) 회의록이 오면 다시 28px 내려갔다.
- **N01 (minor).** 셸 안 경로로 들어왔지만 가드가 셸 없는 화면으로 보내는 경우(비로그인 → 로그인, 미완료 공간 → 온보딩, 비소속 → 접근 불가) 헤더 뼈대가 답을 기다리는 동안(검증자 300ms 지연에서 약 0.3초) 보였다 사라진다.

**사용자 결정(2026-10-06): 참석자 칩은 늘 한 줄이다. 넘치는 사람은 `+N` 으로 줄여 보이고, 눌러서 전체를 본다.** 캔버스(`Meetings.dc.html`)는 참석자 넷을 메타 줄의 겹친 이니셜로만 그려 넘칠 때의 표현이 없다 — 이 결정이 그 빈자리를 채운다.

### 고른 길 — M03: 한 줄 고정 + 잰 만큼 이름 칩 + `+N` 팝오버

```
widgets/meeting-minutes
  ui/AttendeeRow.tsx     참석자 줄. 줄(h-22)에 이름 칩을 들어가는 만큼, 남으면 `+N`(Radix Popover 트리거)
  lib/fitAttendees.ts    칩 폭 · 줄 폭 · 간격 · `+N` 폭 → 보일 칩 수 (순수 함수)
shared/ui/popover        Radix Popover 에 떠 있는 면만 입힌 공통 팝오버 (D-113)
```

- **높이는 재기에 기대지 않는다.** 참석자 줄 칸 `ATTENDEE_ROW`(`flex h-22 items-center gap-6`)를 회의록 머리 · 목록 요약 머리(`참석자 N명`) · 참석자 없음 문구(`참석자 정보가 없어요`, 원래 21.25px 글 한 줄)가 함께 쓰고, 뼈대(`MinutesSkeleton.tsx`)의 참석자 줄도 같은 `h-22` 다. 이름 칩은 `shrink-0 whitespace-nowrap` 이고 목록은 접지 않고(`flex`, `overflow-hidden`) 넘치면 자른다. 잰 결과가 틀리거나 재기 전이어도 줄은 22px 이다 — 세 머리와 뼈대의 탭 줄이 참석자 수 · 폭과 상관없이 같은 자리다.
- **보일 수는 실제 폭을 잰다(측정).** CSS 만으로는 한 줄에 몇 개가 들어갔는지 알 수 없어 `+N` 의 N 을 쓸 수 없다(줄 바꿈·잘림은 되지만 남은 수를 세지 못한다). 이름 길이가 제각각이라 글자 수로 어림하면 틀린다. 그래서 줄 안에 보이지 않는 재는 칸(`invisible` · `aria-hidden` · 줄 크기로 잘림)에 이름 칩 전부와 `+전체 인원` 칩을 늘어놓고 폭을 잰다.
  - 재는 칸의 글자는 `::before { content: attr(data-label) }` 로만 그린다. 화면 글자(textContent)가 두 번 생기지 않아 `getByText` 같은 조회와 복사가 깨끗하다.
  - `fitAttendees` — 모두 들어가면 모두 보인다(`+N` 자리를 미리 떼지 않는다). 아니면 앞에서부터, 뒤에 간격 + `+N` 칩이 붙을 수 있는 데까지만 넣는다. 순서를 건너뛰지 않는다(뒤의 짧은 이름을 앞당기지 않는다 — 회의록의 참석자 순서를 지킨다). `+N` 폭은 자릿수가 가장 긴 `+전체 인원` 으로 잰다.
  - `useLayoutEffect` 에서 그리기 전에 한 번 재고, `ResizeObserver` 로 줄 폭(창 크기)과 재는 칸 크기(글꼴이 늦게 와 칩 폭이 바뀜)를 지켜 다시 잰다. 재는 값은 보이는 칩 수와 무관해 되먹임이 없다. jsdom 처럼 잴 수 없는 환경(폭 0)에서는 모두 보인다.
- **`+N` 은 칩 모양의 버튼이다.** 이름은 `+6, 참석자 10명 모두 보기` — 보이는 글자로 시작한다(보이는 이름과 읽히는 이름이 이어진다, WCAG 2.5.3). 누르거나 Enter · Space 로 열고, 팝오버(`dialog`, 이름 `참석자 10명`)에 전체 이름 칩이 있다. Esc · 바깥 누르기로 닫고 닫히면 `+N` 으로 포커스가 돌아온다 — 모두 Radix 가 한다. 포커스 표시는 전역 `:focus-visible` 그대로다.
- **스크린리더에는 전체 목록이다.** `참석자` 목록(`ul aria-label="참석자"`)은 늘 모든 사람의 `li` 를 갖고, 줄에 들어가지 않은 사람만 `sr-only` 로 시각적으로 숨긴다. 기존의 `참석자` 목록 단언(`meetingMinutes.test.tsx` 의 이름 넷, E2E 의 `toContainText`)이 그대로 맞는다. 팝오버의 목록은 이름이 없어 `참석자` 목록과 섞이지 않는다.
- **팝오버는 공통 UI 로 새로 둔다(`shared/ui/popover`).** D-113 이 팝오버를 Radix 로 하기로 했고 아직 없었다. `DropdownMenu` 는 쓰지 않았다 — 메뉴(`menuitem`)는 고르는 행동이 있는 항목이라, 행동 없는 이름 목록을 메뉴로 읽히면 스크린리더에 틀린 말을 한다. 면은 `DropdownMenu` 와 같은 떠 있는 면(반경 14 · 테두리 한 겹 · 그림자 없음 · 최대 292px)이다. 패키지 `@radix-ui/react-popover@1.1.23` 은 이미 깔린 Radix 묶음(popper 1.3.7 · dismissable-layer 1.1.19 · focus-scope 1.1.16 …)과 같은 판이라 잠금 파일에 그 한 항목만 더해졌다.
- 새 값은 없다. 칩 · 간격 · 색은 기존 칩(`h-22 rounded-6 bg-control px-8 text-meta text-sub`) 그대로, `+N` 은 가리키거나 열린 동안 글자만 먹(`text-ink`)이다.

버린 길:

- **이름 칩을 두 줄까지 허용하고 뼈대 · 요약 머리를 두 줄로 맞추기.** 회의록이 오기 전에는 이름을 몰라(목록 요약은 참석자 수뿐) 줄 수를 알 수 없다. 두 줄로 고정하면 대부분의 한 줄 회의에 빈 줄이 생긴다.
- **선택 대기 동안만 이전 높이를 들고 있기.** 첫 진입의 뼈대 → 회의록 28px 은 남는다.
- **CSS 만으로 자르기(`max-height` + `overflow`).** 높이는 지키지만 몇 명이 가려졌는지 보이지 않고 전체를 볼 길이 없다.

### N01 — 고치지 않고 알려진 동작으로 둔다

가드가 셸 없는 화면으로 보낼지는 세션(`/auth/me`)이나 소속 목록이 와야 안다. 그 답을 기다리는 동안에는 셸 안 화면으로 갈 수도, 셸 없는 화면으로 갈 수도 있어 어느 쪽 뼈대가 맞는지 알 수 없다. 헤더 뼈대를 늦게 보이면 정상 경로(대부분)에서 M01 의 76px 이동이 되살아나고, 뼈대를 아예 비우면 정상 경로의 첫 화면이 빈 칸이 된다. 미리 알 수 있는 단서(세션의 `workspace_count === 0`)는 비소속 · 미완료 · 비로그인 어느 경우도 가려내지 못한다. 가드 판단 순서 · 권한을 바꾸지 않고는 고칠 방법이 없어 이번에는 그대로 둔다.

- 보이는 것은 `aria-hidden` 장식 뼈대뿐이고 데이터 · 내비게이션은 노출되지 않는다. 최종 목적지(로그인 · 온보딩 · 접근 불가)에는 남지 않는다(2회차 검증 0 RAF).
- 세션 · 소속 캐시가 이미 있는 화면 안 이동에서는 가드가 기다리지 않아 생기지 않는다. 콜드 첫 진입에서 서버 왕복만큼만 보인다.

### 고른 길 — M04: 제목 한 줄 · 말줄임 · 잘렸을 때만 툴팁

```
widgets/meeting-minutes/ui/MinutesTitle.tsx   h2 · h-lh · truncate. 잘렸으면 Tab 자리 + 툴팁(전체 제목)
shared/ui/tooltip                             Radix Tooltip 에 떠 있는 면만 입힌 공통 툴팁 (D-113)
```

- **높이는 글자 수에 기대지 않는다.** 제목(`h2`)은 `h-lh truncate`(한 줄 높이 고정 · 줄 바꿈 없음 · 넘치면 말줄임)다. 뼈대의 제목 줄도 `h-lh` 26px · 1.3 이라 둘 다 33.8px 이다. 목록 요약 머리(들고 있기 · 선택 뒤 뼈대)도 같은 `Head` 를 써 같은 제목 칸이다. 제목이 몇 자든 · 폭이 얼마든 탭 줄이 같은 자리다.
- **머리의 다른 줄도 같은 꼴로 막았다.** 메타와 출처 칩 줄은 `flex-wrap` 이었다 — 폭이 좁으면 칩이 다음 줄로 내려갈 수 있었다. 칩 한 줄 높이(`h-22`)로 고정하고 접지 않으며, 메타 글이 넘치면 말줄임이고 칩은 줄지 않는다(뼈대의 같은 줄도 `h-22`). 지원 폭(1024px 이상)의 날짜 · 길이 메타는 실제로 잘리지 않는다. 참석자 줄은 개정 2 에서 이미 `h-22` 다. 안내 화면(정리 중 · 실패 · 회의 중)의 제목은 뒤에 탭 줄이 없어 접혀도 밀릴 것이 없어 그대로 둔다.
- **스크린리더에는 전체 제목이다.** 자르기는 CSS 뿐이라 `h2` 의 글자 · heading 이름은 전체 제목이다. 기존 `getByRole('heading', { name })` 단언이 그대로 맞는다.
- **전체 제목 보기 — `title` 속성 대신 공통 툴팁을 골랐다.** `title` 속성은 마우스로만 뜨고(키보드 포커스로는 뜨지 않는다) 뜨는 시점 · 모양을 정할 수 없으며, 스크린리더가 heading 이름 뒤에 같은 제목을 한 번 더 읽는다. 사용자 결정의 「키보드 포커스 사용자도 전체를 안다」를 지키려면 포커스로 열리고 Esc 로 닫히는 툴팁이 필요하고, D-113 이 이런 공통 UI 를 Radix 로 하기로 했다.
  - 잘렸을 때만(`scrollWidth > clientWidth`, 그린 뒤 재고 ResizeObserver 로 다시 잰다) 제목이 Tab 자리(`tabIndex 0`)가 되고 툴팁이 열릴 수 있다. 다 보이는 제목은 Tab 자리도 툴팁도 없다 — 쓸모없는 Tab 정지와 같은 글을 되풀이하는 툴팁을 만들지 않는다.
  - Radix Tooltip 의 동작을 그대로 쓴다 — 가리키면 잠깐(기본 700ms) 뒤, 키보드 포커스면 바로 열고, Esc · 포커스 잃기 · 누르기로 닫고, 떠 있는 면 위로 포인터를 옮겨도 열린 채 둔다(WCAG 1.4.13). 포커스 표시는 전역 `:focus-visible` 그대로다.
  - 툴팁은 제목 글자를 다시 보이는 것이라 트리거의 `aria-describedby` 를 지우고 면은 `aria-hidden` 이다 — 이으면 스크린리더가 같은 제목을 두 번 읽는다.
  - 제목은 누를 것이 아니라 heading 의미 그대로다. `jsx-a11y/no-noninteractive-tabindex` 를 그 한 줄만 사유와 함께 끈다(WAI-ARIA tooltip 패턴은 포커스 가능한 트리거를 요구한다).
  - 면은 `Popover` 와 같은 떠 있는 면(테두리 한 겹 · 그림자 없음)에 반경 9 · 안쪽 12/8 · `text-control` 이다. 폭은 제목 칸 폭(`--radix-tooltip-trigger-width`)을 넘지 않아 긴 제목은 그 아래에 접혀 다 보인다. 새 값은 없다.
  - 패키지 `@radix-ui/react-tooltip@1.2.16` 은 이미 깔린 Radix 묶음(popper 1.3.7 · dismissable-layer 1.1.19 · portal 1.1.17 · presence 1.1.10 · visually-hidden 1.2.11 …)과 같은 판이다. 최신 1.3.0 은 그 묶음보다 새 판들을 요구해 고르지 않았다. 이 저장소 npm 11 의 `npm install` 이 잠금 파일의 다른 항목(@emnapi · ajv 등)까지 다시 써서, 잠금 파일에는 루트 의존성 한 줄과 패키지 항목 하나만 더하고 `npm ci` 로 맞췄다(개정 2 의 Popover 와 같은 방식).
- **목록(왼쪽) 행 제목은 바꾸지 않았다.** 행은 높이가 정해진 자리가 아니라 회의마다 행 높이가 달라도 위아래가 밀리지 않는다(선택 · 뼈대와 무관). 다 보이는 행 제목이 긴 제목을 고를 때의 단서이기도 하다.

버린 길:

- **두 줄까지 허용하고 뼈대 · 요약 머리를 두 줄로 맞추기.** 첫 진입의 뼈대는 제목을 몰라 줄 수를 알 수 없다. 두 줄로 고정하면 대부분의 짧은 제목 아래 빈 줄이 생긴다(개정 2 의 참석자와 같은 까닭).
- **글자 크기를 줄여 맞추기.** 캔버스의 제목 26px 위계를 깨고, 그래도 넘치는 제목은 남는다.

### 고른 길 — N02: 다시 잰 결과를 그 프레임에 반영

ResizeObserver 콜백은 배치 뒤 · 그리기 전에 돈다. 그 안의 `setState` 는 React 가 다음 작업에서 렌더해, 새 폭에 이전 칩 수가 한 프레임 그려졌다. 콜백 안에서 `flushSync` 로 반영해 그 프레임에 고친 모습이 그려진다. 반영해도 줄과 재는 칸의 크기는 바뀌지 않아 되먹임이 없다(브라우저의 ResizeObserver 반복도 생기지 않는다). 처음 재기는 레이아웃 효과 안이라 이미 그리기 전이다. CSS 만으로 넘침을 처리하는 길은 `+N` 의 N 을 셀 수 없어 버렸다(개정 2).

### 고른 길 — N03: 회의를 바꾸며 그린 뼈대는 300ms 둔다

상한 근처의 답은 미리 알 수 없어 뼈대를 건너뛸 수 없다(답이 251ms 에 올지 2초 뒤에 올지 모른다). 그래서 **한 번 그린 뼈대는 하나의 상태로 읽힐 만큼 둔다** — `MINUTES_SKELETON_MIN_MS` 300ms.

- 300ms 는 즉시로 느끼는 한계(100ms, `MINUTES_DIM_DELAY_MS`)의 세 배라 깜빡임이 아닌 기다림으로 보인다. 들고 있기(250)와 합쳐도 550ms 라 흐름이 끊긴다고 느끼는 1초보다 짧다. 답이 300ms 보다 늦게 오면 뼈대를 더 늘리지 않고 오는 대로 바꾼다.
- 대가: 상한을 막 넘긴 답(251~549ms)은 회의록이 최대 299ms 늦게 보인다. 250ms 안의 답(대부분 — 미리 받기 · 짧은 응답)과 550ms 를 넘는 답은 그대로다.
- 첫 진입은 두지 않는다 — 라우트 뼈대부터 이어지는 같은 뼈대라 번쩍일 것이 없다. 목록 요약이 없어 들고 있지 않고 바로 넘어가는 경우에도 그린 뼈대는 300ms 둔다.
- 뼈대를 두는 동안 다른 회의를 고르면 그 뼈대 위에서 들고 있다 — 그사이 도착한 이전 회의의 본문을 처음 보이지 않는다. 새 회의도 상한까지 답이 없으면 그 회의의 뼈대로 넘어가 300ms 를 새로 잰다.
- 시간 규칙을 조회에서 떼어(`useSelectionTimeline(meetingId, settled, canHold)`) `useShownMeeting` 이 조회 결과(`settled`)를 넘긴다. 규칙만 가짜 타이머로 경계 전후를 검사할 수 있다. 화면에는 `keepSkeleton` 으로 넘기고 `MinutesDetail` 이 그동안 뼈대(머리는 고른 회의의 요약)를 그린다.

버린 길: **상한 근처에서는 뼈대 없이 더 들고 있기.** 「근처」를 정하려면 결국 상한을 늘리는 것이고, 상한 뒤에도 답이 없으면 이전 회의가 더 오래 남는다(M02 의 오인).

### 고른 길 — T01: 시간 검사를 가짜 시계와 Chromium 으로 나눈다

기대값을 넓히지 않았다. 실제 시간에 기대던 검사를 두 곳으로 옮겼다.

- **Vitest — 시간은 가짜 시계가 정하고, 순서 · 조건 · 요청 횟수와 규칙이 정한 정확한 시각을 본다.**
  - `widgets/meeting-minutes/model/useShownMeeting.test.ts` — 규칙(`useSelectionTimeline`)을 `vi.useFakeTimers()` 로: 상한 1ms 전까지 들고 있기 · 상한에 뼈대 · 연달아 바꿔도 처음부터 · 요약 없으면 바로 · 뼈대 최소 시간 1ms 전/정각 · 늦은 답은 늘리지 않음 · 뼈대 위에서 들고 있기 · 새 회의 뼈대의 시간 새로 재기.
  - `app/meetingMinutesSelection.test.tsx` — 회의록을 연 뒤 `setTimeout` · `Date` 만 가짜로 바꾸고, 상세 답은 문(deferred)으로 정한 가짜 시각에 보낸다. 답이 화면에 닿는 동안 가짜 시각은 멈춰 있다(`deliver`). 두 가지를 테스트 쪽에서 맞췄다: Query 의 알림 묶음(기본 `setTimeout 0`)은 가짜 시계가 진행 중에 건 0ms 타이머를 1ms 뒤로 밀어 답이 시간을 소비하므로 그 테스트 동안 `notifyManager.setScheduler` 로 진짜 다음 틱(`setImmediate`)에 돌린다. RTL 의 `waitFor` · `findBy` 는 끝에 `setTimeout(0)` 을 기다려 가짜 시계에서 멈추므로 쓰지 않는다(주소는 `visited()` 로 바로 본다). React 스케줄러 · MSW · XHR 은 진짜다.
- **Chromium E2E — 실제 프레임 · 밀리초.** 부하는 시간을 늦출 뿐 당기지 않으므로 아래쪽 한계만 잰다(이보다 일찍 바뀌지 않는다). 위쪽 한계(「상한 안에 끝났다」)는 실제 페인트로 본다 — 흐림은 들고 있기가 100ms 를 넘겨야 그려지므로 「흐린 프레임이 없다」가 「들고 있기 < 100ms」의 실제 모습이다.

### 다시 고민할 때 (개정 3)

- 목록 요약 · 회의록이 제목 전체를 주지 않는(서버가 잘라 주는) 계약이 생기면 툴팁도 그 글을 쓰게 된다 — 그때는 상세의 제목을 쓴다.
- 실제 서버에서 상한(250ms)을 막 넘기는 답이 잦으면, 뼈대 최소 시간(300ms)이 회의록을 늦게 보이는 대가가 커진다. 그때는 상세 · 본문을 한 번에 주는 API(위 「다시 고민할 때」)를 먼저 본다.
- 앱 테스트의 첫 렌더 부하 민감성(위 logout)은 M4 부터의 것이다. 전체 실행이 자주 흔들리면 파일마다 첫 렌더의 콜드 비용을 테스트 시간 밖으로 옮기는 방법(이미 화면 모듈은 `renderApp` 로드 때 미리 읽는다)을 본다.
