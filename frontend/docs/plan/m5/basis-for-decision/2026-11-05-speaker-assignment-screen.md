# 업로드 회의의 화자 지정 화면과 대기 상태 추적

- 기록일: 2026-11-05
- 관련 마일스톤: M5 회의 업로드·처리·회의록 보완, 이슈 #256·#342

## 문제와 제약

수동 업로드 회의는 AI가 화자를 나눈 뒤 `awaiting_speakers`가 되고, PM이 라벨마다 팀원을 지정해야 `processing`으로 돌아간다(계약 §2.3.1). 이전 FE는 이 상태를 모르는 값으로 보고 `created`로 읽었고, 처리 추적기는 `lost`로 판정해 polling을 멈췄다. 그래서 업로드 회의가 화면에서 멈춘 것처럼 보였고 PM이 지정할 길도 없었다.

제약은 아래와 같다.

- BE는 화자 조회·제출·원본 재생 API를 구현했다. 서버는 구간을 자르지 않으므로 FE가 원본에서 구간만 재생한다.
- AI 샘플은 라벨마다 최대 3개이고 1개뿐이거나 0.5초까지 짧을 수 있다(#342).
- 화자 지정 대기는 7일이 지나면 실패로 끝난다(BE PR #301). 제출 직후 만료되면 409 `details.status=failed`가 온다.
- 알 수 없는 enum 전반의 정책(#348)과 회의 상세의 워크스페이스 불일치 처리(#349)는 이번 범위가 아니다.

## 실제 검토한 선택지

사용자가 2026-11-05에 정한 것:

- 진입점은 세 곳이다. 처리 화면을 보고 있으면 지정 화면으로 안내하고, 회의록 목록에 `화자 지정 필요` 행을 두고, 다른 화면이면 토스트로 알린다.
- 지정 화면은 별도 주소로 두어 새로고침·직접 진입에 열린다. PM만 쓰고 팀원에게는 PM이 지정 중이라는 안내를 보인다.
- 후보는 `candidates`(업로드 때 고른 참석자)를 위에, 펼치는 「다른 팀원」 묶음을 아래에 두고 「외부 참석자」(`null`)를 둔다. 같은 팀원을 여러 라벨에 지정할 수 있다.
- 모든 라벨을 직접 골라야 제출할 수 있다. 남은 개수를 제출 버튼 근처에 보인다.

이 세션에서 기본값으로 정하며 비교한 것:

| 질문 | 선택지 | 고른 것 |
|---|---|---|
| 대기 중 polling | 3초 유지 / 멈춤 / 느리게 유지 | 30초로 유지 |
| 대기 안내 대상 | 추적 중인 모든 사용자 / PM만 | PM만 |
| 새로고침 뒤 대기 회의 발견 | `processing`처럼 추적에 등록 / 등록하지 않음 | 등록하지 않음 |
| 팀원 진입 | 라우터 PM 가드로 막음 / 화면 안 안내 | 화면 안 안내 |
| 구간 끝 판정 | `timeupdate`만 / 화면 갱신마다 + 남은 시간 타이머 | 화면 갱신마다 + 타이머 |

## 선택과 이유

- **대기 상태는 지켜보는 상태다.** `TrackerOutcome`에 `awaiting_speakers`를 더하고 30초 간격으로 계속 묻는다. 멈추면 다른 창이나 다른 PM이 제출한 뒤의 처리와 7일 만료를 놓친다. 3초를 유지하면 사람이 지정할 때까지 최대 7일 동안 요청이 이어진다. 이 화면에서 제출하면 상세를 바로 무효화하므로 30초 간격은 다른 곳에서 낸 제출을 늦게 볼 때만 체감된다.
- **안내는 처음 보일 때 회의마다 세션당 한 번, PM에게만 한다.** 처리 화면을 보고 있으면 지정 화면으로 옮기고, 아니면 `화자 지정이 필요해요` 토스트의 `화자 지정하기`로 옮긴다. 팀원은 지정할 수 없으므로 토스트를 띄우지 않고 처리 화면에 「PM이 지정하고 있어요」를 보인다. 한 번 표시를 추적 store에 두어 재렌더·StrictMode에도 반복하지 않는다.
- **새로고침 뒤 발견은 `processing`만 등록한다.** 대기 회의까지 등록하면 새로고침할 때마다 토스트가 다시 뜬다. 새로고침 뒤의 대기 회의는 회의록 목록의 `화자 지정 필요` 행이 진입점이다.
- **제출 가능 여부는 고른 값 하나에서 계산한다.** 라벨→선택(`member` 또는 `external`) 맵에서 남은 개수와 보낼 mapping을 함께 만든다. 별도 boolean을 두지 않아 화면과 제출이 어긋날 수 없다.
- **제출 오류는 이유 하나로 바꿔 화면이 고른다.** 409는 `details.status=failed`일 때만 만료로 보고 상세를 다시 받아 실제 `failed_stage`를 안내하며 다시 내지 못하게 한다. 그 밖의 409는 이미 진행된 것으로 안내한다. 같은 지정 재제출은 BE가 200으로 받으므로 응답 유실 뒤 다시 내도 안전하다.
- **원본 하나를 모든 샘플이 함께 쓴다.** 화면에 `<audio>` 하나를 두고 버튼마다 그 구간으로 옮긴다. `timeupdate`는 약 250ms 간격이라 0.5초 구간을 넘겨 다음 화자가 들리므로, 화면 갱신마다와 남은 시간 타이머로 끝을 확인한다.

## 장단점과 감수한 제약

- 다른 창에서 낸 제출이나 만료를 최대 30초 늦게 본다.
- 새로고침 뒤에는 토스트가 없다. PM은 회의록 목록의 행으로 대기 회의를 찾는다.
- 「다른 팀원」 선택은 지금 BE 제출 검증(탈퇴하지 않은 워크스페이스 멤버면 받음)에 기댄다. BE가 제출을 참석자로 제한하면 이 선택은 400 `member_ids`가 되고, 화면은 그 선택만 지우고 다시 고르게 한다.
- 검증은 MSW와 jsdom 기준이다. jsdom은 미디어를 재생하지 않아 재생 위치는 테스트가 옮겼다. 실제 m4a 원본의 시작 지연(#342)은 실서버에서 확인해야 한다.

## 영향 범위와 재검토 조건

- BE가 후보를 참석자로 제한하기로 하면 「다른 팀원」 묶음을 지운다.
- 대기 회의가 많아져 30초 polling이 부담이 되거나, 지정 알림을 서버 알림으로 받게 되면 대기 중 polling을 다시 정한다.
- 실서버에서 m4a 재생 시각이 체감될 만큼 어긋나면 구간 시작 보정이나 서버 변환을 AI·BE와 다시 정한다.
