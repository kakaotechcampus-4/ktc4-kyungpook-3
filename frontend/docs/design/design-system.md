> 팀싱크(Manager's Manager) 웹 애플리케이션의 시각 디자인 기준.
> 화면을 그릴 때 이 문서의 값과 규칙을 따른다.

| 항목 | 값 |
|---|---|
| 버전 | v0.1 (2026-09-08) |
| 대상 | PM 전용 웹 애플리케이션 (데스크톱 우선) |
| 미결 | **시각 톤 A / B** — 프로토타입 2개 비교 후 확정 |

## 0. 확정된 제품 결정 (디자인 전제)

이 4가지는 이미 결정됐고, 디자인 시스템은 여기서 파생된다.

| # | 결정 | 디자인에 미치는 영향 |
|---|---|---|
| 1 | **웹의 사용자는 PM 한 명.** 팀원은 디스코드만 만진다 | 권한·역할 UI 없음. 다인용 협업 패턴(멘션, 코멘트, 담당자 배지 강조) 불필요. 화면은 "내가 지금 처리할 것" 중심 |
| 2 | **모든 승인은 웹에서.** 디스코드는 알림만 | 디스코드 embed 디자인 불필요. 대신 **알림 → 해당 카드 딥링크**가 필수. 승인 화면이 제품의 중심 화면 |
| 3 | **신뢰도는 3단 배지로만.** 원시 소수(0.92) 노출 금지 | 배지 3종 + "왜 확인이 필요한지" 이유 캡션이 정보 구조의 축 |
| 4 | 시각 톤 미결 | 컬러는 **역할 이름**으로 정의하고, 톤 A/B는 값만 교체한다 |

## 1. 디자인 원칙

### 1-1. 확정된 사실과 AI의 추측을 눈으로 구분한다

이 제품 화면의 절반은 확률적 산출물이다. 사용자가 "이건 확정인가, AI가 그렇게 본 것인가"를 **읽지 않고 알아야** 한다. 그래서 컬러·타이포와 나란히 **확정도**를 세 번째 축으로 둔다. 확정도는 색이 아니라 **경계선과 표면**으로 표현한다 — 색은 이미 상태 판단(정상/주의/위험)에 쓰이고 있어 충돌한다.

### 1-2. 색은 행동이 필요한 곳에만 쓴다

승인 화면에 색이 많으면 PM은 전부 훑고 아무것도 판단하지 못한다. 승인 워크벤치에서 **색을 쓰는 요소는 `확인 필요`(주황) 하나**다. 확정 항목은 무채색, 보류는 점선 무채색. PM의 시선이 자기 판단이 필요한 지점에만 간다.

### 1-3. 되돌릴 수 있는 것과 없는 것을 다르게 그린다

노션 게시는 되돌릴 수 있고, 디스코드 DM 발송은 되돌릴 수 없다. 발송 관련 화면은 폭을 좁히고(단일 결정 레이아웃) 다른 액션을 같은 화면에 두지 않는다. 게시 관련 화면은 목록형·고밀도로 훑을 수 있게 한다.

### 1-4. 숫자에는 항상 기준 시각을 붙인다

`API 명세서 10%`는 자기보고 값이고 근거는 8/21 디코 발언이다. 기준 시각 없이 숫자만 보여주면 PM은 실시간 사실로 오해한다. **모든 진행률·상태값 옆에 `8/21 기준`을 상시 노출**하고, 오래된 값은 대비를 낮춘다.

### 1-5. 판단을 유도하는 UI를 만들지 않는다

`전체 승인` 버튼, 신뢰도 점수, 초록색 자동 게시 배지는 모두 rubber stamp를 만든다. 자세한 금지 목록은 [12. 금지 목록](#12-금지-목록-donts).

## 2. 시각 톤 (미결 — 프로토타입 비교 후 확정)

두 톤은 **같은 구조·같은 컴포넌트·같은 데이터**로 만들고 값만 다르다.

| | 톤 A — 노션 인접 | 톤 B — 개발자 도구 |
|---|---|---|
| 기본 모드 | 라이트 | 다크 |
| 중성 램프 | 따뜻한 중성 (베이지 기운) | 차가운 중성 (블루블랙) |
| 밀도 | 여유 (본문 13.5px) | 고밀도 (본문 12.5px, 간격 ×0.85) |
| 주 액션 버튼 | 잉크 채움(거의 검정) | 정보색 채움(블루) |
| 근거 | 사용자가 노션과 번갈아 본다. 이질감이 크면 "또 하나의 도구"가 된다 | 옆 창이 디스코드(다크)다. 밤에 쓰는 도구다 |
| 위험 | 밋밋해서 기억에 안 남을 수 있다 | 감정적 문구(리마인드 DM 초안)가 차갑게 읽힐 수 있다 |

**판정용 프로토타입 3화면** — `반영 대기`(정보 밀도 최대) / `팀원별 진행률`(데이터 시각화) / `DM 승인`(감정적 톤). 이 3개면 톤 차이가 드러난다. 나머지 8화면은 톤 확정 후 하나로만 그린다.

## 3. 컬러

### 3-1. 1축 · 중성 램프

10단계. 컴포넌트는 원시 단계 대신 아래 **역할 이름**으로 지정한다.

| 역할 | 용도 | 톤 A (라이트) | 톤 B (다크) |
|---|---|---|---|
| `bg` | 페이지 배경 | `#F6F5F3` | `#0E1013` |
| `surface` | 카드·패널 | `#FFFFFF` | `#14171C` |
| `surface-sunken` | 눌린 영역 (근거 블록, 로그) | `#F6F5F3` | `#0E1013` |
| `surface-raised` | 떠 있는 영역 (드롭다운, 토스트) | `#FFFFFF` + shadow | `#1A1E24` |
| `surface-hover` | 호버 | `#EFEEEB` | `#22272F` |
| `line` | 기본 경계 | `#E4E2DE` | `#262C34` |
| `line-strong` | 강조 경계 · 점선 | `#D3D0CA` | `#39414A` |
| `ink` | 제목·본문 | `#23211C` | `#E4E8EB` |
| `ink-sub` | 보조 설명 | `#605C54` | `#98A0A8` |
| `ink-faint` | 메타·타임스탬프 — **텍스트 최저선** | `#757168` | `#7C848D` |
| `ink-disabled` | 비활성 (텍스트로 쓰지 않는다) | `#A5A19A` | `#5A626B` |

> **`ink-faint`보다 연한 색으로 글자를 쓰지 않는다.** 프로토타입의 `.muted`가 이 선을 넘는 곳이 여러 곳 있다 — 특히 캘린더 이벤트의 부제와 로그 목록.

### 3-2. 2축 · 의미색 — 프로젝트 상태에만

| 역할 | 의미 | 쓰는 곳 | 톤 A | 톤 B |
|---|---|---|---|---|
| `ok` | 정상 · 완료 | 진행률 정상, 완료 태스크, 승인 버튼 | `#2F7A4B` | `#5FCE87` |
| `warn` | 주의 · **확인 필요** | 확인 필요 배지, 주의 구간 진행률 | `#B4530A` | `#E8A13A` |
| `bad` | 위험 | 위험 구간, 마감 초과, 무응답, 블로커 | `#B02525` | `#F0736B` |
| `pri` | 정보 · 링크 · 포커스 | 링크, 포커스 링, 정보 안내 박스 | `#2A6FD4` | `#6EA8FE` |

각 색은 `-soft`(배경)와 `-line`(경계) 변형을 갖는다.

| | ok-soft / ok-line | warn-soft / warn-line | bad-soft / bad-line | pri-soft / pri-line |
|---|---|---|---|---|
| 톤 A | `#EAF3EC` / `#BFDBC8` | `#FBF0E6` / `#EBC9A6` | `#FBEBEB` / `#EFC4C4` | `#EBF1FB` / `#C2D5F2` |
| 톤 B | `#14261B` / `#2C5B3B` | `#2B2113` / `#5C4520` | `#2C1817` / `#5E2E2B` | `#16202F` / `#2A4573` |

**사용 규칙**

- `pri`(블루)는 **액션 색이 아니다.** 링크·포커스·정보 안내에만. 주 액션 버튼은 톤 A에서 잉크 채움, 톤 B에서 별도 액션색을 쓴다.
- `bad`(빨강)는 **승인 카드에 쓰지 않는다.** 빨강은 "AI가 틀렸다"로 읽혀 불필요한 불신을 만든다. 빨강은 프로젝트 리스크(마감 초과·무응답·위험 구간·블로커) 전용.
- 한 화면에서 `warn`과 `bad`를 동시에 강하게 쓰지 않는다. 승인 화면은 `warn`만, 팀원별 화면은 `ok/warn/bad` 3단.

### 3-3. 3축 · 확정도 — 색이 아니라 표면 처리

AI 산출물의 확정 정도를 나타낸다. **컬러 토큰을 새로 만들지 않는다.**

| 상태 | 의미 | 경계 | 배경 | 잉크 | 좌측 액센트 |
|---|---|---|---|---|---|
| `posted` 게시됨 | 확정 사실. 노션에 이미 있다 | 실선 1px `line` | `surface` | `ink` (100%) | 없음 |
| `review` 확인 필요 | 뽑았지만 필드 하나가 불확실 | 실선 1px `warn-line` | `surface` | `ink` (100%) | **3px `warn`** |
| `hold` 보류 | 정보 자체가 부족하다 | **점선 1px `line-strong`** | `surface-sunken` | `ink-sub` | 없음 |

`hold`는 경고가 아니라 미완성이다. 점선과 눌린 배경이 "아직 채워지지 않았다"를 말하고, 색은 쓰지 않는다.

폴링이 감지한 **변경 제안**도 `review` 처리를 그대로 쓴다. 새 상태를 만들지 않는다.

### 3-4. 대비 기준

| 대상 | 최소 대비 |
|---|---|
| 본문·라벨 (13.5px 이하) | 4.5:1 |
| 큰 텍스트 (19px 이상 / 15px bold) | 3:1 |
| 경계선·아이콘 등 비텍스트 | 3:1 |

램프는 이 기준을 만족하도록 골랐으나, **화면 완성 후 실측 검증이 필요하다**(§11 참조). 특히 톤 B의 `warn` 계열과 톤 A의 `ink-faint`가 경계값에 가깝다.

**색맹 검증**: 승인 워크벤치는 색을 `warn` 하나만 쓰므로 색 정보 없이도 구분돼야 정상이다. 팀원별 화면의 3단(ok/warn/bad)은 색 외에 **배지 텍스트와 진행률 숫자**가 항상 함께 있어야 한다.

## 4. 타이포그래피

| 폰트 | 용도 |
|---|---|
| **IBM Plex Sans KR** (400 / 500 / 700) | 모든 UI 텍스트 |
| **IBM Plex Mono** (400 / 500) | 숫자, 날짜, 타임스탬프, 태스크 ID, 진행률 % |

같은 계열이라 섞어 써도 무너지지 않고, 근거 인용의 타임스탬프를 모노로 두면 "출처가 있는 값"이라는 느낌이 생긴다.

### 4-1. 스케일

| 이름 | 크기 / 행간 | 굵기 | 용도 |
|---|---|---|---|
| `display` | 24 / 1.35 | 700 | 온보딩 질문 ("어떤 프로젝트로 시작할까요?") |
| `h1` | 19 / 1.4 | 700 | 화면 제목 ("반영 대기") |
| `h2` | 15 / 1.45 | 700 | 카드 제목, 섹션 헤더 |
| `body` | 13.5 / 1.65 | 400 | 본문, 태스크명, 근거 인용 |
| `sm` | 12.5 / 1.55 | 400 | 보조 설명, 필드 라벨, 버튼 |
| `xs` | 11.5 / 1.45 | 500 | 배지, 메타, 기준 시각 |

톤 B는 `body` 12.5 / `sm` 11.5 / `xs` 11로 한 단 내린다.

### 4-2. 한글 규칙

- **행간을 1.6 미만으로 내리지 않는다** (본문). 한글은 라틴보다 글자 밀도가 높아 좁히면 바로 답답해진다.
- **자간을 조이지 않는다.** 트래킹은 0. 라틴 숫자만 `-0.02em`으로 조여 표 정렬을 맞춘다.
- 굵기는 400 / 500 / 700 세 단계만. 600은 700과 화면에서 구분되지 않는다.
- 한 줄 길이는 본문 **최대 78자** (약 640px). 온보딩 설명문이 이 선을 넘지 않게 한다.
- 줄바꿈은 `word-break: keep-all`. 어절 중간에서 끊기지 않게 한다.

## 5. 간격 · 레이아웃

4px 기반. 톤 B는 전체에 ×0.85.

| 토큰 | 값 | 주 용도 |
|---|---|---|
| `sp-1` | 4 | 배지 내부, 인라인 간격 |
| `sp-2` | 8 | 버튼 내부 세로, 필드 라벨↔입력 |
| `sp-3` | 12 | 카드 내부 요소 간, 리스트 항목 간 |
| `sp-4` | 16 | 카드 패딩 (기본) |
| `sp-5` | 20 | 카드 패딩 (넓은 카드) |
| `sp-6` | 24 | 카드 간 |
| `sp-7` | 32 | 섹션 간 |
| `sp-8` | 40 | 화면 상단 여백 |
| `sp-9` | 56 | 빈 상태 내부 세로 여백 |

### 레이아웃 폭

| 이름 | 폭 | 쓰는 화면 |
|---|---|---|
| `max` | 1180px | 반영 대기, 팀원별, 대시보드 |
| `narrow` | 720px | 온보딩 6스텝, DM 승인, 처리 중 |

**DM 승인 화면은 반드시 `narrow`.** 되돌릴 수 없는 결정 하나만 놓는 화면이라 폭을 좁혀 다른 선택지가 시야에 없게 한다.

### 반경 · 경계 · 고도

| 항목 | 값 |
|---|---|
| 반경 | `4` 배지·입력 / `8` 카드·버튼 / `12` 큰 패널·모달 / `999` 아바타·칩 |
| 경계 두께 | 기본 1px, 확인 필요 카드 좌측 액센트 3px |
| 고도 | 톤 A는 경계 + 미세 그림자(`0 1px 2px 6%`), 떠 있는 요소만 `0 4px 14px 10%`. **톤 B는 그림자 없이 표면 밝기 단계로만 표현** |

## 6. 아이콘 · 이모지 정책

프로토타입은 📋 🎙 🗂️ 🔌 ⚠ 📅 🎉 를 섞어 쓴다. 이모지는 OS마다 모양이 달라 시스템이 성립하지 않고, 여러 개 섞이면 완성도가 떨어진다.

| 대상 | 정책 |
|---|---|
| UI 아이콘 (연결, 업로드, 달력, 경고, 되돌리기) | **단일 아이콘 세트 하나만.** Lucide 권장 — 1.5px 스트로크, 16px/20px 두 사이즈만 |
| 팀원 아바타 | 이름 첫 글자 + 배경색. 이모지 금지 |
| 로고 | 이모지(📋) 금지. 텍스트 워드마크 또는 단색 심볼 |
| 디스코드로 나가는 메시지 본문 | **이모지 허용.** 사람이 쓴 것처럼 보여야 하는 유일한 곳이다 (🙂 🙏) |
| 빈 상태 일러스트 | 아이콘 32px + `ink-faint`. 큰 이모지 금지 |

아이콘 색은 항상 인접 텍스트와 같은 잉크 역할을 쓴다. 아이콘만 유색으로 두지 않는다.

## 7. 컴포넌트

### 7-1. 배지 — 확정도 3단 (핵심)

Q3-b의 구현체. **원시 신뢰도 숫자를 절대 넣지 않는다.**

| 배지 | 라벨 | 배경 | 경계 | 잉크 |
|---|---|---|---|---|
| 게시됨 | `자동 게시` | 투명 | 실선 `line` | `ink-sub` |
| 확인 필요 | `확인 필요` | `warn-soft` | 실선 `warn-line` | `warn` |
| 보류 | `보류` | 투명 | **점선** `line-strong` | `ink-faint` |

- 크기: `xs`(11.5 / 500), 세로 패딩 2px, 가로 6px, 반경 4px
- 배지는 **등급만** 말한다. "왜"는 바로 아래 **이유 캡션**이 말한다 (§9-1)

```
┌─────────────────────────────────────────┐
│ [확인 필요]  발표 준비                   │  ← 배지 + 태스크명
│  담당자 후보가 둘 — 서연 / 지민          │  ← 이유 캡션 (sm, ink-sub)
└─────────────────────────────────────────┘
```

### 7-2. 상태 칩 — 라이프사이클 vs 리스크를 분리한다

프로토타입은 `진행 중`을 주황, `시작 전`을 빨강으로 칠한다. 진행 중은 정상 상태이고 시작 전은 마감이 멀면 문제가 아니다. **라이프사이클과 리스크는 다른 축**이므로 분리한다.

| 축 | 값 | 색 |
|---|---|---|
| 라이프사이클 | `시작 전` · `진행 중` · `완료` | **무채색 칩** (`line` 경계, `ink-sub`) |
| 라이프사이클 예외 | `막힘` | `bad` — 블로커는 실제 리스크다 |
| 리스크 (PM 룰 판정) | `정상` · `주의` · `위험` | `ok` / `warn` / `bad` |

한 행에 두 축이 함께 올 수 있다: `진행 중`(무채색) + `주의`(주황).

### 7-3. 승인 카드 (제품의 중심 컴포넌트)

반영 대기 화면의 항목. 확정도 3단(§3-3)의 표면 처리를 그대로 입는다.

**구조 (위→아래)**

1. **헤더** — 확정도 배지 + 태스크명(`h2`)
2. **이유 캡션** — 무엇이 불확실한지 한 줄 (`sm` / `ink-sub`). `게시됨`에는 없다
3. **필드 3열** — 태스크명 / 담당자(select) / 마감(date). 인라인 수정 가능
4. **하위 태스크 제안** — 있을 때만. 한 줄 요약 + `단위 조정`
5. **근거 블록** — §7-4. `확인 필요`는 접힘, `보류`는 **항상 펼침**
6. **액션 행** — 확정도별로 다르다

| 확정도 | 액션 |
|---|---|
| 게시됨 | `되돌리기` 만. **승인 버튼 없음** |
| 확인 필요 | `근거 보기` · `승인` · `반려` |
| 보류 | (근거 상시 노출) · `승인` · `반려` — 승인은 필드를 채운 뒤에만 활성 |

**규격**: 패딩 `sp-4`, 카드 간 `sp-3`, 반경 8, 필드 3열 그리드 `gap: sp-3`.

**결정 후 상태**: 승인/반려한 카드는 사라지지 않고 자리를 유지한 채 `승인됨` / `반려됨` 표식을 붙이고 `ink-sub`로 눌린다 — 목록이 흔들리면 PM이 위치를 잃는다.

### 7-4. 근거 블록

이 제품 신뢰의 근간. 모든 AI 판단에 붙는다.

```
┌───────────────────────────────────────────────────────┐
│ 전사문 12:40 — 재환: "API 명세서는 제가 수요일까지     │
│ 정리해서 올릴게요"                            원문 ↗  │
└───────────────────────────────────────────────────────┘
```

- 배경 `surface-sunken`, 좌측 2px `line-strong` 경계, 패딩 `sp-3`, 반경 4
- 출처 표기는 **모노**, `ink-faint`. 형식: `전사문 12:40` / `디코 #개발 8/21 17:30` / `Notion 수정 이력 8/21`
- 인용문은 `body`, `ink`, 큰따옴표 포함. **요약하지 않고 원문 그대로**
- 우측에 `원문 ↗` — 전사문 해당 구간으로 점프
- 근거가 없으면 블록을 비우지 않고 **`근거 없음 — 회의에서 결정되지 않음`**을 `ink-faint`로 명시한다

### 7-5. 진행률 바

```
API 명세서   10%   [진행 중]   마감 8/27
▓▓░░░░░░░░░░░░░░░░░░
8/21 기준 · 디코 발언                          근거 보기
```

- 높이 6px, 반경 999, 트랙 `surface-sunken`
- 채움 색은 **리스크 판정** 기준: 정상 `ok` / 주의 `warn` / 위험 `bad`
- 숫자는 **모노**
- **`8/21 기준`을 상시 노출** (원칙 1-4). 3일 이상 지난 값은 바 전체 투명도를 60%로 낮춘다
- 0%는 빈 트랙 + 좌측 2px 스텁으로 표시해 "값이 없음"과 구분한다

> 팀원 헤더의 `평균 33%` 같은 합성 지표는 근거가 약하다. 유지 여부는 미결 — 유지한다면 반드시 계산식을 툴팁으로 밝힌다.

### 7-6. 버튼

| 종류 | 톤 A | 톤 B | 용도 |
|---|---|---|---|
| 주 액션 | 잉크 채움 / 흰 글자 | 액션색 채움 / 흰 글자 | 화면당 **1개만** (`다음`, `게시`, `발송`) |
| 기본 | `surface` + `line` 경계 | 동일 | 보조 액션 |
| 승인 | `ok-soft` 배경 + `ok-line` + `ok` 글자 | 동일 | 카드 승인 |
| 반려 | 기본 + 호버 시 글자 `bad` | 동일 | 카드 반려. **빨강 채움 금지** — 정상적인 선택지다 |
| 고스트 | 투명 + `ink-sub` | 동일 | `이전`, `가이드 보기` |

- 크기: 기본 32px(패딩 `sp-2`/`sp-3`), 소형 26px, 라벨 `sm`
- 반경 8 (소형 4)
- 포커스: `pri` 2px 아웃라인 + 2px 오프셋. 모든 인터랙티브 요소 필수
- **파괴적 액션의 빨강 채움은 `삭제`에만.** `반려`·`보내지 않음`은 파괴가 아니다

### 7-7. 필드

- 라벨: `sm` / 500 / `ink-sub`, 입력과 `sp-2` 간격, 항상 입력 **위**에 (좌측 배치 금지 — 3열 그리드가 무너진다)
- 입력: 높이 32, 패딩 `sp-2`/`sp-3`, 경계 1px `line`, 반경 4, 포커스 시 경계 `pri`
- **AI가 채운 값과 PM이 고친 값을 구분한다**: AI 값은 그대로, PM이 수정하면 라벨 옆에 `수정됨` 무채색 칩. 이게 로그·되돌리기와 이어진다
- 마감일은 항상 달력 피커. 텍스트 입력 금지 (상대 날짜 오류의 원천)
- 담당자는 select. `미지정 (보류)`가 첫 옵션

### 7-8. 팀원 그룹

- 헤더: 아바타 28px + 이름·역할(`h2`) + 우측 리스크 배지
- 아바타 배경색은 팀원별 고정. **6색 팔레트를 고정 배정**하고 이름 해시로 자동 배정하지 않는다(색이 바뀌면 사람이 헷갈린다)
- 태스크 행 간 `sp-3`, 그룹 간 `sp-6`

### 7-9. 주간 일정 (캘린더)

- 7열 그리드, 요일 헤더 높이 40, 오늘 열은 배경 `pri-soft` + 날짜 `pri`
- 이벤트 칩: 높이 auto, 패딩 `sp-1`/`sp-2`, 반경 4, 좌측 3px 담당자 색
- 이벤트 부제(`담당자 · ~8/27`)는 `xs` / `ink-faint` — 이 문서의 대비 최저선을 넘지 않게 주의
- 변경된 마감은 원래 위치에 **점선 유령 칩**을 남기고 새 위치에 실선 칩. `8/27→8/29` 표기

### 7-10. 반영 로그

- `surface-sunken` 패널, 항목당 1줄, 최신순
- 형식: `[모노 시각] 동작 — 대상 · 사유` + 우측 `되돌리기`
- 되돌리기가 가능한 항목만 버튼 노출. 만료된 항목은 `되돌리기 불가` `ink-faint`
- 자동 게시 항목과 PM 승인 항목을 **행 좌측 2px 마커**로 구분 (자동=`line-strong`, 승인=`ok`)

### 7-11. 스테퍼 (온보딩 6스텝)

`프로젝트 → Discord → Notion → 정리 형태 → 담당자 매핑 → 알림 룰`

- 상단 고정, 현재 스텝만 `ink`/700, 완료 스텝 `ink-sub` + 체크, 미방문 `ink-faint`
- 6개는 한 줄에 다 들어간다. 숫자 원형 배지 없이 텍스트 + `→`로 충분

### 7-12. 선택 카드 · 카운터 · 세그먼티드

| 컴포넌트 | 규격 |
|---|---|
| 선택 카드 | 체크박스 16px + 제목(`body`/500) + 설명(`sm`/`ink-sub`). 선택 시 경계 `pri` + 배경 `pri-soft`. 패딩 `sp-3` |
| 카운터 | `− [값] +`. 값은 **모노**, 최소 폭 56px로 고정해 숫자가 바뀔 때 버튼이 흔들리지 않게 한다 |
| 세그먼티드 | `surface-sunken` 트랙 + 선택 항목만 `surface` 실선. 2~3개까지만 |

### 7-13. 상태 박스

| 종류 | 배경 / 경계 / 아이콘 | 용도 |
|---|---|---|
| 정보 | `pri-soft` / `pri-line` / info | AI 자동 판단 안내 |
| 성공 | `ok-soft` / `ok-line` / check | 권한 확인 완료 |
| 경고 | `warn-soft` / `warn-line` / alert | 부분 실패, 재시도 가능 |
| 오류 | `bad-soft` / `bad-line` / x | 전사 실패, 권한 부족 |

**오류 박스에는 항상 대체 경로 버튼이 있어야 한다.** (`텍스트 회의록으로 업로드`, `권한 다시 확인`) — 흐름이 끊기지 않게 하는 것이 이 제품의 실패 설계다.

### 7-14. 처리 단계 리스트

`음성 → 텍스트 전사` / `결정사항 추출` / `담당자 매칭`

- 완료 `ok` 체크 / 진행 중 회전 인디케이터 + `ink` / 대기 `ink-faint`
- 진행 중 단계에는 **경과 시간**을 모노로 노출 (10분 목표를 사용자가 체감해야 한다)
- 하단에 고정 문구: `승인 전에는 Notion에 아무것도 쓰지 않아요`

### 7-15. 빈 상태

아이콘 32px `ink-faint` → 제목(`h2`) → 설명 2줄 이내(`sm`/`ink-sub`) → 주 액션 1개 → 연결 상태 한 줄(`xs`/`ink-faint`).
세로 여백 `sp-9`, 폭 `narrow` 중앙 정렬.

### 7-16. 토스트

- 우하단, `surface-raised`, 반경 8, 패딩 `sp-3`/`sp-4`, 4초 후 소멸
- **되돌릴 수 있는 동작의 토스트에는 `되돌리기` 버튼을 넣는다**
- 오류는 토스트로 처리하지 않는다 — 사라지면 안 되므로 상태 박스로

### 7-17. 테이블 (담당자 매핑)

- 헤더 행 `surface-sunken`, `xs`/500/`ink-sub`, 행 높이 40, 구분선 `line`
- 매핑 안 된 행은 좌측 2px `warn` 마커 + `미매칭` 배지. **미매칭이 남아 있으면 온보딩 완료 버튼을 비활성**한다 (매핑이 없으면 DM 발송이 불가능하다)

### 7-18. 앱 셸

- 헤더 높이 52, `surface` + 하단 `line`
- 좌측 워드마크 → 탭 4개(`대시보드` `반영 대기` `팀원별` `설정`) → 우측 워크스페이스명 + 아바타
- `반영 대기` 탭에는 **대기 건수 배지**. 0건이면 배지를 숨긴다(0을 보여주면 노이즈)
- 탭 활성 표시는 하단 2px `ink` 바. 배경 채움 금지

## 9. 카피 규칙

### 9-1. 이유 캡션 패턴

배지가 등급을, 캡션이 이유를 말한다. **PM이 3초 안에 판단할 수 있는 유일한 정보**다.

| 불확실한 것 | 캡션 |
|---|---|
| 담당자 후보 복수 | `담당자 후보가 둘 — 서연 / 지민` |
| 담당자 미지정 | `회의에서 담당자가 정해지지 않음` |
| 마감 모호 | `마감이 '다음 주쯤'으로만 언급됨` |
| 수락 미확인 | `지명은 됐지만 본인 확인이 없음` |
| 전사 불명 | `해당 구간 인식 불가 — 원문 8:15 확인 필요` |

### 9-2. 문장 규칙

- **숫자로 확신을 표현하지 않는다.** `신뢰도 0.74` (✕) → `담당자 후보가 둘` (○)
- AI의 판단은 단정하지 않는다. `진행률 50%입니다` (✕) → `답장 기준 50%로 봤어요` (○)
- 되돌릴 수 없는 액션의 버튼은 동작을 명시한다. `확인` (✕) → `이대로 발송` (○)
- 사용자를 주체로 쓴다. `AI가 정리했습니다` (✕) → `정리해 드렸어요, 확인해 주세요` (○)
- 해요체 통일. 오류 메시지도 해요체 + 원인 + 다음 행동 순서
- 전문용어는 노출하지 않는다. `폴링` `MCP` `STT` (✕) → `1시간마다 확인` `연결` `음성 변환` (○)

## 12. 금지 목록 (Don'ts)

| 금지 | 이유 |
|---|---|
| **`전체 승인` 버튼** | 게이트 전체를 장식으로 만든다. 자율성 설계의 근간이 무너진다 |
| **신뢰도 소수점 노출** (`0.74`) | PM은 0.74와 0.71로 다른 행동을 하지 않는다. 근거 없는 정밀도이고, 숫자를 본 PM은 근거 원문을 읽지 않는다 |
| **`자동 게시` 배지에 승인 버튼** | 기획안은 0.8 이상을 승인 없이 게시하고 사후 롤백한다. 승인 버튼을 달면 자동화 주장이 사라진다 |
| **`보류`를 빨강으로** | 보류는 틀린 게 아니라 정보가 부족한 것이다. 빨강은 불필요한 불신을 만든다 |
| **`진행 중`·`시작 전`을 유색으로** | 라이프사이클은 리스크가 아니다. 색이 많아지면 실제 리스크가 안 보인다 |
| **기준 시각 없는 진행률** | 자기보고 값을 실시간 사실로 오해하게 만든다 |
| **AI 값과 PM 수정값의 무구분** | 로그·되돌리기·신뢰도 보정의 근거가 사라진다 |
| **이모지 아이콘 혼용** | OS마다 모양이 달라 시스템이 성립하지 않는다. 디스코드로 나가는 메시지 본문만 예외 |
| **팀원용 화면·권한 UI** | 웹은 PM 전용이다 (결정 1) |
| **디스코드 embed·버튼 디자인** | 디스코드는 알림만 한다 (결정 2) |
| **요약된 근거 인용** | 근거는 원문 그대로여야 검증 가능하다 |
| **오류를 토스트로 처리** | 사라지면 사용자가 대체 경로를 놓친다 |
