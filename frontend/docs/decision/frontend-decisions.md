# 프론트엔드 개발 결정 기록

## 목적

프론트엔드 개발 전에 필요한 사항을 한 항목씩 논의하고, 합의된 결정과 그 이유를 기록한다.

## 기록 원칙

- 논의 중인 내용과 확정된 결정을 구분한다.
- 확정된 결정에는 선택 이유와 영향을 함께 기록한다.
- 아직 정하지 않은 내용은 임의로 확정하지 않는다.
- 결정이 변경되면 이전 내용을 삭제하지 않고 변경 사유를 남긴다.

## 논의 순서

1. 화면·기능 명세
2. URL과 라우팅 정책
3. API 계약
4. 상태 관리와 상태의 소유권
5. 인증과 권한
6. 폼과 유효성 검증 정책
7. 디자인 시스템 구현 기준
8. 접근성과 반응형
9. 테스트 전략
10. 운영·배포 준비

## 결정 내역

### D-001. 1차 개발 화면 범위

- 결정일: 2026-09-13
- 상태: 확정

1차 개발 범위는 다음 8개 영역으로 한다.

1. 랜딩, 로그인, 회원가입
2. 워크스페이스 선택 및 초기 설정
3. Discord, Notion, 팀원 연결
4. 대시보드
5. 회의 업로드, 처리, 회의록
6. 태스크 목록, 보드, 캘린더, 간트차트
7. 메시지
8. 워크스페이스 관리, 설정

현재 1차 범위에 포함하지 않는 화면:

- 비밀번호 재설정
- 활동 로그
- 내 계정
- 시작 가이드
- 서비스 안내
- 디자인 시스템 문서 화면

비고:

- 제외된 화면의 삭제 여부나 후속 개발 시점은 아직 결정하지 않았다.
- 간트차트는 현재 프로토타입의 기존 화면 목록에는 없지만 1차 개발 범위에 새로 포함한다.

### D-002. 랜딩 페이지의 데모 기능 제외

- 결정일: 2026-09-13
- 상태: 확정

1차 개발의 랜딩 페이지에는 `1분 데모 보기` 기능과 버튼을 넣지 않는다.

비고:

- D-002 논의 시점에는 랜딩 페이지의 최종 디자인이 업데이트 전이었으며, 이후 업데이트된 디자인의 CTA를 D-003에 반영했다.
- 랜딩 페이지의 나머지 버튼과 이동 경로는 최종 디자인과 후속 논의를 거쳐 확정한다.

### D-003. 랜딩 페이지의 주요 CTA

- 결정일: 2026-09-13
- 상태: 확정

업데이트된 랜딩 디자인의 주요 CTA는 다음과 같이 구현한다.

- 버튼 문구: `시작하기`
- 이동 화면: 로그인 페이지

`무료로 시작하기` 문구는 사용하지 않으며, 주요 CTA에서 회원가입 페이지로 직접 이동하지 않는다.

### D-004. 회원가입 페이지 진입 경로

- 결정일: 2026-09-13
- 상태: 확정

회원가입 페이지는 랜딩 페이지에서 직접 연결하지 않는다. 사용자는 랜딩의 `시작하기` 버튼으로 로그인 페이지에 진입한 후, 로그인 페이지에 제공되는 회원가입 링크를 통해 회원가입 페이지로 이동한다.

### D-005. 비밀번호 재설정 링크의 1차 처리

- 결정일: 2026-09-13
- 상태: 확정

로그인 페이지의 `비밀번호를 잊으셨나요?` 항목은 화면에서 제거하지 않고 비활성화 상태로 표시한다.

- 마우스 클릭이나 키보드 실행에 반응하지 않는다.
- 비밀번호 재설정 페이지로 이동하지 않는다.
- 비활성화 이유를 설명하는 문구나 표식은 D-006에서 표시하지 않기로 결정했다.

### D-006. 비밀번호 재설정의 최종 배포 조건

- 결정일: 2026-09-13
- 상태: 확정

- 1차 개발 중 비활성화된 `비밀번호를 잊으셨나요?` 항목에 `준비 중` 문구나 별도 배지를 표시하지 않는다.
- 비활성화 상태는 개발 중에만 허용되는 임시 처리다.
- 최종 배포 전에는 비밀번호 재설정 기능과 이동 페이지를 구현하여 활성화한다.

### D-007. 로그인 인증 방식

- 결정일: 2026-09-13
- 상태: 확정

1차 개발에서 다음 로그인 방식을 지원한다.

- 이메일과 비밀번호
- Google 계정

Google 이외의 소셜 로그인은 현재 1차 개발 범위에 포함하지 않는다.

### D-008. Google 최초 로그인 후 온보딩

- 결정일: 2026-09-13
- 상태: 확정

가입 이력이 없는 사용자가 Google 계정으로 처음 로그인하면 계정을 생성한 후 온보딩(설정) 페이지로 이동한다.

온보딩은 다음 순서로 진행한다.

1. 워크스페이스 만들기
2. Discord 연결
3. Notion 연결
4. 팀원 연결

각 단계의 건너뛰기, 이전 단계 이동, 중단 후 재개 정책은 아직 결정하지 않았다.

### D-009. 이메일 회원가입 후 온보딩

- 결정일: 2026-09-13
- 상태: 확정

이메일과 비밀번호로 회원가입한 사용자도 가입 완료 후 D-008과 동일한 온보딩 파이프라인으로 이동한다.

`회원가입 완료 → 워크스페이스 만들기 → Discord 연결 → Notion 연결 → 팀원 연결`

### D-010. 기존 사용자 로그인 후 이동 경로

- 결정일: 2026-09-13
- 상태: 확정

기존 사용자가 로그인하면 소속 워크스페이스 개수에 따라 다음 화면으로 이동한다.

- 소속 워크스페이스가 없는 경우: 온보딩 페이지
- 소속 워크스페이스가 1개인 경우: 해당 워크스페이스의 대시보드
- 소속 워크스페이스가 2개 이상인 경우: 워크스페이스 선택 페이지

### D-011. 온보딩 단계의 필수 여부

- 결정일: 2026-09-13
- 상태: 확정

- `워크스페이스 만들기` 단계는 필수다.
- `Discord 연결`, `Notion 연결`, `팀원 연결` 단계는 건너뛸 수 있다.
- 건너뛴 연결은 이후 `워크스페이스 관리·설정` 화면에서 완료할 수 있다.

### D-012. 중단된 온보딩 재개

- 결정일: 2026-09-13
- 상태: 확정

- 온보딩의 각 단계가 완료되거나 건너뛰어졌는지 저장한다.
- 사용자가 온보딩 도중 이탈한 뒤 다시 로그인하면 마지막으로 완료한 단계의 다음 단계부터 재개한다.
- 건너뛰기를 선택한 단계는 온보딩 재개 대상에서 제외하고, 이후 `워크스페이스 관리·설정`에서 완료한다.

### D-013. 온보딩 완료 후 이동

- 결정일: 2026-09-13
- 상태: 확정

`팀원 연결` 단계까지 완료하거나 건너뛰어 온보딩이 종료되면, 사용자를 새로 생성한 워크스페이스의 대시보드로 이동시킨다.

### D-014. 워크스페이스 만들기 입력 항목

- 결정일: 2026-09-13
- 상태: 확정

온보딩의 `워크스페이스 만들기` 단계에서는 워크스페이스 이름만 입력받는다. 워크스페이스 이미지, 설명 등의 추가 정보는 온보딩 입력 항목에 포함하지 않는다.

### D-015. 워크스페이스 이름 중복 제한

- 결정일: 2026-09-13
- 상태: 확정

중복된 워크스페이스 이름은 현재 사용자 계정을 기준으로 허용하지 않는다.

- 사용자가 이미 소속된 워크스페이스과 같은 이름으로 새 워크스페이스을 만들 수 없다.
- 다른 사용자 계정에만 존재하는 워크스페이스과는 이름이 같아도 된다.
- 워크스페이스은 이름이 아닌 고유한 워크스페이스 ID로 식별한다.

워크스페이스 이름의 공백, 글자 수, 대소문자 처리 규칙은 별도로 결정한다.

### D-016. 워크스페이스 이름의 앞뒤 공백 처리

- 결정일: 2026-09-13
- 상태: 확정

- 워크스페이스 이름을 저장하거나 중복 검사하기 전에 앞뒤 공백을 제거한다.
- 앞뒤 공백을 제거한 결과가 빈 문자열이면 워크스페이스을 생성할 수 없다.
- 이름 중간에 포함된 공백의 처리 방식은 아직 결정하지 않았다.

예: `"  디자인 워크스페이스  "`은 `"디자인 워크스페이스"`으로 저장하고 검사한다.

### D-017. 워크스페이스 이름의 글자 수 제한

- 결정일: 2026-09-13
- 상태: 확정

- 앞뒤 공백을 제거한 워크스페이스 이름은 1자 이상 20자 이하여야 한다.
- 이름 중간에 포함된 공백도 글자 수에 포함한다.

### D-018. 워크스페이스 이름 중간의 연속 공백 처리

- 결정일: 2026-09-13
- 상태: 확정

- 워크스페이스 이름을 저장하거나 중복 검사하기 전에 이름 중간의 연속 공백을 하나로 합친다.
- 공백을 정규화한 뒤 D-017의 글자 수 제한을 검사한다.

예: `"디자인   워크스페이스"`은 `"디자인 워크스페이스"`으로 저장하고 검사한다.

### D-019. 워크스페이스 이름의 대소문자 중복 판정

- 결정일: 2026-09-13
- 상태: 확정

- 영문 대소문자를 구분하여 서로 다른 워크스페이스 이름으로 판정한다.
- 같은 사용자 계정에 `Alpha`와 `alpha`를 각각 생성할 수 있다.
- 공백 정규화 후의 이름을 대소문자를 유지한 상태로 비교한다.

### D-020. 워크스페이스 이름에 허용할 문자

- 결정일: 2026-09-13
- 상태: 1차 개발 기준 확정

- 1차 개발에서는 워크스페이스 이름에 특수문자와 이모지를 허용한다.
- 문자 종류를 이유로 입력을 차단하지 않는다.
- 앞서 결정한 공백 정규화, 필수 입력, 20자 이하 및 사용자 계정 기준 중복 제한은 그대로 적용한다.
- 운영 과정에서 문제가 확인되면 허용 문자 정책을 다시 검토할 수 있다.

### D-021. 워크스페이스당 Discord 서버 연결 개수

- 결정일: 2026-09-13
- 상태: 1차 개발 기준 확정

- 1차 개발에서는 워크스페이스 하나에 Discord 서버를 하나만 연결할 수 있다.
- 새로운 서버를 연결하려면 기존 연결을 해제하거나 교체해야 한다.
- 여러 Discord 서버 연결 지원은 후속 범위로 남긴다.

### D-022. 워크스페이스당 Notion 워크스페이스 연결 개수

- 결정일: 2026-09-13
- 상태: 1차 개발 기준 확정

- 1차 개발에서는 워크스페이스 하나에 Notion 워크스페이스를 하나만 연결할 수 있다.
- 새로운 Notion 워크스페이스를 연결하려면 기존 연결을 해제하거나 교체해야 한다.
- 여러 Notion 워크스페이스 연결 지원은 후속 범위로 남긴다.

### D-023. Notion에 저장할 데이터 범위

- 결정일: 2026-09-13
- 상태: 확정

연결한 Notion 워크스페이스에는 태스크뿐 아니라 회의록도 저장한다.

아직 결정할 내용:

- 태스크와 회의록을 같은 데이터베이스에 저장할지 별도 데이터베이스로 분리할지
- 각 데이터베이스의 개수와 속성 구조
- Manager's Manager와 Notion 사이의 동기화 방향

책임 구분:

- 위 데이터 저장 구조와 동기화 정책은 프론트엔드에서 단독으로 결정하지 않는다.
- 백엔드와 제품 요구사항 논의를 통해 결정한 후 API 계약으로 프론트엔드에 전달한다.
- 프론트엔드는 API 계약을 기준으로 Notion 연결, 선택, 진행 상태 및 오류 UI를 구현한다.

### D-024. Discord·Notion 연결 주체

- 결정일: 2026-09-13
- 상태: 확정

- Discord와 Notion 연동은 모두 워크스페이스의 PM 한 명이 자신의 계정으로 진행한다.
- 팀원 각자가 Discord와 Notion OAuth 인증을 별도로 진행하는 구조가 아니다.
- PM 계정으로 연결한 Notion 워크스페이스와 Discord 서버를 워크스페이스 단위로 사용한다.
- PM의 구체적인 권한 요건과 연결 권한 이전 정책은 아직 결정하지 않았다.

### D-025. 팀원 연결의 목적과 대상

- 결정일: 2026-09-13
- 상태: 확정

- `팀원 연결`은 Discord 사용자와 Notion 사용자를 매핑하는 기능이 아니다.
- Notion 사용자는 팀원 매핑 대상으로 고려하지 않는다.
- Discord에서 가져오는 음성 파일은 Discord 사용자별로 구분된다.
- PM은 음성 파일의 Discord 사용자 식별자를 Manager's Manager의 실제 팀원과 연결한다.
- 이 매핑은 회의 음성의 화자가 어떤 팀원인지 식별하기 위해 사용한다.

### D-026. Discord 사용자 매핑 입력 방식

- 결정일: 2026-09-13
- 상태: 확정

- 연결된 Discord 서버에서 사용자 목록을 자동으로 불러온다.
- PM이 각 Discord 사용자 옆에 실제 팀원 이름을 직접 입력한다.
- 입력한 이름을 해당 Discord 사용자의 음성 파일과 화자 식별에 사용한다.

예:

- `seoyeon_01 → 김서연`
- `jaehwan_dev → 이재환`

### D-027. Discord 사용자와 팀원의 중복 매핑 제한

- 결정일: 2026-09-13
- 상태: 확정

- 한 Discord 사용자는 한 명의 실제 팀원에게만 연결한다.

- 팀원 매핑은 워크스페이스 내부에서 1:1 관계를 유지한다.

### D-028. 매핑되지 않은 Discord 사용자의 표시 이름

- 결정일: 2026-09-13

- 실제 팀원 이름 대신 해당 Discord 아이디를 화자 이름으로 표시한다.
- 이후 팀원 매핑이 완료되면 Discord 아이디 표시를 매핑된 실제 팀원 이름으로 대체한다.

### D-029. 일부 팀원만 매핑한 상태의 저장과 완료

### D-031. Discord 서버에서 나간 사용자의 기록 보존

### D-032. 대시보드의 역할

### D-034. 대시보드 검토 항목의 처리 화면

보류된 내용:

- `확인하기`로 진입했을 때 검토 상태를 자동으로 열지 여부
- `채워 넣기`로 진입했을 때 편집 상태를 자동으로 열고 누락 항목에 포커스할지 여부

### D-035. 최근 반영의 전체 로그 버튼

### D-036. 최근 반영 항목 되돌리기

- 사용자가 확인 모달에서 취소하면 아무 변경도 적용하지 않고 대시보드로 돌아간다.

### D-037. 되돌린 최근 반영 항목의 표시

- 별도의 활동 로그 화면이 없는 1차 개발에서도 사용자가 방금 수행한 결과를 확인할 수 있어야 한다.

### D-038. 최근 반영 영역의 데이터 범위

- 결정일: 2026-09-14
- 상태: 확정

- 대시보드의 `최근 반영`은 서비스 전체에서 가장 최근에 처리된 항목을 시간순으로 보여주는 영역이 아니다.
- 현재 선택된 워크스페이스의 가장 최근 회의록 한 건을 기준으로, 해당 회의록에서 Notion에 반영한 항목만 보여준다.
- 이전 회의록에서 반영한 항목은 이 영역에 섞어서 표시하지 않는다.
- 한 회의록에서 반영된 항목의 최대 표시 개수와 초과 항목 처리 방식은 별도로 결정한다.

### D-039. 최근 반영 항목의 표시 개수 제한

- 결정일: 2026-09-14

- 대시보드에는 정해진 최대 개수까지만 일부 항목을 표시한다.
- 현재 디자인에 표시된 `3개`를 임시 구현 기준으로 사용할 수 있으나, 최대 표시 개수는 최종 확정하지 않고 보류한다.
- 표시되지 않은 항목을 확인하는 경로도 아직 결정하지 않았다.

### D-040. 최근 반영 영역의 빈 상태

- 결정일: 2026-09-14
- 상태: 확정

- 아직 회의가 없거나 가장 최근 회의록에서 Notion에 반영한 항목이 없는 경우에도 `최근 반영` 영역을 숨기지 않는다.
- 기존 영역의 위치를 유지하고 데이터가 없음을 설명하는 빈 상태 안내를 표시한다.
- 빈 상태의 구체적인 문구, 원인별 구분 및 행동 버튼은 별도로 결정한다.

### D-041. 최근 반영 빈 상태의 원인 구분

- 결정일: 2026-09-14
- 상태: 확정

`최근 반영` 영역의 빈 상태는 하나의 공통 문구로 처리하지 않고 다음 원인을 구분해 표시한다.

1. 아직 생성된 회의록이 없음
2. 최근 회의록은 있지만 Notion에 반영한 항목이 없음
3. 워크스페이스에 Notion이 연결되지 않음

각 상태의 안내 문구와 다음 행동은 해당 원인에 맞게 제공한다.

### D-042. 최근 반영 빈 상태의 이동 경로

- 결정일: 2026-09-14
- 상태: 확정

`최근 반영`의 각 빈 상태에서 다음 행동 버튼과 이동 경로를 제공한다.

- 회의록 없음: `회의 업로드` 화면으로 이동
- 최근 회의록에 반영 항목 없음: 가장 최근 `회의록 상세` 화면으로 이동
- Notion 미연결: `워크스페이스 설정` 화면의 `Notion 연결` 영역으로 이동

이동한 화면에서는 사용자가 선택한 목적에 해당하는 영역을 바로 확인할 수 있어야 한다.

### D-043. 마감 임박 태스크의 기간 기준

### D-044. 기한이 지난 태스크의 마감 임박 표시

- 상태: 확정

- 기한이 지난 태스크를 아직 기한이 남은 태스크보다 목록 위에 배치한다.
- 지난 마감일은 일반 마감일과 구분되는 경고 상태로 표시한다.

### D-045. 마감 임박 태스크의 최대 표시 개수

- 결정일: 2026-09-14
- 상태: 확정

- 조건에 해당하는 태스크가 5개를 초과할 때 나머지 항목을 확인하는 경로는 별도로 결정한다.

### D-046. 마감 임박 전체 보기

- 결정일: 2026-09-14
- 상태: 확정

- `마감 임박` 조건에 해당하는 태스크가 5개를 초과하면 영역 우측에 `전체 보기`를 표시한다.

### D-047. 마감 임박 개별 행의 클릭 동작

- 결정일: 2026-09-14
- 상태: 확정

- 행을 클릭하거나 키보드로 실행하면 해당 태스크의 상세 화면으로 이동한다.
- 행 안에 추후 별도 액션 버튼이 추가되면 해당 버튼의 동작은 상세 화면 이동보다 우선하며 이벤트가 중복 실행되지 않아야 한다.

### D-048. 마감 임박 영역의 빈 상태

- 결정일: 2026-09-14
- 상태: 확정

- 기한이 지났거나 오늘부터 7일 이내에 마감되는 미완료 태스크가 하나도 없어도 `마감 임박` 영역을 숨기지 않는다.
- 목록 대신 `마감이 임박한 태스크가 없습니다`라는 빈 상태 안내를 표시한다.

### D-049. 확인이 필요한 일의 회의 범위

- 결정일: 2026-09-14
- 상태: 확정

- 대시보드의 `확인이 필요한 일`은 가장 최근 회의록에서 생성된 태스크에만 한정하지 않는다.
- 현재 워크스페이스의 모든 회의록에서 생성된 태스크 중 아직 확인이나 정보 보완이 완료되지 않은 항목을 함께 표시한다.
- 이전 회의에서 생성되었더라도 해결되지 않은 항목은 새 회의가 생성된 뒤에도 목록에서 제외하지 않는다.

### D-050. 확인이 필요한 일의 정렬 기준

- 결정일: 2026-09-14
- 상태: 확정

- `확인이 필요한 일`에는 아직 확인이나 정보 보완이 완료되지 않은 태스크만 정렬 대상으로 포함한다.
- 각 태스크가 확인·보완 필요 상태에 들어온 시각을 기준으로 오래 기다린 항목부터 표시한다.
- 필요한 확인이나 보완을 완료한 태스크는 이 목록과 정렬 대상에서 제외한다.

### D-051. 확인이 필요한 일의 최대 표시 개수

- 결정일: 2026-09-14
- 상태: 1차 개발 기준 확정

- 최대 표시 개수는 1차 개발의 임시 운영 기준이며 실제 사용량을 확인한 뒤 조정할 수 있다.

### D-052. 대시보드 확인 대기 수

- 결정일: 2026-09-14
- 상태: 확정

- D-051에 따라 목록에는 최대 5개만 보여도 전체 미해결 항목이 12개라면 `확인 대기 12`로 표시한다.

### D-053. 대시보드 7일 이내 마감 수

- 결정일: 2026-09-14
- 상태: 확정

- 대시보드 상단의 `다음 주 마감 N` 문구를 `7일 이내 마감 N`으로 변경한다.
- 숫자는 오늘을 포함하여 앞으로 7일 이내에 마감되는 미완료 태스크의 전체 개수를 나타낸다.
- 마감일이 이미 지난 미완료 태스크는 이 숫자에 포함하지 않는다.

### D-054. 대시보드 기한 지남 수

- 결정일: 2026-09-14
- 상태: 확정

- 대시보드 상단 요약에 `기한 지남 N` 항목을 추가한다.
- 숫자는 현재 워크스페이스에서 마감일이 이미 지났지만 아직 완료되지 않은 태스크의 전체 개수를 나타낸다.
- 기한이 지난 태스크는 D-053의 `7일 이내 마감 N`과 중복 집계하지 않는다.

### D-055. 대시보드 상단 요약의 배치 순서

- 결정일: 2026-09-14
- 상태: 확정

대시보드 상단의 워크스페이스 현황 요약을 다음 순서로 배치한다.

1. `확인 대기 N`
2. `기한 지남 N`
3. `7일 이내 마감 N`
4. `막힌 일 N`

확인이나 보완이 필요하거나 이미 지연된 항목을 기한이 남은 항목보다 먼저 확인할 수 있도록 구성한다.

### D-056. 막힌 일의 상태와 집계

- 결정일: 2026-09-14
- 상태: 확정

- PM이나 담당자가 직접 막힘으로 지정한 경우와 Discord 메시지 무응답을 시스템이 감지한 경우를 서로 다른 종류의 태스크로 분리하지 않는다.
- 두 경우 모두 하나의 태스크 상태인 `막힘`으로 처리한다.
- 하나의 태스크가 수동 지정과 자동 감지 조건에 동시에 해당하더라도 `막힌 일 N`에는 한 건으로만 집계한다.
- 막힘의 원인은 태스크 상세에서 구분해 보여줄 수 있으나, 구체적인 표시 방식은 별도로 결정한다.

### D-057. Discord 무응답의 자동 막힘 전환

- 결정일: 2026-09-14
- 상태: 확정

- 담당자에게 Discord 태스크 알림을 발송한 뒤 3일 동안 응답이 없으면 해당 태스크를 자동으로 `막힘` 상태로 전환한다.
- 자동 전환된 태스크는 D-056에 따라 수동으로 지정된 막힘과 동일한 상태 및 집계 규칙을 사용한다.
- 3일의 정확한 시간 계산 방식과 응답으로 인정할 Discord 행동은 별도로 결정한다.

### D-058. Discord 응답 인정 기준

- 결정일: 2026-09-14
- 상태: 확정

- 담당자에게 태스크 알림을 보낸 이후 동일한 Discord 개인 메시지 대화에 담당자의 새 답장이 도착하면 응답으로 인정한다.
- 답장의 구체적인 내용이나 완료 보고 여부는 프론트엔드에서 판단하지 않는다.
- 응답이 확인되면 Discord 무응답으로 자동 설정된 `막힘`을 해제한다.
- 수동으로도 막힘이 지정된 태스크의 처리 방식은 별도로 결정한다.

### D-059. Discord 답장 시 수동 막힘 해제

- 결정일: 2026-09-14
- 상태: 확정

- 담당자의 유효한 Discord 답장이 확인되면 자동으로 설정된 막힘뿐 아니라 PM이 수동으로 지정한 막힘도 함께 해제한다.
- 하나의 태스크에 자동·수동 막힘 원인이 모두 기록되어 있어도 답장이 도착하면 태스크 상태를 `막힘`에서 해제한다.
- 별도로 PM의 추가 확인을 요구하지 않는다.

### D-060. Discord 무응답 3일의 시간 계산

- 결정일: 2026-09-14
- 상태: 확정

- Discord 무응답의 `3일`은 날짜 단위가 아니라 태스크 알림 발송 시각부터 정확히 72시간으로 계산한다.
- 예를 들어 월요일 오후 3시에 알림을 발송했다면 목요일 오후 3시에 응답 여부를 판정하여 `막힘` 상태로 전환한다.
- 시간대 표시와 서버 판정의 기준 시간대는 API 계약 단계에서 정하되, 사용자 화면에는 사용자의 로컬 시간대로 표시한다.

보류된 내용:

- 대시보드 상단의 `막힌 일 N`을 클릭 가능한 요소로 만들지 여부
- 클릭할 경우 `막힘` 필터가 적용된 태스크 목록으로 이동할지 여부

### D-061. 대시보드 상단 요약의 클릭 동작

- 결정일: 2026-09-14
- 상태: 확정

- `확인 대기 N`, `기한 지남 N`, `7일 이내 마감 N`은 클릭 가능한 링크나 버튼으로 만들지 않는다.
- 세 항목은 현재 워크스페이스의 상태와 전체 개수만 보여주는 정보로 유지한다.
- 관련 목록으로의 이동은 각 본문 영역에 제공된 `전부 보기` 또는 `전체 보기`를 사용한다.
- `막힌 일 N`의 클릭 여부와 이동 경로는 D-060의 보류 사항으로 유지한다.

### D-062. 대시보드 제목의 확인 대기 개수 제거

- 결정일: 2026-09-14
- 상태: 확정

- 대시보드 제목의 `확인이 필요한 일 N개`에서 개수를 제거한다.
- 확인할 항목이 있을 때 제목은 `확인이 필요한 일이 있어요`로 표시한다.
- 전체 미해결 확인·보완 태스크 수는 D-052의 `확인 대기 N`에서만 제공하여 같은 숫자를 반복하지 않는다.
- 확인할 항목이 없을 때 사용할 제목은 별도로 결정한다.

### D-063. 최근 처리 회의록 안내의 클릭 동작

- 결정일: 2026-09-14
- 상태: 확정

- 대시보드 제목 아래의 최근 처리 회의록 안내는 클릭 가능한 링크로 만들지 않는다.
- 회의명, 처리 완료 안내 및 녹음 분량을 보여주는 정보로만 사용한다.
- 해당 회의록 상세 화면으로 이동하려면 회의록 목록 등 기존 탐색 경로를 사용한다.

### D-064. 확인할 태스크가 없을 때의 대시보드 제목

- 결정일: 2026-09-14
- 상태: 확정

- 현재 워크스페이스에 확인하거나 보완할 태스크가 하나도 없으면 대시보드 제목을 `확인이 필요한 일이 없어요`로 표시한다.
- 확인·보완할 태스크가 하나 이상이면 D-062에 따라 `확인이 필요한 일이 있어요`로 표시한다.
- 제목에는 두 상태 모두 개수를 포함하지 않는다.

### D-065. 처리된 회의가 없을 때의 대시보드 안내

- 결정일: 2026-09-14
- 상태: 확정

- 현재 워크스페이스에 처리 완료된 회의가 하나도 없으면 대시보드 제목 아래에 `아직 정리한 회의가 없어요`를 표시한다.
- 이 안내는 클릭 가능한 링크나 버튼이 아닌 정보 문구로 제공한다.
- 회의 업로드로 이동하는 행동 버튼은 대시보드의 다른 빈 상태나 회의록 화면에서 제공한다.

### D-066. 헤더에서 워크스페이스 전환 후 이동

- 결정일: 2026-09-14
- 상태: 확정

- 공통 헤더에서 다른 워크스페이스을 선택하면 현재 보고 있던 기능 화면을 유지하지 않는다.
- 선택한 워크스페이스의 대시보드로 항상 이동한다.
- 예를 들어 워크스페이스 A의 태스크 화면에서 워크스페이스 B을 선택하면 워크스페이스 B의 태스크 화면이 아니라 워크스페이스 B 대시보드를 연다.
- 선택한 워크스페이스을 이후 요청과 화면 상태의 현재 워크스페이스으로 갱신한다.

### D-067. 저장하지 않은 변경이 있을 때 워크스페이스 전환

- 결정일: 2026-09-14
- 상태: 확정

- 폼이나 편집 화면에 저장하지 않은 변경사항이 있을 때 다른 워크스페이스을 선택하면 즉시 전환하지 않고 확인 모달을 표시한다.
- 모달은 워크스페이스을 전환하면 저장하지 않은 변경사항이 사라진다는 점을 안내한다.
- 사용자가 취소하면 현재 워크스페이스, 현재 화면 및 입력 상태를 그대로 유지한다.
- 사용자가 전환을 확인하면 변경사항을 버리고 D-066에 따라 선택한 워크스페이스의 대시보드로 이동한다.

### D-068. 기존 사용자의 새 워크스페이스 만들기 흐름

- 결정일: 2026-09-14
- 상태: 확정

- 기존 워크스페이스에 소속된 사용자가 워크스페이스 전환 메뉴에서 `새 워크스페이스 만들기`를 누르면 최초 가입과 동일한 온보딩을 시작한다.
- 진행 순서는 `워크스페이스 만들기 → Discord 연결 → Notion 연결 → 팀원 연결`이다.
- 기존에 소속된 워크스페이스과 데이터는 그대로 유지한다.
- 온보딩을 완료하거나 선택 단계를 건너뛰면 새로 만든 워크스페이스의 대시보드로 이동한다.
- 각 단계의 필수·건너뛰기 및 재개 정책은 D-011과 D-012를 동일하게 적용한다.

### D-069. 새 워크스페이스 온보딩 중 기존 워크스페이스으로 돌아가기

- 결정일: 2026-09-14
- 상태: 확정

- 기존 사용자가 새 워크스페이스 온보딩을 진행할 때 화면 좌측 상단에 나가기용 뒤로가기 화살표를 표시한다.
- 화살표를 누르면 새 워크스페이스의 온보딩 진행 상태를 저장하고, 사용자가 이전에 이용하던 워크스페이스의 대시보드로 돌아간다.
- 중단한 새 워크스페이스 온보딩은 D-012에 따라 이후 다시 진입했을 때 다음 미완료 단계부터 재개한다.

### D-070. 설정 미완료 워크스페이스의 표시와 온보딩 재개

- 결정일: 2026-09-14
- 상태: 확정

- 중단된 새 워크스페이스은 워크스페이스 전환 메뉴에 `설정 미완료` 상태로 표시한다.
- 사용자가 해당 워크스페이스을 선택하면 대시보드가 아니라 마지막 미완료 온보딩 단계로 이동하여 설정을 이어서 진행한다.

### D-071. 설정 미완료 워크스페이스의 대시보드 접근 제한

- 결정일: 2026-09-14
- 상태: 확정

- 설정 미완료 워크스페이스은 온보딩을 끝내기 전까지 해당 워크스페이스의 대시보드에 접근할 수 없다.
- 사용자는 필수 단계를 완료하고 선택 단계를 완료하거나 `건너뛰기`로 처리하여 온보딩을 종료해야 대시보드에 진입할 수 있다.

### D-072. 재로그인 시 미완료 온보딩 복귀

- 결정일: 2026-09-14
- 상태: 확정

- 사용자가 로그아웃한 뒤 다시 로그인했을 때 마지막으로 이용하던 워크스페이스가 `설정 미완료` 상태라면, 해당 워크스페이스의 마지막 미완료 온보딩 단계로 바로 이동한다.
- 이 경우 설정이 완료되기 전까지는 D-071의 대시보드 접근 제한을 유지한다.

### D-073. Discord 연결을 건너뛴 경우의 팀원 연결 처리

- 결정일: 2026-09-14
- 상태: 확정

- Discord 연결을 건너뛰면 Discord 사용자 정보를 불러올 수 없으므로 `팀원 연결` 단계도 자동으로 `건너뜀` 처리한다.
- 이 경우 Notion 단계의 완료 또는 건너뛰기 처리가 끝나면 온보딩을 종료하고 새 워크스페이스의 대시보드로 이동한다.

### D-074. 온보딩 이후 Discord 연결 완료 시 이동

- 결정일: 2026-09-14
- 상태: 확정

- 온보딩에서 Discord 연결을 건너뛴 사용자가 나중에 워크스페이스 설정에서 Discord 연결을 완료하면 팀원 연결 화면으로 바로 이동한다.
- 해당 화면에서는 연결한 Discord 서버의 사용자와 서비스 내부 팀원을 매핑한다.

### D-075. 온보딩 이후 팀원 연결 화면의 무매핑 이탈

- 결정일: 2026-09-14
- 상태: 확정

- 워크스페이스 설정에서 Discord를 연결한 뒤 열린 팀원 연결 화면에서도 아무 Discord 사용자도 매핑하지 않은 채 나갈 수 있다.
- 매핑하지 않은 사용자의 화자는 D-028에 따라 Discord 아이디로 표시한다.
- 사용자는 이후 워크스페이스 설정에서 팀원 연결 화면에 다시 진입하여 매핑할 수 있다.

### D-076. 연결되지 않은 계정의 인원수 표시

- 결정일: 2026-09-14
- 상태: 확정

- 새로 반영된 미매핑 Discord 사용자는 워크스페이스 관리 화면의 `연결되지 않은 계정` 영역에 표시한다.
- `연결되지 않은 계정` 영역의 제목에는 미매핑 인원수를 별도로 표시하지 않는다.

### D-077. 회의 자료 입력 방식

- 결정일: 2026-09-15
- 상태: 일부 폐기(D-084로 대체)

- `회의 올리기`에서는 Discord에서 수집된 음성 파일뿐 아니라 사용자의 로컬 음성 파일도 직접 업로드할 수 있다.
- 로컬 녹음 파일은 화면에 끌어다 놓거나 컴퓨터의 파일 선택기를 통해 선택할 수 있다.
- `텍스트 회의록` 입력 방식을 포함하기로 한 내용은 D-084에서 철회한다.

### D-078. 회의당 녹음 파일 개수

- 결정일: 2026-09-15
- 상태: 확정

- 1차 개발에서는 회의 하나당 녹음 파일 하나만 업로드할 수 있다.
- 다른 녹음 파일을 선택하려면 현재 선택한 파일을 제거하거나 교체해야 한다.

### D-079. 회의 날짜 기본값과 텍스트 회의록 입력 방식

- 결정일: 2026-09-15
- 상태: 일부 변경(D-083)

- Discord에서 가져온 녹음 파일은 Discord가 제공하는 녹음 날짜를 회의 날짜의 기본값으로 사용한다.
- 사용자가 직접 올린 로컬 녹음 파일은 브라우저에서 확인할 수 있는 파일의 `lastModified` 날짜를 기본값으로 사용한다.
- `텍스트 회의록`의 파일 업로드 전제는 D-083에서 철회한다.
- 자동 입력된 회의 날짜는 실제 회의 날짜와 다를 수 있으므로 사용자가 수정할 수 있다.

### D-080. 텍스트 회의록 파일 형식

- 결정일: 2026-09-15
- 상태: 폐기(D-083으로 대체)

- `.txt` 파일 업로드를 지원하기로 한 이 결정은 D-083에서 철회한다.

### D-081. 파일 선택 시 회의 제목 자동 입력

- 결정일: 2026-09-15
- 상태: 일부 변경(D-083)

- 음성 파일을 선택하면 확장자를 포함한 전체 파일명을 회의 제목의 기본값으로 자동 입력한다.
- 예: `3주차_정기회의_0909.m4a`는 그대로 `3주차_정기회의_0909.m4a`로 입력한다.
- 자동 입력된 회의 제목은 사용자가 수정할 수 있다.

### D-082. 업로드 출처별 참석자 입력

- 결정일: 2026-09-15
- 상태: 일부 변경(D-083)

- Discord 녹음 파일은 파일에 포함된 Discord 사용자 정보를 바탕으로 참석자를 자동 입력한다.
- 자동 입력 시 D-025부터 D-031까지의 Discord 사용자·팀원 매핑 정책을 적용한다.
- 로컬 음성 파일은 참석자를 자동 입력하지 않고 비워 두며, 사용자가 직접 선택한다.

### D-083. 로컬 텍스트 파일 업로드 미지원

- 결정일: 2026-09-15
- 상태: 폐기(D-084로 대체)

- 1차 개발에서는 `.txt`를 포함한 로컬 텍스트 파일 업로드를 지원하지 않는다.
- 직접 입력·붙여넣기 방식의 `텍스트 회의록`을 제공하기로 한 내용도 D-084에서 철회한다.
- 이 결정 중 로컬 텍스트 파일 업로드를 지원하지 않는다는 내용은 D-084에 통합한다.

### D-084. 회의 자료 직접 업로드는 음성 파일만 지원

- 결정일: 2026-09-15
- 상태: 확정

- 사용자가 회의 자료를 직접 올릴 때는 음성 파일만 지원한다.
- 로컬 텍스트 파일 업로드와 텍스트 직접 입력·붙여넣기는 모두 지원하지 않는다.
- 현재 `회의 올리기` 디자인의 `텍스트 회의록` 탭과 관련 입력 영역은 실제 구현에서 제거한다.
- 이 결정은 D-077의 `텍스트 회의록` 포함 결정과 D-083을 대체한다.

### D-085. 로컬 음성 파일의 참석자 필수 입력

- 결정일: 2026-09-15
- 상태: 확정

- 로컬 음성 파일을 직접 업로드할 때 참석자를 최소 한 명 이상 반드시 추가해야 한다.
- 참석자가 한 명도 선택되지 않은 상태에서는 `정리 시작하기`를 실행할 수 없으며, 참석자 선택이 필요하다는 검증 안내를 표시한다.

### D-086. 로컬 음성 파일의 참석자 선택 범위

- 결정일: 2026-09-15
- 상태: 확정

- 로컬 음성 파일의 참석자는 현재 워크스페이스에 등록된 팀원 중에서만 선택할 수 있다.
- 워크스페이스에 등록되지 않은 외부 참석자의 이름을 직접 입력하는 기능은 1차 범위에 포함하지 않는다.

### D-087. 회의 제목 필수 입력

- 결정일: 2026-09-15
- 상태: 확정

- 회의 제목은 필수값으로 처리한다.
- 파일명으로 자동 입력된 제목은 사용자가 수정할 수 있지만, 제목을 비운 상태에서는 `정리 시작하기`를 실행할 수 없다.
- 빈 제목으로 실행하려 하면 제목 입력이 필요하다는 검증 안내를 표시한다.

### D-088. 회의 정리 동시 실행 제한

- 결정일: 2026-09-15
- 상태: 확정(D-089에서 범위 확정)

- 한 회의의 음성 정리가 진행 중일 때 다른 회의의 정리를 동시에 시작할 수 없다.
- 제한 범위는 D-089에 따라 워크스페이스 전체를 기준으로 한다.

### D-089. 회의 정리 동시 실행 제한 범위

- 결정일: 2026-09-15
- 상태: 확정

- 회의 정리 동시 실행 제한은 사용자 개인이 아니라 워크스페이스 전체를 기준으로 적용한다.
- 같은 워크스페이스에서 한 사용자가 회의를 정리 중이면 해당 워크스페이스의 다른 사용자도 새 회의 정리를 시작할 수 없다.
- 다른 워크스페이스의 처리 상태에는 영향을 주지 않는다.

### D-090. 처리 중인 워크스페이스에서 회의 올리기 진입 동작

- 결정일: 2026-09-15
- 상태: 보류

- 임시 방향은 워크스페이스에서 회의를 정리 중일 때 `회의 올리기`를 누르면 새 업로드 화면 대신 현재 진행 중인 회의의 `정리 중` 화면으로 이동하는 것이다.
- PM 외 팀원의 회의 업로드 권한이 확정된 뒤 이 동작과 접근 권한을 함께 최종 확정한다.

### D-091. 회의 정리 실패 시 파일과 이동 처리

- 결정일: 2026-09-15
- 상태: 확정

- 1차 개발에서는 회의 정리에 실패했을 때 업로드한 원본 파일을 재시도용으로 유지하지 않는다.
- 실패하면 사용자를 해당 워크스페이스의 `회의록` 페이지로 이동시킨다.
- 다시 정리하려면 사용자가 `회의 올리기`에서 원본 파일을 다시 선택하고 업로드해야 한다.

### D-092. 회의 정리 실패 안내

- 결정일: 2026-09-15
- 상태: 확정

- 회의 정리 실패 후 회의록 페이지로 이동하면 상단에 오류 토스트를 표시한다.
- 토스트의 기본 문구는 `회의를 정리하지 못했어요. 파일을 다시 올려 주세요.`로 한다.
- 토스트는 실패 사실과 같은 파일을 다시 업로드해야 한다는 다음 행동을 함께 안내한다.

### D-093. 정리 실패 회의의 목록 표시

- 결정일: 2026-09-15
- 상태: 확정

- 정리에 실패하여 결과물이 생성되지 않은 회의는 회의록 목록에 항목을 남기지 않는다.
- 실패 사실은 D-092의 오류 토스트로만 안내한다.

### D-094. 회의 정리 중 앱 내부 이동

- 결정일: 2026-09-15
- 상태: 확정

- 회의 정리가 진행 중이어도 사용자는 대시보드 등 앱 내부의 다른 페이지로 이동할 수 있다.
- 페이지를 이동해도 백그라운드의 회의 정리 작업은 계속된다.
- `회의 올리기` 화면의 `올리는 동안 창을 닫아도 됩니다` 문구는 제거하고, 앱의 다른 페이지를 이용할 수 있다는 의미로 수정한다.
- 브라우저 창을 닫아도 된다는 동작은 보장하거나 안내하지 않는다.

### D-095. 다른 화면에서 회의 정리 완료 알림

- 결정일: 2026-09-15
- 상태: 확정

- 사용자가 앱 내부의 다른 페이지를 보고 있는 동안 회의 정리가 완료되면 현재 화면 상단에 전역 토스트를 표시한다.
- 토스트의 기본 문구는 `회의 정리가 끝났어요`로 한다.
- 토스트에 `회의록 보기` 버튼을 제공하고, 누르면 방금 생성된 회의록 상세 화면으로 이동한다.

### D-096. Notion 미연결 워크스페이스의 회의 정리 사용

- 결정일: 2026-09-15
- 상태: 1차 임시 확정·최종 보류

- 1차 기준에서는 Notion이 연결되지 않은 워크스페이스의 회의 음성 업로드와 정리 시작을 허용하지 않는다.
- Notion 연결이 완료된 뒤에만 회의 정리를 사용할 수 있다.
- 향후 서비스 내부 저장만으로 회의 정리를 허용할지는 다시 논의한다.

### D-097. Notion 미연결 상태의 회의 올리기 접근 안내

- 결정일: 2026-09-15
- 상태: 확정

- Notion 미연결 상태에서 사용자가 `회의 올리기`를 누르면 업로드 화면으로 이동하지 않고 차단 안내 모달을 표시한다.
- 모달 제목은 `Notion 연결이 필요해요`로 하고, 회의를 정리하려면 Notion을 먼저 연결해야 한다는 내용을 안내한다.
- 모달에는 `취소`와 `Notion 연결하기` 버튼을 제공한다.
- `Notion 연결하기`를 누르면 워크스페이스 설정의 Notion 연결 영역으로 이동한다.

### D-098. Notion 연결 완료 후 회의 올리기 복귀

- 결정일: 2026-09-15
- 상태: 확정

- D-097의 차단 모달을 통해 Notion 연결을 시작한 경우 해당 진입 경로를 유지한다.
- Notion 연결이 성공하면 워크스페이스 설정에 머무르지 않고 현재 워크스페이스의 `회의 올리기` 화면으로 자동 복귀한다.
- 연결을 취소하거나 실패하면 자동 복귀하지 않는다.

### D-099. 회의 정리 중 Notion 연결 해제 처리

- 결정일: 2026-09-15
- 상태: 확정

- 회의 정리 도중 Notion 인증이 만료되거나 연결이 끊기면 해당 정리를 실패 처리한다.
- 완성되었거나 일부 생성된 회의록 결과를 서비스 내부에 보존하지 않는다.
- 업로드한 원본 파일도 D-091에 따라 유지하지 않는다.
- 사용자는 Notion을 다시 연결한 뒤 원본 음성 파일을 다시 업로드하여 회의록을 처음부터 생성해야 한다.

### D-100. 회의 정리 중 Notion 연결 해제 안내

- 결정일: 2026-09-15
- 상태: 확정

- 회의 정리 중 Notion 연결이 끊겨 실패하면 회의록 페이지로 이동한다.
- 이 경우 일반 처리 실패 토스트 대신 `Notion 연결이 끊어졌어요`라는 차단 모달을 표시한다.
- 모달에는 `Notion 다시 연결하기` 버튼을 제공하고, 누르면 Notion 재연결 절차를 시작한다.
- 재연결이 성공하면 현재 워크스페이스의 `회의 올리기` 화면으로 이동하며, 사용자는 원본 파일을 다시 업로드해야 한다.

### D-101. 회의 정리 완료 후 Notion 반영 시점

- 결정일: 2026-09-15
- 상태: 확정

- 회의 정리가 완료되면 생성된 회의록 본문과 확실하게 추출된 태스크는 즉시 Notion에 반영한다.
- 담당자, 마감 또는 내용이 불명확하여 `확인 필요`로 분류된 태스크는 사용자가 확인하기 전까지 Notion에 반영하지 않는다.
- 확인 필요 태스크는 수정·보완 후 승인될 때 Notion에 반영한다.
- `회의 올리기`와 `정리 중` 화면의 `확인이 끝나기 전에는 Notion에 아무것도 쓰지 않아요` 문구는 이 정책과 충돌하므로, 확실한 항목은 자동 반영되고 확인 필요 항목만 보류된다는 내용으로 수정한다.

### D-102. 확인 필요 태스크의 접근 권한

- 결정일: 2026-09-15
- 상태: 서술 정정(D-163)

- `확인 필요` 태스크는 PM만 조회하고 수정·보완·승인·반려할 수 있다.
- PM이 아닌 일반 팀원은 `확인 필요` 태스크의 목록과 상세 화면에 접근할 수 없다.
- 일반 팀원의 태스크 상태 범위에는 `전체`, `진행 중`, `완료`만 제공한다.
- 일반 팀원의 `전체`에는 해당 사용자가 접근할 수 있는 `진행 중`과 `완료` 태스크만 포함하며 `확인 필요` 태스크는 포함하지 않는다.
- PM에게는 확인 필요 태스크를 처리할 수 있는 기존 화면과 행동을 제공한다.

### D-103. 확인 필요 태스크에 대한 비인가 직접 접근

- 결정일: 2026-09-15
- 상태: 일부 변경(D-162)

- 일반 팀원이 공유 링크나 직접 URL로 `확인 필요` 태스크에 접근하면 해당 내용을 표시하지 않는다.
- 사용자를 현재 워크스페이스의 `태스크 > 리스트` 뷰로 이동시킨다.
- 이동 후 `접근 권한이 없어요` 토스트를 표시한다.

### D-104. 일반 팀원의 회의록 내 확인 필요 영역 노출

- 결정일: 2026-09-15
- 상태: 확정

- 일반 팀원이 회의록 상세를 볼 때 `확인이 필요한 일` 영역 전체를 숨긴다.
- 확인 필요 태스크의 내용뿐 아니라 존재 여부와 개수도 일반 팀원에게 노출하지 않는다.
- 해당 영역은 PM에게만 표시한다.

### D-105. 일반 팀원의 회의록 상세 권한

- 결정일: 2026-09-15
- 상태: 확정

- 일반 팀원은 회의록 상세의 요약, 전사문 및 Notion에 반영된 태스크를 조회할 수 있다.
- 일반 팀원에게 해당 내용은 읽기 전용으로 제공한다.
- `되돌리기`처럼 Notion 반영 내용이나 회의 결과를 변경하는 버튼은 PM에게만 표시한다.

### D-106. 회의록 목록 기본 정렬과 최초 선택

- 결정일: 2026-09-15
- 상태: 확정

- 회의록 목록은 회의 날짜가 최신인 순서로 정렬한다.

- 결정일: 2026-09-15

### D-116. E2E 테스트 작성과 실행 시점

- 결정일: 2026-09-15
- 상태: 확정

- E2E 테스트는 각 핵심 기능의 해피패스가 완성되는 시점에 함께 작성하고 해당 시나리오를 검증한다.
- E2E 작성을 배포 직전까지 미루지 않는다.
- 모든 PR에서 전체 브라우저 E2E를 실행하지 않는다.
- 전체 E2E는 1차 배포, 2차 배포 및 최종 배포 전에 이전 시나리오를 포함하여 누적 실행한다.
- 2차 기능 범위는 아직 정해지지 않았으므로, 범위가 확정되는 대로 신규 E2E 시나리오를 추가한다.
- 정기 nightly 실행을 도입할지는 별도로 결정한다.

### D-117. 핵심 E2E 시나리오 범위

- 결정일: 2026-09-15
- 상태: 일부 확정

- 이메일 회원가입 또는 로그인부터 온보딩 완료까지 한 경로를 검증한다. Google 로그인은 테스트 서버가 세션을 발급하도록 하고 실제 Google 인증은 수동 검증한다.
- 기존 사용자의 워크스페이스 선택과 워크스페이스 전환을 검증한다. 설정 미완료 워크스페이스 재개 등 세부 분기는 통합 테스트에서 검증한다.
- 음성 업로드부터 정리 완료와 회의록 확인까지 검증한다. 테스트 서버에서는 회의 정리를 즉시 또는 짧은 시간 안에 완료한다.
- 확인 필요 태스크 승인 후 화면에서 Notion `반영됨` 상태가 표시되는지 검증한다. 실제 Notion 데이터베이스 반영은 수동 검증한다.
- 메시지 검토와 Discord 발송 상태 시나리오는 메시지 화면 정책이 확정된 뒤 고정한다.
- PM과 일반 팀원의 권한 차이는 목록, 상세 및 직접 URL 중 대표적인 1~2개 경로만 E2E로 검증하고 나머지 버튼 노출 규칙은 통합 테스트에서 검증한다.
- 최종 배포 E2E에는 D-006의 비밀번호 재설정 해피패스를 추가한다.
- 실제 Google, Discord, Notion 및 STT 외부 서비스 연동은 자동 E2E 범위에서 제외하고 배포 전 수동으로 검증한다.

### D-119. 패키지 관리자는 npm 사용

- 결정일: 2026-09-15
- 상태: 확정

- 프론트엔드 패키지 관리자는 `npm`을 사용한다.
- 의존성 버전은 `package-lock.json`으로 고정하고 CI에서는 재현 가능한 설치를 위해 `npm ci`를 사용한다.
- 현재 저장소에는 여러 JavaScript 패키지를 함께 관리하는 프론트엔드 모노레포가 없고 `frontend`의 단일 React 애플리케이션을 구성하므로, pnpm의 공유 저장소와 workspace 효율이 필수적이지 않다.
- npm은 Node.js 개발 환경에서 기본적으로 함께 사용하기 쉬워 팀원이 별도의 패키지 관리자를 설치하고 사용법을 맞춰야 하는 비용이 적다.
- 따라서 현 단계에서는 설치 효율의 차이보다 개발 환경의 단순성과 팀 접근성을 우선하여 pnpm 대신 npm을 선택한다.
- npm과 pnpm의 잠금 파일을 혼용하지 않는다.

### D-120. 공통 HTTP 클라이언트로 Axios 사용

- 결정일: 2026-09-15
- 상태: 확정

- 프론트엔드의 공통 HTTP 클라이언트는 `Axios`를 사용하고 FSD의 `shared/api`에 기반 설정을 둔다.
- Axios 인스턴스에서 API base URL, credentials, 공통 헤더 및 응답 오류 변환을 일관되게 관리한다.
- 응답 인터셉터를 이용해 인증 만료와 공통 API 오류를 한 곳에서 처리할 수 있다는 점을 선택 근거로 삼는다.
- 음성 파일 업로드, 업로드 진행률, 요청 타임아웃 및 `AbortController` 기반 취소 처리를 공통화하기 쉽다는 점을 선택 근거로 삼는다.
- 캐시, 서버 데이터 동기화, mutation 상태 및 재요청 정책은 D-110에 따라 TanStack Query가 담당하며 Axios 인터셉터에 비즈니스 로직을 넣지 않는다.
- MSW는 Axios와 네이티브 `fetch`를 모두 지원하므로 MSW 호환성 자체는 Axios 선택 근거가 아니다.
- 통합 테스트에서는 API 함수를 직접 mock하기보다 MSW가 실제 Axios 요청을 가로채도록 하여 인터셉터, 인증 설정 및 공통 오류 변환까지 함께 검증한다.
- 참고: [Axios 인터셉터](https://axios-http.com/docs/interceptors), [Axios 요청 취소](https://axios-http.com/docs/cancellation), [MSW 소개](https://mswjs.io/docs/)

### D-121. TypeScript 엄격 모드와 any 사용 원칙

- 결정일: 2026-09-15
- 상태: 확정

- TypeScript의 `strict: true`를 활성화한다.
- 암묵적으로 `any`가 추론되는 코드는 허용하지 않는다.
- 명시적인 `any`도 ESLint 규칙으로 기본 금지하고, 타입이 제공되지 않는 외부 라이브러리 등 불가피한 경우에만 한 줄 단위로 예외 처리한다.
- `any` 예외에는 필요한 이유를 주석으로 기록한다.
- API 응답, catch 오류 등 아직 신뢰할 수 없는 값은 `unknown`으로 받고 타입 검사 또는 스키마 검증 후 사용한다.
- 이 설정은 API 데이터 누락, 회의 처리 상태 전환, 역할별 권한 분기 및 컴포넌트 props 오류를 컴파일 단계에서 발견하기 위해 적용한다.
- 참고: [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html), [noImplicitAny](https://www.typescriptlang.org/tsconfig/noImplicitAny.html), [useUnknownInCatchVariables](https://www.typescriptlang.org/tsconfig/useUnknownInCatchVariables.html)

### D-122. 정적 검사와 코드 포맷팅

- 결정일: 2026-09-15

### D-123. 데스크톱 범위의 반응형 지원

- 결정일: 2026-09-15
- 상태: 확정(D-124에서 최소 너비 확정)

- 1차 개발에서는 모바일·태블릿 전용 레이아웃을 구현하지 않고 데스크톱 웹을 지원한다.

- 콘텐츠 최대 너비, 유동 너비, 좌우 여백 및 필요한 경우 데스크톱 구간별 배치를 조절하여 데스크톱 범위 안에서 반응형으로 동작하게 한다.

### D-124. 최소 지원 데스크톱 너비

- 결정일: 2026-09-15
- 상태: 확정

- 최소 지원 viewport 너비는 1024px로 한다.
- 1024px 이상에서는 핵심 기능과 내비게이션을 사용할 수 있어야 한다.
- 긴 테이블, 보드, 간트차트 등 가용 폭보다 넓은 콘텐츠는 페이지 전체를 고정 폭으로 만들지 않고 해당 콘텐츠 영역 안에서 가로 스크롤을 제공한다.
- 1024px 미만의 모바일·태블릿 전용 레이아웃은 1차 범위에 포함하지 않는다.

### D-125. 1차 공식 지원 브라우저

### D-126. Chrome 공식 지원 버전 범위

- 결정일: 2026-09-15
- 상태: 확정

- 데스크톱 Chrome Stable의 배포 시점 기준 최신 2개 주요 버전을 공식 지원한다.
- 특정 Chrome 버전 번호를 문서에 고정하지 않고 상대적인 최신 2개 버전 정책을 유지한다.
- `Browserslist`에는 `last 2 Chrome versions`를 설정하여 관련 빌드 도구가 같은 지원 범위를 사용하게 한다.
- 개발 중에는 현재 Chrome Stable을 기준으로 확인하고, 배포 전에는 공식 지원 범위의 최신 버전과 바로 이전 주요 버전을 검증한다.
- 지원 범위보다 오래된 Chrome과 다른 브라우저의 접속을 차단하지는 않지만 정상 동작을 보장하지 않는다.

### D-127. 프론트엔드 Node.js 버전

- 결정일: 2026-09-15
- 상태: 확정

- 프론트엔드 개발, CI 및 배포 빌드 환경은 `Node.js 24 LTS` 계열로 통일한다.
- 프론트엔드 범위의 `.nvmrc`, `package.json`의 `engines` 및 CI 설정에 Node.js 24를 명시한다.
- 특정 초기 패치 버전을 장기간 고정하지 않고 Node.js 24 계열의 최신 보안·버그 수정 패치 버전을 사용한다.
- LTS가 아닌 Node.js 26 Current는 사용하지 않는다.
- Node.js 버전 정책은 Node를 사용하는 프론트엔드 환경에만 적용하며 다른 런타임을 사용하는 백엔드와 버전을 맞출 필요는 없다.
- Node.js 24는 현재 LTS이고 Vite, Vitest 및 Playwright의 지원 범위를 충족하므로 안정성과 프로젝트 지원 기간을 고려해 선택한다.
- 참고: [Node.js 릴리스 정책](https://nodejs.org/en/about/previous-releases), [Vite 요구사항](https://vite.dev/guide/), [Vitest 요구사항](https://vitest.dev/guide/), [Playwright 요구사항](https://playwright.dev/docs/intro)

### D-128. 웹 접근성 구현 기준

- 결정일: 2026-09-15
- 상태: 확정

- 프론트엔드는 `WCAG 2.2 AA`를 웹 접근성 구현 기준으로 삼는다.
- 키보드 조작, 명확한 포커스 표시, 의미 있는 HTML, 입력 레이블과 오류 연결, 텍스트·UI 명암 대비 및 색상 외 상태 표현을 기본 구현 범위에 포함한다.
- 시각 포커스에 `outline` 링은 쓰지 않는다 (2026-09-16, design-system.md §3-3 — 테두리 있는 컨트롤에서 선이 두 겹이 되기 때문). **대체 표현은 아직 정해지지 않았고 M2 구현에도 없다.** M4 화면 작업 전에 정한다 — 그때까지 `WCAG 2.2 AA` SC 2.4.7은 미충족 상태다. 키보드 이동·포커스 트랩은 그대로 지킨다.
- 아이콘만 있는 버튼과 동적으로 바뀌는 로딩·성공·오류 상태에는 보조 기술이 이해할 수 있는 이름과 상태 정보를 제공한다.
- Radix UI를 사용하는 모달·드롭다운 등에서도 포커스 이동과 키보드 동작을 실제 화면 흐름 기준으로 확인한다.
- 1차에서는 외부 기관의 공식 접근성 인증과 전 항목 감사는 진행하지 않으며 `WCAG 2.2 AA 완전 준수`를 공식적으로 선언하지 않는다.
- 참고: [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/)

### D-150. 팀 용어를 워크스페이스로 통일

- 결정일: 2026-09-15
- 상태: 확정

- 백엔드 API가 `workspace`를 식별자와 리소스 이름으로 사용하므로 프론트엔드도 용어를 `워크스페이스`로 통일한다.
- URL, 코드 식별자 및 문서 서술을 모두 `workspace`와 `워크스페이스`로 쓴다.
- `팀원`은 그대로 유지한다. 워크스페이스에 속한 사람을 가리키는 말로 계속 사용한다.
- Notion의 워크스페이스와 구분이 필요한 곳에서는 `Notion 워크스페이스`로 표기한다.
- 프론트엔드와 백엔드 개발 조직을 가리키는 `팀`은 통일 대상이 아니다.

개정 대상:

- D-108: URL 구조를 `/teams/:teamId/...`에서 `/workspaces/:workspaceId/...`로 변경한다.
- D-136: 모든 워크스페이스 범위 Query Key에 포함하는 값을 `teamId`에서 `workspaceId`로 변경한다.
- D-001부터 D-149까지의 본문에서 서술적으로 사용한 `팀` 표기를 `워크스페이스`로 일괄 변경했다. 각 결정의 내용 자체는 바뀌지 않았다.

변경 사유:

- 백엔드가 이미 `workspace` 기준으로 API 명세와 데이터 모델을 작성했다.
- 경계마다 이름을 변환하면 변환 계층이 영구히 남고, 디버깅할 때 네트워크 요청과 코드의 용어가 갈린다.
- 프론트엔드에서 실제로 바뀌는 것은 D-108과 D-136 두 결정과 코드 식별자이며, 화면에 표시하는 한국어 문구는 별도로 결정한다.

### D-151. 로그인 세션 방식

- 결정일: 2026-09-15
- 상태: 일부 개정(D-165)

- 세션은 Secure·HttpOnly 쿠키로 전달한다. 응답 본문으로 토큰을 내려받아 저장하지 않는다.
- 쿠키에 담을 토큰 형식은 JWT를 사용한다. 토큰 형식 선택은 프론트엔드 구현에 영향을 주지 않는다.
- 프론트엔드는 Axios 인스턴스에 `withCredentials: true`만 설정하고 토큰 저장, 첨부 및 갱신 로직을 두지 않는다.
- JWT는 만료 전 무효화가 불가능하므로 백엔드는 짧은 만료 시간이나 무효화 목록을 적용한다. 로그아웃(D-072)과 PM 권한 회수(D-102)가 즉시 반영되어야 한다.
- 쿠키의 `SameSite`는 `Lax`를 사용한다. D-152에 따라 프론트엔드와 백엔드가 같은 오리진으로 배포되기 때문이다.

검토 후 제외한 방식:

- Web Storage에 토큰을 저장하고 `Authorization` 헤더로 보내는 방식: XSS가 발생하면 세션이 탈취되며, 직접 작성한 코드뿐 아니라 의존성 오염으로도 발생할 수 있다. 갱신 큐잉과 탭 간 동기화를 프론트엔드가 직접 구현해야 한다.
- access token을 메모리에 두고 refresh token만 쿠키에 두는 하이브리드 방식: 쿠키의 제약과 Web Storage 방식의 구현 부담을 모두 지면서, 앱을 열 때마다 갱신 요청이 한 번 추가된다.

- 이 결정은 D-147과 충돌하지 않는다. D-147은 저장 위치를 규정하며 토큰 형식을 제한하지 않는다.

### D-152. 프론트엔드 배포 구조

- 결정일: 2026-09-15
- 상태: 확정

- 프론트엔드와 백엔드를 카카오테크 캠퍼스가 제공하는 단일 EC2 인스턴스에 함께 배포한다.
- 리버스 프록시로 `/`는 프론트엔드 빌드 산출물을, `/api`는 FastAPI(`:8000`)를 서빙한다.
- 브라우저 기준으로 프론트엔드와 백엔드가 같은 오리진이므로 CORS 설정이 필요 없고, 세션 쿠키는 `SameSite=Lax`를 사용한다.
- 프론트엔드 빌드는 서버에서 실행하지 않는다. CI에서 빌드하고 산출물만 서버에 배치한다.
- 프론트엔드만 확인하는 preview 환경을 추가할 수 있으나 D-139에 따라 통합 검증 환경으로 간주하지 않는다.

선택 이유:

- 회의 음성 파일은 용량이 크므로 브라우저에서 서버로 직접 업로드해야 한다. 프론트엔드를 외부에 배포하고 API를 프록시로 넘기면 프록시의 요청 크기 제한에 걸릴 수 있다.
- 세션을 쿠키로 전달하므로(D-151) 오리진이 갈리면 `SameSite=None; Secure`와 CORS 설정이 필요해지고, Google·Discord·Notion의 OAuth redirect 도메인도 둘로 늘어난다.
- 정적 파일 서빙은 서버 자원을 거의 사용하지 않는다. 메모리를 점유하는 것은 STT 모델과 컨테이너다.

배포 환경의 제약:

- 서버는 `t3.medium`(2 vCPU, 4GB RAM), Ubuntu 24.04, 디스크 50GB이며 사양 변경과 추가 서버 생성이 불가능하다.
- 같은 서버에서 백엔드, 데이터베이스 및 STT 모델이 동작하므로 메모리 여유가 크지 않다. 회의 정리 동시 실행을 워크스페이스 전체에서 1건으로 제한한 D-088이 이 제약과 부합한다.
- Elastic IP 할당이 제한되어 서버를 중지했다 시작하면 공인 IP가 바뀐다. 고정 도메인이 없으면 HTTPS 인증서를 발급할 수 없고 OAuth redirect URI가 매번 깨진다. 도메인 확보 방법은 아직 결정하지 않았다.
- IAM 사용자와 액세스 키 생성이 제한되어 CI에서 서버로 직접 배포할 수 없다. 1차에서는 CI가 빌드 산출물을 아티팩트로 남기고 서버에서 내려받아 배치한다.
- 제공 기간이 2026-11-20까지이므로 최종 배포와 시연을 그 전에 완료한다.

D-139 개정:

- `production` 환경의 구체적인 형태를 위와 같이 확정한다. `local`과 `production`만 두는 방침은 그대로 유지한다.

### D-153. 워크스페이스 생성 요청에서 팀원 정보 제외

- 결정일: 2026-09-15
- 상태: 충족 확인(D-160)

- 워크스페이스 생성 요청에는 이름만 보낸다. 팀원 정보를 함께 보내지 않는다.
- 팀원은 Discord 연결 이후 별도의 사용자 목록 조회와 매핑 엔드포인트로 처리한다.
- 요청 본문에 Notion 사용자 이름을 포함하지 않는다.

이유:

- 온보딩 순서가 `워크스페이스 만들기 → Discord 연결 → Notion 연결 → 팀원 연결`이므로(D-008) 생성 시점에는 Discord 사용자 식별자를 알 수 없다.
- Discord 연결은 건너뛸 수 있고 그 경우 팀원 연결도 자동으로 건너뛰므로(D-011, D-073) 팀원 정보가 끝까지 채워지지 않을 수 있다.
- `팀 만들기` 단계에서 이름만 입력받기로 이미 확정했다(D-014).
- Notion 사용자는 팀원 매핑 대상이 아니다(D-025).

### D-154. Notion 연결 화면의 범위

- 결정일: 2026-09-15
- 상태: 확정

- Notion 연결은 OAuth 인증만 수행한다. 프론트엔드는 데이터베이스 선택과 속성 매핑 화면을 제공하지 않는다.
- 인증으로 얻은 권한을 사용해 회의록과 승인된 태스크를 사용자의 Notion 워크스페이스에 기록하는 일은 백엔드와 AI가 담당한다.
- 프론트엔드는 연결 시작, 연결 상태 표시 및 연결 실패 안내만 구현한다.
- 어떤 문서에 어떤 속성으로 기록하는지는 프론트엔드가 판단하지 않는다.

영향:

- `SetupNotion` 화면 시안은 데이터베이스 목록, 속성 확인 및 `이 보드로 연결` 버튼으로 구성되어 있어 이 결정과 맞지 않는다. 화면을 다시 설계해야 한다.
- 시안의 `쓰던 데이터베이스를 그대로 쓰면 됩니다`와 `새 보드는 만들지 않습니다` 문구도 함께 재검토한다.
- 연결 요청 본문에 데이터베이스 식별자와 인증 토큰을 담지 않는다.

### D-155. 확인 필요 태스크의 조회 경로

- 결정일: 2026-09-15
- 상태: 개정(D-161)

- 확인 필요 태스크를 태스크 조회 API의 상태 값으로 제공받는다. 별도 리소스를 프론트엔드가 조회해 합치지 않는다.
- 백엔드가 내부적으로 승인 요청을 별도 리소스로 관리하더라도 조회 경로는 태스크로 통일한다.

이유:

- 태스크 화면은 하나의 목록에서 `확인 필요`, `진행 중` 및 `완료`를 전환하는 구조다.
- 일반 팀원의 상태 범위를 `전체`, `진행 중`, `완료`로 규정한 D-102가 확인 필요를 이미 상태로 다루고 있다.
- 리소스가 분리되면 정렬 기준, 전체 개수 집계, 태스크 상세 URL의 식별자 해석 및 페이지네이션을 프론트엔드가 각각 처리해야 한다.

### D-156. 회의 자료 업로드 범위 유지와 회의록 본문 조회

- 결정일: 2026-09-15
- 상태: 확정

- D-084를 유지한다. 1차에서 회의 자료 직접 업로드는 음성 파일만 지원한다.
- 백엔드 명세에 회의록 수동 업로드 경로가 있더라도 1차 프론트엔드에서는 사용하지 않는다.
- 회의록 상세 화면에 필요한 요약, 전사문 및 Notion에 반영된 태스크를 조회할 수 있는 API를 요청한다.

이유:

- 회의 상태 조회 응답이 상태와 승인 요청 식별자만 반환하고 있어 회의록 본문을 받을 경로가 없다.
- 일반 팀원도 회의록의 요약과 전사문을 읽기 전용으로 조회한다(D-105).

### D-157. 회의 리소스의 단일 유지

- 결정일: 2026-09-15
- 상태: 충족 확인(D-160)

- Discord 봇이 수집한 회의와 사용자가 직접 업로드한 회의를 하나의 회의 리소스로 유지한다. 수집 경로는 `source` 값으로 구분한다.
- 웹에서 필요한 목록 조회, 음성 파일 업로드 및 회의록 본문 조회 엔드포인트를 추가로 요청한다.
- 기존의 회의 세션 생성과 종료 엔드포인트는 봇 경로로 유지한다.

이유:

- 회의록 목록은 두 경로의 회의를 한 목록에 날짜 최신순으로 표시하고 최초 진입 시 가장 최근 회의록을 선택한다(D-106).
- 대시보드의 최근 반영과 최근 처리 회의 안내도 가장 최근 회의 한 건을 기준으로 한다(D-038, D-063).
- 리소스를 분리하면 두 목록을 프론트엔드가 합쳐 정렬해야 하고 페이지네이션을 적용할 수 없으며, 태스크 상세 URL의 식별자로 리소스를 추측하는 분기가 생긴다.
- 기존 회의 생성 API가 이미 수집 경로를 `discord`와 `manual_upload`로 구분하고 있다.

### D-158. OAuth 화면 전환 방식

- 결정일: 2026-09-15
- 상태: 확정

- Discord와 Notion의 OAuth 인증은 팝업이 아니라 현재 탭 이동으로 구현한다.
- 인증 시작 시 복귀 경로를 `state` 파라미터에 담아 콜백 이후 원래 화면으로 돌아온다.

이유:

- 온보딩 진행 상태를 서버가 저장하므로(D-012) 탭을 이동했다 돌아와도 복원할 화면 상태가 없다.
- Notion 미연결 상태에서는 회의 올리기 화면에 진입할 수 없으므로(D-097) 복귀 시점에 선택해 둔 파일 등 잃을 입력이 없다.
- Notion 연결 후 회의 올리기로 자동 복귀하는 요구(D-098)는 `state` 파라미터로 처리할 수 있다.
- 팝업은 차단 상황 처리와 메시지 출처 검증 코드가 추가로 필요하다.

### D-159. 백엔드 API 합의 없이 프론트엔드 단독 진행

- 결정일: 2026-09-15
- 상태: 확정

- 백엔드와 API 계약을 사전에 합의하는 절차를 진행하지 않는다. 프론트엔드가 필요한 요청과 응답을 스스로 가정해 명세로 고정하고 그에 맞춰 개발한다.
- 가정한 명세는 문서로 남기고 이후 백엔드에 전달한다. D-150부터 D-158까지 정리한 요청 사항은 회의 안건이 아니라 인수인계 자료로 유지한다.
- 모든 화면은 MSW로 동작시킨다. 실제 API가 제공되기 전까지 MSW를 유일한 데이터 출처로 사용한다.
- 실제 API가 제공되면 D-133에 따라 생성 타입으로 교체하고 entities 계층의 변환만 수정한다.

전제 조건:

- 화면과 위젯은 서버 응답 형태를 직접 참조하지 않는다. DTO는 entities 계층에서만 다루고 화면에는 프론트엔드 도메인 모델만 전달한다.
- 가정한 명세는 실제 API와 다를 것이 확실하므로, 이 규칙은 권장이 아니라 필수다. 실제 API 도입 시 수정 범위를 entities 계층으로 한정하기 위한 유일한 장치다.
- 가정한 요청과 응답은 계약 문서에 기록하고 화면 사정에 따라 임의로 바꾸지 않는다.

영향:

- M1의 산출물은 합의된 계약이 아니라 가정 명세다. 작업 순서와 범위는 바뀌지 않는다.
- 실제 외부 연동과 처리 시간은 검증할 수 없다. Google, Discord, Notion 및 STT 연동은 D-117에 따라 배포 전 수동 검증 대상으로 유지한다.
- E2E는 D-146에 따라 MSW 또는 로컬 테스트 서버로 수행한다.
- 백엔드가 실제 API를 제공하는 시점은 미정이므로 교체 작업을 특정 마일스톤에 배치하지 않는다.

### D-160. 백엔드 기존 구현에 프론트엔드를 맞춘다

- 결정일: 2026-09-17
- 상태: 확정

- 백엔드가 이미 구현했거나 정한 것에는 프론트엔드가 맞춘다.
- 백엔드에 대한 요청은 코드에 존재하지 않는 것으로 한정한다.
- 이미 동작하는 엔드포인트와 스키마의 변경·삭제·이름 변경을 요청하지 않는다. 요청은 추가이거나 기존 필드의 의미 확정에 그친다.
- **API 문서를 쓰거나 고칠 때는 최신 `origin/develop` 을 기준으로 삼고, 문서 머리에 기준 커밋을 적는다.**

이유:

- 백엔드가 `meetings`, `extractions`, `approvals`, `workspaces`, `members`, `tasks` 와 데이터 모델을 이미 구현했다. 구현된 것을 바꾸라는 요청은 양쪽의 작업을 모두 되돌린다.
- 프론트엔드가 감수할 비용이 명확히 계산되는 경우 그 비용을 프론트엔드가 진다.

기준 커밋을 적는 규칙을 둔 이유:

- 이 문서의 첫 판은 하루 낡은 로컬 `develop`(66f00c6)을 보고 작성되어, PR #38(2026-09-16 병합)이 추가한 `workspaces` · `members` · `tasks` API 를 신규 요청으로 잘못 적었다.
- 되돌리기 엔드포인트처럼 **이미 있는 것을 만들어 달라고 요청**하는 오류까지 나왔다.
- 백엔드는 빠르게 움직인다. 기준 시점을 적지 않으면 읽는 쪽이 문서의 유효성을 판단할 수 없다.

영향:

- `frontend/docs/plan/backend-alignment.md`(2026-09-15)를 삭제하고, 백엔드 요청을 `frontend/docs/api/frontend-api-contract-draft.md` §4 로 통합한다.
- 요청 문서를 따로 두면 API 형태와 제약이 계약 문서와 양쪽에 존재해 한쪽만 고쳐질 때 어긋난다. 문서를 하나로 두고 백엔드를 향한 내용만 §4 에 모은다.
- D-155 를 D-161 로, D-102 를 D-163 으로, D-151 을 D-165 로 개정한다.
- D-157(회의 리소스 단일 유지)과 D-153(워크스페이스 생성 요청에서 팀원 정보 제외)은 요청 항목이 아니라 **이미 충족된 사실**로 격하한다. `meeting` 이 `workspace_id` 와 `source` 를, `WorkspaceCreateRequest` 가 `name` 만 갖는다.
- 이 원칙은 D-159(백엔드 합의 없이 단독 진행)를 보완한다. 합의 없이 진행하되 이미 구현된 부분은 코드를 근거로 따른다.

### D-161. 확인 필요 태스크의 조회 경로 개정

- 결정일: 2026-09-17
- 상태: 확정

D-155 의 `조회 경로를 태스크로 통일한다` 를 `표시 계층에서만 통일한다` 로 개정한다.

- `확인 필요` 탭은 `GET /api/v1/approvals?workspace_id=...&status=pending` 으로 조회한다.
- `진행 중` 과 `완료` 탭은 `GET /api/v1/tasks` 로 조회한다.
- `전체` 탭에서만 두 응답을 클라이언트에서 병합한다. `확인 필요` 를 대기 오래된 순으로 상단에 고정하고 그 아래에 나머지 태스크를 마감일 순으로 배치한다.

변경 사유 — 구현된 파이프라인이 두 리소스를 명확히 나눈다:

- `POST /extractions` 가 신뢰도로 게이트를 판정해, `gate=auto` 면 `create_task()` 로 태스크를 즉시 만들고 `gate=review|hold` 면 `ApprovalRequest` 를 만든다.
- 따라서 **`확인 필요` 항목에는 승인 전까지 `task_id` 가 존재하지 않는다.** `related_task_id` 는 `null` 이고, 승인 시점에 `_apply_approval` 이 태스크를 만들며 채워진다.
- `TaskStatus` 에 `needs_review` 가 없다. 통합하려면 백엔드의 상태 값과 태스크 생성 시점을 모두 바꿔야 한다(D-160).
- 탭은 한 번에 하나만 보이므로 병합이 필요한 지점은 `전체` 탭 하나뿐이다. 시안의 탭 개수 `전체 13 = 확인 필요 3 + 진행 중 7 + 완료 3` 이 근거다.

전제 조건:

- `확인 필요` 정렬은 D-050 의 대기 오래된 순을 유지하되, 목록이 `created_at` 내림차순 고정이므로 클라이언트에서 뒤집는다.
- `approval_request.payload` 의 형태는 가정이 아니라 사실이다. `api/extractions.py` 가 11개 키로 만들고 `api/approvals.py` 의 `_apply_approval` 이 읽는다. 계약 문서 §2.5 참조.

영향:

- 승인 직후 `GET /approvals` 와 `GET /tasks` 를 모두 다시 조회해야 한다. 승인이 태스크를 새로 만들기 때문이다.
- 확인 필요 항목의 식별자와 이동 경로는 D-162 에서 정한다.

### D-162. 확인 필요 항목의 식별자와 이동 경로

- 결정일: 2026-09-17
- 상태: 확정

- `확인 필요` 항목은 `approval_id` 로 식별한다.
- 상세 화면 URL 은 `/workspaces/:workspaceId/approvals/:approvalId` 로 한다.
- 대시보드의 `확인하기` 와 `채워 넣기` 는 이 경로로 이동한다.

변경 사유:

- D-161 에 따라 확인 필요 항목에 `task_id` 가 없다. 승인 전에 부여할 수 있는 안정된 식별자는 `approval_id` 뿐이다.
- `extraction_item` 이 `task_id` 와 `approval_id` 를 배타적으로 들고 있어, 회의록에서 두 종류를 구분해 링크할 수 있다.

개정 대상:

- D-034: `확인하기` 와 `채워 넣기` 의 이동 대상을 `태스크 상세` 에서 `확인 필요 상세` 로 변경한다. 대시보드에서 작업을 완료하지 않고 상세 화면으로 이동한다는 원칙은 유지한다.
- D-103: 비인가 직접 접근의 차단 대상 경로를 위 URL 로 명시한다. 차단 후 동작은 그대로 유지한다.
- D-108: 워크스페이스 범위 URL 목록에 `/workspaces/:workspaceId/approvals/:approvalId` 를 추가한다.

### D-163. 확인 필요의 상태 표현 정정

- 결정일: 2026-09-17
- 상태: 확정

D-102 의 내용은 유지하고 서술 전제만 정정한다.

- `확인 필요` 는 태스크의 상태 값이 아니라 별도 리소스다. 화면에서만 태스크 목록의 한 탭으로 표시한다.
- `확인 필요` 를 PM 만 조회·수정·승인·반려할 수 있다는 권한 규정은 그대로 유지한다.
- 일반 팀원에게 제공하는 상태 범위가 `전체`, `진행 중`, `완료` 이고 `전체` 에 확인 필요가 포함되지 않는다는 규정도 유지한다.

변경 사유:

- D-102 는 `확인 필요` 가 태스크 상태 축에 속한다는 전제로 서술되어 있었다. D-161 이후 이 전제가 성립하지 않는다.

영향:

- 일반 팀원의 `전체` 탭은 승인 요청을 조회하지 않는다. 병합 자체가 일어나지 않으므로 D-161 의 병합은 PM 화면에만 적용된다.
- 서버도 권한을 검사해야 한다는 D-102 의 요구는 유지한다. 현재 백엔드에 인증이 없어 프론트엔드 분기만으로는 보호되지 않는다.

### D-164. 회의 날짜의 표현

- 결정일: 2026-09-17
- 상태: 프론트엔드 입장 확정, 백엔드 합의 대기

- 회의 날짜를 위한 별도 필드를 요청하지 않는다. `meeting.started_at` 을 회의 날짜로 사용한다.
- 음성 업로드 요청에 사용자가 지정한 날짜를 담고, 백엔드가 그 값을 `started_at` 으로 저장하도록 요청한다.

이유:

- `meeting` 에 `started_at` 과 `ended_at` 이 있고 별도의 날짜 컬럼이 없다. 컬럼 추가보다 기존 필드의 의미를 확정하는 편이 D-160 에 맞는다.
- `started_at` 을 서버 수신 시각으로 두면 지난 녹음을 나중에 올릴 때 회의 날짜가 업로드 날짜가 된다. D-079 의 기본값·수정 정책과 D-106 의 최신순 정렬이 함께 깨진다.
- Discord 봇 경로가 이미 회의 시작 시각을 `started_at` 에 기록하므로 두 경로의 의미가 일치한다.

영향:

- 업로드 시각을 별도로 보존하지 않는다. 1차에서 업로드 시각을 표시하는 화면이 없다.

### D-165. 세션 요구사항에서 토큰 형식 제거

- 결정일: 2026-09-17
- 상태: 프론트엔드 입장 확정, 백엔드 합의 대기

D-151 에서 토큰 형식 지정을 삭제하고 요구사항만 남긴다.

- 세션은 Secure·HttpOnly 쿠키로 전달하고 `SameSite` 는 `Lax` 로 한다. 응답 본문으로 토큰을 내려받지 않는다.
- 로그아웃 시 세션을 즉시 무효화한다.
- 토큰이나 세션에 역할·권한을 담지 않는다. 권한은 요청마다 워크스페이스 멤버십에서 조회한다.
- 위 세 가지를 충족하는 한 토큰 형식과 저장 방식은 백엔드가 정한다. JWT 를 요구하지 않는다.
- 프론트엔드는 Axios 인스턴스에 `withCredentials: true` 만 설정한다. 토큰 저장·첨부·갱신 로직을 두지 않는다.

변경 사유:

- D-151 본문이 이미 `토큰 형식 선택은 프론트엔드 구현에 영향을 주지 않는다` 고 적고 있다. 영향이 없는 항목을 프론트엔드가 지정할 이유가 없다.
- JWT 를 지정하면 만료 전 무효화가 불가능해지고, 그 부작용의 해결(짧은 만료 또는 무효화 목록)을 다시 백엔드에 요구하게 된다.
- D-152 에 따라 단일 서버에 배포하므로 무상태 토큰의 이점이 없다.
- 역할을 토큰에서 제외하면 PM 권한 회수(D-102)는 토큰 형식과 무관하게 즉시 반영된다. 역할은 워크스페이스마다 다르므로 애초에 토큰에 담을 수 없다.

정정:

- D-151 본문의 `로그아웃(D-072)` 인용은 잘못되었다. D-072 는 `재로그인 시 미완료 온보딩 복귀` 다.
- 로그아웃의 동작과 이동 경로를 정한 결정이 D-001 부터 D-159 까지 존재하지 않는다. 별도로 논의해 확정한다.

### D-166. 태스크 목록은 전량을 받아 클라이언트에서 거른다

- 결정일: 2026-09-17
- 상태: 확정

- `GET /api/v1/tasks?workspace_id=` 로 워크스페이스의 태스크 전량을 받아 탭 필터링을 클라이언트에서 수행한다.
- `status` 질의 파라미터를 사용하지 않는다.
- `overdue` 와 담당자 이름도 클라이언트에서 만든다.

이유:

- `status` 가 단일 값만 받는다. 시안의 `진행 중` 탭은 완료가 아닌 모든 상태(`todo`, `in_progress`, `blocked`)를 함께 보여주므로 한 번의 질의로 거를 수 없다. 백엔드에 다중 값 지원을 요청하는 대신 프론트엔드가 감수한다(D-160).
- 목록 API 에 페이지네이션이 없어 어차피 전량이 온다. 상태별로 나눠 부르면 요청만 3배가 되고 총계는 여전히 맞지 않는다.
- `TaskResponse` 가 평평해 담당자 이름이 없고 `overdue` 도 없다. `GET /members` 와의 조인과 날짜 비교를 `entities` 계층에서 함께 처리한다.

전제 조건:

- 1차 규모(워크스페이스당 태스크 수십 건)를 전제한다. 규모가 커지면 다시 정한다.
- 마감 임박 목록은 예외다. `due_before` 질의가 있으므로 서버에서 거른다(D-043).

영향:

- 데이터가 늘어 페이지네이션이 필요해지면 이 결정과 D-161 의 `전체` 탭 병합이 함께 깨진다. 계약 문서 §8 에 결정 대기로 남겼다.


### D-167. 대시보드를 기존 API 로 조립한다

- 결정일: 2026-09-17
- 상태: 확정

- 대시보드 집계 엔드포인트(`GET /workspaces/{id}/dashboard`)를 백엔드에 요청하지 않는다. 이전 판의 요청을 철회한다.
- 상단 요약 4개와 `확인이 필요한 일`·`마감 임박` 목록을 프론트엔드가 기존 API 로 계산한다.
- `최근 반영` 은 최신 회의의 추출 결과에서 `gate=auto` 항목을 골라 조립한다.
- 대시보드 진입 시 호출은 4회이며, `최근 반영` 의 되돌림 여부 확인에 최대 3회가 더해진다.

이유:

- 목록 API 에 페이지네이션이 없어 전량이 온다. `GET /tasks?workspace_id=` 가 워크스페이스의 태스크 전부를, `GET /approvals?workspace_id=&status=pending` 이 확인 필요 전부를 반환한다.
- 집계 API 를 요청했던 근거는 `목록에는 5개만 보여도 상단 숫자는 전체 개수여야 한다`(D-052~D-054)였는데, 전량이 오면 이 문제가 성립하지 않는다.
- `GET /approvals` 의 `total` 이 `status` 필터를 반영한다. `확인 대기 N` 을 그대로 쓸 수 있다.
- 없는 API 를 요청해 기다리는 것보다, 있는 것으로 조립해 화면을 먼저 만드는 편이 D-160 에 맞는다.

전제 조건:

- 대시보드에 추가로 필요한 것은 회의 목록(`GET /workspaces/{id}/meetings`)뿐이며 이미 요청 중이다.
- 빈 상태의 원인 3갈래(D-041)도 조립으로 판정할 수 있다. 회의 목록이 비었는지, 최신 회의에 `gate=auto` 항목이 있는지, Notion 이 연결됐는지를 본다.

영향:

- 페이지네이션이 도입되면 이 결정과 D-161 의 `전체` 탭 병합, D-166 의 클라이언트 필터링이 **함께** 깨진다. 셋을 같이 재검토한다.
- 조립 절차는 계약 문서 §5.4 에 적었다.

### D-168. 팀원 연결 화면의 데이터 출처

- 결정일: 2026-09-17
- 상태: 프론트엔드 입장 확정, 백엔드 합의 대기

- 온보딩의 `팀원 연결` 은 **Discord 서버의 현재 사용자 목록**을 출처로 삼는다. 백엔드에 `GET /workspaces/{workspace_id}/discord/members` 하나를 요청한다.
- 매핑에는 새 엔드포인트를 요청하지 않는다. 기존 `POST /members`(`display_name` 과 `discord_user_id` 를 함께 전달)와 `PATCH /members/{member_id}` 를 쓴다.
- 매핑 현황은 Discord 사용자 목록과 `GET /members?workspace_id=` 를 `discord_user_id` 로 조인해 만든다.
- `GET /members/unresolved-aliases` 는 이 화면에 쓰지 않는다. `워크스페이스 관리·설정`의 별칭 보정 화면에서 쓴다.

이유:

- D-026 은 `연결된 Discord 서버에서 사용자 목록을 자동으로 불러온다` 를 전제한다. 백엔드에 그 경로가 없다.
- `GET /members/unresolved-aliases` 는 `alias_resolution_log` 를 집계해 **회의 전사에서 감지됐지만 매칭되지 않은 이름 문자열**을 준다. 팀원 연결 단계는 회의보다 앞에 있으므로 이 목록이 비어 있다. 두 데이터는 성격이 다르다.
- `member` 테이블에 `discord_user_id` 가 이미 있어 매핑을 담을 자리가 있다. 새 리소스를 만들 필요가 없다(D-160).

백엔드에 함께 요청하는 것:

- `member.discord_user_id` 에 워크스페이스 범위 유일 제약. 한 Discord 사용자가 두 팀원에 연결되지 않아야 한다(D-027). 위반은 409.

영향:

- D-026 부터 D-031 까지는 개정하지 않는다. 이 제안이 그 결정들을 그대로 충족한다.
- D-028(미매핑 사용자를 Discord 아이디로 표시)은 `member` 에 해당 `discord_user_id` 가 없는 경우로 판정한다.
- D-031(나간 사용자 보존)은 `member` 에는 있고 Discord 목록에는 없는 경우로 판정해 `비활성` 으로 표시한다.
- 요청이 거절되면 팀원 연결 화면을 별칭 기반으로 다시 설계해야 하고, 그때 D-026·D-028·D-030 을 개정한다.

### D-169. 태스크 보드의 컬럼

- 결정일: 2026-09-18
- 상태: 확정

- 보드의 컬럼을 목록 탭과 같은 축으로 둔다. `확인 필요` · `진행 중` · `완료` 3개다.
- `확인 필요` 컬럼은 읽기 전용이다. 카드를 드래그할 수 없고, 클릭하면 승인 상세로 이동한다(D-162).
- `진행 중` → `완료` 는 `PATCH /tasks/{id} {status:"done"}`, `완료` → `진행 중` 은 `{status:"in_progress"}` 로 보낸다.
- `blocked` 는 별도 컬럼으로 두지 않고 카드의 배지로 표시한다. 배지를 누르면 `blocker` 를 보여준다.
- 보드는 목록과 같은 전량 조회를 공유한다. 컬럼별로 따로 호출하지 않는다(D-166).

이유:

- 목록과 보드가 같은 축을 쓰면 사용자가 배우는 개념이 하나다. 화면을 옮길 때마다 상태 축이 바뀌면 `확인 필요` 가 어디로 갔는지 매번 다시 찾아야 한다.
- 구현에서도 §3.2 의 필터 함수 하나를 두 화면이 공유한다. 축이 갈리면 같은 데이터에 대한 분류 규칙이 두 벌이 되고, 둘이 어긋나면 개수가 맞지 않는다.
- `확인 필요` 를 드래그 대상에서 뺀 것은 D-161 의 귀결이다. 승인 항목에는 `task_id` 가 없어 `PATCH /tasks` 를 보낼 수 없다. 승인은 태스크를 생성하는 외부 효과가 있는 조작이라 D-137 에 따라 서버 성공 후에 반영해야 하며, 드래그의 즉시성과 맞지 않는다.
- `완료` 에서 되돌릴 때 `todo` 가 아니라 `in_progress` 를 쓰는 것은, 한 번 완료된 일이 착수 전으로 돌아가지는 않기 때문이다. 이전 상태를 복원하려면 `task_history` 를 거슬러야 하는데 드래그 한 번에 조회를 더할 만한 이득이 없다.

전제 조건:

- `blocked` 가 컬럼에서 사라지므로 배지가 유일한 표시 수단이다. 배지가 빠지면 대시보드의 `막힌 일 N`(D-056)과 화면이 어긋난다.
- 백엔드 `TaskStatus` 4값은 그대로 둔다. 화면의 3컬럼은 표시 계층의 묶음이며 §4.8-4 의 가정 위에 선다.

영향:

- 계약 문서 §3.2 · §5.6 · §7 에 반영했다.
- 보드 내 이동은 D-137 의 낙관적 업데이트 대상 그대로다.


### D-170. 간트차트의 기간 표현

- 결정일: 2026-09-18
- 상태: 프론트엔드 입장 확정, 백엔드 합의 대기

- 간트의 막대는 `start_date` 부터 `due_date` 까지로 그린다.
- 백엔드에 `task.start_date`(nullable, `YYYY-MM-DD`)를 응답과 `POST` · `PATCH` 에 추가해 달라고 요청한다. 계약 문서 §4.7 의 6번이다.
- 답을 기다리지 않는다. `start_date` 가 없거나 `null` 이면 `created_at` 의 날짜 부분을 시작일로 쓴다. 이 폴백을 §4.8 의 가정 5번으로 고정한다.
- 폴백 계산은 `entities/task` 의 변환에서 하고, 화면은 항상 `startDate` 를 받는다.

이유:

- `task` 에 시작일이 없고 `due_date` 만 있다. 기간 축이 없으면 간트가 성립하지 않는데, 간트는 D-016 에서 1차 범위에 새로 넣기로 한 화면이다.
- `created_at` 만으로 그리면 막대가 `언제 시작했는가` 가 아니라 `언제 추출됐는가` 를 뜻한다. 같은 회의에서 나온 태스크는 시작점이 전부 같아지고, 사용자가 고칠 수단도 없다.
- 그렇다고 요청의 답을 기다리면 간트 하나 때문에 M1 전체가 멈춘다. 가정을 고정해 두면 백엔드가 필드를 넣든 거절하든 `entities` 계층의 변환만 바뀐다(D-159, D-160).
- 폴백을 두면 요청이 거절돼도 화면이 죽지 않는다. 막대의 의미가 약해질 뿐이다.

전제 조건:

- `start_date` 는 `due_date` 보다 앞선다는 보장이 없다. 역전되면 시작일을 마감일로 잘라 최소 폭 막대로 그린다.
- 날짜 계산은 `date-fns`, `YYYY-MM-DD` 는 문자열로 유지한다(D-145).

영향:

- 계약 문서 §4.7 · §4.8 · §5.6 · §6 · §7 에 반영했다.
- `start_date` 가 들어오면 태스크 수정 화면에 시작일 입력을 추가할지 다시 논의한다. 지금은 넣지 않는다.


### D-171. 메시지 화면의 1차 범위

- 결정일: 2026-09-18
- 상태: 확정

- 1차에서 메시지 화면을 만들지 않는다.
- 내비게이션의 `메시지` 항목과 `/messages` 라우트는 유지하고, 들어가면 `준비 중` 안내만 표시한다. D-002 의 화면 목록은 개정하지 않는다.
- 메시지 관련 API 를 백엔드에 요청하지 않는다. 계약도 엔티티도 MSW 픽스처도 만들지 않는다.

이유:

- 제품 결정이 D-106 까지만 있고 메시지 화면의 정책이 없다. 검토 단계가 있는지, 발송이 자동인지 수동인지, 재발송이 있는지가 전부 미정이라 화면을 정의할 수 없다.
- 백엔드에도 대응하는 리소스가 없다. 정책 없이 가정만으로 계약을 쓰면 가정의 범위가 화면 전체가 되고, 틀렸을 때 재작업도 화면 전체가 된다.
- 내비게이션에서 항목을 빼면 시안과 D-002 를 함께 고쳐야 한다. 정책이 서면 다시 넣을 자리라 지금 빼는 편의 이득이 없다.

전제 조건:

- `준비 중` 화면은 빈 상태 컴포넌트를 재사용한다. 전용 화면을 만들지 않는다.
- Discord 알림 발송과 무응답 감지(D-057, D-058)는 백엔드 동작이며 이 결정과 무관하게 진행된다. 화면이 없을 뿐이다.

영향:

- 계약 문서 §5.7 과 착수 가능 여부 요약에 반영했다. 메시지가 M1 을 막지 않게 됐다.
- D-117(메시지 E2E 시나리오)과 D-136(메시지 상태 동기화 polling)의 보류는 유지한다. 정책이 서면 셋을 함께 푼다.


### D-172. 백엔드 실제 API 도착에 따른 가정 명세 대조

- 결정일: 2026-09-22
- 상태: 확정

D-159 가 예고한 대조를 수행했다. 기준은 `origin/develop` `f441ea4` 이며, PR #59(`feature/58-backend-api-contract`)가 계약 §4.1~§4.5 를 구현했고 PR #55(`fix/be-review-week6-1`)가 기존 API 의 의미를 바꿨다.

- **가정 명세는 유지한다.** `entities` 의 도메인 타입과 mapper 를 재작성하지 않는다. 실제 구현이 가정과 **필드 이름·형태 수준에서 일치**했다.
- **구현 편차는 mapper 가 흡수한다.** 화면 계층은 편차를 알지 못한다. 흡수 대상은 계약 §6 에 목록으로 두었다.
- **MSW 는 실 API 의 의미에 맞춘다.** 형태만이 아니라 쓰기 경로의 의미까지 맞춘다. 어긋난 채로 두면 MSW 로 통과한 화면이 실 API 에서 깨진다.
- **스텁으로 구현된 기능은 MSW 로 개발한다.** 온보딩 단계 저장, Discord 사용자 목록, 회의록 본문 셋이다. 실 API 연결을 미루되 화면 코드는 바꾸지 않는다.
- 편차 목록과 구현 현황은 **계약 문서 §4.0** 한 곳에 모은다. 이 결정 기록에 중복해 적지 않는다.

이유:

- M1 의 전제는 `가정 명세는 실제 API 와 다를 것이 확실하다` 였다(D-159). 실제로는 오류 코드 11개가 이름과 상태 코드까지 제안 그대로 들어왔고, 세션 요구 3가지(D-165)도 그대로 충족됐다. 가정을 버릴 이유가 없다.
- 다른 것은 **값**이지 **형태**가 아니었다. 회의록 본문이 비어 있고 Discord 목록이 하드코딩이지만 필드 이름은 계약대로다. 변환 계층을 둔 효과가 여기서 나타난다.
- 편차를 두 문서에 적으면 한쪽이 먼저 낡는다. 계약 문서가 백엔드를 향하는 유일한 절(§4)을 이미 갖고 있다.

영향:

- **D-170 의 요청이 받아들여졌다.** `task.start_date` 가 응답 · `POST` · `PATCH` 에 들어왔고 `ChangedField.START_DATE` 도 생겼다. §4.8-5 의 폴백은 **가정에서 폴백으로 내려갔을 뿐 없어지지 않는다.** 컬럼이 방금 생겨 기존 태스크 행이 전부 `null` 이다.
- **D-071 의 집행 주체가 바뀐다.** 온보딩 미완료 대시보드 접근의 403 `ONBOARDING_INCOMPLETE` 를 백엔드가 던지지 않는다. 코드는 정의돼 있다. **M3 의 라우터 가드가 `onboarding.completed` 로 먼저 판단한다.** 결정 자체는 개정하지 않는다.
- **D-100 을 실 API 로 검증할 수 없다.** 연동 상태에 `revoked` 를 표현할 컬럼이 없어 `not_connected` 와 구분되지 않는다. 끊김 모달(D-100)과 미연결 모달(D-097)의 분기는 MSW 로만 확인된다. 계약 §4.0-②-6 으로 요청했다.
- **D-015~D-020 의 이름 정규화가 서버에 없다.** 409 는 생겼으나 완전일치 + 전역 비교다. 남이 쓴 이름도 막히고 `팀 A` 와 `팀  A` 는 둘 다 통과한다. **M4 의 입력 정규화는 프론트엔드가 그대로 수행한다.** 서버 중복 판정은 보조로만 믿는다.
  **대소문자는 D-019 대로 구분한다.** 계약 문서가 초안(`c94cc4d`)부터 `대소문자 무시` 를 요청해 온 것은 D-019 와 어긋난 오류였고, 이 결정으로 바로잡는다. `Alpha` 와 `alpha` 는 서로 다른 이름이다. MSW 도 같은 규칙으로 고친다.
- **D-027 은 DB 제약까지 충족됐다.** 다만 소프트 삭제(`is_deleted`)가 새로 생겨, 탈퇴한 팀원의 Discord 사용자를 다시 붙이면 409 가 아니라 500 이 난다. 계약 §4.5 로 알렸다.
- **D-165 의 로그아웃 동작이 정해졌다.** 세션 행 삭제 + 쿠키 삭제다. **이동 경로만 미정으로 남는다.**
- **D-085 · D-086 의 참석자가 서버에 저장되지 않는다.** 업로드가 `attendee_member_ids` 를 받고 버린다. 최소 1명 규칙은 **프론트엔드 폼이 강제한다.**
- `PATCH` 의 명시적 `null` 이 필드 해제가 됐다. 화면은 보내지 않을 필드를 `undefined` 로 빼야 한다. 되돌리기에는 충돌 감지가 붙어 **최신 이력부터** 되돌려야 한다. 둘 다 계약 §2.6 에 적었다.
- 추출 게이트의 `confidence >= 0.8` 이 `auto` 의 충분조건이 아니게 됐다. `needs_check` 면 점수와 무관하게 `review` 다. **`확인 필요` 를 신뢰도 순으로 정렬해 낮은 것만 의심하는 UI 를 만들지 않는다.**
- **인증이 절반만 걸려 있다.** `workspaces` · `integrations` · `meetings/{id}/minutes` 에는 의존성이 있지만
  **`tasks` · `approvals` · `extractions` · `members` 에는 하나도 없고 전역 미들웨어도 없다.** (`members.py` 는 `get_current_member` 를 import 만 하고 쓰지 않는다.)
  태스크 조회·수정·되돌리기와 승인 처리가 비로그인으로 가능하다. `GET /workspaces/{workspace_id}` 는 로그인은 요구하되 멤버십을 보지 않는다.
  **따라서 M3 의 라우터 가드는 UX 장치이지 보안 경계가 아니다.** 서버가 막아 준다고 가정하고 가드를 설계하지 않는다.
  프론트엔드가 해결할 수 있는 문제가 아니므로 라우터별 표를 계약 §4.0-②-1 에 그대로 실어 백엔드에 전달한다.
- **승인 반영이 `extraction_item.approval_id` 를 비우지 않는다.** `task_id` 만 채워서 한 항목이 두 ID 를 동시에 갖는다.
  계약이 `task_id` XOR `approval_id` 를 화면의 불변식으로 적어 온 것이 **승인 후에는 틀렸다.**
  그대로 두면 승인된 항목이 `반영됨` 과 `확인 필요` 양쪽에 나타나고, D-104 로 `approval_id` 항목을 숨기는 일반 팀원에게는 영원히 보이지 않는다.
  **`확인 필요` 의 기준을 `approval_id != null 이고 task_id == null` 로 바꾼다.** `task_id` 가 우선이라 백엔드가 비우든 안 비우든 결과가 같다.
  비워 달라는 요청은 계약 §4.0-②-12 로 올린다.

- 1차에서는 일반 API 응답 전체를 Zod로 중복 검증하지 않는다. 사용자 입력과 URL 파라미터처럼 신뢰할 수 없는 입력은 Zod로 검증하고, 일반 API 응답은 OpenAPI 생성 타입과 MSW 기반 통합 테스트로 검증한다. Axios 공통 계층은 HTTP 상태 및 표준 오류 응답을 정규화하고 DTO 변환 단계에서는 nullable과 기본값을 처리한다. 브라우저가 백엔드를 거치지 않고 외부 데이터를 직접 받는 경계가 생기거나 실제 응답 불일치가 반복되면 해당 경계 또는 OpenAPI 기반 런타임 스키마 자동 생성을 재검토한다(D-134)
- TanStack Query의 조회 요청은 취소 오류와 `400`, `401`, `403`, `404`, `422`, `429`에는 자동 재시도하지 않고, 일시적인 네트워크 오류와 `408`, `5xx`에만 exponential backoff를 적용해 최대 1회 재시도한다. `429`는 서버의 `Retry-After` 규격이 정해진 API에서만 별도 처리한다. mutation과 파일 업로드는 기본적으로 자동 재시도하지 않으며 백엔드가 idempotency를 보장하는 mutation만 API별 예외를 허용한다. 최종 실패 화면에는 수동 `다시 시도`를 제공하고, 인증 만료 처리와 회의 정리 polling은 일반 오류 재시도 정책에서 분리한다. Axios 인터셉터에서는 동일 요청을 다시 시도하지 않는다(D-135)
- TanStack Query 캐시는 대시보드·태스크·회의록 목록을 30초, 워크스페이스 목록·팀원·설정 정보와 완료된 회의록 상세를 5분 동안 최신으로 간주하고, 사용하지 않는 캐시는 기본 5분 뒤 제거한다. 오래된 데이터는 화면 재진입·브라우저 탭 복귀·네트워크 재연결 시 다시 요청하며 생성·수정·삭제 성공 후 관련 캐시를 즉시 무효화한다. 모든 워크스페이스 범위 Query Key에는 `workspaceId`를 포함하고 워크스페이스 전환 시 다른 워크스페이스의 캐시를 표시하지 않는다. 회의 정리 상태는 처리 중에만 별도 polling하고 메시지 상태 동기화는 정책 확정 후 결정하며, 시간값은 실제 API 부하와 사용성을 측정한 뒤 조정할 수 있다(D-136)
- 태스크 상태 변경, 보드 내 이동, 단순 순서 변경처럼 즉시 반응이 중요하고 원상 복구할 수 있는 조작에만 낙관적 업데이트를 적용한다. 변경 전 캐시를 보관하고 실패 시 복구와 오류 토스트를 제공하며 완료 후 서버 데이터를 다시 조회해 최종 상태를 맞추고, 같은 태스크의 요청이 진행 중일 때 중복 조작을 막는다. 태스크 생성·삭제, 확인 필요 승인, Discord 메시지 발송, Discord·Notion 연결, 회의 파일 업로드·정리 시작, 워크스페이스 생성·설정 변경은 외부 효과나 중복 위험이 있으므로 서버 성공 후 화면에 반영한다(D-137)
- 서버에 저장해야 하지만 아직 저장하지 않은 폼 변경값이나 회의 업로드 화면에서 아직 전송하지 않은 선택 파일이 있을 때만 공통 이탈 확인을 표시한다. 앱 내부 링크·뒤로가기·워크스페이스 전환에는 `계속 작성하기`와 `변경 내용 버리고 나가기`가 있는 공통 확인 모달을 사용하고, 브라우저 새로고침·탭 닫기에는 브라우저 기본 경고를 사용한다. 저장 성공·폼 초기화·회의 정리 시작 후에는 경고를 해제하며 URL에 즉시 반영되는 검색·필터·정렬과 일시적인 UI 상태는 대상에서 제외한다. 기존 워크스페이스 전환 확인 정책도 이 공통 기능으로 통합한다(D-138)
- 현재 공식 프론트엔드 환경은 `local`과 `production`만 둔다. 로컬에서는 Vite 개발 서버와 MSW 또는 로컬 백엔드를 사용하고, 배포 전에는 로컬에서 프로덕션 빌드를 실행해 단위·통합 테스트와 Playwright E2E를 검증한다. 운영 환경 변수는 배포 환경에서 주입하며 환경 변수 접근과 형식 검증은 `shared/config`에서 통합하고, `.env.example`에는 필요한 공개 변수 이름을 기록하되 실제 로컬 설정은 Git에서 제외한다. 브라우저에 노출되면 안 되는 비밀키와 OAuth client secret은 프론트엔드 환경 변수에 두지 않는다. 백엔드 staging이 제공되면 프론트엔드 staging도 함께 추가하며, 그전까지 frontend-only preview를 실제 통합 검증 환경으로 간주하지 않는다(D-139)
- production에서는 Root·Route Error Boundary가 포착한 오류, 처리되지 않은 JavaScript 오류, 반복되는 `5xx`, 청크 로드 실패 등 예상 밖의 프론트엔드 오류를 외부 모니터링 도구로 수집하는 정책을 도입한다. 앱 버전·라우트·브라우저 등 최소 진단 정보만 포함하고 토큰·비밀번호·API 본문·회의 내용·파일명은 수집하지 않으며 초기에는 session replay를 사용하지 않는다. 구체적인 제품과 연동 범위는 실제 개발 시점에 다시 검토한다(D-140)
- Storybook을 도입하되 `shared/ui` 공통 디자인 시스템 컴포넌트와 여러 화면에서 재사용되는 복합 컴포넌트에 범위를 한정한다. 기본·비활성화·로딩·오류·빈 상태·긴 텍스트 등 주요 변형을 Story로 작성하고 API 의존 상태는 기존 MSW mock을 재사용한다. CI에서는 Storybook 정적 빌드 성공을 검사하되 전체 페이지의 중복 구현, 외부 Storybook 배포, 유료 시각 회귀 서비스는 1차에서 제외하며 동작 검증은 React Testing Library와 Playwright가 담당한다(D-141)
- 공통 폼은 React Hook Form에서 `mode: 'onTouched'`, `reValidateMode: 'onChange'`, `shouldFocusError: true`를 사용한다. 최초 입력 중에는 오류를 노출하지 않고 첫 blur에서 해당 필드를 검증하며, 한 번 상호작용한 필드와 제출 후 오류 필드는 값 변경 시 다시 검증한다. 제출 시 전체 필드를 검증해 첫 오류로 포커스를 이동하고, 클라이언트 오류와 서버의 필드별 오류는 입력 아래에, 비필드 서버 오류는 폼 상단에 표시한다. 실패 시 입력값을 유지하고 제출 중에는 로딩 표시와 중복 제출 방지를 적용하며 오류 문구를 입력과 접근성 속성으로 연결한다. 서버 필드 오류는 `setError`로 폼 상태에 반영한다(D-142)
- 기본 CI 품질 게이트는 Node.js 24 LTS에서 `npm ci` 후 TypeScript strict 검사, ESLint, Prettier 검사, Vitest 단위·통합 테스트, production 빌드, Storybook 정적 빌드를 수행한다. FSD 계층 의존성 및 위험한 외부 패키지 barrel·동적 import를 ESLint 규칙으로 제한하고, Swagger/OpenAPI 명세 연결 후에는 생성 타입 최신 상태 검사도 추가한다. 주요 화면 구현 뒤 번들 크기 보고서를 추가하고 기준 크기를 측정한 후에만 상한선을 병합 차단 조건으로 설정한다. CI는 코드를 자동 수정하지 않으며 선행 조건이 있는 단계는 순차로, 서로 독립적인 정적 검사·테스트와 산출물 빌드는 병렬로 실행한다. 정확한 job 수·worker·캐시 구성은 실제 CI 환경에서 정한다. 매 PR 전체 E2E, 초기 커버리지 수치 차단, Lighthouse 및 시각 회귀 차단은 포함하지 않는다(D-143)
- 1차 UI 언어와 날짜 표기는 `ko-KR`, 정확한 시각의 표시 시간대는 `Asia/Seoul`로 고정한다. 태스크 마감일과 회의 날짜처럼 날짜만 의미하는 값은 `YYYY-MM-DD`로 다루고 시간대 변환하지 않으며, 메시지 발송·처리 완료·생성 시각은 서버의 ISO 8601 timestamp를 한국 시간으로 변환해 표시한다. 날짜 포맷과 계산은 `shared/lib/date`로 통합하고 브라우저 기본 시간대에 의존하지 않는다. Swagger 명세에서도 날짜와 timestamp 형식을 구분해야 하며 1차에서는 상대 시간보다 정확한 날짜·시각 표기를 기본으로 사용한다(D-144)
- 사용자에게 보여주는 날짜·시간 포맷은 `Intl.DateTimeFormat`, 캘린더·간트·마감 범위 등의 날짜 계산은 `date-fns`, 공통 포맷·파싱·계산 함수는 `shared/lib/date`를 사용한다. `date-fns`는 필요한 함수만 정적으로 가져오고 날짜 규칙은 단위 테스트한다. 날짜 전용 `YYYY-MM-DD` 값은 가능한 한 문자열로 유지해 불필요한 `Date` 변환과 시간대에 따른 날짜 이동을 방지하며 입력 형식 검증은 Zod가 담당한다(D-145)
- MSW handler를 로컬 개발·Vitest 통합 테스트·Storybook에서 공유하되 production에서는 완전히 제외한다. 정상 응답을 기본으로 두고 빈 상태·권한 오류·검증 오류·서버 오류·느린 응답은 테스트와 Story에서 개별 override하며, 고정 ID·날짜·내용과 Swagger/OpenAPI 생성 DTO 타입을 사용한다. 테스트의 미처리 요청은 실패시키고 로컬의 미처리 요청은 경고하며 실제 개발 API 요청만 명시적으로 허용한다. 자동 테스트에는 불필요한 지연을 두지 않고 mock 실행 코드는 동적 import하여 production 번들에서 제외하며 컴포넌트는 실제 API와 mock을 구분하지 않는다. 배포 전 프론트엔드 E2E는 로컬 테스트 서버 또는 MSW를 사용할 수 있지만 실제 외부 연동은 테스트 계정으로 별도 검증한다(D-146)
- 브라우저 저장소는 기본적으로 사용하지 않고 다음 방문에도 유지할 필요가 있는 비민감 UI 환경설정만 허용 목록 방식으로 저장한다. Zustand 전체 store에는 persist를 적용하지 않으며, 필요한 slice에서 `partialize`로 사이드바 접힘 같은 값만 골라 버전이 포함된 key로 `localStorage`에 저장한다. 현재 확정된 요구사항에는 `sessionStorage` 대상이 없어 기본적으로 사용하지 않는다. 사용자·워크스페이스·태스크·회의록은 TanStack Query에서 다시 조회하고 현재 워크스페이스은 URL, 마지막 이용 워크스페이스과 온보딩 진행 상태는 서버가 관리한다. 작성 중인 폼과 선택 파일은 메모리에만 두며 토큰·비밀번호·회의 및 메시지 내용·전체 서버 객체는 Web Storage에 저장하지 않는다. 인증 세션은 백엔드와 협의해 Secure·HttpOnly Cookie를 우선 사용하고 저장소 오류는 앱 실행을 막지 않도록 처리한다(D-147)
- 사용자 피드백은 목적에 따라 구분한다. 특정 입력 문제는 필드 오류, 해당 영역에서 해결할 수 있는 조회 실패·빈 상태는 화면 내 인라인 안내, 현재 작업을 막지 않는 작업 결과는 토스트, 일정 시간 지속되는 연결·시스템 상태는 배너, 사용자의 결정 없이는 진행할 수 없는 삭제·이탈·연결 전제 조건은 모달을 사용한다. 같은 내용을 여러 방식으로 중복 표시하지 않고 기술 오류를 사용자 행동 중심 문구로 변환하며, 반복 토스트를 병합하고 동시 표시 수를 제한하고 `aria-live` 등 접근성을 적용한다. 액션이 있는 알림은 조작 시간을 보장한다. 이 구분은 1차 기본 원칙이며 최종 디자인과 실제 기능 흐름을 구현하면서 세부 표시 방식·지속 시간·우선순위를 조정할 수 있다(D-148)
- 1차 사용자 화면은 한국어만 지원하고 다국어 라이브러리는 도입하지 않는다. 문서 언어는 `ko`, 날짜·숫자 locale은 `ko-KR`을 사용하며 공통 오류·확인 문구는 중앙 관리하고 기능 전용 문구는 해당 기능 가까이에 둔다. 공통 UI 컴포넌트에는 기능 전용 한국어 문구를 고정하지 않고 label·description 등의 props로 전달하며, 백엔드 기술 문구를 그대로 표시하지 않고 오류 코드를 사용자용 한국어 문구로 변환한다. 동적 문구는 단편 문자열을 이어 붙이기보다 완성된 문장 단위로 생성해 향후 다국어 도입 시 구조 변경 범위를 줄인다(D-149)
