# 디스코드 채팅 수집 채널 설정(저장·공지·잠금)

- 기록일: 2026-11-06
- 관련 마일스톤: M4 (이슈 #428, FE 요청 #429)

## 문제와 제약

- 봇이 매일 디스코드 채팅을 읽어 task 제안에 쓰려면, 워크스페이스마다 어느 채널을 읽을지 PM 이 정해 BE 에 저장해 둬야 한다. AI 가 #428 에서 경로와 응답을 제안했다.
- 채널을 켜면 그 채널의 팀원이 대화가 읽힌다는 것을 알아야 한다. 켠 사실을 채널에 알리고, 알리지 못했으면 켜지 않아야 한다.
- 허락 범위: `integration` 에 nullable 열 2개와 마이그레이션 1개, 새 경로 4개, 연결 조회 응답 필드 1개, 새 에러 코드 2개, `DISCORD_API_FAILED` 문구 일반화. 새 PM 경로 3개는 PM 전용, 봇 경로는 서비스 토큰이다.
- 로컬 DB 명령과 실제 Discord 호출은 하지 않았다. 테스트는 sqlite 와 스텁이라 `FOR UPDATE` 와 마이그레이션은 검증하지 못했다.

## 실제 검토한 선택지

대화에서 비교한 선택지만 적는다.

1. 저장 위치: A. 디스코드 `Integration` 행의 두 열(채널 ID·이름) / B. 채널을 따로 표에 저장
2. 켬·끔 처리 방식
   - A. 요청 안에서 차례로 처리하고 연결 행을 `FOR UPDATE` 로 잠금
   - B. 잠금 없이, 마지막에 값이 그대로인지 조건부 UPDATE 로 저장하고 충돌하면 409
   - C. BE 는 저장만 하고 공지는 AI 봇이 나중에 보냄
3. 켬 공지를 보내지 못했을 때: 저장 실패 / 저장하고 경고만
4. 끔 공지를 보내지 못했을 때: 끄기 실패 / 끄기는 성공
5. 채널 목록 범위: 일반 텍스트 채널(type 0)만 / 공지·포럼·음성 채팅 채널까지
6. 끄는 API 응답: 204 / 200 봉투 `{off_notice_sent}`
7. 같은 채널을 다시 저장할 때: 다시 확인·공지 / Discord 를 부르지 않고 현재 값

## 선택과 이유

사람이 정한 것(이슈 #428 설계 확정 댓글과 사용자 확인)

1. 저장 위치는 디스코드 `Integration` 행의 두 열 `chat_channel_id`(32자)·`chat_channel_name`(100자)이다. 연결 행을 지우면 채널도 함께 사라진다. 대안(따로 표)은 워크스페이스마다 채널 여러 개를 허용할 수 있지만 합의(채널 하나, 연결 해제 시 함께 삭제)보다 넓고 표·코드가 늘어 버렸다.
2. 처리는 A. BE 가 직접 확인하고 공지한 뒤 저장한다. 순서는 행 잠금 → 서버의 텍스트 채널인지 → 읽기 확인(`GET /channels/{id}/messages?limit=1`) → 켬 공지 → 두 열 저장·커밋이다. 잠그는 이유는 같은 워크스페이스의 동시 저장이 서로 다른 채널에 공지만 남기고 마지막 값만 저장하는 일을 막기 위해서다.
   - 대가: 디스코드가 느리면 같은 워크스페이스의 연결 해제가 대략 15초 안팎 기다린다(Discord 호출마다 5초 제한, 세 번 부름). 호출 제한 시간을 5초로 줄인 것(사용자 목록 조회는 10초 그대로)도 이 대가를 보고 정했다.
   - B 를 버린 이유: 충돌 때 켬 공지가 이미 나가 정정 공지까지 보내야 해 코드·테스트가 늘고, 두 PM 이 동시에 저장하는 일은 드물어 얻는 게 적다.
   - C 를 버린 이유: 공지 실패를 저장 실패로 만들 수 없고, 공지가 다음 봇 실행까지 늦어져 합의("저장하는 순간 BE 가 공지")와 달라진다.
3. 켬 공지 실패는 저장 실패다. 공지 없이 수집이 시작되면 팀원 고지가 빠지기 때문이다(AI 추천과 같음). 대안 "저장하고 경고만"은 버렸다. 403 이면 409 `DISCORD_CHANNEL_NOT_ACCESSIBLE`(`need: "send"`), 그 밖은 502 `DISCORD_API_FAILED`다. 읽기 확인의 403 은 `need: "read"`, 서버에 없는 채널은 404 `DISCORD_CHANNEL_NOT_FOUND`다. 오류의 `details`에 Discord 오류 JSON 의 `code`(`discord_code`)를 싣는다.
4. 끔 공지는 best-effort 다. 채널 해제, 채널 변경(옛 채널), 디스코드 연결 해제 때 커밋 뒤에 시도하고, 실패해도 끄기·변경·연결 해제는 성공이다. 채널이 지워졌거나 권한이 빠져도 PM 이 끌 수 있어야 하기 때문이다. 대안 "사용 안 함 때만 공지"는 채널 변경·연결 해제 때 옛 채널 팀원이 몰라 버렸다. 다른 서버로 재연결하면 이전 서버의 채널을 부를 수 없으니 공지 없이 비운다(같은 서버는 유지).
5. 목록은 type 0(GUILD_TEXT)만 준다. 공지·포럼·음성 채팅 채널은 뺀다. 고를 수 있는 채널이 모두 실제로 수집 가능해야 하고, 공지 채널은 팀원 대화가 거의 없고 봇 공지에도 어울리지 않아서다.
6. 끄는 API 는 204 가 아니라 200 봉투 `{off_notice_sent}`다. FE 가 공지 실패를 PM 에게 알릴 수 있게 하려는 것이다. 204 는 기존과 모양이 같지만 실패를 알 수 없어 버렸다. 이미 꺼져 있어도 200 이다.
7. 같은 채널 재저장은 Discord 를 부르지 않고 현재 값을 200 으로 준다. 채널 이름은 저장한 시점의 값이다. 공지 반복을 막고 설정 화면이 디스코드 장애에 영향받지 않게 하려는 것이고, 대가는 디스코드에서 이름이 바뀌면 다음 저장까지 옛 이름이 보이는 것이다.
8. 배포 순서는 BE → 운영 PM 이 채널을 켬 → AI 전환이다. Message Content Intent 는 AI 담당이 켜고, BE 는 README 포털 설정에 한 줄 적는다.

구현에서 정한 것(대화에서 따로 논의하지 않았다)

- 채널 목록 정렬: 카테고리 없는 채널이 먼저, 그다음 카테고리 position, 같은 카테고리 안은 채널 position, 같으면 id. Discord 화면 순서에 가깝게 맞췄다.
- PUT 중 서버 채널 목록 조회가 실패하면 502 `DISCORD_API_FAILED`로 처리하고 아무것도 저장하지 않는다.
- 연결 행이 없거나 채널이 비어 있을 때 `DELETE chat-channel`은 오류가 아니라 200 `off_notice_sent: false`다(이미 꺼진 경우와 같게 다뤘다).
- `PUT`은 봇 토큰 확인을 먼저 한다. `DISCORD_BOT_TOKEN`이 없으면 같은 채널 재저장도, 연결 없음도 409·200 이 아니라 502 `DISCORD_API_FAILED`(`reason: bot_token_missing`)다. 채널 목록 조회는 반대로 연결 확인이 먼저다.
- `channel_id`는 앞뒤 공백을 지운 숫자 1~20자만 받는다(Discord 채널 ID 형식). 아니면 400 `INVALID_REQUEST`.

## 장단점과 감수한 제약

- PUT 은 Discord 를 세 번까지 부르는 동안 행을 잠근다. 같은 워크스페이스의 다른 연결 변경(연결 해제, 재연결 callback, 다른 PUT)은 그동안 기다린다. 호출마다 5초 제한(단계별 제한이라 합계 상한은 아니다)이고 세 번 부르므로 대략 15초 안팎이다.
- 켬 공지를 보낸 뒤 DB 저장이 실패하면 공지는 이미 나갔고 저장은 없다(로그만 남긴다). 켜지지 않은 채널에 켬 공지가 남을 수 있다.
- 끔 공지는 커밋 뒤라 앱이 그 사이에 죽으면 안 나간다. 수집은 이미 꺼졌으니 대화가 읽히지는 않는다.
- 채널 이름은 스냅숏이라 디스코드에서 바뀌어도 화면에는 옛 이름이 보일 수 있다.
- 채널은 워크스페이스당 하나다.
- 운영 중에 봇이 그 채널을 읽을 수 없게 돼도 BE 는 알지 못한다(저장 시점에만 확인한다).
- 읽기 확인은 VIEW_CHANNEL 만 있고 READ_MESSAGE_HISTORY 가 없으면 403 이 아니라 200 빈 목록을 받아 통과할 수 있다(Discord 동작, 확인 필요). 동작은 그대로 둔다.
- BE 는 회의 생성(`POST /meetings`)에서 채팅 수집 여부를 확인하지 않는다. 봇이 실행 직전에 목록을 다시 받아 거르므로, 목록과 실행 사이에 PM 이 끄면 그날 실행분은 회의가 만들어질 수 있다.
- `FOR UPDATE` 와 마이그레이션 `fe08fcbd6dc6`은 sqlite 테스트와 로컬 DB 없이 쓴 것이라 CI migrations 잡(PG)으로 확인해야 한다.
