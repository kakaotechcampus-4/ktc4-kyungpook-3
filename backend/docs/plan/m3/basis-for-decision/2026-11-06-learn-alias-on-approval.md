# 승인 때 별칭 학습: 저장 대상과 판단 위치

- 기록일: 2026-11-06
- 관련 마일스톤: M3 (회의·전사·AI 결과 수신)
- 관련 이슈: #459 (PR ②. 님·조사 후보 검색과 팀원 이름·디스코드 닉네임 별칭은 PR ①)

## 문제와 제약

- `member_alias` 는 PM 이 수동 API 로 넣을 때만 채워지고 등록 화면도 없어 사실상 비어 있다. 그래서 이름으로 지목된 담당자가 대부분 PM 보류(`hold`)로 간다.
- PM 은 보류된 항목을 승인하면서 담당자를 직접 고른다. 이때 회의에서 부른 말과 실제 담당자의 짝이 생기지만 버려지고 있었다.
- AI 는 `assignee_type` 을 보내지만 BE 는 판단에만 쓰고 저장하지 않았다. 승인 시점에는 이 항목이 이름으로 부른 것인지 알 수 없었다.
- 잘못 배운 별칭은 다음 회의의 매칭을 망가뜨린다. `resolve_assignee` 는 같은 글자를 두 명이 가지면 애매함(ambiguous)으로 판정한다.

## 실제 검토한 선택지

1. **후보 여부를 응답 때 계산(채택)**: DB 에는 `extraction_item.assignee_type` 만 저장한다. `alias_candidate`·`alias_text` 는 응답을 만들 때 추출 항목과 승인 상태로 계산하고, 승인할 때 같은 함수로 다시 판정한다.
2. **승인 요청 payload 에 후보 여부 저장**: 쿼리는 늘지 않는다. 하지만 `POST /approvals` 로 누구나 payload 에 값을 넣을 수 있어 승인 때 결국 다시 판정해야 하고, 판단 기준이 두 곳이 된다. 승인 뒤에도 값이 남는다.
3. **이미 그 글자를 가진 팀원 목록(`alias_owner_member_ids`)도 응답에 싣기**: FE 가 미리 숨길 수 있지만 필드와 조회가 늘어난다. 아래 4번 규칙으로 필요가 없어졌다.
4. 같은 글자를 다른 팀원이 이미 가진 경우:
   - (가) 그대로 저장
   - (나) 후보에서 빼고 저장하지 않음(채택). 최종 리뷰에서 (가)가 원래 팀원의 매칭을 애매함으로 바꾼다는 지적이 나왔다.

## 선택과 이유

- **선택지 1**: 판단 기준이 `app/services/alias_learning.py` 한 곳에 모인다. auto 되돌리기로 생긴 승인과 이미 쌓인 pending 승인에도 같은 규칙이 적용된다.
- **학습 대상**: 추출 때 담당자가 비어 있었던(못 찾음·애매함) 새 항목 중 `assignee_type` 이 `thirdname` 인 것만 학습한다. 이슈 규칙 ④ 는 `thirdrole` 도 대상이었지만 지금은 뺐다(아래 역할 항목). (2026-11-09 #522 로 다시 넣음, 아래 갱신)
  - 찾은 담당자를 PM 이 바꾼 경우와 1·2인칭·대명사·그룹은 부른 말과 담당자의 짝이 아니라서 뺐다.
  - `assignee_type` 이 NULL 인 옛 항목도 판단 근거가 없어 뺐다.
- **이미 누군가 가진 글자**: 같은 워크스페이스에서 탈퇴하지 않은 팀원이 그 글자를 별칭으로 가졌으면 묻지 않고 저장하지 않는다.
  - 이 기능은 비어 있는 별칭을 채우려는 것이고, 잘 찾히던 사람을 애매하게 만들면 안 된다.
  - 탈퇴 팀원의 별칭은 세지 않는다. #463 의 `resolve_assignee` 가 담당자를 찾을 때 탈퇴자 별칭을 보지 않으므로, 세면 그 글자는 PM 이 탈퇴자 별칭을 지울 때까지 배울 수 없다(#464 리뷰). 처음에는 develop 의 찾기 규칙이 탈퇴자를 셌기 때문에 같이 셌다.
  - 탈퇴자 별칭은 지우지 않는다. 지금 팀원 탈퇴 API 가 없어 지울 시점이 없고, 지우면 되돌릴 수 없다. PM 이 별칭 관리(`DELETE /members/aliases/{id}`)에서 직접 지울 수 있고, 팀원 탈퇴 기능을 만들 때 정리할지 다시 정한다.
- **1인칭이 주어로 쓰인 꼴은 학습하지 않음**: AI 가 "제가 맡을게요" 같은 1인칭을 `thirdname` 으로 잘못 분류한 기록이 있다(#502). 그대로 두면 다듬은 "제"·"우리"가 확인된 별칭이 되어 오분류된 말이 그 팀원으로 채워진다. 한 글자는 #463 의 한 글자 규칙으로 확정 매칭은 안 되지만 "저희"·"우리"·"본인"은 두 글자라 걸리지 않는다. 지적마다 단어를 하나씩 더하면 끝이 없어(도, 들, 들은, 만 …) 규칙 하나로 선을 그었다.
  - **선(기준)**: 1인칭이 할 일의 주어로 쓰인 꼴만 막는다. 규칙은 어간(제·저·나·내 / 저희·우리 / 본인) × 복수 "들"(저희·우리·본인에만, "저들"은 3인칭) × 주어 표지(도·만, 은은 받침 있는 말 뒤에서만). 이·가·는·를 같은 격조사는 다듬기가 먼저 뗀다.
  - **막지 않는 것**: 주어 표지가 아닌 부사어·구·끝말(우리끼리, 우리까지, 저희 모두, 제가요)과 3인칭 "저들". 새는 경우는 PM 동의, 한 글자 확인 필요(#463), 별칭 삭제, AI 오분류 개선이 받는다. legacy 경로의 오분류율은 아직 재지 않았다(AI 담당이 judge 경로만 쟀다).
  - **판단 질문**: 새 꼴이 거론되면 "이 규칙이 만드는 조합인가"로 본다. 안이면 버그라 고치고, 밖이면 문서에 남긴다. 규칙이 만드는 조합은 `tests/services/test_alias_learning.py` 가 전부 돌려 고정한다. 새 어간(예: "소인")을 더할지는 버그가 아니라 규칙을 바꾸는 결정이다.
  - **"은"은 받침 있는 말 뒤에서만**: 받침 없는 어간은 "는"이 붙어 "나은"(이름)은 막지 않는다. AI 쪽 오분류를 고치는 것은 AI 몫이다.
- **이미 찾히는 표현은 찾기 후보 전체로 본다**(#464 리뷰, #463 머지 뒤): 저장할 글자 하나만 비교하면 "하은은"(후보 하은은·하은, "하은"은 두 팀원)이 아무도 안 가진 글자로 보여 저장되고, 이후 "하은은"이 긴 후보가 먼저 걸려 그 팀원으로 항상 확정된다. 그래서 저장할 글자와 #463 의 `name_candidates(assignee_raw)` 중 하나라도 탈퇴하지 않은 팀원이 가졌으면 묻지도 저장하지도 않는다.
- **저장 값**: `source=learned`, `verified=true`, `confidence=0.9` 다. PM 이 승인으로 확인한 짝이라 확인된 별칭으로 둔다. 0.9 는 auto 기준 0.8 이상이다.
- **역할(`thirdrole`)**: 맡은 사람이 바뀔 수 있다. 그래서 학습한 별칭으로 확신도가 높아져도 새 항목을 `auto` 로 보내지 않는다. legacy 경로는 확신도만 보기 때문에 BE 에서 막았다.
- **역할은 지금 학습하지 않음**(#464 리뷰 뒤 사용자 결정): AI 는 `thirdrole` 이면 역할 원문을 빼고, 문맥으로 추측한 이름(`assignee_resolved`)이 있으면 그것을 `assignee_raw` 로 보낸다(`ai/capture/handoff.py`, `ai/judge/pipeline.py`). 그래서 지금 `thirdrole` 은 배울 글자가 없거나, 있으면 AI 가 추측한 이름이다. BE 는 둘을 구분할 수 없어 추측한 이름이 확인된 별칭이 될 수 있다. AI 가 역할 원문을 보내고 추측 이름은 보내지 않게 되면 다시 넣는다. (2026-11-09 #522 로 다시 넣음, 아래 갱신)
- **모르는 `assignee_type` 이나 16자를 넘는 값**: NULL 로 저장하고 경고 로그를 남긴다. 저장 전에는 어떤 값이 와도 등록이 성공했으므로, 칸을 추가했다고 등록이 실패하게 만들지 않았다.
- **`thirdname` 학습을 둔 이유**: PR ① 이 머지되면 팀원 이름·닉네임과 님·조사는 추출 때 찾힌다. 그래도 STT 오인식("화은"), 애칭, 영어 이름처럼 이름 규칙으로 못 잡는 표현을 배우는 역할이 남는다.

## 장단점과 감수한 제약

- 승인 목록·단건 조회와 추출 조회마다 조회가 최대 2번 늘어난다(후보 항목을 찾는 `IN` 조회, 그 글자를 이미 가진 별칭을 찾는 `IN` 조회). `extraction_item.approval_id` 에는 인덱스가 없다. 지금 규모에서는 문제가 없다고 보고 마이그레이션 범위를 넓히지 않았다.
- 두 사람이 정말 같은 별칭을 써야 하는 경우는 학습되지 않는다. PM 이 수동으로 등록해야 한다.
- 1인칭 거르기는 규칙과 통째로 일치할 때만 막는다(`startswith` 로 하면 "제인"·"나연"이 막힌다). 그래서 조사 "이"를 떼면 "제"·"나"가 되는 실제 이름 "제이"·"나이"는 배우지 않는다. 못 배우는 쪽이라 해가 없고 PM 이 별칭을 직접 등록한다. 애매하면 막는 쪽으로 둔다. 이름을 막는 비용(못 배움)이 잘못된 별칭의 오배정 비용보다 싸기 때문이다.
- 한 글자 별칭은 학습해도 바로 확정 매칭되지 않는다. #463 의 찾기 규칙이 한 글자 별칭을 확정 근거로 쓰지 않아(`needs_check=True`) 담당자만 채우고 PM 확인으로 간다. 미매칭 목록에서는 PM 이 직접 등록한(`manual`·`learned`) 별칭이라 해결로 보고 뺀다(`resolved_texts`). 다듬기가 조사와 같은 끝 글자를 뗄 수 있어("민이" → "민") 한 글자가 되는 경우도 같다.
- 저장 글자를 승인에서 고칠 수 없다(`save_alias` 는 bool). 잘못 저장된 별칭은 PM 이 별칭 삭제(`DELETE /members/aliases/{id}`)로 지우고 필요하면 다시 등록한다. 수정 API 는 없다. "이상하면 PM 이 고친다"는 이 삭제 후 재등록을 뜻하며, 받아들인 제약이다.
- 다른 팀원 둘에게 같은 글자를 동시에 승인하면 둘 다 저장될 수 있다. 유니크 제약은 같은 팀원 기준이기 때문이다. 드문 경합이라 막지 않았다.
- 다듬기 규칙이 이름 끝 글자를 조사로 뗄 수 있다("민이" → "민"). 이상하게 저장되면 PM 이 고친다고 사용자와 정했다.

## 영향 범위와 재검토 조건

- 계약: `PATCH /approvals/{id}` 요청에 `save_alias` 를 추가했다. 승인 응답과 추출 조회 항목에 `alias_candidate`·`alias_text` 를 추가했다. 모두 기본값이 있어 하위 호환이다. AI 요청 모양은 바뀌지 않는다.
- DB: `extraction_item.assignee_type VARCHAR(16) NULL`.
- 다시 볼 때:
  - AI 가 역할 원문을 보내고 추측 이름은 보내지 않게 될 때. `thirdrole` 을 학습 대상에 다시 넣는다. 그때 역할을 맡은 사람이 바뀌면 이전 사람의 별칭이 남는 문제(수정 API 없음)도 함께 본다.
    - 2026-11-09 갱신(#522): AI 가 역할 원문을 보내게 되어 같은 PR 에서 `thirdrole` 을 학습 대상에 다시 넣었다. 맡은 사람이 바뀐 역할의 옛 별칭은 따로 막지 않았다. `thirdrole` 새 항목은 `auto` 로 가지 않아 PM 이 카드에서 담당자를 보고 바꿀 수 있고, 옛 별칭은 `DELETE /members/aliases/{id}` 로 지운다. AI 쪽 결정은 [0060](../../../../../ai/docs/basis_for_decision/ai/2026-11-09-0060-thirdrole-sends-original-mention.md).
  - 승인 목록이 느려질 때. `approval_id` 인덱스를 추가한다.
