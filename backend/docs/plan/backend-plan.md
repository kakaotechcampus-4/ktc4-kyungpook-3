# 백엔드 개발 계획 — 구현 현황 반영 개정안

- 기준일: 2026-10-02
- 기준 커밋: `develop@0517775`
- 문서 경로: `backend/docs/plan/backend-development-plan.md`
- 범위: 백엔드 전체 로드맵. AI·Discord는 백엔드와의 연동 계약 및 의존 작업까지 포함한다.

## 1. 계획의 기준과 마일스톤 재구성

현재 백엔드는 **회의 결과를 저장하고 태스크·승인으로 전환하는 핵심 기능이 이미 구현된 상태**다. 앞으로의 핵심 작업은 권한 보완, 실제 외부 연결, 웹 업로드, 통합 검증이다.

따라서 기존 계획에서 뒤쪽에 배치했던 태스크·승인·Notion 동기화를 앞쪽의 기존 구현 마일스톤으로 이동한다. 외부 연결과 웹 업로드는 이를 활용해 사용자 흐름을 완성하는 단계로 구분한다.

상태 표기는 다음과 같다.

- **구현됨**: 동작을 수행하는 코드가 있다.
- **부분 구현**: 경로는 있지만 스텁·권한 누락·계약 차이 등이 남아 있다.
- **미구현**: 필요한 동작을 수행하는 코드가 없다.
- **검증 대기**: 구현 유무와 별개로 실제 통합·운영 확인이 필요하다.

테스트가 존재하는 항목은 근거로 명시한다. 이번 조사에서 테스트를 실행하지 않았으므로 통과 여부나 완료율은 표시하지 않는다.

### 마일스톤 개요

| 단계 | 마일스톤 | 현재 상태 | 남은 목표 |
|---|---|---|---|
| M0 | 서버·DB·실행·검증 기반 | 구현됨 · 보완 필요 | 실행 재현성과 PostgreSQL 검증 확보 |
| M1 | 인증·워크스페이스·온보딩·권한 | 부분 구현 | 실제 사용자와 역할 기준으로 접근 통제 완결 |
| M2 | 태스크·승인·변경 이력·동기화 | 핵심 구현됨 | 기존 기능의 권한·동시성·반영 상태 보완 |
| M3 | 회의·전사·AI 결과 수신 | 핵심 구현됨 | 요약·참석자·진행 상태까지 회의록 완결 |
| M4 | Google·Discord·Notion 실제 연결 | 대부분 미구현 | 수동 DB 설정 없이 외부 서비스 연결 |
| M5 | 웹 음성 업로드·비동기 처리 | 스텁 | 업로드부터 회의록 조회까지 실제 처리 |
| M6 | 프론트·AI 통합과 계약 확정 | 검증 대기 | MSW 없이 핵심 사용자 흐름 검증 |
| M7 | 운영 배포·관찰·복구 | 부분 구현 | 실서버 시연과 장애 복구 가능 상태 |

번호는 기능 묶음과 인수 기준이다. 이미 구현된 M2·M3을 M1 완료 후 다시 개발하는 순서를 의미하지 않는다.

**남은 작업의 우선순위:** M0 검증 기준 정리 → M1 권한 보완 → M2·M3 보완과 M4 연결 병행 → M5 업로드 → M6 통합 → M7 운영 인수.

## 2. 마일스톤별 진행 상태와 세부 작업

### M0. 서버·DB·실행·검증 기반

| 세부 항목 | 상태 | 확인 내용 |
|---|---|---|
| FastAPI 라우터·응답 봉투·오류 처리 | 구현됨 | `/api/v1`, `Envelope`, 예외 핸들러 |
| PostgreSQL·SQLAlchemy·Alembic | 구현됨 | 모델·마이그레이션·로컬 DB 구성 |
| pgvector | 구현됨 | 태스크 임베딩과 유사 검색 |
| 로컬 실행·운영 Docker 구성 | 구현됨 | 개발/운영 Compose, API Dockerfile |
| 백엔드 CI | 구현됨 | pytest 및 PostgreSQL 서비스 구성 |
| 마이그레이션·실제 동시성 검증 | 보완 필요 | 기존 CI의 테스트 실행 범위 확대 필요 |
| README·프론트 계약의 최신성 | 부분 구현 | 인증·전사·온보딩 등에 오래된 설명 존재 |

**남은 작업**

- 현재 코드·OpenAPI와 문서의 차이를 정리하고 기준 커밋을 남긴다.
- 빈 DB 초기화와 기존 DB 업그레이드를 CI에서 검증한다.
- SQLite 테스트를 유지하되 잠금·경합·유일 제약은 실제 PostgreSQL 테스트로 보완한다.
- 환경변수, 워커 활성화 조건, 프록시·health 점검 경로를 정리한다.
- 전체 테스트의 기준 실행 결과를 기록한다.

**완료 기준:** 새 환경에서 설치·마이그레이션·서버 실행·테스트를 문서대로 재현할 수 있다.

### M1. 인증·워크스페이스·온보딩·권한

| 세부 항목 | 상태 | 확인 내용 |
|---|---|---|
| 이메일 가입·로그인·로그아웃·`me` | 구현됨 | 비밀번호 해시, DB 세션, 쿠키 |
| 세션 만료·워크스페이스 소속 검사 | 구현됨 | 인증 가드 테스트 존재 |
| 워크스페이스 생성·목록·상세 | 구현됨 | 생성자 PM 등록, 소속 목록 조회 |
| 온보딩 단계 저장·재개·건너뛰기 | 구현됨 | 반복 요청·PM 제한 테스트 존재 |
| 팀원·별칭·Discord ID 매핑 | 구현됨 | CRUD와 워크스페이스 범위 유일 제약 |
| 이름 정규화·계정 범위 중복 | 미구현 | 현재 전역 완전일치 검사 |
| 전체 API의 PM 권한 통일 | 부분 구현 | 온보딩에는 있으나 승인 등은 소속만 확인 |
| 일반 팀원의 확인 필요 정보 비노출 | 미구현 | 승인 조회·추출 응답에 서버 필터 필요 |
| 내부 API 서비스 인증 | 부분 구현 | 전사·유사 검색에만 적용 |

**남은 작업**

- 웹 API별로 로그인·소속·PM 권한 표를 만들고 공통 의존성으로 적용한다.
- 승인·반려·되돌리기·팀원 관리·연동 관리의 PM 제한을 서버에서 강제한다.
- 일반 팀원에게 승인 항목·개수·참조 정보가 노출되지 않도록 조회 응답을 제한한다.
- 봇/AI의 회의 생성·종료·실패·추출 등록에 서비스 인증을 적용하고 호출 클라이언트도 함께 변경한다.
- 이름 정규화와 계정 범위 중복 검사를 구현하고 동시 생성도 처리한다.
- 소프트 삭제 후 Discord 계정 재매핑 시 DB 제약과 사전 검사가 일치하도록 수정한다.
- 쿠키 설정과 동일 출처 변경 요청 검증을 로컬·운영 환경에서 확인한다.

**완료 기준:** 미로그인·비소속·일반 팀원·PM·서비스 호출자의 허용 범위가 테스트로 고정되고, 기존 온보딩 흐름이 실제 API에서 재개된다.

### M2. 태스크·승인·변경 이력·동기화

기존 계획에서 신규 개발처럼 보였던 항목 중 상당수가 이미 구현되어 있다.

| 세부 항목 | 상태 | 확인 내용 |
|---|---|---|
| 태스크 생성·목록·상세·수정 | 구현됨 | 담당자·상태·진척·시작일·마감일 |
| 변경 이력·행위자 기록 | 구현됨 | 세션의 팀원 ID 사용, 관련 테스트 존재 |
| 이력 되돌리기 | 구현됨 | 중복·최초 생성·후속 변경 충돌 차단 |
| 승인 생성·조회·승인·반려 | 구현됨 | 승인 상태 조건부 갱신 |
| AI 수정 제안의 기준값 저장 | 구현됨 | 변경 필드의 `base_values` |
| 승인 충돌·확인 후 재승인 | 구현됨 | `APPROVAL_CONFLICT`, `confirm_task_version` 테스트 |
| Notion outbox·워커 | 구현됨 | 태스크 변경과 같은 트랜잭션에 작업 저장 |
| Notion 재시도·중복 생성 방지 | 구현됨 | 타임아웃 조회·오래된 작업 복구 테스트 |
| 역할 제한·실제 동시 변경 검증 | 보완 필요 | 기능 존재와 권한·경합 완결은 별개 |
| 화면의 반영 상태와 서버 의미 일치 | 보완 필요 | 페이지 ID만으로 최신 반영 완료 판단 불가 |

**남은 작업**

- M1의 PM 권한을 태스크 쓰기·승인·되돌리기·수동 동기화 재시도에 적용한다.
- 동시 승인, 승인과 수동 수정, 되돌리기와 수정의 경합을 PostgreSQL에서 검증하고 필요한 잠금·조건부 갱신을 보완한다.
- 승인 충돌 시 승인 상태·태스크·이력·outbox가 부분 반영되지 않는지 확인한다.
- `pending / synced / failed`와 동기화 버전을 프론트 표시 기준으로 정리한다.
- 최근 반영 이력에 필요한 작업 연결·성공 시각을 제공한다.
- 연결 해제·재연결 전후의 대기·실패 작업 처리 규칙을 M4와 맞춘다.

**완료 기준:** 권한이 있는 사용자만 변경할 수 있고, 충돌·재시도에도 DB 이력과 Notion 반영 작업이 일관되게 남는다.

### M3. 회의·전사·AI 결과 수신

| 세부 항목 | 상태 | 확인 내용 |
|---|---|---|
| 회의 생성·종료·실패·상태 조회 | 구현됨 | 상태 전이와 실패 조건부 갱신 |
| 회의 목록·회의록 조회 | 구현됨 | 저장된 전사와 화자 정보 반환 |
| 전사 저장 API | 구현됨 | 서비스 인증, 배치 저장, 순번 중복 무시 |
| 화자 매핑·표시 이름 fallback | 구현됨 | 팀원 이름·Discord 표시 이름·UID |
| 전사 근거와 추출 항목 연결 | 구현됨 | Source·Evidence 모델과 테스트 |
| 추출 등록 멱등 처리 | 구현됨 | 회의 상태 선점 및 기존 결과 반환 |
| 담당자 매칭·게이트 | 구현됨 | 자동 태스크 또는 확인 필요 생성 |
| AI create/update 결과 수신 | 구현됨 | update 승인, 변경 없는 제안 제외 테스트 |
| 임베딩·유사 태스크 검색 | 구현됨 | 비동기 임베딩, 서비스 인증, pgvector 테스트 |
| 회의 요약 | 부분 구현 | 저장 컬럼·조회는 있으나 입력 경로 없음 |
| 참석자 | 부분 구현 | 발화한 팀원에서 역산 |
| 진행률·처리 완료 시각 | 부분 구현 | 발화·추출 항목 존재와 종료 시각에 의존 |

**남은 작업**

- 선택적 구조화 요약 입력을 추출 계약에 추가해 저장·조회까지 연결한다.
- 참석자 정보를 별도로 저장해 말하지 않은 참석자와 웹 업로드 참석자도 보존한다.
- 전사·추출 결과가 비어 있어도 단계 완료를 표현할 수 있도록 처리 상태를 보완한다.
- 녹음 종료와 처리 완료 시각을 구분한다.
- AI 호출 순서와 재전송 계약을 검증한다. 전사 저장과 추출 등록의 중간 실패를 포함한다.
- 기존 AI 결정대로 자동 복구 중에는 `processing`, 재시도 소진 시에는 `failed`를 유지한다.
- 로컬 음성의 화자 라벨을 Discord UID와 혼동하지 않도록 입력 어댑터를 구분한다.

**완료 기준:** 실제 AI 결과로 요약·전사·참석자·근거·태스크·승인 요청이 연결되고, 재전송해도 중복 결과가 생기지 않는다.

### M4. Google·Discord·Notion 실제 연결

| 세부 항목 | 상태 | 확인 내용 |
|---|---|---|
| Google 로그인 | 미구현 | start·callback 없음 |
| Discord·Notion OAuth | 미구현 | 연결을 생성할 API 없음 |
| 연결 조회·해제 | 부분 구현 | DB 행 존재 기준, 생성 문자열 표시 |
| 연결 끊김 상태 | 미구현 | `revoked` 표현 필요 |
| Discord 사용자 목록 | 스텁 | 고정 사용자 2명 반환 |
| 길드→워크스페이스 조회 | 미구현 | 기존 AI는 단일 설정에 의존 |
| Notion 태스크 쓰기 | 구현됨 | 토큰·대상 DB가 준비된 경우 동작 |
| Notion 대상 자동 준비·회의록 쓰기 | 미구현 | 기존 태스크 동기화와 별도 보완 필요 |

**남은 작업**

- Google 및 provider별 OAuth start·callback을 구현한다.
- 서버 관리 일회성 `state`에 사용자·워크스페이스·허용된 복귀 경로를 연결한다.
- 실제 외부 식별자·표시 이름·연결 상태를 저장한다.
- Discord 서버 목록과 사용자 목록을 실제 데이터로 연결하고 서비스용 길드 매핑 조회를 추가한다.
- Notion 저장 대상을 준비하고 기존 태스크 동기화와 결합한다.
- 회의록 반영도 영속 작업으로 처리한다. 회의록과 자동 태스크는 처리 후, 확인 필요 태스크는 승인 후 반영한다.
- 일시 장애와 권한 철회를 구분하고, 재연결 후 실패 작업을 복구한다.

**완료 기준:** 사용자가 수동 DB 조작 없이 연결을 만들고, 실제 Discord 목록과 Notion 회의록·태스크 반영을 확인한다.

### M5. 웹 음성 업로드·비동기 처리

| 세부 항목 | 상태 | 확인 내용 |
|---|---|---|
| multipart 업로드 경로·202 응답 | 부분 구현 | 회의 행 생성까지 |
| 처리 중 회의 검사 | 부분 구현 | 조회 기반 검사, 경합 방지 보완 필요 |
| 파일 저장·AI 전달 | 미구현 | TODO 상태 |
| 참석자 파싱·소속 검증·저장 | 미구현 | 입력받은 값을 사용하지 않음 |
| 용량·길이·형식 검증 | 미구현 | 오류 코드 일부만 존재 |
| Notion 연결 차단 | 미구현 | 업로드 경로 검사 없음 |
| 업로드 작업 복구·임시 파일 정리 | 미구현 | 영속 처리 흐름 필요 |

**남은 작업**

- 제목·회의 날짜·참석자를 검증하고, 제한을 적용하며 파일을 스트리밍 저장한다.
- 웹과 Discord 경로에 공통으로 적용되는 워크스페이스 처리 제한을 원자적으로 구현한다.
- 업로드 접수·파일 저장·AI 전달 상태를 영속적으로 기록해 재시작 시 복구한다.
- AI의 기존 후처리·복구 흐름을 활용하는 업로드 어댑터를 추가한다.
- 최종 성공·실패 시 임시 파일을 정리한다.
- 실패 회의는 목록에서 제외하되 상태 조회로 오류를 전달하고 처리 제한을 해제한다.

**완료 기준:** 웹 업로드가 영구 `processing`에 머무르지 않고 성공 또는 실패로 끝나며, 이후 업로드가 가능하다.

### M6. 프론트·AI 통합과 계약 확정

**현재 상태:** 각 API와 대역 테스트가 존재하지만 전체 실서비스 흐름의 완료는 확인되지 않았다.

- 프론트 계약의 오래된 스텁 설명을 현재 구현에 맞춰 갱신한다.
- 승인 충돌, 실제 전사, 온보딩 저장, Notion 비동기 상태를 DTO·mapper·MSW에 반영한다.
- 대시보드는 기존 목록 API를 조합한다. 별도 집계 API나 페이지네이션을 이번 단계에서 추가하지 않는다.
- 보드·간트·캘린더는 공통 태스크 조회 계약을 유지한다.
- 실제 API로 다음 시나리오를 검증한다.
  - 가입·로그인 → 워크스페이스 → 연결 → 팀원 매핑 → 온보딩 완료.
  - Discord 회의 또는 웹 업로드 → 처리 → 회의록.
  - 확인 필요 → 승인 → Notion 반영.
  - 승인 충돌 → 변경 확인 → 재승인.
  - 변경 이력 되돌리기 → Notion 재반영.
  - 일반 팀원의 읽기 전용 접근과 확인 필요 정보 비노출.

**완료 기준:** 핵심 흐름이 MSW 없이 동작하고, 외부 서비스 대역을 사용하는 자동 회귀 테스트가 마련된다.

### M7. 운영 배포·관찰·복구

| 세부 항목 | 상태 |
|---|---|
| API·DB 운영 컨테이너 구성 | 구현됨 |
| API 내부 Notion·임베딩 워커 | 구현됨 |
| AI 봇·별도 워커 모드 | AI 영역에 구현됨 |
| 전체 서비스 배포 결합 | 검증 대기 |
| HTTPS·OAuth 운영 주소 | 환경 확인 필요 |
| DB 백업·복원·배포 복귀 절차 | 문서화·검증 필요 |
| 장기 처리·실패 작업·디스크 관찰 | 보완 필요 |

**남은 작업**

- 단일 EC2에서 프록시·API·DB·봇·AI 워커의 실행 경계를 확정한다.
- 현재 구조에서는 API 프로세스 1개를 유지한다. AI는 별도 worker 모드를 기본 제안으로 삼고 메모리를 실측한다.
- CI 산출물 배치, 환경변수, 마이그레이션, 재시작과 이전 버전 복귀 절차를 작성한다.
- DB 백업·복원을 검증한다.
- 장기 `processing`, Notion 실패 작업, 워커 heartbeat, 디스크 사용량을 관찰한다.
- 민감한 본문 대신 요청·회의·작업 ID로 장애를 추적한다.
- 실제 계정의 OAuth·Discord·STT·Notion 연결을 최종 검증한다.

**완료 기준:** 배포와 재시작 후 데이터·작업이 보존되고, 장애 복구 절차를 다른 팀원이 재현할 수 있다.

## 3. 권장 기본값과 범위

아래는 기존 제품 결정이 아닌 이 계획의 제안이다. 구현 착수 전에 결정 기록에 명시한다.

| 미정 항목 | 권장 기본값 | 적용 시점 |
|---|---|---|
| 웹 업로드·태스크 변경 권한 | PM 전용 | M1 |
| 워크스페이스 이름 중복 범위 | 요청 사용자가 소속된 워크스페이스 | M1 |
| 삭제 팀원 재매핑 | Discord 연결을 해제하고 과거 근거는 보존 | M1 |
| Google 기존 계정 연결 | 이메일만으로 자동 병합하지 않음 | M4 |
| Discord 길드 연결 | 길드당 활성 워크스페이스 1개 | M4 |
| Notion 저장 대상 | 공유된 부모 페이지 아래 서비스용 영역 준비 | M4 |
| 웹 업로드 한도 | 파일 1개, 100MiB·60분, 서버 설정으로 관리 | M5 |
| 음성 보존 | 처리 중 임시 보관, 최종 종료 후 삭제 | M5 |

| 운영 AI 실행 | 별도 worker 모드, 메모리 상한은 실측 | M7 |

Notion 저장 대상 준비 방식은 M4 첫 작업에서 공급자 API·권한으로 가능한지 확인한다. 제한이 있으면 연결 계약을 먼저 수정한다.

메시지·리마인더 발송, 범용 페이지네이션, 별도 대시보드 집계, 다중 서버·다중 워커 확장은 후속 범위다.

## 4. 인터페이스 변경과 완료 관리

### 주요 인터페이스 변경

- 기존 내부 API에 서비스 인증 추가.
- Google·Discord·Notion OAuth 및 길드 매핑 조회 추가.
- 회의 요약·참석자·처리 단계·처리 완료 시각 보완.
- 연동 상태와 Notion 반영 상태·성공 시각 보완.
- 업로드 검증·실패 응답 구체화.
- 역할에 따른 승인·추출 조회 응답 제한.

선택 필드 추가로 기존 클라이언트와의 호환성을 유지한다. 인증 강화와 응답 노출 변경은 AI·프론트 수정과 배포 순서를 함께 기록한다.

### 검증과 상태 갱신

- 기존 테스트는 회귀 기준으로 활용한다. 온보딩·전사·승인 충돌·행위자 기록·Notion·임베딩 테스트를 신규 작업으로 다시 세지 않는다.
- 새 테스트는 실제로 남은 권한·동시성·외부 연결·복구 경계를 대상으로 추가한다.
- 마일스톤별로 `구현 상태`, `자동 테스트 결과`, `실제 연동 결과`를 분리해 기록한다.
- 완료 표시는 코드 존재만으로 올리지 않고 해당 마일스톤의 완료 기준을 만족한 뒤 갱신한다.
- 문서에는 근거 PR·커밋과 검증일을 함께 남긴다.
