# 승인 카드를 본 뒤 내용이 바뀌었으면 승인·반려를 409 로 막는다

- 기록일: 2026-11-08
- 관련 마일스톤: M6. 요청은 이슈 #535(설계 확정 댓글 2026-11-08), FE 요청은 #512(hotpringles 2026-11-08 답), 앞선 기록은 [다른 회의의 같은 새 항목을 승인 대기 카드에 합친다](2026-11-07-pending-merge.md)

## 문제와 제약

#533 으로 다른 회의의 항목이 승인 대기 task_create 카드에 합쳐질 수 있게 됐다. PM 이 카드를 연 뒤 승인하기 전에 합쳐지면 다음 두 문제가 생긴다.

- task 값: FE 의 열린 승인 상세 폼은 다시 조회해도 고치지 않은 칸을 갱신하지 않는다. 그래서 PM 이 본 값과 다른 값으로 task 가 만들어질 수 있다. FE 가 승인 직전에 다시 조회해도 그 사이에 합쳐질 수 있어 서버 검사가 필요하다(#512 FE 답).
- 별칭: 담당자를 말한 항목이 합쳐지면 담당 항목이 바뀐다. 그러면 save_alias=true 승인 때 PM 이 보지 못한 글자가 확인된 별칭으로 저장될 수 있다(#535).

제약은 다음과 같다.

- 지금 FE 는 버전을 보내지 않는다. 하위 호환이어야 BE 를 먼저 배포할 수 있다.
- 기존 409 APPROVAL_CONFLICT 는 task_update 전용이고, FE 는 그 details 를 task 충돌로 읽는다.

## 실제 검토한 선택지

| 결정 | 선택지 | 결과 |
|---|---|---|
| #535 를 어떻게 다룰지 | payload 버전 409 에 흡수 / alias_text 도 따로 받음 / #535 만 하고 409 는 안 함 | 흡수. 담당 항목을 바꾸는 합치기는 payload 를 반드시 바꾸고, 별칭 글자는 payload 와 바뀌지 않는 추출 항목 행에서만 정해진다. 그래서 버전이 맞으면 글자도 맞다 |
| 버전 표현 | payload 저장 문자열 해시 / 정수 컬럼 + 합칠 때 +1 / updated_at | 해시(sha256 앞 16자). 컬럼·마이그레이션이 없고, payload 를 쓰는 코드가 늘어도 빠뜨릴 일이 없다 |
| 반려도 검사할지 | 보내면 승인·반려 모두 / 승인만 | 모두. 반려는 합쳐진 다른 회의 항목까지 반려한다 |
| 409 본문 | 버전만 / 카드 전체 | 버전만(`approval_id`, 지금 `payload_version`). 서버는 PM 이 본 내용을 몰라 바뀐 칸을 계산할 수 없다. FE 가 상세를 다시 받아 비교한다 |
| 필드 필수 여부 | 선택 / 필수 | 선택. FE 반영 뒤 필수로 바꿀지 따로 본다 |
| 에러 코드 | APPROVAL_CONFLICT 재사용 / 새 코드 | 새 코드 APPROVAL_CHANGED. FE 가 둘을 구분해 달라고 했다 |

사용자가 설계 초안의 추천안을 모두 골랐다(2026-11-08).

## 선택과 이유

- 승인 목록·상세와 POST·PATCH 응답 최상위에 `payload_version` 이 실린다. task_create 카드만 값이 있고(처리된 카드도 계산), 그 밖은 null 이다.
- PATCH 요청에 `payload_version` 이 오면, 조건부 UPDATE 와 카드 다시 읽기 뒤에 비교한다. 비교는 task 반영 전에 한다. 다르면 되돌리고 409 APPROVAL_CHANGED 를 낸다. 카드는 대기로 남고 task·추출 항목 task_id·별칭은 생기지 않는다.
- 이미 처리된 카드는 APPROVAL_ALREADY_RESOLVED 가 먼저다. task_create 가 아닌 카드에 온 값은 무시한다.
- PostgreSQL 에서는 조건부 UPDATE 가 카드 행을 잠그고, 합치기는 같은 행을 FOR UPDATE 로 기다린다. 그래서 비교한 뒤 커밋할 때까지 payload 가 바뀌지 않는다. 잠금을 새로 더하지 않았다.

## 장단점과 감수한 제약

- FE 가 보내기 전까지는 보호 효과가 없다.
- 버전은 같은지만 비교하는 불투명한 값이다. 내용이 같아도 저장 형식만 바뀌면 값이 달라질 수 있다. 이 경우는 막는 쪽으로 틀린다.
- 담당자 합치기 때 #535 원안은 "별칭만 건너뛰고 승인은 성공"이었는데, 이 안은 승인 전체가 409 다. task 값도 PM 이 못 본 값이라 다시 보는 쪽으로 맞췄다.
- 추출 조회(GET /extractions/{id}) 응답에는 버전이 없다. 회의록 화면에서 승인하려면 승인 상세에서 값을 받아야 한다.

## 영향 범위와 재검토 조건

- 코드: `app/api/approvals.py`(`_payload_version`, 응답, 비교), `app/schemas/approval.py`, `app/core/errors.py`. 모델·마이그레이션은 바뀌지 않았다.
- 계약: FE 계약이다. 응답·요청에 `payload_version` 이 생기고, 409 `APPROVAL_CHANGED` 가 추가된다. 경로는 그대로다. AI 계약은 바뀌지 않았다.
- 재검토: FE 반영이 배포되면 task_create 승인에서 필수로 바꿀지 본다. 대기 중에 payload 를 바꾸는 다른 경로가 생기면 그 경로도 자동으로 잡힌다. 다만 PM 에게 보이지 않는 변경이면 불필요한 409 가 될 수 있다.
