# 답장 판단 재시도 상한을 숫자 대신 판단 창으로 지킨다

- 기록일: 2026-11-08
- 관련 마일스톤: M6. 요청은 이슈 #548(설계 확정 댓글 2026-11-08), 출처는 PR #382 멘토 리뷰(replies.py:163 스레드)

## 문제와 제약

답장 판단 claim 은 맡길 때마다 attempt 를 올리기만 하고 숫자 상한이 없다. 멘토 리뷰는 BE 가 어떤 판단 결과에 5xx 를 계속 내면 봇이 리스(3분)마다 같은 답장을 다시 받아 LLM 을 다시 부르고, 같은 대화의 뒤 답장도 막힌다고 짚었다.

코드를 다시 보니 시간 상한은 이미 있었다. 답장을 받은 뒤(PM 이 고르면 고른 뒤) 10분(JUDGE_WINDOW)이 지나면 스케줄러가 판단을 timed_out 으로 닫고 PM 에게 reply_unjudged 를 보낸다. 그래서 한 차례에 맡기는 횟수는 최대 4회였다. 남은 빈틈은 다음과 같다.

- 상한이 스케줄러 틱에 달려 있다. 스케줄러를 끄거나 그 행의 닫기에서 예외가 나면 상한이 없다.
- 10분이 지나도 틱 전이면 claim 이 한 번 더 내준다.

제약은 다음과 같다.

- API 모양·DB·마이그레이션을 바꾸지 않는다.
- PM 이 고른 재판단은 attempt 를 초기화하지 않는다. 고르기 전 판단의 재전송을 attempt 로 거르기 때문이다.

## 실제 검토한 선택지

| 결정 | 선택지 | 결과 |
|---|---|---|
| 상한 방식 | 문서·테스트만 / claim 이 판단 창을 직접 봄 / 숫자 attempt 상한 N | 판단 창을 직접 봄. 숫자 상한은 PM 이 고른 재판단이 앞 차례 횟수를 이어받아 기회를 덜 받고, 차례별로 세려면 컬럼과 마이그레이션이 든다. N=3 이면 9분이라 10분 창과 얻는 것도 거의 없다 |
| 실패 상태 | 기존 timed_out / 새 상태 | 기존 timed_out. 뜻이 같고 늦은 결과 처리와 FE 표시가 그대로 맞는다 |
| PM 재요청 | 새 API / 없음 | 없음. 알림으로 대화를 열어 직접 처리한다 |
| AI 5xx 처리 | 리스에 맡김 / 바로 실패 보고 | 리스에 맡김. 배포 재시작 중 502 같은 일시 오류에 멀쩡한 판단이 실패로 바뀌지 않게 한다 |

사용자가 설계 초안의 추천안을 모두 골랐다(2026-11-08). 이 PR 은 사용자 지시로 ai/ 파일도 함께 고쳤고 머지 전에 AI 담당 승인을 받는다.

## 선택과 이유

- claim 루프는 대화를 seen 에 넣기 전에 창을 본다. 창이 지난 행은 savepoint 안에서 기존 expire 로 닫고 seen 에 넣지 않아, 같은 claim 에서 같은 대화의 다음 행으로 넘어간다.
- 닫기가 실패하면 savepoint 만 되돌리고 로그를 남긴 뒤 그 대화를 seen 에 넣는다. 그래서 다른 대화의 판단은 멈추지 않고, 앞 답장을 건너뛴 채 뒤 답장이 먼저 나가지도 않는다.
- 알림은 expire 의 기존 중복 방지를 쓰므로, 스케줄러와 claim 중 먼저 본 쪽만 알린다.
- 봇은 동작을 바꾸지 않고 설명과 고정 테스트만 더했다.

## 장단점과 감수한 제약

- claim 트랜잭션이 알림(푸시 행 포함)을 쓴다. 알림이 계속 실패하면 claim 할 때마다 그 행을 다시 시도하며 로그가 쌓인다. 스케줄러도 같은 동작이다.
- savepoint 경로는 sqlite 로만 돌려 봤다. PostgreSQL 에서는 CI 에서 처음 돈다.
- 숫자로 된 attempt 상한은 없다. 문서에는 "한 차례 최대 4회(10분 ÷ 3분 리스)"로 적었다.
