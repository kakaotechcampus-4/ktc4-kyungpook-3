## 2026-11-09 추가: #575 전체 계정 탈퇴 구현과 검증

사용자가 첫 준비 단위 이후 남은 구현을 진행하도록 요청했다. 아래는 준비 단위와 구분되는 전체 기능의 결과다. 별도 Herdr 정책 탭에서 사용자는 계정 접근을 즉시 종료하고, AI 정리가 늦으면 `개인정보 정리 중`, 실제 확인 후 `탈퇴 완료`를 표시하도록 승인했다. 취소 유예기간 없이 즉시 새 계정 가입을 허용한다. 앞 절의 미전달 질문은 이 후속 결정으로 해소됐다. 비어 있는 M1 계획에 완료조건을 만들거나 마일스톤 전체 완료로 판정하지 않는다.

### 실제 구현

- `app/services/account_withdrawal.py`와 `app/api/withdrawal.py`에 계획 조회, 본인 탈퇴와 인증 없이 키로 읽는 정리 영수증을 구현했다. 최초 요청은 현재 계정과 expected 계정 ID를 비교한다. 모든 공간의 마지막 PM 조건을 재검사하며 하나라도 막히면 아무 공간도 변경하지 않는다. 활성 Discord 전용 팀원도 단독 여부에 포함한다.
- 계정·모든 세션·비밀번호 재설정·푸시와 개인 프로필·연결·별칭을 삭제한다. 남은 공동 기록은 비식별 Member를 참조한다. 단독 활성 공간은 업무 내용을 지우고 파일 정리가 끝나면 임시 식별 행도 삭제한다. 같은 이메일·카카오 재가입은 새 User와 새 초대만 사용한다.
- 독립 `PrivacyCleanup`에 backend·AI 완료를 따로 기록한다. 기존 파일 정리 워커가 backend 삭제를 재시도하고, AI는 실제 로컬 사본 정리 후 임대 토큰으로 확인한다. 두 완료가 교차해도 최신 행 잠금으로 최종 삭제를 판정한다. 세션 종료는 소켓 폐기와 송수신 재검사로 반영한다.
- `identity_epoch`로 탈퇴 이전 명단·추론 결과의 늦은 저장을 거절한다. AI는 계산 시작 시의 세대를 유지한다. 필드별 담당자·발화자 소유와 알림의 thread·bundle·watch·reply 연결로 구조화 개인정보를 정리하며 임의 본문을 이름 문자열로 치환하지 않는다.
- 명시적인 `include_withdrawn=true` 조회만 기록용 익명 Member를 포함한다. 새 담당자·초대·재촉 목록은 활성 명단을 유지한다. 웹 화면·PM 이전·응답 유실 재시도·영수증 복원은 [FE 결과](../../../../frontend/docs/issues/575-account-withdrawal/result.md)에 있다.

스키마 head는 `e575b02d8a31`이며 익명 주체의 `e575a01c9d42` 다음이다. 공개 요청·오류는 [FE 대표 계약](../../../../frontend/docs/contracts/frontend-api-contract.md#계정-탈퇴와-정리-상태-575-2026-11-09), 정리 claim·ack와 세대는 [BE–AI 계약](../../contracts/backend-ai-contract.md#계정-탈퇴의-개인정보-정리-575-2026-11-09), 선택 근거는 [정리 프로토콜 결정](basis-for-decision/2026-11-09-withdrawal-cleanup-protocol.md)에 기록했다.

실제 HTTPS 여정은 마지막 PM의 전체 원자성, 계정 교체 거절, 다른 기기까지 세션 401, WSS 4401, 옛 세대 409와 최신 세대 저장, 같은 이메일 새 User·새 초대, 옛 영수증 재요청 후 새 로그인 유지까지 확인했다. Windows 파일 잠금으로 삭제를 실패시킨 뒤 해제해 실제 워커의 재시도를 확인했다. 실제 AI 정리 함수가 공유 음성 바이트와 동명이인 자료·같은 guild의 새 공간을 보존하고, 옛 capture 재생성을 막으며 단독 capture를 삭제하는지도 확인했다. STT·외부 모델 추론은 이 fixture 검증에 포함하지 않았다.

독립 리뷰는 서비스가 만든 bundle 알림의 이름 사본, 담당자와 발화자가 다른 JSON의 잘못된 담당자 정리, AI judge의 raw 발화자 ID 누락을 실행으로 재현했다. `7a186358`에서 수정하고 root와 별도 검증자가 다시 실행했다. 별도 검증은 SQLite·PostgreSQL 반례 4, 인접 backend 12, AI 3 통과이며 새로 입증한 결함은 없었다. 사용 가능한 GPT 계열 내 독립 검증이며 교차 모델 계열 검토로 표현하지 않는다. 전용 deslop·Comment Sicko 도구는 없어 실행했다고 주장하지 않는다.

수정 이전의 광범위 SQLite 실행은 2,810 통과, 1,901 건너뜀이었다. 이 수치를 최종 코드 전체 회귀로 대체하지 않는다. Windows의 POSIX 신호·resource 모듈 제약으로 전체 backend·AI Linux 테스트는 CI에서 추가 확인해야 한다. AI 영향 범위 실행과 전체 collection 실패를 구분한다.

## 2026-11-09 추가: #584 CI 동시성 회귀 수정

사용자가 CI 실패 수정과 병합을 요청했다. 최초 Linux backend CI는 4,757 통과·3 실패·53 건너뜀이었다. 승인·합치기 동시성 두 건과 답장 제출·만료 교착 한 건을 확인했다. 최신 develop `a6e9ea68`은 일반 merge로 반영했으며 응답 검증과 탈퇴 계약 두 절을 모두 보존했다.

- 승인 API는 PM 권한 검사에서 공간 잠금을 기다린 뒤, 미리 읽었던 카드 객체를 갱신하지 않아 `APPROVAL_CHANGED`를 잘못 반환했다. 잠금 직후 `db.refresh(target)`으로 최신 payload를 기준 삼는다. 클라이언트가 명시한 과거 payload_version의 409 검사는 유지한다.
- 제출은 Workspace → ReplyJudgment 순서였으나 만료는 ReplyJudgment를 먼저 잠그고 알림 INSERT의 Workspace FK를 기다렸다. 만료도 공간을 먼저 잠가 순서를 맞췄다. 내부 만료 작업은 AI 결과 제출과 달리 개인정보 세대 헤더를 요구하지 않는다.
- 승인 합치기 테스트는 공간 잠금 이전에 두 요청을 겹치도록 관측 지점을 옮겼다. 두 항목의 보존·최신 마감 반영·명시 버전 충돌 검사는 유지했다. 잠금 범위를 넓게 완화하거나 타임아웃을 늘려 통과시키지 않았다.

기존 코드에서 승인 두 실패를 root와 독립 검토자가 각각 재현했다. 자연 경합에 의존하던 답장 교착은 실제 공간 잠금과 `pg_blocking_pids`로 순서를 고정한 회귀를 추가했다. 수정 전에는 실제 `DeadlockDetected`로 실패했고 수정 후에는 제출만 반영되고 불필요한 만료 알림이 생기지 않았다. 재현 테스트는 `8ac09e4a`에 먼저 커밋했다.

수정 작성자의 실제 PostgreSQL 핵심 검사는 6 통과·SQLite 변형 2 건너뜀이며, root도 같은 반례의 수정 전 출력을 별도로 확인했다. Ruff는 통과했다. 확대 회귀·독립 실행과 Linux 전체 CI의 최종 결과는 [PR #584](https://github.com/kakaotechcampus-4/ktc4-kyungpook-3/pull/584)에 연결한다. 이 절의 핵심 검사만으로 전체 CI 성공이나 병합을 미리 판정하지 않는다.
