# 비밀번호 재설정 메일에 전체 상한과 IP 상한을 둔다

- 기록일: 2026-11-08
- 관련 마일스톤: M1(비밀번호 재설정·로그인 제한과 같은 마일스톤). 요청은 이슈 #550(설계 확정·보충 댓글 2026-11-08). 앞선 기록은 [비밀번호 재설정](2026-11-05-password-reset.md), [로그인 제한](2026-11-06-login-rate-limit.md)

## 문제와 제약

재설정 메일(#356)은 2026-11-08 운영에서 실제 발송을 확인했다(#451). 발송 제한은 계정마다 60초 1번·1시간 5번뿐이라, 가입된 주소 여러 개로 요청을 돌리면 팀 Gmail 의 하루 발송 한도(약 500통)가 바닥나고 같은 계정을 쓰는 다른 메일도 함께 막힌다.

제약은 다음과 같다.

- 상한에 걸려도 응답은 지금처럼 200 `{}` 로 같아야 한다. 가입 여부가 드러나면 안 된다.
- 모델·마이그레이션·계약을 바꾸지 않는다.
- 운영은 단일 프로세스(`--workers 1`)다.

## 실제 검토한 선택지

| 질문 | 선택지 | 결정 |
|---|---|---|
| 전체 상한 저장 | 재설정 토큰 테이블의 지난 1시간 발급 수(DB) / 메모리 카운터 | DB. 실제 발송 기록이라 재시작해도 풀리지 않고 마이그레이션이 없다 |
| 가입 코드(#454)와 합칠지 | 한 예산을 같이 씀 / 따로 둠 | 따로. 재설정 쪽 공격이 가입을 막지 않고, 머지되지 않은 #454 에 묶이지 않는다 |
| #454 상한 조정 | 20 → 15 로 낮춰 합계를 시간당 20통에 맞춤 / #454 그대로 | #454 그대로(사용자 결정). 아래 감수 사항 |
| IP 상한 저장 | 메모리(로그인 제한과 같은 방식) / 토큰 행·별도 테이블에 IP 저장 | 메모리. DB 저장은 모델·마이그레이션이 필요하고 없는 이메일 요청도 행을 써야 해 공격 중 DB 쓰기가 늘어난다 |
| 수치 | 전체 시간당 5통·IP 시간당 5번 / 전체 10통·IP 5번 / 가입 12 + 재설정 8 로 #454 와 합계를 나눔 | 전체 10통·IP 5번. 처음에는 5·5 로 정했으나, 전체가 IP 상한과 같으면 공인 IP 하나로 전체 예산을 다 써 다른 사람의 재설정을 막을 수 있다(PR #559 hwnv 리뷰). 전체를 IP 상한의 두 배로 두어 최소 공인 IP 둘을 돌려야 하게 했다. 합계를 나누는 안은 이미 머지된 #454 상한을 바꿔야 해 고르지 않았다(사용자 결정, 2026-11-09). IP 상한 5는 데모 규모에서 실제 재설정이 하루 몇 건이고 계정별 시간당 한도와 같은 값이라 그대로 둔다 |
| 막혔을 때 | 같은 200 + 로그 / 429 | 같은 200 + 로그. 가입 여부를 드러내지 않는다. FE 안내도 바꾸지 않는다 |

사용자가 설계 초안의 추천안을 모두 골랐고, #454 상한 조정 요청은 하지 않기로 따로 정했다(2026-11-08).

## 선택과 이유

- 순서: 메일 설정 503 → IP 상한(메모리, 첫 DB 쿼리 전) → 전체 상한(DB, 사용자 조회 전) → 기존 계정별 제한과 발급. 막힌 동안에는 있는 이메일과 없는 이메일이 같은 경로를 탄다.
- IP 키는 로그인 제한의 `client_ip_key` 를 그대로 쓴다. 사설 주소와 해석할 수 없는 값은 IP 상한을 건너뛴다. 가입 여부와 상관없이 모든 요청을 세고, 막힌 요청은 세지 않는다.
- 전체 상한은 쓰거나 무효가 된 토큰도 센다. 실제로 보낸 메일 수이기 때문이다. 없는 이메일 요청은 토큰을 만들지 않으므로 예산을 쓰지 않는다.
- 막혀도 이전 링크는 무효로 바꾸지 않는다.
- 로그는 이유(`ip`·`global`)와 IP 키만 남기고 이메일 원문은 남기지 않는다.

## 장단점과 감수한 제약

- Gmail 합계: #454 의 가입 코드 전체 상한(시간당 20통)과 따로라, 최악의 경우 합계 시간당 30통(하루 720통)으로 약 500통을 넘을 수 있다. 공격자가 두 경로를 24시간 내내 채워야 하는 경우라 감수한다.
- 전체 상한은 서로 다른 사용자의 동시 요청을 줄 세우지 않아 몇 통 넘을 수 있다.
- 전체 상한은 공인 IP 여러 개로 채울 수 있다. 공격자는 계정 없이 가입된 이메일(남의 주소여도 된다)만 알면 되고, IP 둘에서 각각 5번씩 요청하면 전체 10통을 다 써 매시간 다른 사용자의 재설정을 막는다(응답은 200 이라 메일만 오지 않는다). DB 집계라 재시작으로도 풀리지 않는다. IP 하나로는 채우지 못하게 한 것까지가 이 PR 의 대응이고, 메일 한도를 지키는 대가로 나머지는 감수한다. `reason=global` 로그와 IP 키(`reason=ip` 로그)로 알아챈 뒤 남의 주소로 요청하는 IP 를 막거나(계정이 아니라 IP 가 대상이다) 상한을 올려 대응한다(최종 리뷰, PR #559 hwnv 리뷰).
- IP 카운터가 5만 개로 차고 만료된 항목이 없으면 잠금 안에서 정렬해 지운다. 로그인 제한과 같은 방식이다.
- `created_at` 인덱스가 없어 전체 집계는 표를 훑는다. 지금 규모에서는 문제가 아니다.
- IP 카운터는 재시작하면 풀리고, 프로세스가 둘 이상이면 따로 쌓인다(로그인 제한과 같은 전제).
- 같은 공인 IP(교육장 등)에서 1시간에 5번을 넘으면 그 IP 의 재설정 요청이 모두 막힌다. 급하면 재시작으로 푼다.
- 운영 프록시 뒤의 클라이언트 IP 해석(XFF)은 로그인 제한 기록의 프록시 위험과 같고 서버 확인은 아직 하지 않았다.
- 카카오 연결 알림 메일(#454, 상한 없음)은 범위 밖이다. 실제 카카오 계정이 있어야 보낼 수 있어 공격 비용이 크다.

## 영향 범위와 재검토 조건

- 코드: `app/services/password_reset.py`(`GLOBAL_HOURLY_LIMIT`), `app/services/password_reset_limit.py`(신규), `app/api/auth.py`(요청 경로), `tests/conftest.py`. 모델·마이그레이션·에러 코드·계약 변경 없음.
- 재검토: `reason=global` 로그가 반복될 때(전체 상한을 한 사람이 채우는 경우), 실제로 Gmail 한도에 닿을 때(그때 #454 상한을 낮추거나 두 메일을 한 예산으로 묶는다), `--workers` 를 늘릴 때, 재설정 요청이 많아져 전체 집계가 느려질 때(`created_at` 인덱스).
