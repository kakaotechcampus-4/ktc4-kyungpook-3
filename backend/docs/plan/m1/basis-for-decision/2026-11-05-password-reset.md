# 비밀번호 재설정: 메일 발송·토큰·요청 제한 방식

- 기록일: 2026-11-05
- 관련 마일스톤: M1(인증). 운영 메일 설정은 M7(운영 배포) 시점에 한다.
- 관련 이슈: #356 (BE 제안 2026-11-04, FE 답변 2026-11-04, 설계 확정 댓글 2026-11-05)

## 문제와 제약

- 제품 결정 D-006 이 최종 배포 전에 비밀번호 재설정을 구현하도록 정했다. BE 에는 메일을 보내는 코드와 웹 주소 설정이 없었다.
- 카테캠 AWS 계정은 IAM 사용자를 만들 수 없고, 서비스 도메인이 DuckDNS 라 SES·Resend 발신 도메인 인증이 어렵다(#356 BE 제안).
- 가입하지 않은 이메일인지 응답으로 드러나면 안 된다. 토큰 원문은 DB·로그에 남기지 않는다.
- 운영은 uvicorn 프로세스 하나(`--workers 1`)이고, 기존 백그라운드 일은 lifespan 워커와 `BackgroundTasks` 두 방식이 있다.
- BE 에는 비밀번호 규칙이 없었다(`app/schemas/auth.py` 의 `password: str`). FE 화면만 8자 이상·숫자 포함을 검사했다.

## 실제 검토한 선택지

설계 초안과 사용자 확정(2026-11-05)에서 비교한 것이다.

| 결정 | 선택지 | 결과 |
|---|---|---|
| 메일 서비스 | Gmail SMTP(앱 비밀번호) / SES·Resend | Gmail SMTP. 환경변수만 바꾸면 다른 SMTP 로 옮길 수 있다 |
| 발송 방식 | 응답 뒤 `BackgroundTasks` + 메모리 재시도 / 메일 전용 스레드 + 메모리 재시도 / 발송 대기열 테이블 + 워커 | 메일 전용 스레드 2개(`mailer._executor`). 처음엔 `BackgroundTasks` 로 정했지만, SMTP 가 응답하지 않으면 재시도(시도마다 timeout 10초에 대기 2·4·8초라 1분 가까이)가 API 스레드 풀을 물고 있어 로그인 같은 다른 요청까지 막혀 바꿨다(PR #398 리뷰, dw021213). 대기열 테이블은 메일 본문(토큰 원문)을 DB 에 둬야 해서 해시만 저장한다는 합의를 깬다 |
| 요청 제한 저장 | 토큰 테이블의 발급 기록 / 별도 제한 테이블(이메일·IP) / 프로세스 메모리 | 토큰 테이블. 메모리는 재시작에 풀리고, 별도 테이블은 합의 범위 밖이다 |
| 링크 주소 | 새 환경변수 `APP_BASE_URL` / 요청 Host 헤더 / 기존 `NOTION_REDIRECT_URI` 에서 잘라 쓰기 | `APP_BASE_URL`. Host 헤더는 공격자 도메인으로 가는 재설정 링크를 만들 수 있다 |
| verify 응답 | 만료 시각만 / 가린 이메일 추가(FE 요청) | 가린 이메일 추가. 토큰을 가진 사람에게만 가는 값이다 |
| 회원가입 규칙 | 같은 규칙 적용 / 재설정에만 적용 | 같이 적용. API 를 직접 불러 약한 비밀번호로 가입하는 우회를 막는다 |
| 이메일 찾기 | 정확 일치(로그인과 같음) / 대소문자 무시 | 정확 일치. 재설정만 대소문자를 무시하면 결국 로그인에서 막힌다 |

## 선택과 이유

- 토큰은 `secrets.token_urlsafe(32)`, 저장은 sha256 hex. 엔트로피가 충분해 느린 해시는 쓰지 않았다. 30분, 1회용.
- confirm 은 `used_at·invalidated_at 이 비었고 만료 전` 조건의 UPDATE 가 한 행을 바꿨을 때만 비밀번호를 바꾸고 세션을 지운다. 같은 토큰으로 동시에 불러도 하나만 성공한다.
- 새 토큰을 실제로 발급할 때만 이전 미사용 토큰을 무효로 한다. 제한에 걸려 보내지 않을 때 이전 링크까지 죽이면 쓸 수 있는 링크가 하나도 남지 않는다.
- 요청 제한은 계정마다 60초에 1번, 1시간에 5번. 무효가 된 토큰 행도 지우지 않고 세며, 7일 지난 행은 그 계정이 요청할 때 정리한다. 동시 요청은 사용자 행을 `FOR UPDATE` 로 읽어 줄 세운다(PostgreSQL).
- 메일 설정이 없으면 이메일을 보기 전에 503 `MAIL_UNAVAILABLE` 을 준다. 설정이 있으면 가입 여부·제한 여부와 상관없이 같은 200 이다.
- 발송은 첫 시도 뒤 2·4·8초 간격으로 3번 더. 최종 실패 로그에는 user_id 와 마지막 예외의 종류·메시지를 남긴다(SMTP 인증 실패 같은 원인을 보려고, PR #398 리뷰). 본문(토큰)과 traceback 은 남기지 않는다. 수신 거부(`SMTPRecipientsRefused`)는 메시지에 받는 사람 이메일이 그대로 들어 종류만 남긴다(PR #398 리뷰, hwnv).
- 로그인과 confirm 의 순서: confirm 은 사용자 행을 `FOR UPDATE` 로 잠근 채 비밀번호를 바꾸고 세션을 지운다. 로그인은 비밀번호 검사(PBKDF2 26만 회, 약 0.2초)를 잠금 없이 하고, 세션을 넣기 직전에만 사용자 행을 `FOR SHARE` 로 다시 읽어 해시가 그대로인지 본다. 다르면 401 이다. 처음에는 검사 내내 공유 잠금을 잡았는데, PostgreSQL 은 대기 중인 배타 잠금이 있어도 새 공유 잠금을 주므로 로그인이 계속 겹치면 confirm·request 가 끝없이 밀리고 기다리는 요청마다 DB 연결을 물고 있어 바꿨다(PR #398 리뷰, hwnv). 잠금 없이 해시만 읽으면 confirm 이 끝난 뒤 옛 비밀번호 세션이 들어가 7일 동안 남는다.

## 장단점과 감수한 제약

- 재시도 중 서버가 재시작되면 그 메일은 사라진다. 사용자가 다시 요청해서 회복한다.
- 가입한 이메일은 DB 쓰기가 있어 응답 시간이 미가입 이메일과 조금 다르다. 상태 코드와 본문은 같다.
- 사용자 행 잠금은 sqlite 에서 효과가 없어 동시 요청 경쟁은 테스트로 검증하지 못했다. 로그인 잠금 문장은 PostgreSQL 로 컴파일한 SQL 로, 검사 도중 비밀번호가 바뀐 경우는 해시 재확인 테스트로 확인한다.
- 운영은 프로세스 하나에 메일 스레드 2개라, 메일이 몰리면 늦게 나갈 뿐 API 는 막히지 않는다.
- Gmail 하루 발송 한도(약 500통)와 스팸함 분류는 데모 규모에서 감수한다. FE 가 스팸함 확인 안내를 넣는다.
- 회원가입은 약한 비밀번호와 이미 있는 이메일이 함께 오면 409 대신 400 을 준다.

## 영향 범위와 재검토 조건

- 코드: `app/api/auth.py`, `app/schemas/auth.py`, `app/services/passwords.py`, `app/services/mailer.py`, `app/services/password_reset.py`, `app/models/models.py`(`PasswordResetToken`), `app/core/errors.py`, 마이그레이션 `a7c3e91d5b24`.
- 운영: 머지·배포 뒤 팀 Gmail 을 만들어 `.env` 에 `SMTP_*`·`APP_BASE_URL` 을 넣는다. 그전에는 request 가 503 이다. 설정과 실제 메일 확인은 아직 하지 않았다.
- 재검토: 발송량이 Gmail 한도에 가까워지거나 스팸 분류가 잦으면 발신 도메인 인증이 되는 서비스로 옮긴다. 이메일 대소문자 통일이 필요하면 로그인·가입·재설정을 함께 바꾼다. 운영이 여러 프로세스가 되면 요청 제한·발송 방식이 그대로 맞는지 다시 본다.
