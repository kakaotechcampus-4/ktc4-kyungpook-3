# 이용약관·개인정보처리방침 동의 기록

- 기록일: 2026-11-08
- 관련 마일스톤: M1(인증)
- 관련 이슈: #564, FE 요청 #566, 남은 결정 #565

아래는 2026-11-08 최초 선택과 당시 열린 PR의 제약을 기록한 것이다. #454 병합과 #575 탈퇴 구현 이후의 현재 경계·멱등 처리·공개 조건은 [2026-11-09 후속 결정](2026-11-09-consent-transaction-boundary.md)에 있다.

## 문제와 제약

- 팀 밖 사용자를 받기 전에 가입자의 약관·처리방침 동의를 받아야 한다. 2026-09-29 회원가입 범위 결정에서는 연결할 문서와 저장할 필드가 없어 동의 체크를 뺐다. 저장하지 않는 체크는 받지 않는다는 판단은 그대로 둔다.
- 동의를 받아야 하는 경우가 셋이다. 일반 가입, 카카오 첫 로그인(열린 PR #454), 이미 가입한 팀원. 문서를 고치면 다시 받아야 한다.
- 열린 #454 가 `api/auth.py`, `schemas/auth.py` 와 마이그레이션 `d2f6b81c4e07` 을 더한다. 같은 파일을 건드리면 충돌한다.

## 실제 검토한 선택지

| 선택지 | 결과 |
|---|---|
| 가입 요청에 동의 필드를 더해 가입과 함께 저장 | 쓰지 않음. 카카오 로그인과 기존 사용자는 따로 받아야 하고, `auth.py`·`schemas/auth.py` 에서 #454 와 겹친다 |
| 로그인한 사용자용 조회·저장 API 두 개 | 고름. 세 경우를 같은 흐름으로 받는다. 가입 화면은 체크를 받은 뒤 가입이 성공하면 저장 API 를 부른다 |

## 선택과 이유

- `user_consent` 표에 사용자·문서 종류·버전·동의 시각을 문서 버전마다 한 행으로 둔다. 새 버전에 동의하면 행이 하나 더 생기고 옛 동의 기록은 남는다.
- 문서의 지금 버전은 `services/consents.py` 의 `CURRENT_VERSIONS` 한곳에 둔다. 올리면 모든 사용자가 다시 `required` 가 된다.
- 저장은 두 문서를 함께 받는다. 하나라도 지금 버전이 아니면 아무것도 저장하지 않고 400 `CONSENT_VERSION_MISMATCH` 다. 화면이 옛 문서를 보여 준 채 동의를 보내는 경우를 막는다.
- 같은 버전을 다시 보내면 행을 더하지 않고 200 이다. 동시에 두 번 와서 유일 제약에 걸려도 이미 저장된 것이라 성공으로 본다. 처음 동의한 시각이 남는다.

## 장단점과 감수한 제약

- 가입 성공과 동의 저장이 두 요청이라, 가입 뒤 저장이 실패하면 동의 기록 없는 계정이 잠깐 생긴다. 다음 화면에서 `required` 가 true 라 동의 화면이 다시 나온다.
- 서버는 동의하지 않은 사용자의 다른 API 를 막지 않는다. 동의 화면은 FE 가 `required` 로 띄운다.
- #454 와 마이그레이션 head 가 같다(`d6e1b4a8c297`). 나중에 머지되는 쪽이 `down_revision` 을 앞 PR 의 리비전으로 바꿔야 head 가 둘이 되지 않는다.

## 영향 범위와 재검토 조건

- 새 표 하나, 새 API 두 개, 새 오류 코드 하나. 기존 API 와 가입 요청 모양은 바뀌지 않는다.
- FE 와 경로·필드를 합의하면 [FE 계약](../../../../../frontend/docs/contracts/frontend-api-contract.md) §4.1.5 의 상태를 고친다.
- 탈퇴(#565)를 만들면 동의 기록은 `ON DELETE CASCADE` 로 함께 지워진다. 동의 기록을 탈퇴 뒤에도 보관해야 한다는 검토가 나오면 다시 본다.
