# 로그인 제한: 수치·응답·저장 위치

- 기록일: 2026-11-06
- 관련 마일스톤: M1(인증). 서버 확인 항목은 머지 전에 사람이 한다.
- 관련 이슈: #436 (설계 합의 2026-11-06)
- 관련 결정: [비밀번호 재설정 결정 기록](2026-11-05-password-reset.md)의 "요청 제한 저장" 판단(토큰 테이블)과 저장 위치 판단이 다르다. 그 기록은 그대로 두고 아래에서 이유를 적는다.

## 문제와 제약

- 로그인에는 시도 횟수 제한이 없어 비밀번호를 무제한으로 대입할 수 있었다.
- 없는 이메일, 비밀번호가 없는 계정, 틀린 비밀번호는 해시 계산 횟수와 응답이 같아야 가입 여부가 드러나지 않는다. 같은 이유로 막힌 응답도 있는 이메일과 없는 이메일이 같아야 한다.
- 해시 계산은 느려서(코드 주석: 약 0.2초) 검사 뒤에 횟수를 세면 그 사이의 동시 요청이 모두 검사를 통과한다. 해시 전에 잠금 안에서 예약해야 한다.
- 서버는 단일 프로세스다(`Dockerfile` 의 `--workers 1`). 모델·마이그레이션 변경은 하지 않는다.
- 수치와 설계 질문은 사람이 정했다(2026-11-06).

## 실제 검토한 선택지

| 결정 | 선택지 | 결과 |
|---|---|---|
| 저장 | 프로세스 메모리 / DB 테이블 | 프로세스 메모리(사람이 정함). 이유는 아래 |
| 막힌 응답 | 429 로 알림 / 막혀도 401 | 429. 스펙의 완료 조건이 429 와 `Retry-After` 이고, 막힌 이유를 401 과 구분하지 않는 안은 버렸다 |
| 기준 | 이메일 + IP 각각 / `(이메일, IP)` 조합 | 이메일과 IP 를 따로 센다. 조합 안은 버렸다 |
| 점증 잠금 | 실패가 늘수록 막는 시간을 늘림 / 고정 시간 | 고정 15분. 점증 잠금은 하지 않는다(완료 조건) |

막힌 동안 401 을 주는 안과 `(이메일, IP)` 조합 안을 버린 이유는 스펙과 브리프에 적혀 있지 않다. 결과만 사람이 정했고, 이유는 이 기록에서 추정해 쓰지 않는다. 필요하면 사람이 보충한다.

## 선택과 이유

- 수치: 같은 이메일 15분 안에 10번 실패(첫 실패부터 창 시작)면 11번째 시도부터 15분 동안 막는다. 같은 공인 IP 는 15분 안에 50번 실패면 15분 막는다. 이메일 막힘과 IP 막힘 응답은 구분하지 않는다.
- 응답: 429 `TOO_MANY_LOGIN_ATTEMPTS`, 문구 "로그인 시도가 너무 많습니다. 잠시 후 다시 시도해 주세요.", `Retry-After` 헤더와 `details.retry_after_seconds`(같은 정수 초). `AppError` 에 `headers` 인자를 더하고 `app_error_handler` 가 넘긴다.
- 막힘은 시간이 지나면 풀린다. 막힌 동안 시도해도 시간이 늘지 않는다. 재설정 confirm 이 commit 된 뒤 그 이메일의 막힘을 풀고, 성공 로그인은 이메일 횟수를 지운다. 성공 때 IP 는 이번 예약만 되돌린다. IP 전체를 지우면 자기 계정으로 로그인해 초기화할 수 있어서다.
- 메모리를 고른 이유: 서버가 단일 프로세스라는 전제(`Dockerfile`)에서 `threading.Lock` 안의 예약만으로 동시 요청을 막을 수 있다. 막힌 요청이 DB 연결을 잡지 않는다(`login` 의 코드 주석). 항목은 5만 개로 제한하고 넘치면 만료된 것을 먼저, 그다음 오래된 것부터 지운다.
- #398 과 판단이 다른 이유: 재설정 요청 제한은 토큰 테이블의 발급 기록을 썼고 메모리는 재시작에 풀린다는 점을 이유로 피했다. 로그인 제한은 같은 약점(재시작하면 풀림)을 알면서 메모리를 택한다. 로그인 제한은 해시 전에 잠금 안에서 예약해야 하고, 테이블이면 그 예약을 DB 쓰기와 잠금으로 풀어야 한다. 이 대비는 스펙의 완료 조건에서 끌어낸 설명이고, 사람이 별도로 남긴 근거 문장은 확인하지 못했다.
- 서로게이트 비밀번호: `verify_password` 가 `surrogatepass` 로 인코딩해 있는 계정과 없는 계정 모두 401 이다. `hash_password` 쪽 500 은 #448 이다.

## 장단점과 감수한 제약

- 남의 계정 잠금을 일부 감수한다. 이메일 기준이라 누군가 내 이메일로 10번 실패하면 내 로그인이 15분 막힌다. 막힘은 맞는 비밀번호도 막는다. 재설정 confirm 으로 풀 수 있다.
- 서버를 재시작하면 모든 횟수와 막힘이 풀린다.
- 프로세스가 둘 이상이면 횟수가 프로세스마다 쌓여 한도가 실질적으로 늘어난다.
- 이미 로그인한 세션은 막힘 영향이 없다.

## 영향 범위와 재검토 조건

- 코드: `app/services/login_limit.py`(신규), `app/api/auth.py`(login 예약·성공·취소, confirm 뒤 해제), `app/services/passwords.py`(`DUMMY_PASSWORD_HASH`, `surrogatepass`), `app/services/password_reset.py`(`confirm_reset` 이 해제할 이메일을 돌려줌), `app/core/errors.py`, `app/main.py`. 모델·마이그레이션 변경은 없다.
- 남은 노출(범위 밖): 가입의 `EMAIL_ALREADY_EXISTS` 로 가입 여부가 드러남(#427), `hash_password` 의 서로게이트 비밀번호 500(#448), 재설정 요청의 응답 시간 차이(감수).
- 재검토 조건: `--workers` 를 늘릴 때, 서버를 2대 이상 둘 때. 그때 저장소부터 다시 설계한다.
- 머지 전 사람이 서버에서 확인할 것: Caddy 가 `X-Forwarded-For` 를 어떻게 처리하는지. 위조한 헤더가 실제 클라이언트 IP 로 찍히면 IP 제한은 우회된다. 이메일 제한은 헤더와 무관해 유효하다. 저장소에 Caddyfile 이 없어 처리 방식은 아직 확인하지 못했다. 위조가 통한다고 확인된 것은 아니다.
- 확인 상태: 코드·테스트는 구현됐다. 서버의 Caddy 확인은 하지 않았다.
