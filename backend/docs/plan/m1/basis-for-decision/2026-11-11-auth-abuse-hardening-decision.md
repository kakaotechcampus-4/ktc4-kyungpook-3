# 가입 코드 IP 상한, 잠긴 이메일의 재설정, 비밀번호 해시 횟수를 보강한다

- 기록일: 2026-11-11
- 관련 마일스톤: M1(로그인 제한·재설정·가입 코드와 같은 마일스톤). 요청은 이슈 #691(2026-11-11 보안 점검). 앞선 기록은 [재설정 메일 상한](2026-11-08-reset-mail-cap.md), [로그인 제한](2026-11-06-login-rate-limit.md)

## 문제와 제약

#691 의 네 항목이다. 세션 탈취나 인증 우회는 아니고, 남의 가입·로그인을 막거나 가입 여부를 알아내는 경로다.

- 가입 코드 요청에는 이메일별 제한과 전체 시간당 20통만 있었다. 한 곳에서 서로 다른 이메일로 20번 요청하면 그 시간 동안 모든 신규 가입이 막힌다.
- 재설정 전체 상한(시간당 10통)과 이메일 기준 로그인 잠금이 맞물리면, 남이 전체 상한을 채우고 내 이메일로 10번 틀려 로그인과 재설정을 함께 막을 수 있다.
- 가입 코드 요청은 이미 가입한 이메일에 409 를 주고, 이 판단이 모든 횟수 제한보다 앞이었다.
- 비밀번호 해시는 PBKDF2 260,000회였다(OWASP 2023 권고 600,000회). 저장 형식에 횟수가 없어 횟수를 올리면 옛 해시를 맞춰 볼 수 없었다.

제약은 다음과 같다.

- 모델·마이그레이션을 바꾸지 않는다. `password_hash` 는 `String(255)` 이고 새 형식은 118자다.
- 운영은 단일 프로세스(`--workers 1`)이고, IP 제한은 메모리다(재설정 IP 상한과 같은 전제).
- FE 코드는 이 PR 에서 고치지 않는다. 응답이 바뀌면 계약에 적는다.

## 실제 검토한 선택지

| 질문 | 선택지 | 결정 |
|---|---|---|
| 가입 코드 IP 상한 저장 | 재설정 IP 제한기(`password_reset_limit`)에 `scope` 를 더해 같이 씀 / 새 제한기 | 같이 씀. 키 앞에 `signup:` 를 붙여 따로 세고 상한만 인자로 받는다. 재설정 쪽 키·동작은 그대로다 |
| 가입 코드 IP 상한 수치 | 5(재설정과 같음) / 10 | 10. 전체 20보다 작아 공인 IP 하나로 전체를 다 쓰지 못한다. 재발송 제한에 걸린 요청과 가입한 이메일 요청도 세므로, 한 와이파이에서 여럿이 가입하는 시연을 생각해 재설정보다 넉넉히 뒀다. 리뷰에서 확인받을 수치다 |
| 가입 코드 IP 상한에 걸렸을 때 | 429 `SIGNUP_CODE_RATE_LIMITED` `reason: "ip"` / 기존 `hourly` 로 뭉뚱그림 | `ip`. 기존 응답이 이미 `cooldown`·`hourly`·`global` 을 나눠 주고, FE 는 `cooldown` 만 따로 읽어 나머지는 같은 문구다 |
| 잠금과 재설정 전체 상한 | 전체 상한을 넉넉히 올림 / 로그인이 잠긴 이메일의 요청은 전체 상한을 보지 않음 | 잠긴 이메일은 전체 상한 밖. 상한을 올리면 공격자가 채워야 할 수만 늘 뿐 같은 일이 남는다. 계정당 60초 1번·1시간 5번과 IP 시간당 5번은 그대로다 |
| 가입 여부 노출 | 가입한 이메일에도 같은 200 을 주고 메일로 안내 / 판단을 횟수 제한 뒤로 옮김 | 뒤로 옮김. 같은 200 은 안내 메일 양식이 새로 필요하고, FE 가입 화면이 409 를 이메일 칸 오류로 보이는데 200 이면 오지 않을 코드를 기다리는 화면으로 넘어간다. 화면 흐름과 계약이 바뀌는 일이라 이 PR 에 넣지 않았다 |
| 해시 형식 | `pbkdf2_sha256$횟수$salt$digest` / 횟수를 설정값으로만 두고 일괄 재해시 | 형식에 횟수를 담는다. 비밀번호 원문 없이는 일괄 재해시를 할 수 없으므로, 옛 형식(`salt$digest`)은 260,000회로 맞춰 보고 로그인에 성공할 때 다시 해시한다 |
| 다시 해시하는 위치 | 세션을 넣는 같은 트랜잭션에서 "해시가 그대로일 때만" UPDATE / 공유 잠금으로 재확인한 뒤 UPDATE / 세션 commit 뒤 따로 | 같은 트랜잭션의 조건부 UPDATE 가 공유 잠금 재확인을 대신한다. 공유 잠금을 잡은 채 UPDATE 하면 같은 계정의 로그인 둘이 서로 기다리다 교착한다. 해시 계산은 잠금 밖에서 한다 |

## 선택과 이유

- 가입 코드 요청 순서: 메일 설정 503 → 공인 IP 상한(메모리, 첫 DB 조회 전) → 이메일별 재발송·시간당 제한 → 전체 상한 → 가입 여부 → 발급. 막힌 요청은 세지 않는다. 사설 주소와 해석할 수 없는 값은 로그인 제한과 같이 IP 상한을 건너뛴다.
- 가입한 이메일에는 코드 행이 없어 이메일별 제한이 걸리지 않는다. 그래서 가입 여부를 묻는 요청을 실제로 줄이는 것은 IP 상한이다. 전체 상한이 찬 동안에는 모든 요청이 429 라 가입 여부가 보이지 않는다.
- 잠금 여부는 API 에서 `login_limit.email_blocked` 로 세지 않고 읽어 `request_reset(login_locked=...)` 로 넘긴다. 로그인 제한은 단조 시계, 재설정은 UTC 시각을 쓰기 때문이다. 없는 이메일도 잠글 수 있고 응답은 여전히 같은 200 이라 가입 여부와는 무관하다.
- 옛 해시는 맞춰 볼 때 모자란 횟수(340,000회)를 한 번 더 계산한다. 더미 해시와 응답 시간을 맞춰, 아직 로그인하지 않은 옛 계정이 응답 시간으로 드러나지 않게 한다. 더미 해시는 지금 횟수를 따른다(테스트에서 횟수를 1로 줄여도 같이 줄어든다).

## 장단점과 감수한 제약

- 잠긴 이메일의 재설정은 전체 메일 상한을 넘을 수 있다. 계정을 잠그려면 로그인 실패 10번이 필요하고(IP 하나에 15분 50번), 계정당 시간당 5통·IP 시간당 5번은 그대로다. IP 여러 개로 가입된 계정을 많이 잠가 돌리면 Gmail 하루 한도를 쓸 수 있다. 재설정을 막는 것보다 낫다고 보고 감수한다.
- 가입 여부는 여전히 409 로 드러난다. 공인 IP 시간당 10회·전체 상한 안에서만 물을 수 있게 됐고, IP 여러 개로는 더 물을 수 있다.
- 가입 코드 IP 상한은 같은 공인 IP 에서 시간당 10번이다. 시연처럼 여럿이 한 IP 에서 가입하면 막힐 수 있다(전체 20통 상한은 원래 있었다). 급하면 재시작으로 푼다.
- 옛 해시 계정이 같은 순간 두 번 로그인하면, 다시 해시한 쪽이 먼저 끝난 뒤 다른 쪽은 해시가 바뀐 것으로 보고 401 을 받고 실패 1번으로 센다. 계정마다 한 번뿐인 경우라 감수한다.
- 해시 계산이 260,000회에서 600,000회로 늘어 로그인·가입·재설정 확인이 그만큼 느려진다. 옛 해시 계정의 첫 로그인은 다시 해시까지 두 번 계산한다.

## 영향 범위와 재검토 조건

- 코드: `app/services/passwords.py`, `app/services/password_reset_limit.py`(`scope`·`limit`·`retry_after`), `app/services/signup_codes.py`(`IP_HOURLY_LIMIT`, 가입 여부 판단 위치), `app/services/password_reset.py`(`login_locked`), `app/services/login_limit.py`(`email_blocked`), `app/api/auth.py`. 모델·마이그레이션·에러 코드 변경 없음. 계약은 `SIGNUP_CODE_RATE_LIMITED` 의 `reason` 에 `ip` 가 더해졌다.
- 재검토: 시연에서 가입 코드 `reason=ip` 로그가 보일 때(상한을 올리거나 사설 주소 경로를 확인), 재설정 메일이 Gmail 한도에 닿을 때, 가입 여부 노출을 없애기로 할 때(같은 200 과 안내 메일, FE 가입 화면 변경이 함께 필요), 옛 형식 해시가 남지 않게 되었을 때(옛 형식 처리를 지운다).
