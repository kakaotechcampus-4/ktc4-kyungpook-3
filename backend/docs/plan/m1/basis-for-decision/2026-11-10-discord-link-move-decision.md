# 디스코드 연결은 한 요청으로 옮기고, 이으면 지난 발화 화자도 다시 붙이고, 같은 이름은 서버가 막는다

- 날짜: 2026-11-10
- 상태: 결정됨(이름 비교의 대소문자는 확인 필요, 아래 결정 3)

## 배경

배포된 빌드에서 팀원마다 디스코드 계정을 다시 고르면 다른 팀원의 이름이 바뀌는 문제가 있었다(#647). FE 가 이를 "팀원마다 계정 고르기" 로 고치려면 BE 에 세 가지가 없었다.

- 같은 계정은 두 활성 팀원에 붙을 수 없다(`uq_workspace_discord_user`, 409 `DISCORD_USER_ALREADY_MAPPED`). 계정을 옮기려면 앞 팀원 풀기와 새 팀원 잇기로 PATCH 를 두 번 불러야 하고, 사이에서 실패하면 둘 다 풀린 채로 남는다
- 발화의 `source.member_id` 는 저장할 때의 연결로 정해지고(`api/sources.py`, `matching.resolve_speaker`) 나중에 고치는 코드가 없다. 회의록과 요약 입력은 읽을 때 그 member 의 지금 이름을 붙인다(`api/meetings.py` 회의록, `services/summary.py` `_input_lines`). FE 를 고쳐 계정을 옳게 옮겨도 지난 회의록은 앞 팀원 이름으로 남는다
- 팀원 이름이 같아도 서버가 막지 않는다. FE 만 보내기 전에 막는다(#613, D-187)

## 검토한 선택지

계정 옮기기

- PATCH 두 번(앞 팀원 null, 새 팀원 계정): BE 를 바꾸지 않는다 / 사이에서 실패하면 둘 다 풀린다
- PATCH 한 번에 옮기기 플래그를 더한다: 한 트랜잭션이라 반쯤 옮겨진 상태가 없다 / 요청 필드가 하나 는다

지난 발화

- 앞으로 저장하는 발화만 새 연결을 따른다: 고칠 것이 없다 / 지난 회의록이 앞 팀원 이름으로 남는다
- 계정을 이으면 그 계정이 말한 지난 발화를 새 팀원으로 다시 붙인다: 회의록이 실제 화자를 따른다 / 한 계정은 한 사람이라는 가정에 기댄다
- 옮길 때마다 PM 에게 지난 발화도 바꿀지 묻는다: PM 이 고를 수 있다 / 화면과 요청이 하나씩 는다

같은 이름

- FE 에서만 막는다: 지금 그대로다 / 다른 화면이나 직접 부른 API 로 중복이 생긴다
- BE 도 막는다: 어디서 만들든 같은 규칙이다 / 이미 있는 중복과 동시 요청을 따로 생각해야 한다

## 결정

사람이 2026-11-10 에 정했다.

1. `PATCH /members/{id}` 에 `move_discord_link`(기본 false)를 더한다. true 면 그 계정을 가진 다른 활성 팀원의 연결을 풀고 이 팀원에 한 트랜잭션으로 잇는다. 두 팀원 행은 `member_id` 순서로 잠근다. 앞 팀원 풀기를 먼저 flush 한 뒤 새 팀원에 잇는다. 같은 표의 UPDATE 는 기본 키 순서로 나가므로, 순서를 정하지 않으면 한 계정이 잠깐 두 활성 팀원에 붙어 유일 인덱스에 걸린다. 앞 팀원의 닉네임 별칭은 보통 연결 해제와 같이 지운다. 응답에 앞 팀원 id 는 싣지 않는다. FE 는 목록을 다시 읽는다
2. 계정을 팀원에 이으면(새로 잇든 옮기든, `POST` 포함) 같은 트랜잭션에서 이 워크스페이스 회의의 발화 중 그 계정이 말한 행의 `member_id` 를 그 팀원으로 바꾼다. 한 번의 `UPDATE source ... WHERE speaker_discord_user_id = ? AND meeting_id IN (이 워크스페이스 회의)` 다. 연결이 없던 발화와 삭제한 팀원에 붙어 있던 발화도 바뀐다. 연결을 풀기만 하면 발화를 건드리지 않는다. 계정 탈퇴는 그 팀원 발화의 화자 계정을 지우므로(`account_withdrawal._scrub_shared`) 다시 붙을 일이 없다
3. `POST /members` 와 이름이 바뀌는 `PATCH display_name` 에서 같은 워크스페이스 활성 팀원과 이름이 같으면 409 `MEMBER_NAME_DUPLICATED`. 이미 있는 중복은 그대로 두고 새로 만드는 것만 막는다. 그래서 DB 유일 제약은 두지 않는다. 사람이 정한 문구는 "대소문자·공백 무시, FE 키 함수와 같은 규칙" 인데 FE `memberNameKey` 는 앞뒤 공백만 지우고 대소문자는 그대로 둔다(그 테스트가 `Alex` 와 `alex` 를 다르게 본다). 두 조건이 맞지 않아 지금은 FE 와 같게 앞뒤 공백만 지우고 견준다. 대소문자도 무시할지는 확인이 필요하다

## 다시 볼 조건

- 이름 비교에서 대소문자를 무시하기로 하면 BE 와 FE `memberNameKey` 를 같이 바꾼다. BE 만 바꾸면 FE 가 통과시킨 이름을 서버가 409 로 막는다
- 한 디스코드 계정을 여러 사람이 쓰는 팀이 생기면 결정 2 의 가정이 깨진다
- 같은 이름이 동시에 만들어진 사례가 나오면 기존 중복을 정리하고 DB 제약을 둔다
- 승인 카드 payload 의 `evidence_speaker_member_id` 와 이미 저장된 요약 문서의 이름도 옮긴 팀원을 따라야 한다는 요구가 나오면 따로 본다
