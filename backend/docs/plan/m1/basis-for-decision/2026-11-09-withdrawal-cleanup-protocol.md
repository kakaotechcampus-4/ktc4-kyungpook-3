# #575 계정 삭제와 파일 정리 확인의 경계

## 요구와 선택

2026-11-09 사용자 요청으로 첫 준비 단위 이후의 실제 탈퇴 API·화면·정리 흐름을 구현한다. 초기 Member 보존 선택은 [익명 기록 주체 결정](2026-11-09-withdrawn-record-actor.md)에 있다. 계정 접근은 즉시 끝내고, AI 장애로 로컬 사본 정리가 늦으면 정리 중 상태를 표시하며 실제 확인 뒤에만 완료한다는 정책을 별도 대화에서 확인했다. 취소 유예기간과 과거 권한 복원은 없다.

계정 삭제 전체를 파일·외부 서버의 동기 HTTP 작업으로 묶으면 장애 때 계정 삭제가 끝났는지 재시도하기 어렵다. User를 soft delete하면 같은 이메일·카카오의 즉시 새 계정 가입과 개인정보 제거를 별도로 우회해야 한다. 그래서 계정·세션·푸시·소유가 확인된 프로필 정리를 한 DB 트랜잭션으로 처리하고, durable 정리 작업과 개인정보 없는 영수증을 같은 commit에 남긴다.

## 다중 공간과 잠금

계획 조회는 보존·단독 공간 삭제·PM 이전 필요만 보여 준다. 실제 명령은 모든 공간을 다시 검사하며 하나라도 마지막 PM 조건을 위반하면 어느 공간도 변경하지 않는다. 활성 Discord 전용 팀원도 단독 여부에 포함하고 다른 PM은 로그인 계정 연결을 요구한다.

기존 인증 의존성이 User 공유 잠금을 먼저 보유하므로 탈퇴는 User → 정규화 이메일 advisory → worker gate → 정렬된 Workspace → 정렬된 Member 순서를 사용한다. 초대 생성·수락도 필요한 이메일 잠금을 Workspace·Member·Invitation보다 먼저 얻는다. 신규 가입은 이메일 잠금 후 새 User만 만들며 이전 User를 복원하지 않는다. 여러 공간을 순회하는 메시지 워커는 공간 행을 잡기 전에 같은 worker gate를 얻어 역순 공간 잠금을 막는다. 단순 조회는 불필요한 행 잠금을 보유하지 않는다.

이 구조는 실제 공유 불변식이 있는 다중 공간 작업을 직렬화하는 비용을 감수한다. 전역 이름 문자열 치환이나 공간별 중간 commit으로 단순화하지 않는다. 실제 PostgreSQL 경합에서 PM 승격·동시 탈퇴·다른 공간의 새 이메일 초대·backend와 AI의 교차 완료를 검사한다.

## 재시도와 계정 교체

최초 명령은 현재 쿠키와 expected 계정 ID를 비교한다. FE가 응답을 잃어도 같은 256비트 무작위 키로 기존 영수증을 읽는다. 서버는 키 원문 대신 SHA-256만 저장하고 User FK에 영수증 생존을 맡기지 않는다. 이전 영수증의 재요청이 새로 로그인한 계정이나 새 쿠키를 지우지 않는다. API 형식은 [FE 대표 계약](../../../../../frontend/docs/contracts/frontend-api-contract.md#계정-탈퇴와-정리-상태-575-2026-11-09)에 있다.

## 정리와 늦은 결과

단독 공간의 업무 내용은 즉시 지우고 파일 확인에 필요한 이름 없는 식별 행을 잠시 유지한다. cleanup은 부모 Workspace FK에 의존하지 않으며 backend·AI 완료를 별도로 기록한다. backend 파일 실패는 기존 정리 워커에서 재시도한다. 각 정리 행을 최신 값으로 잠가 두 완료가 교차해도 마지막 판정에서 공간을 최종 삭제한다.

AI는 익명 Member·회의·메시지 UUID로 정확한 사본을 찾는다. 과거 미귀속 녹음 탐색의 guild ID는 개인 사용자 ID와 다른 공동 리소스 selector이며 완료 후 지운다. session 세대 표식과 writer 잠금으로 지운 자료를 옛 캐시가 재생성하지 못하게 한다. 같은 guild의 새 Workspace는 별개 세대다.

공유 공간은 identity_epoch를 증가시키고 서비스가 시작할 때 읽은 roster·claim 세대를 고정한다. 옛 AI 결과에 최신 세대만 다시 붙여 저장하지 않는다. 소켓은 commit 후 즉시 폐기 신호를 보내고 송수신도 세션을 재검사한다. 외부로 이미 나간 작업을 회수했다고 주장하지 않는다.

## 필드별 소유 관계

담당자·발화자·프로필은 같은 JSON 객체에 있어도 다른 사람일 수 있다. 특정 Member 키 하나가 일치한다는 이유로 객체의 모든 이름 필드를 바꾸지 않는다. 서비스 생성 알림도 대화 링크뿐 아니라 실제 bundle·reply·task 연결로 이름 사본의 소유를 찾는다. 임의 본문을 이름 문자열 일치로 지우는 방식은 쓰지 않는다.

실제 결과와 수정 전 반례·회귀는 [M1 결과](../result.md)에 남긴다. [정리 계약](../../../contracts/backend-ai-contract.md#계정-탈퇴의-개인정보-정리-575-2026-11-09)과 [운영 안내](../../../../../deploy/README.md#계정-탈퇴와-정리-작업-575)를 함께 사용한다.

소유 근거가 없는 공유 legacy 자료와 구조화 전사 줄이 없는 markdown은 pending으로 남기며 완료를 먼저 확인하지 않는다. 다른 활성 writer로도 정리가 지연될 수 있다. 임의 공동 본문·음성 익명화, 공급사 원격 보관·삭제와 기존 외부 게시물 회수는 이 로컬 정리 완료의 근거로 추정하지 않는다.
