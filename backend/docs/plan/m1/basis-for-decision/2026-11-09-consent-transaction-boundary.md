# 동의 기록의 멱등 저장과 계정 종료 경계

2026-11-09 사용자가 #572의 처리 가능한 코드·문서를 진행하도록 요청했다. [최초 동의 API 결정](2026-11-08-consent-records.md)은 기록 모델의 근거로 유지하며, 여기에는 실제 후속 구현에서 선택한 경계를 기록한다.

## 현재 요구와 대안

#454는 이미 병합됐으므로 예전의 가입 파일 충돌은 현재 제약이 아니다. PR #569 리뷰는 가입과 동의를 한 commit으로 묶는 대안과 동의 없는 계정의 다른 API 사용 가능성을 지적했다. 이번 단위는 로그인 사용자용 동의 조회·기록 API를 최신 인증·탈퇴 구현에 통합한다. 아직 공개 이메일·공급사 조건·법률 검토가 끝나지 않은 정책 초안을 공개 동의 대상으로 전환하지 않는다.

가입 필드와 전체 접근 제어를 바꾸는 방안은 #566의 최종 공개 흐름 통합에서 다룬다. 현재 API가 동의 없는 사용자의 다른 API를 막지 않는 것은 구현 사실이며, 이를 공개 정책의 준수 완료나 팀의 최종 동의 강제 합의로 표시하지 않는다. `2026-11-08`은 초안·제안 판본이므로 공개 시 새 검토 완료 판본으로 문서·BE·FE를 함께 맞추고 과거 초안 동의를 유효 동의로 재사용하지 않는다.

## 멱등과 오류

기존 조회 후 추가 방식은 동시 요청에서 유일키 충돌이 발생했다. API가 모든 `IntegrityError`를 같은 성공으로 처리해, 실제 NOT NULL 저장 실패도 200으로 숨기는 반례를 SQLite와 PostgreSQL에서 재현했다.

오류 종류를 예외 문자열로 판별하는 대신 `(user_id, kind, version)` 충돌만 `ON CONFLICT DO NOTHING`으로 수렴시킨다. 처음 동의한 시각과 과거 판본은 유지한다. 나머지 저장 오류는 정상 오류 경계로 전파해 200으로 숨기지 않는다. 현재 버전 검사를 통과한 두 문서를 한 트랜잭션에서 기록한다.

## 계정 종료와 응답

별도 전역 잠금을 만들지 않고 인증이 이미 얻는 `lifecycle.user` 공유 잠금을 사용한다. 실제 두 HTTP 요청을 겹쳐 동의가 먼저 잠그면 탈퇴가 기다린 후 기록을 CASCADE로 지우고, 탈퇴가 먼저 잠그면 기다리던 옛 세션의 동의 요청이 401인 것을 검증했다.

commit 뒤 User ORM을 다시 읽으면, commit과 응답 사이에 탈퇴가 끝난 경우 저장은 성공했어도 응답이 500이었다. 실제 commit 직후를 멈추는 반례로 재현했다. 응답 데이터를 같은 트랜잭션 안에서 계산하고 commit 성공 후 반환해, 응답은 해당 요청이 성공시킨 상태를 나타내며 이후 탈퇴가 개인정보를 복원하지 않는다.

## 영향과 검증

외부 API 형식과 회원가입 요청 모양은 유지한다. migration `f7f0dc53a63a`는 최신 `e575b02d8a31`을 부모로 사용한다. 저장 표의 `ON DELETE CASCADE`와 익명 기록 주체의 역할은 바꾸지 않는다.

실제 결과는 [M1 결과](../result.md), 요청·응답과 공개 경계는 [FE 대표 계약](../../../../../frontend/docs/contracts/frontend-api-contract.md#414-이용약관개인정보처리방침-동의-564-be-제안-fe-합의-전)에 있다. 운영 정책 공개나 실사용자 동의 수집은 이번 검증 범위가 아니다.
