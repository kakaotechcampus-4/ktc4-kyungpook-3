# 멈춘 업로드 회의를 서버 안 워커가 실패로 정리한다

- 기록일: 2026-11-03
- 관련 마일스톤: M5 (이슈 #266 남은 항목, #255 BE 답변 8, #288)

## 문제와 제약

- AI 가 업로드를 가져간 뒤 죽거나 PM 이 화자를 지정하지 않으면 회의가 `processing`·`awaiting_speakers` 에 남는다. 업로드는 공간마다 처리 중 회의 하나만 허용하므로 그 공간의 새 업로드가 409 로 막힌다.
- BE 는 AI 가 멈췄는지 느린지 구분할 수 없다. 되돌려 다시 맡기면 같은 회의를 두 번 처리할 수 있다(#288).
- AI 는 화자 분리를 30분씩 최대 5번 기다린다(#288 본문). 정리 기준이 이보다 짧으면 정상 처리를 실패시킨다.
- 정리와 AI 보고·PM 지정이 동시에 올 수 있다.

## 실제 검토한 선택지

- 정리 방법: 실패 처리(원본 삭제) / pending 으로 되돌리기. #288 에서 hwnv 가 실패 처리를 제안했고 사용자가 확인했다.
- 실행 방식(설계 초안): 서버 lifespan 워커 / CLI 스크립트와 호스트 cron·systemd timer / UPDATE 한 문장으로 일괄 처리.
- 사용자와 정한 질문(2026-11-03 설계 확정, #266 댓글):
  - 아직 가져가지 않은 업로드도 정리할지: 대상 아님 / 24시간 뒤 실패
  - 지정 뒤 멈춤의 `failed_stage`: 모두 `diarize` / 지정 뒤는 `stt`
  - 발화 저장을 진행으로 칠지: 친다 / 안 친다
  - 한도를 상수로 둘지 환경변수로 둘지
  - 남은 폴더 정리를 같이 할지

## 선택과 이유

- 실패 처리. 처리 중 회의를 두 번 처리하는 위험이 없다.
- 서버 lifespan 워커(`app/services/upload_sweeper.py`, `UPLOAD_SWEEP_INTERVAL_SECONDS` 기본 300초). Notion 동기화·임베딩 워커와 같은 방식이라 배포를 바꾸지 않는다.
- 회의마다 조건부 UPDATE 한 번. 후보를 고를 때와 같은 시각 조건을 UPDATE 에도 걸어, 그 사이 AI 보고나 PM 지정이 먼저 반영되면 진다. `/fail` 과 같은 함수(`app/services/meeting_failure.py`)를 쓴다.
- 기준: `processing` 은 가져간 시각·지정 시각·다시 가져간 시각·마지막 발화 저장 중 가장 늦은 것에서 3시간, `awaiting_speakers` 는 라벨 보고에서 7일. 발화 저장을 진행으로 쳐서 긴 전사가 잘리지 않게 했다.
- `failed_stage` 는 `diarize`·`speaker_assignment_expired` 둘. 지정 뒤 멈춤도 `diarize` 로 두고, 어느 단계였는지는 로그에 남긴다.
- 아직 가져가지 않은 업로드는 정리하지 않는다. AI 가 다시 켜지면 손실 없이 처리된다.
- 3시간·7일은 코드 상수. AI 와 맞춘 계약 값이라 바꿀 때 PR 로 남긴다.

## 장단점과 감수한 제약

- 서버가 내려가 있는 동안은 돌지 않는다. 다시 뜨면 바로 한 바퀴 돈다.
- 3시간 경계에서 resume 200 이나 발화 저장 201 직후 회의가 failed 일 수 있다. resume 은 회의 행을 잠그지 않고, PostgreSQL 에서 sweeper 의 UPDATE 가 발화 저장의 행 잠금을 기다린 뒤에도 발화 조건은 문장 시작 시점으로 본다고 판단했다(검증하지 않은 추론). 이어지는 발화 저장·추출 등록이 409 로 막는다.
- AI 가 꺼져 있으면 가져가지 않은 업로드로 공간이 계속 막힌다. `PATCH /meetings/{id}/fail` 로 푼다.
- 삭제에 실패해 남은 폴더는 여전히 사람이 지운다.
- 동시 실행 경합은 sqlite 로 확인할 수 없고, PostgreSQL 두 세션 테스트는 두지 않았다.

## 영향 범위와 재검토 조건

- AI 의 화자 분리 대기나 전사 시간이 3시간에 가까워지면 한도를 다시 본다.
- 업로드 처리 단계가 늘어 `failed_stage` 로 화면을 나눌 필요가 생기면 값을 나눈다.
