# 배포 전 CI 를 매번 전부 돌리고 워크플로 단위로 순서를 지킨다

- 기록일: 2026-10-09
- 관련 마일스톤: M7

## 문제와 제약

- develop push 가 오면 deploy.yml 이 바로 배포했다. CI 는 develop 으로 가는 PR 에서만 돌아서 실제 배포 커밋(머지 커밋)은 검사를 받지 않았다(#175 고민 3).
- 서버는 `.git/mm-deployed-sha`(마지막 성공 배포) 이후 바뀐 파트를 올린다. Actions 는 이 값을 모른다.
- 서버는 한 대이고 배포는 동시에 하나만 돌아야 한다.

## 실제 검토한 선택지

검사를 배포에 연결하는 방식

1. 각 CI 에 push 트리거를 더하고 deploy 를 `workflow_run` 으로 잇기. 여러 워크플로의 완료를 한 번에 기다리기 어렵다.
2. 각 CI 를 `workflow_call` 로 만들고 deploy.yml 안에서 부른 뒤 `needs` 로 기다리기.

검사 범위

1. 이번 push 에서 바뀐 파트만 검사하기(이슈 초안).
2. 매번 세 파트를 모두 검사하기.

동시 실행 제한 위치

1. deploy 잡에만 `concurrency` 를 두어 CI 는 병렬로 돌리기.
2. 워크플로 전체에 두기(기존).

## 선택과 이유

- `workflow_call` + `needs`: 검사한 커밋과 배포하는 커밋이 같고, 한 실행 화면에서 결과를 본다.
- 매번 전부 검사: 커밋 A 의 backend CI 가 실패해 배포되지 않고, 다음 커밋 B 가 frontend 만 바꾸면 B 의 변경만 본 검사는 frontend 만 돈다. 그런데 서버는 A 이후 기준으로 backend 도 다시 올린다. 실패한 backend 가 검사 없이 배포되는 것을 막으려고 전부 검사한다.
- 워크플로 단위 제한: 잡 단위로 두면 CI 가 먼저 끝난 새 커밋의 배포가 대기하다가, 뒤늦게 CI 를 마친 옛 커밋의 배포에 밀려 취소된다. 그러면 최신 커밋이 다음 push 까지 배포되지 않는다. 워크플로 단위면 대기 중인 실행이 새 실행으로만 바뀌어 최신 커밋이 남는다.

## 장단점과 감수한 제약

- push 마다 frontend storybook·e2e, ai 테스트, backend 네 잡이 모두 돌아 배포가 몇 분 늦어진다.
- 워크플로 단위 제한이라 앞 배포가 끝날 때까지 다음 커밋의 CI 도 시작하지 않는다.
- 문서만 바뀐 push 도 세 CI 를 돈다. 서버 쪽은 문서만 바뀐 파트를 건너뛴다.

## 영향 범위와 재검토 조건

- 배포 대기 시간이 문제가 되면 서버의 `mm-deployed-sha` 를 먼저 읽어 그 이후 바뀐 파트만 검사하는 방식을 검토한다.
- CI 이름이나 트리거를 바꿀 때 deploy.yml 의 `uses` 경로도 함께 바꾼다.
