# 녹음 시작 때 배포 재시작 잠금 확인

- 요청 파트: Backend(배포)
- 수신 파트: AI(녹음 봇)
- 요청일: 2026-10-09
- 처리 상태: 요청 전달 대기

## 배경

배포 스크립트([ec2-deploy.sh](../../../deploy/ec2-deploy.sh))는 녹음 중인지 확인한 뒤 봇(mm-bot)을 재시작한다. 확인과 재시작 사이에 새 녹음이 시작되면 그 녹음이 끊긴다(#175 멘토 리뷰).

배포 쪽은 녹음 확인부터 재시작이 끝날 때까지 잠금 파일을 쥐도록 바꿨다. 봇이 새 녹음을 시작할 때 같은 파일을 확인해야 이 틈이 닫힌다.

## 요청 작업

| 항목 | 내용 |
|---|---|
| 잠금 파일 | 봇 녹음 폴더의 `restart.lock`. 서버 기준 `/opt/mm/ai/recordings/restart.lock`. git 이 무시하는 폴더다 |
| 잠그는 방식 | OS 파일 잠금(POSIX `flock`, 배타). 배포 스크립트는 `flock` 명령으로 같은 파일을 잡는다 |
| 녹음 시작 | 기다리지 않고 잡아 본다(`LOCK_EX \| LOCK_NB`). 이미 잡혀 있으면 배포 중이니 시작을 거절하고 잠시 뒤 다시 하라고 안내한다 |
| 쥐는 동안 | 매니페스트를 `recording` 으로 쓰고 그 회의 잠금(`session_<회의ID>.lock`)을 잡을 때까지 쥔다. 그 뒤 바로 놓는다 |
| 파일이 없을 때 | 만들어서 잡는다. 배포 쪽이 아직 한 번도 돌지 않았어도 동작해야 한다 |
| 사용자·권한 | 서버의 봇과 배포 스크립트는 둘 다 ubuntu 사용자로 돈다(저장소 예시 유닛 `ai/deploy/systemd/mm-bot.service`는 `User=mm`). 배포 쪽은 파일을 읽기로 열어 잡으므로, 봇이 쓰기로 열지 않아도 된다. 봇은 읽기로 열어도 `flock` 이 걸린다 |
| 봇 시작(부팅) | 이 잠금을 잡지 않는다. 배포가 잠금을 쥔 채 봇을 재시작하므로, 시작할 때 기다리면 서로 막힌다 |

배포 쪽은 이 잠금을 최대 60초 기다리고, 못 잡으면 봇 재시작을 건너뛴다. 봇은 녹음을 시작하는 짧은 순간만 쥐어야 한다.

## 완료조건

- 배포가 잠금을 쥔 동안 녹음 시작 명령이 거절되고 안내가 나온다.
- 봇이 잠금을 쥔 동안 배포는 기다렸다가 녹음 중임을 확인하고 재시작을 건너뛴다.
- 잠금 파일이 없을 때도 녹음이 시작된다.

## 배포 순서

어느 쪽이 먼저 배포돼도 지금보다 나빠지지 않는다. 배포 쪽만 있으면 봇이 잠금을 보지 않아 틈이 남고, 봇 쪽만 있으면 아무도 쥐지 않아 그냥 녹음이 시작된다. 두 쪽이 모두 배포되면 틈이 닫힌다.
