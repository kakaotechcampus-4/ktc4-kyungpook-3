## 1. 프로젝트 개요

### 1.1 이름과 한 줄 정의

- 프로젝트 이름: **Manager's Manager** (디자인 문서의 제품 표기는 "팀싱크(Manager's Manager)", `frontend/docs/design/design-system.md`). AI 파트 README 의 제목은 "PM 에이전트".
- 소속: 카카오테크 캠퍼스 4기 2단계 팀 프로젝트, 경북대 3팀 (`README.md`).
- 한 줄 정의 (`docs/Manager's Manager 계약·엔티티·흐름.excalidraw.md`, 2026-09-27):
  > Discord 회의를 녹음하면 할 일을 뽑아 담당자·마감을 붙이고, 확실한 건 바로 Task로, 애매한 건 PM 승인 뒤 Task·Notion에 반영한다.

### 1.2 풀려는 문제

- 팀 회의에서 정한 할 일, 담당자, 마감, 일정 변경은 말로만 남고 정리되지 않는다. PM 이 회의 뒤 기억에 기대어 Notion 보드를 고치는 일이 반복된다.
- 회의에서 "그거 금요일까지로 미루죠"처럼 **기존 할 일의 변경**도 자주 나오는데, 새 할 일만 뽑는 도구로는 놓친다.
- 자동으로 뽑은 결과를 그대로 반영하면 틀린 일이 보드에 들어간다. 그래서 **근거(원문·화자·시각)**와 **확실한 정도**를 함께 보여 주고, 애매한 것만 PM 이 확인하게 해야 한다.
- 회의 뒤에도 팀원이 할 일을 잊거나 답이 없으면 PM 이 일일이 재촉해야 한다.

### 1.3 목표 (파트 계획 문서 기준)

- **AI** (`ai/docs/plan/전체 계획.md`, 2026-10-02): 회의 음성에서 새 할 일과 기존 task 의 일정·담당자·상태·범위 변경을 찾아, 근거와 함께 승인용 초안을 BE 에 넘긴다. 변경이 없는 발화는 승인 후보에서 뺀다.
  - 목표 흐름: 음성 캡처 → 화자별 전사 → Luna 후보 추출 → 유사 task 검색(BE) → Terra 변경 판단 → Luna 초안 → BE 인계 → [PM 승인 → Notion 반영]
- **Backend** (`backend/docs/plan/backend-plan.md`, 2026-10-02): "회의 → 추출 → 매칭 → 게이트 → 승인" 파이프라인과 인증·권한·외부 연결·웹 업로드·운영 배포.
- **Frontend** (`frontend/docs/plan/frontend-plan.md`, 2026-09-15 작성): 결정 기록 D-001~D-172 를 실행 순서로 나눈 M0~M8. "계약을 먼저 가정하고 MSW 를 유일한 데이터 출처로" 개발한 뒤 실제 API 에 대조한다.

### 1.4 대상 사용자와 그 변화

- 초기 전제 (`frontend/docs/design/design-system.md` §0):
  1. 웹의 사용자는 PM 한 명이고, 팀원은 Discord 만 쓴다.
  2. 모든 승인은 웹에서 하고, Discord 는 알림만 한다.
  3. 신뢰도는 배지·점으로만 보이고 원시 숫자는 노출하지 않는다.
- 이후 바뀐 점:
  - 팀원도 웹에 들어온다. 팀원 초대·수락(#321 BE, #332 FE), 소속 없는 계정의 "팀원으로 시작 / PM 으로 팀 만들기" 선택(#306).
  - 권한을 PM / 팀원으로 나눴다(#164). 승인·업로드·설정 쓰기는 PM 만 한다.
  - 리마인드 DM 에 팀원이 답장하면 AI 가 판단해 태스크에 반영하거나 PM 확인 카드로 올린다.
  - 모바일 360px 폭과 설치형 앱(PWA)을 지원한다(#478, #430).

### 1.5 핵심 가치 (발표용 요약)

1. **회의만 하면 할 일이 정리된다**: 녹음, 웹 업로드, Discord 채팅 세 경로에서 할 일과 변경을 뽑는다.
2. **근거가 붙는다**: 모든 항목에 원문 인용, 화자, 회의 내 시각이 붙고, 원문을 다시 들을 수 있다.
3. **확실한 것만 자동, 애매한 것은 PM 확인**: 근거 검증(Jev)과 조건 기반 게이트(auto / review / hold).
4. **기존 할 일의 변경까지 다룬다**: 유사 task 검색 + 변경 판단(Terra)으로 마감·담당·상태·범위 변경을 제안한다.
5. **회의 뒤 후속 관리**: 마감 전 재촉 제안, DM 발송, 답장 판단, 72시간 무응답 시 막힘 표시.
6. **Notion 과 동기화**: 승인된 태스크를 팀이 쓰던 Notion 보드에 반영한다.

### 2.4 AI 코딩 에이전트와의 협업 체계

이 프로젝트는 Claude Code·Codex 를 개발 도구로 적극적으로 썼고, 그 규칙을 저장소에 남겼다.

- 진입점: `CLAUDE.md`, `AGENTS.md` → 공통 규칙 `docs/agent-rules.md`.
  - 전체 계획 문서는 보호 문서라 에이전트가 고치지 않는다.
  - 개발 뒤 결과(`result.md`), 결정 기록(`basis-for-decision`), 계약 갱신이 의무다.
  - 트러블슈팅 기록은 사람만 쓴다.
- 팀 스킬(`.agents/skills/`, `.claude/skills/`): contract-update, decision-record, docs-audit, docs-bootstrap, milestone-plan, milestone-result, troubleshooting-review, verify-managers-manager(Playwright·MSW 검증 증거 보관).
- AI 파트 전용 하네스(mm-harness 플러그인): `ai-feature`(설계 초안 → 사용자와 설계 확정 → 테스트 먼저 구현 → 셀프 리뷰 → PR), `ai-pr-reply`(리뷰 지적 검증·반영·답글), `ai-review-pr`(팀원 PR 을 AI 관점으로 리뷰). 이슈 템플릿 "AI Feature(하네스)" 로 맡긴다.
- `ai/CLAUDE.md` 의 깨면 안 되는 규칙 7가지 (일부는 테스트로 강제):
  1. Discord 는 `capture/` 에만 있다(`tests/test_platform_isolation.py`).
  2. `shared/schemas.py` 는 BE 와의 계약이다.
  3. BE 와는 HTTP API 로만 이야기한다.
  4. LLM 호출 실패는 `None` 이다. 테스트에서 실제 API 를 부르지 않는다.
  5. 실제 API 를 부르는 평가 스크립트는 pytest 에 넣지 않는다.
  6. 상대 날짜("내일")의 기준일은 회의 날짜다(채팅은 메시지 작성일, KST).
  7. `.env` 는 읽지 않는다.

## 3. 시스템 전체 구조

### 3.1 구성 요소

```text
[Discord 음성 채널]  [웹 녹음 업로드]  [Discord 텍스트 채널]
        │                  │                    │
        ▼                  ▼                    ▼
  AI 녹음 봇(mm-bot)   AI 워커(mm-worker)    채팅 폴러(mm-chat-poll, 매일 09:00)
        └───────── 전사(STT) · 판단(judge) · 초안 ─────────┘
                               │  HTTP (X-Service-Token)
                               ▼
                    Backend (FastAPI + PostgreSQL/pgvector)
          매칭 · 게이트(auto/review/hold) · 승인 · 이력 · 리마인드 · 알림
                │                         │
                ▼                         ▼
           Notion 보드              Frontend (React SPA, PWA)
        (outbox 동기화)          PM/팀원: 회의록 · 승인 · 태스크 · 메시지 · 설정
```

- 세 파트가 한 EC2(t3.medium)에 함께 올라간다(7장).
- 외부 서비스: Elice MLAPI(STT whisper-large-v3, LLM Terra·Luna, 임베딩, Jev 판정), pyannoteAI(화자 분리), Discord(봇·OAuth), Notion(OAuth·API), Gmail SMTP, Web Push(VAPID).

### 3.2 입력 경로 세 가지

1. **Discord 음성 녹음** (`ai/capture/discord_adapter.py`, `ai/capture/worker.py`)
   - 봇이 `/record`·`/stop` 으로 화자별 트랙(16kHz 모노 wav)을 저장한다. 화자 분리는 화자별 트랙이 대신한다.
   - `/record` 때 Discord 서버 ID 로 BE 에 워크스페이스를 물어 고정한다(연결이 없으면 녹음하지 않음, #199).
   - 워커가 전사 → 발화 저장(`/sources`) → 추출·판단 → `POST /extractions` 순으로 처리한다.
2. **웹 녹음 업로드** (`ai/upload/`, BE `api/uploads.py`)
   - PM 이 웹에서 음성 파일 1개를 올린다(최대 100MiB). BE 가 저장하고 AI 워커가 가져간다.
   - pyannoteAI 로 화자를 나누고 라벨별 샘플 구간을 BE 에 보고한다. PM 이 웹에서 라벨마다 팀원(또는 외부 참석자)을 지정하면 처리가 이어진다.
   - `MM_UPLOAD_INTAKE=1` 일 때만 켜진다.
3. **Discord 텍스트 채팅** (`ai/capture/chat_poll.py`)
   - PM 이 웹 설정에서 수집할 채팅 채널을 고르면, 매일 09:00 KST 에 BE 커서 이후 메시지를 워크스페이스별 "채팅 회의" 하나로 넘긴다.
   - 채팅 회의 항목은 PM 이 보지 않고 반영되지 않도록 auto 를 review 로 낮춘다.

이 밖에 **리마인드 DM 답장 판단**(`ai/capture/dm.py` → `ai/judge/reply.py`)과 **리마인드 문구 초안**(`ai/draft/reminder_draft.py`)이 있다.

### 3.3 회의 하나가 처리되는 순서 (음성 회의, judge 경로)

1. 녹음 → 화자별 트랙 저장 → 단계 `saved`.
2. 배치 전사(Elice) → 회의록 jsonl·md → `transcribed`.
3. 발화를 BE 에 저장(`POST /meetings/{id}/sources`, `seq` 단위) → `sourced`.
4. 판단 파이프라인:
   1. Luna 1단계: 전사에서 할 일·변경 후보(finding)를 뽑는다(담당자 유형, 근거 문장 포함).
   2. BE 유사 task 검색: 임베딩 코사인 유사도 상위 3개 중 0.4 이상.
   3. Terra 2단계: 의미 있는 변경인지, 새 항목인지 기존 task 수정인지, 대상 task, 상태, 카테고리(schedule·assignee·status·scope·decision)를 정한다.
   4. Luna 초안: 제목, 마감일, 설명(doc_text).
   5. Jev 근거 검증(새 항목만): 근거 원문에 할 일·마감이 명시됐는지 물어 `certain / inferred / missing`.
5. `POST /extractions` → BE 가 담당자를 매칭하고 게이트를 정한다 → `handed_off`.
6. BE 게이트:
   - **auto**: 승인 없이 Task 생성 → Notion 반영. PM 은 되돌리기 가능.
   - **review**: PM 확인 카드(ApprovalRequest).
   - **hold**: 담당자를 못 찾는 등 PM 이 채워야 하는 항목.
   - 기존 task 수정(update)은 항상 review 다.
7. PM 이 웹에서 승인(값을 고쳐 승인 가능) → Task 반영 → Notion outbox 동기화.

### 3.4 단계 상태 (AI 매니페스트)

`recording → saved → transcribed → sourced → extracted → handed_off`. 업로드 회의는 그 앞에 `diarized`(화자 지정 전), `mapped`(지정 후)가 있다. 실패하면 `failed` 와 `failed_stage`(stt | sources | extract | handoff)를 남기고, 워커는 마지막으로 끝난 단계 다음부터 다시 시작한다. BE 회의 상태는 `created / recording / processing / awaiting_speakers / done / failed` 이고, 처리 단계(`stt → sources → extract → handoff`)를 웹에 보여 준다(#381).

### 4.2 전사 (STT)

> **추후 갱신 예정**: 회의 음성 보관(#568: 인계 뒤 바로 삭제, 포기 7일 뒤 삭제), 전사 진행 보고(#542), Elice 장애 때 GPU 전사 자동 전환(#581, 열림)

- **방식**: 회의가 끝난 뒤 화자별 트랙을 배치로 전사한다(결정 0008, 실시간 전사 0003 을 번복).
  - 클립: VAD 기준 800ms 침묵에서 자른 조각(8초 넘는 발화는 400ms).
  - 턴: 같은 화자의 클립이 3초 안에 이어진 묶음. 회의록 한 줄이고 `seq` 하나.
  - 묶음(chunk): 턴을 이어 28초 안으로 채운 전사 호출 단위(기본 모드).
  - 단어 시각이 없는 Elice 는 다른 화자가 말을 시작한 자리에서 묶음을 가른다(0023, 교차 대화에서 건너뛴 줄 6·7 → 0).
- **품질 장치**:
  - 팀원 이름 힌트 프롬프트(BE 팀원 이름, 최대 15명, 약 170토큰, 0020·0024). 9/29 녹음의 이름 자리 0/4 → 3/4.
  - 1.5초 미만 짧은 묶음에는 앞 줄을 프롬프트로 싣고 최소 발화를 100ms 로 낮춤(0031). CER 4.78 → 4.67%, 짧은 대답 3/7 → 5/7.
  - 배치 전사에서는 말 필터(Silero VAD 말 비율 0.60)를 끔(0030).
  - 기존 할 일 제목 힌트는 CER 이 나빠져 넣지 않음(0025).
  - 노이즈 필터는 효과가 없어 두지 않음(0007).
- **엔진 선택**: 운영 기본 Elice whisper-large-v3(0019). t3.medium 에서 로컬 turbo 는 62분 회의에 85분(RTF 1.36)이 걸리고 워커 둘이면 스왑이 생겨서다.
- **GPU 장애 대응**: Elice 장애 때 사람이 판단해 켜는 g4dn.xlarge(vLLM, whisper-large-v3) 대기 서버(0039, 0047). 상시 운영은 손익분기가 월 오디오 1,863시간(50~104팀)이라 지금 규모에선 맞지 않는다.

### 4.3 판단 파이프라인 (judge)

> **추후 갱신 예정**: 전사 오인식 검사(#532, 열림: 제목 명사를 워크스페이스 용어 목록과 비교하고 Jev 로 확인), thirdname 원문 전송(#501, 결정 기록 0057), 재실행 결과 합치기(#570, 열림), 1단계 재시도(#580, 열림), 자동 생성 스위치(#526)

- 값마다 출처가 하나다: 담당자·근거는 finding(1단계), 새 항목/수정·대상·상태는 Terra, 제목·마감·설명은 Luna, 근거 상태는 Jev.
- 실패를 두 갈래로 나눈다: 회의 전체 실패(키 없음, 1단계 실패)는 예외로 단계를 실패시키고, finding 하나의 실패는 `failures` 에만 남기고 나머지를 처리한다. 판단 못 한 finding 이 남으면 최대 2번 다시 돌린다(0016).
- 담당자 유형 7가지: `first`(1인칭, 화자로 찾음) / `second`(2인칭) / `thirdname`(이름 지목) / `thirdpronoun`(그분) / `thirdrole`(역할 지목) / `group` / `none`. BE 에 보내는 `assignee_raw` 는 별칭으로 찾을 수 있는 값만 보낸다(2인칭·대명사·역할은 문맥으로 푼 이름, 이름 지목은 원문).
- 같은 회의 안에서 같은 일을 가리키는 뒤 발화는 앞 카드에 합친다. 담당자 근거는 담당을 정한 발화를 따른다(0045, #420).
- 근거 발화의 `seq` 를 함께 보내 BE 가 원문·화자·시각을 이어 준다(#229, #422).
- **Jev 근거 검증**(0031 evidence): 값을 만든 LLM 이 스스로 평가하면 거의 다 certain 이 되므로, 다른 모델(Jev)에게 "근거 원문에 명시돼 있나"를 다시 묻는다. yes 확률 0.8 이상만 certain, 호출 실패는 inferred. 요일을 함께 줘 달력 계산 실수를 줄였다.
- **리마인드 답장 판단**(`judge/reply.py`, 0043): 팀원 답장을 회의 파이프라인에 넣어 상태 변경·마감 변경·담당 변경을 판단한다. 상태 변경이 certain 이고 본인이고 판단이 본 값이 지금도 그대로일 때만 BE 가 자동 반영한다.
- **legacy 추출 경로**: LLM 두 번(관련 문장 필터 → 구조화 추출), 마감일 검증, "OO님" 정규식 교차검증, self-consistency. 기준 원본은 `TASK_CRITERIA.md`(행동·미완료·의지 또는 요청).

### 4.5 채팅 수집 (#378, #431)

- BE `GET /bot/chat-channels` 로 워크스페이스별 채널 목록을 받아 차례로 돈다. 워크스페이스마다 읽기 직전에 목록을 다시 받아, 그사이 수집이 꺼졌거나 채널이 바뀐 곳은 건너뛴다.

- 봇은 음성 봇 하나(`DISCORD_BOT_TOKEN`)를 쓴다. REST 로만 읽으므로 개발자 포털의 Message Content Intent 가 켜져 있어야 본문이 온다.
- 채팅 경로는 `MM_EXTRACT_PATH` 와 상관없이 항상 judge 경로를 쓴다.

## 5. 백엔드 파트 상세 (`backend/`)

### 5.1 기술 스택

- Python 3.12, FastAPI, SQLAlchemy 2, Alembic(마이그레이션 27개), PostgreSQL 16 + pgvector(`vector(1536)`), httpx, pywebpush, pydantic.
- 모든 응답은 `{data, error:{code,message,details}}` 봉투. 오류 코드 약 60종(`backend/README.md`).
- API 접두어 `/api/v1`, 헬스 체크 `/health`.
- 서버 안 백그라운드 워커 4개(lifespan 스레드): 리마인드 스케줄러(60초), Notion 동기화(5초), 임베딩 채우기(5초), 업로드 sweeper(300초). 그래서 운영은 프로세스 하나(`--workers 1`)이고, 스케줄러·답장 claim 은 PostgreSQL advisory lock 으로 한 곳만 돈다.
- 테스트는 SQLite in-memory 가 기본이고, PostgreSQL 전용 테스트는 `TEST_DATABASE_URL` 이 있을 때 CI 에서 돈다.

### 5.2 도메인 모델 (`app/models/models.py`)

- 계정·공간: User, Session(쿠키 7일), PasswordResetToken(해시만), Workspace, 온보딩 단계 상태, Member(role pm/member, `discord_user_id`, 계정 없는 팀원 허용, 소프트 삭제), Invitation, WorkspaceMessageSettings.
- 연동: Integration(notion/discord, OAuth 토큰, Notion DB ID 또는 Discord 서버 ID, 채팅 수집 채널). Discord 서버 하나는 한 워크스페이스에만 연결.

### 5.4 핵심 로직

> **추후 갱신 예정**: judge auto 조건에 자동 생성 스위치(#526)와 전사 오인식 사유(#532, 열림) 추가, 답장 판단 창(#552)

- **게이트** (`services/matching.py`)
  - legacy 경로: 확신도 0.8 이상 auto, 0.5 이상 review, 그 미만 hold. 별칭이 미검증이거나 중의적이면 0.8 이상이어도 review.
  - judge 경로: 숫자 하나가 아니라 조건을 모두 만족할 때만 auto(#232). 새 항목, 할 일 근거 certain, 담당자를 한 명으로 확정(검증된 별칭 또는 화자)했거나 담당 언급 없음, 담당 유형이 추론형(2인칭·대명사·역할)이 아님, 마감 근거 certain 또는 missing(날짜 유무와 일치), 유사 task 0건이고 임베딩이 없는 활성 task 도 없음.
  - 담당자를 지목했는데 찾지 못하면 hold. 기존 task 수정은 항상 review. 채팅 회의는 auto 를 review 로 낮춤.
  - auto 되돌리기: task 를 소프트 삭제하고 같은 내용의 승인 요청을 다시 만든다.
- **담당자 매칭**: 별칭 텍스트로 찾아 1건 matched, 2건 이상 ambiguous, 0건 not_found. 1인칭은 근거 발화의 화자(멤버 ID → Discord uid → 결론 발화 화자 순). 별칭 후보 확장(님·조사 떼기, 이름·닉네임 자동 별칭, #463)과 승인 때 별칭 학습(#464)은 PR 진행 중.
- **유사 task 검색**: 임베딩은 요청 안에서 부르지 않고 워커가 채운다. pgvector 코사인 유사도 상위 3개 중 0.4 이상. 입력 오류는 그 task 만 건너뛰고, 그 밖의 실패는 지수 백오프.
- **승인 충돌**: 수정 제안마다 AI 가 본 값(`target_snapshot`)을 기준값으로 남긴다. 승인 때 지금 값이 기준값과 다르면 409 `APPROVAL_CONFLICT` 로 base·current·proposed 를 보여 주고, PM 이 확인한 버전으로 다시 승인한다.
- **Notion 동기화**: outbox 패턴. Task 변경과 같은 트랜잭션에 job 을 넣고 워커가 현재 값 전체를 보낸다. 429·409·5xx 는 지수 백오프 최대 5회, 401 은 refresh 한 번. 생성 직전 시각을 기록해 결과를 모르고 끝난 생성은 "Task ID" 속성으로 먼저 조회해 중복을 막는다. 연결 때 DB 속성(Name, Status, Assignee, Due Date, Blocker, Task ID)을 검증한다.
- **리마인드 스케줄러** (`services/scheduler.py`): 틱은 멱등. 마감 전 발송 시각(기본 마감 하루 전 09시, 설정 0~3일 전·0~23시) 3일 전부터 재촉을 제안하고, 발송 직전에 이미 답이 왔으면 뺀다. DM 전달 보고 뒤 72시간 무응답이면 태스크를 막힘으로 바꾸고 PM 에게 알린다(답이 오면 풀고, PM 이 되돌릴 수 있음). 자동 승인 설정이 켜지면 발송 시각에 묶음을 자동 승인한다.
- **업로드 sweeper**: 가져간 업로드가 3시간 진행이 없으면 failed(diarize), 화자 지정 대기 7일이면 failed(speaker_assignment_expired), 채팅 회의가 `/end` 뒤 7시간 processing 이면 failed(chat_stalled). 워크스페이스당 처리 중 회의는 하나(행 잠금).
- **비밀번호 재설정**: 30분 1회용 토큰(해시 저장), 계정당 60초 1회·1시간 5회, Gmail SMTP.

  - 녹음 보호: 녹음 중이면 봇을 재시작하지 않는다(`ai/recordings/restart.lock` 을 60초 안에 잡지 못하면 건너뜀). 워커는 SIGTERM 을 받으면 하던 회의를 마치고 끝난다.
  - systemd 유닛 파일은 `/etc/systemd/system/` 에 복사해 설치하는 방식이라 유닛 변경은 자동 배포에 포함되지 않는다(수동 `cp` + `daemon-reload`).
- **롤백**: develop 에서 revert 하면 자동 배포. 마이그레이션은 추가만 하고 삭제·이름 변경은 두 번에 나눈다. DB 백업·downgrade 는 운영에서 실행해 본 적이 없다(#359).
- **운영 스위치**(`ai/.env.example` 이름만):
  - `MM_EXTRACT_PATH=legacy|judge`: 코드 기본값 legacy. **Jev 근거 상태는 judge 경로에서만 쓰인다.** 운영 서버 값은 저장소로 확인할 수 없다 **[미확인]**.
  - `MM_UPLOAD_INTAKE=1`: 웹 업로드 가져오기(서버 한 대에서만).
  - `JEV_API_KEY`: 없으면 근거 상태가 모두 inferred 라 judge 항목이 auto 로 가지 않는다.

## 13. 알려진 한계와 위험

### 13.1 기술 한계

- **단일 서버**: t3.medium 한 대에 DB·API·봇·워커·프론트. 프로세스 하나에 백그라운드 워커 4개. 확장·장애 격리 없음.
- **외부 서비스 의존**: STT·LLM·Jev·임베딩이 Elice MLAPI 에 몰려 있다. 장애 대응은 GPU 대기 서버(수동 전환, 전환·복귀 미연습).
- **STT**: 단어 시각이 없어 묶음 단위 회의록. 업체 비교에서 더 낮은 CER(Soniox 7.54%)이 있었으나 바꾸지 않음.
- **LLM 비결정성**: 온도를 낮출 수 없어 실행마다 결과가 달라진다. 근거 판정이 기준 0.8 근처에서 흔들림(0.78 ↔ 0.82). 1인칭 오분류 약 1%.
- **겹친 발화**: 업로드 회의에서 두 화자로 두 번 전사될 수 있음(0027).
- **Jev 운영 의존**: `JEV_API_KEY` 가 없거나 `MM_EXTRACT_PATH=legacy` 면 judge auto 가 열리지 않는다.
- **승인 충돌이 잦을 수 있음**: 제목 띄어쓰기만 바뀌어도 충돌(BE m2).
- **Discord 읽기 확인의 빈틈**: 기록 읽기 권한이 없어도 200 빈 목록이 올 수 있음.

### 13.2 운영 위험

- DB 백업·복원·downgrade 를 운영에서 해 본 적 없음(#359).
- 의존성은 하한만 지정(버전 고정 안 됨).
- 관찰 수단 부족: 장기 processing, 워커 heartbeat, 디스크 사용량(BE M7).
- systemd 유닛 변경은 자동 배포되지 않음.
- AWS 실습 환경 종료 2026-11-20.

## 14. 최종 산출물에 쓸 이야기 거리

### 14.1 기술적 도전과 해결 (발표·테크스펙 후보)

1. **서버 한 대로 회의 전사를 감당하기**: 로컬 전사가 실시간보다 느리다는 측정(RTF 1.36) → 외부 STT 기본 + 장애 때 켜는 GPU 서버, 손익분기 계산(월 1,863시간). 수치가 있는 결정 과정.
2. **화자 분리 없이 화자 구분**: Discord 화자별 트랙을 그대로 쓰고, 업로드만 외부 화자 분리 + PM 지정.
3. **전사 품질을 숫자로 올리기**: 이름 힌트(이름 자리 0/4 → 3/4), 화자 경계 가르기(건너뛴 줄 6 → 0), 짧은 묶음 앞 줄 프롬프트(짧은 대답 3/7 → 5/7).
4. **LLM 결과를 믿을 수 있게 만들기**: 역할을 나눈 다단계 판단, 다른 모델로 근거 검증(Jev), 숫자 점수 대신 조건 게이트, 실패를 회의 단위·항목 단위로 나눠 처리.
5. **기존 할 일의 변경 감지**: 임베딩 유사 검색으로 후보를 좁히고 Terra 가 비교 판단, AI 가 본 값을 기준값으로 저장해 승인 충돌 감지.
6. **신뢰를 주는 UX**: 신뢰도 숫자 대신 근거·이유·원문 듣기, auto 반영도 되돌리기 가능.
7. **회의 뒤 후속 관리 자동화**: 재촉 제안 → PM 승인 → DM → 답장 판단 → 자동 반영 또는 확인 카드, 72시간 무응답 막힘.
8. **안전한 자동 배포**: 세 파트 CI 통과 커밋만 OIDC·SSM 으로 배포, 녹음 중 재시작 방지, 바뀐 파트만 재시작.
9. **AI 에이전트와 함께 개발하는 팀 규칙**: 보호 문서, 결정 기록 의무, 하네스(설계 확정 → TDD → 셀프 리뷰 → PR), 파트 간 요청 라벨과 합의 알림.

### 14.2 시연 시나리오 후보

1. PM 이 웹에서 회의 음성 업로드 → 화자 지정 → 처리 진행 토스트 → 회의록(요약·전사·추출) 확인.
2. 추출 결과에서 auto 로 생긴 태스크와 확인 필요 항목 비교 → 근거 인용·원문 듣기 → 값 고쳐 승인 → Notion 반영.
3. 마감 임박 태스크에 재촉 제안 → PM 승인 → 팀원 DM → 팀원 답장 → 상태 자동 반영.
4. Discord 채팅 채널을 설정에서 켜고 다음 날 채팅 회의로 정리된 결과 확인.
5. 모바일(360px)·PWA 설치 화면.
