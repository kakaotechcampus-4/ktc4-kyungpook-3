# 공통 에이전트 작업 규칙

## 작업 시작

- 적용되는 지침과 이 규칙을 확인한다. 현재 컨텍스트에 있고 변경되지 않은 내용은 반복해서 읽지 않는다. 새 세션, 축약으로 내용이 사라진 경우, 변경을 알게 된 경우에는 다시 읽는다.
- 대상 파트와 마일스톤을 지시·문서 근거로 정하고 관련 README, 계획, 계약·요청을 필요한 범위에서 읽는다. 번호나 누락된 계획을 추정하지 않는다.
- 작업 전 사용자 변경과 보호 문서 상태를 확인하고 보존한다.

## 수정 범위

- 전체 개발 계획은 파일명과 무관하게 작성·수정하지 않는다.
- 마일스톤 plan.md는 사용자가 해당 계획의 작성·수정을 명시적으로 요청한 경우에만 수정한다. 초안만 요청하면 응답으로 제시한다.
- 초기 구조화에서는 없는 plan.md를 0바이트로만 생성한다.
- trouble-shooting 기록은 사람이 작성·관리한다. 에이전트는 읽기·참조와 원문 기반 정리안 제시만 한다. 원본 반영은 사람이 수행한다.
- 초기 구조화에 필요한 보호 문서 이동은 내용 변경 없이 허용한다. 내부 링크 문제는 임의 수정하지 않고 보고한다.
- design/, mascot/ 등 파트 고유 문서·자산은 유지한다. 일반 개발 중 문서를 자동 재배치하지 않는다.

## 개발 후 기록

- 의미 있는 개발 작업 후 실제 구현과 검증을 현재 마일스톤 result.md 및 파트 README에 반영한다.
- 계획 대비 변경은 result.md에 이유·영향을, 중요한 실제 선택은 basis-for-decision/에 근거를 남긴다.
- 계약은 대표 문서를 중심으로 갱신하고 구현 사실과 합의 상태를 구분한다. 요청·합의·검증 결과·과거 판단을 추정하지 않는다.
- 계획이 비어 있으면 완료조건을 만들거나 완료를 선언하지 않는다. 별도 지시가 명확하면 이를 작업 근거로 기록한다.
- 마일스톤이나 작업 범위가 불명확하면 해당 기록·작업을 보류하고 필요한 정보를 확인한다. 독립적으로 가능한 작업은 계속한다.

## 스킬 선택

- 초기 구조화·보완 요청: docs-bootstrap
- 명시적인 마일스톤 계획 작성 요청: milestone-plan
- 사람의 트러블슈팅 정리 요청: troubleshooting-review
- 인터페이스 계약 변경: contract-update
- 개발 결과 기록: milestone-result
- 중요한 선택 기록: decision-record
- 문서 작업 마무리 검사: docs-audit

해당 작업에 필요한 스킬과 참조만 읽는다. 상세 절차·양식은 각 스킬에 있으며, 문서 구조·탐색이 필요할 때 [문서 안내](README.md)를 확인한다. 스킬 부재는 수정 권한을 확대하지 않는다.

## 마무리

- 변경 문서의 링크와 완료조건 대응, 보호 문서의 시작 상태 대비 보존 여부를 확인한다. 초기화의 내용 보존 이동·빈 파일 생성과 명시적으로 요청된 계획 작성만 예외다.
- 비교 기준이 없으면 검증 불가로 보고하며 HEAD 차이만으로 변경 주체를 단정하지 않는다.
- 사용자 변경을 되돌리거나 기록을 중복 생성하지 않는다. 한국어·상대 링크·실제 기록일을 사용한다.

## 현재 저장소

파트 문서는 기존 경로를 유지하며 전체 재배치는 별도 초기 구조화 요청으로 진행한다. frontend/docs/plan/frontend-development-plan.md와 backend/docs/plan/backend-development-plan.md도 보호하는 전체 계획이다.
