# 트레이드오프

개발하면서 두 길 사이에서 고른 것을 모았다. 한 줄이 결정 하나다. 수치는 결정 기록에 적힌 값 그대로 옮겼고 조건을 같이 적었다. 번호(0008 등)는 결정 기록 번호이고 표 아래 [결정 기록 찾는 법](#결정-기록-찾는-법)에 경로가 있다.

## 수치를 읽는 법

평가 데이터의 성격이 달라서, 숫자 옆에 아래 표기를 붙였다.

| 표기 | 뜻 |
|---|---|
| 정렬본 (m01, m02) | 6명이 대본을 각자 읽은 실제 목소리를 대본 순서로 놓은 녹음. 시간축은 합성이다 |
| 대본 낭독 회의 | 디스코드에서 대본을 읽으며 한 회의. 2026-09-29 1인, 10-02 2인, 10-14 6인, 11-04 6인 |
| 반복 합성 62분 | 짧은 녹음을 이어 붙인 62.42분. 속도와 메모리 측정에만 쓴다 |
| 합성 | 사람이 지은 대사나 일부러 넣은 오류로 만든 평가 세트 |
| 실제 음성 | AI Hub 회의 음성(KconfSpeech). 교육·방송 회의다 |

대본 없이 한 실제 회의의 CER 은 아직 재지 못했다. 할 일 추출 정확도도 합성과 대본 낭독 데이터로 잰 값이다.

## 1. 입력: 왜 디스코드인가

| 고민 | 버린 길과 이유 | 고른 길 | 근거 |
|---|---|---|---|
| 회의 음성을 어디서 받나 | 시스템 오디오 캡처(특정 플랫폼에 묶이지 않는 회의록 도구의 방식): 여러 목소리가 한 줄기로 섞여 화자가 늘수록 구분이 어렵다. 그런 도구는 "나"와 "상대" 두 갈래로만 나눈다 | 디스코드 봇. 디스코드는 참가자별 오디오를 따로 준다. 화자 분리 모델 없이 첫 회의부터 발화마다 화자가 정해진다. 타깃을 디스코드로 회의하는 대학생 팀 프로젝트로 좁혔다 | 팀 노션 4주차 기술 멘토링 사전 질문, 2026-09-04·09-05 회의록, 0008 |
| 플랫폼에 묶이는 비용 | 디스코드만 지원: 오프라인 회의와 다른 도구로 한 회의를 못 받는다 | 웹 녹음 업로드 경로를 더했다. 파일 하나를 올리면 호스팅 화자 분리로 나누고 PM 이 라벨마다 팀원을 지정한다 | 0028, 0029 |
| 웹을 어디까지 만들까 | 디스코드 안에서 전부 처리하기, 자체 웹으로 전부 합치기. 설문은 9 대 8 로 갈렸다 | 음성 수신과 알림은 디스코드, 승인·태스크·답장은 웹 | 팀 노션 2026-09-05 회의록 |

|---|---|---|---|
| 회의 중에 전사할까, 끝난 뒤에 할까 | 실시간 발화 단위 전사(0003): 구현했다가 번복했다. 같은 0.96초 클립의 응답이 2.62초와 20.58초로 갈렸고 복잡도에 비해 얻는 것이 적었다 | 회의가 끝난 뒤 저장된 트랙을 배치로 전사 | 0003, 0008 |

| 전사 전에 말이 아닌 구간을 거를까 | 말 필터(Silero, 0005)를 켜 둠: "네", "좋아요" 같은 짧은 대답이 사라진다 | 배치에서는 말 필터를 끄고 1.5초 미만 묶음에서만 이름 힌트를 뺀다. 대본 낭독 회의 3개에서 CER 5.45 → 4.78%, 짧은 대답 2/7 → 3/7 | 0005, 0030 |
| 짧은 묶음이 문맥 없이 틀린다 | 최소 발화 200ms, 0ms, 이름 힌트 유지 | 최소 발화 100ms 와 앞 줄 프롬프트. CER 4.78 → 4.67%, 짧은 대답 3/7 → 5/7. 결과를 가른 묶음은 5개뿐이다 | 0031 |
| 팀원 이름이 틀리게 적힌다 | 사전 치환, LLM 으로 다듬기 | BE 의 팀원 이름을 전사 프롬프트 힌트로 싣는다. 이름 자리 1/6 → 4/6(0020), 1/4 → 3/4(0024). 태스크 제목까지 힌트로 넣는 안은 CER 이 39.9% 까지 나빠져 넣지 않았다 | 0020, 0024, 0025 |
| 화자가 겹쳐 말하면 순서가 뒤집힌다 | 턴마다 따로 호출: 호출이 10 → 34 로 는다 | 다른 화자가 말을 시작한 자리에서 묶음을 가른다. 건너뛴 줄 6·7 → 0 | 0023 |
| 노이즈를 지우고 보낼까 | 스펙트럼 게이팅, 100Hz 하이패스: 8.56 → 8.42% 로 차이가 작다 | 지우지 않는다. 디스코드는 무음을 디지털 0 으로 보낸다 | 0007 |
| 한국어 회의 음성으로 미세조정하면 나아질까 | LoRA 채택: 성공 기준(정렬본 둘 다 나빠지지 않고 평균 CER 0.5포인트 이상 개선)을 측정 전에 정했다. m01 은 6.52 → 4.94% 로 나아졌지만 m02 는 4.86 → 6.31%, 11-04 6인 회의는 6.72 → 8.06% 로 나빠졌다. 문장부호도 줄었다. Elice 에 올릴 수 없어 GPU 를 늘 켜야 한다 | 기본 모델 유지. AI Hub 회의 음성 274.4시간(1차), 484.5시간(2차)을 g5.xlarge 에서 학습했고 비용은 $56.50 였다 | 0052 |

## 3. 화자

| 고민 | 버린 길과 이유 | 고른 길 | 근거 |
|---|---|---|---|
| 디스코드 회의의 화자 | 화자 분리 모델 | 쓰지 않는다. 트랙이 곧 화자다. 남의 목소리가 마이크에 섞여 들어오는 경우는 거르지 못한다 | 0008, 0005 |
| 업로드 파일의 화자 분리 | 서버에서 pyannote 를 직접 돌림: t3.medium 에서 처리 워커와 같이 띄울 수 없다고 봤다(재지 않은 판단이다) | 호스팅 API(pyannoteAI). 제출만 하고 작업 ID 를 기록해 다음 바퀴에 결과를 가져온다. 워커가 중간에 죽어도 이어 받는다 | 0028, 0040 |

## 4. 판단 파이프라인

| 고민 | 버린 길과 이유 | 고른 길 | 근거 |
|---|---|---|---|

| 근거를 어떻게 가리킬까 | 문장 번호 하나: 결정 하나가 둘로 쪼개진다 | 번호 배열. 314/337(93%) → 331/340(97%) | 진행 로그 judgefinding-evidence-span |

| 임베딩 유사도로 같은 일인지 정할까 | 임계값으로 판정: 경계(0.34 ~ 0.59)에서 틀린다 | 0.4 는 후보로 넘길지만 정하는 낮은 문턱이다. 불일치 최고 0.33, 매치 최저 0.42 사이. 같은 일인지는 Terra 가 정한다. 실데이터로 다시 맞추지는 않았다 | 0010 |
| 근거가 분명한지 누가 정하나 | 값을 만든 모델의 자기 표시: 거의 다 "분명"이라고 한다. 코드 규칙: 하루 써 보고 버렸다 | 다른 모델(Jev)에 "원문에 명시됐나"를 묻고 yes 확률 0.8 이상만 분명으로 본다. 0.85 로 올리면 맞는 마감의 57% 만 통과한다. 합성 217대사에서 잘못된 "분명"은 할 일 1/83(95% 상한 6.5%), 마감 1/44(상한 11.8%) | 0031, 진행 로그 jev-evidence-eval-extended |
| 근거가 충실해도 전사가 틀렸으면 | 형태소 미등록어와 자모 한 글자 차이로 잡기: 합성 오류에서 93% 를 막았지만 실제 음성(1,397발화, 명사 오류 230)에서는 14% 였다. 국어사전 목록: 오류 발화의 97% 가 사전에 있는 낱말이었다 | 제목 명사 중 팀 용어 목록에 없는 말을 같은 Jev 호출로 확인한다. 실제 음성에서 47%(정상 발화 19% 를 막음). 기준 0.8 은 잠정값이다 | 0051 |
| 자동 반영을 점수로 정할까 | 신뢰도 숫자 하나: 중복 위험이 점수에 안 들어가고, 왜 탈락했는지 남지 않는다 | 조건을 각각 검사해 모두 통과해야 자동 반영. 탈락 사유 코드를 남긴다. 게이트는 BE 한 곳에 둔다 | [에이전트 설계](agent-design.md#게이트-be), 팀 노션 10주차 기술 멘토링 |
| 기존 할 일 수정도 자동으로 할까 | 자동 반영: 판단이 틀리면 이미 있는 데이터가 망가진다 | 수정은 항상 PM 확인. 승인할 때 그사이 값이 바뀌었으면 409 로 비교 화면을 띄운다 | [승인과 충돌](../design/backend/approval-conflict.md) |

| 채팅에 같은 판단을 써도 되나 | 채팅 전용 파이프라인: 단계 순서까지 달라질 때 나누기로 했다 | 하루치 채팅을 "채팅 회의" 하나로 만들어 같은 경로에 넣되, 새 항목의 자동 반영은 확인 필요로 낮춘다 | 0042, 0046 |

| 같은 일이 두 번 나오면 | 뒤 발화를 새 카드로: 카드가 둘, 번복은 취소 카드가 따로 생긴다 | 같은 회의 안에서는 앞 카드에 합친다(카드 2 → 1). 다른 회의의 승인 대기 카드도 후보로 보여 합친다 | 0018, BE 결정 pending-merge |
| LLM 호출이 실패하면 | 회의 전체를 다시 돌림: 성공한 호출까지 다시 부른다 | 실패한 호출만 그 자리에서 다시 부른다. 긴 응답이 2,000토큰에서 잘려 스트리밍으로 바꿨다 | 0063, 0061 |
| "넘겼어요"처럼 상태 단어가 없는 진척 | 완료로 보지 않음 | 넘긴 것도 완료로 본다. 58개(40번부터 합성) 3회 반복에서 52/52, 완료 오판 0 | 0033 |

## 5. 책임 분리

| 고민 | 버린 길과 이유 | 고른 길 | 근거 |
|---|---|---|---|
| AI 와 BE 를 어떻게 잇나 | Redis·Celery 큐 서버: t3.medium 의 코어를 뺏는다 | HTTP API 로만 잇는다. 서비스 토큰을 확인하고, 매니페스트에 적은 회의 ID 로 다시 보내도 중복이 없다 | 0009, 0004 |
| 자동 반영을 누가 정하나 | AI 가 정해서 보냄: 지금 값 확인은 어차피 BE 가 해야 해서 정책이 두 곳으로 갈린다 | AI 는 근거와 검색 결과를 보내고 BE 가 정한다. 별칭 확정, 승인 대기 중복처럼 BE 만 아는 값이 조건에 들어간다 | [매칭과 게이트](../design/backend/gate-matching.md) |
| 봇이 전사까지 할까 | 봇이 처리까지 하는 방식, 두 방식을 같이 두기, DB·Redis 큐 | 봇은 저장만 하고 워커가 처리한다. 봇 토큰을 워커에 두지 않으려고 둘은 파일로 주고받는다. 코드 831 → 570줄 | 0026 |
| 재시작하면 어디서 이어 가나 | 담당 표시와 만료 시각을 DB 에 두기, SQS, Redis | 회의마다 매니페스트에 단계를 적고, 워커가 마지막으로 끝난 단계 다음부터 한다. 회의별 잠금으로 두 워커가 같은 회의를 잡지 않는다 | 0013, 0017 |
