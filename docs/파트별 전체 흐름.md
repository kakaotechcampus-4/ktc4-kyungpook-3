# 파트별 전체 흐름

현재 저장소의 frontend 문서 구조화 범위에서 확인한 흐름이다. backend·AI의 세부 계획과 마일스톤 문서는 재배치하지 않았다. API 제공과 소비의 현재 차이는 [프론트엔드 대표 계약](../frontend/docs/contracts/frontend-api-contract.md)의 현재 코드 대조를 따른다.

## 목적과 책임

사용자가 공간을 선택하고 회의 음성을 올리면 회의 상태·회의록·추출 결과를 확인할 수 있도록 프론트엔드가 화면과 사용자 행동을 구성한다. 백엔드는 인증·권한·저장·API 제공을 담당한다. 회의 전사·추출·Notion 반영은 서버 측 파이프라인에 의존하며, 프론트엔드 업로드 경로의 실제 파이프라인 연결은 아직 TODO다.

## 주요 처리 순서

1. 앱의 인증 초기화와 라우트 가드가 공개 화면·로그인·공간 소속·온보딩 완료·PM 권한을 구분한다. 업무 조회는 가드를 통과한 화면에서 시작한다.
2. 로그인·가입 후 공간 선택 또는 생성·온보딩으로 이동한다. Discord·Notion 연동, 팀원 연결, 단계 저장 뒤 대시보드에 진입한다. 개발 MSW 모드의 OAuth 화면과 실 OAuth를 구분한다.
3. PM이 회의 업로드 화면에 진입하면 처리 중 회의·Notion 연결을 확인한다. 파일·제목·날짜·참석자를 검증하고 multipart 요청을 전송한다.
4. 202 응답의 회의 ID를 처리 추적기에 등록한다. 로그인 영역의 추적기가 공간별 캐시와 회의 상세를 사용해 3초 간격으로 상태를 읽는다. 완료·실패·접근 상실 시 추적을 중단한다.
5. 완료 시 관련 캐시를 무효화하고 회의록 진입을 안내한다. 회의록 화면은 목록·상세·본문·추출·권한별 대기 승인을 조합한다. PM과 일반 팀원의 확인 필요 영역은 구분된다.
6. 태스크 상세·승인으로 이어지는 경로는 존재하지만 이번 구조화로 M6 이후 구현이나 완료를 판정하지 않는다. 대시보드 완성과 후속 화면의 범위는 [전체 계획](../frontend/docs/plan/frontend-plan.md)에 있다.

## 데이터와 의존성

`pages/widgets/features → entities API → shared/api → /api/v1 → backend` 순서로 요청하고, 응답 DTO는 entities mapper를 거쳐 도메인 모델로 화면에 전달한다. 프론트엔드의 전체 계층 의존 방향은 `app → pages → widgets → features → entities → shared`다.

개발·테스트에서는 [MSW](../frontend/docs/msw-guide.md)가 같은 HTTP 경계의 응답과 회의 전이를 모의한다. [기존 M5 인수인계](../frontend/docs/plan/m5/m5-handoff.md)의 MSW 검증은 실제 파일 저장·큐 전송·OAuth·STT 성공과 구분한다. 서버에 최근 구현된 기능과 기존 기록의 차이는 계약의 현재 코드 대조에 남긴다.

기존 [프론트엔드 흐름 도식](Manager's%20Manager%20프론트엔드%20흐름.excalidraw.md)과 [계약·엔티티·흐름 도식](Manager's%20Manager%20계약·엔티티·흐름.excalidraw.md)은 공유 자료로 원위치에 유지한다.
