# 제출 전 문서 마무리

## 절대 규칙

1. 추측으로 값을 채우지 않는다. 확인할 수 없는 값은 `docs/TODO-human-check.md`에 모은다.
2. 사실은 코드·설정·CI·결정 기록에서 직접 확인한 것만 쓰고, 출처(파일 경로 또는 PR·커밋)를 함께 적는다.
3. 비밀값(토큰, 비밀번호, 키)은 커밋하지 않는다.
4. 기존 브랜치·커밋·PR 컨벤션을 따른다. 작업마다 별도 브랜치를 만들고 커밋은 작게 나눈다.
5. 코드 로직은 건드리지 않는다. 문서·README·시드 사용 절차만 다룬다.
6. 문서 검사를 돌리고, 돌리지 못한 것은 못 돌렸다고 적는다.

## 작업 경계

- 적용되는 진입점과 docs/agent-rules.md를 따른다. 전체 개발 계획, 마일스톤 plan.md, 사람의 trouble-shooting/ 기록은 `[확인 필요]`가 남아 있어도 수정하지 않고 TODO로만 넘긴다.
- 컨벤션은 `docs/collab/conventions.md`, `docs/collab/branch-strategy.md`, `.github/pull_request_template.md`와 최근 `git log`에서 확인한다. 기억으로 쓰지 않는다.
- 사용자가 작업 번호를 지정하면 그 작업만 한다. 지정이 없으면 1 → 2 → 3 순서로 진행하고, 한 작업의 막힘이 다른 작업을 멈추게 하지 않는다.
- 커밋·푸시·PR 생성은 사용자가 요청했을 때만 한다. 요청이 없으면 브랜치의 작업 트리 변경과 PR 초안 설명까지만 만든다.
- 한국어와 상대 링크를 사용하고, 없는 문서로 가는 링크를 만들지 않는다.

## 훅

`.claude/settings.json`에 연결된 훅 두 개가 이 작업을 돕는다. 스크립트는 `.claude/hooks/`에 있다.

- `count-confirm-needed.sh`: docs/, ai/docs/, 루트 README.md를 고칠 때마다 남은 `[확인 필요]` 개수를 알려 준다. 작업 1의 진행 확인에 쓴다.
- `check-staged-secrets.sh`: `git commit` 직전에 스테이징된 변경에서 비밀값 패턴을 찾고 걸리면 커밋을 막는다. `git add`와 `git commit`은 나눠 실행해야 스테이징된 내용만 정확히 검사한다.

훅에 막히면 우회하지 않는다. 값을 지우거나 TODO로 넘긴다. 시드 코드에 공개로 정의된 데모 값처럼 공개해도 되는 근거가 있을 때만 그 줄에 `secret-scan: allow` 주석(Markdown은 `<!-- secret-scan: allow -->`)을 달고, 근거 파일을 PR 설명에 적는다. 훅 통과는 비밀값이 없다는 보증이 아니므로 커밋 전 diff를 직접 읽는다.

## 작업 1. `[확인 필요]` 정리

1. `grep -rn "확인 필요\]" docs README.md ai/docs`로 전부 찾고 시작 건수를 기록한다.
2. 항목마다 코드·설정·CI·결정 기록에서 값을 찾는다. 확인되면 표시를 값으로 교체하고 출처를 단다.
3. 확인할 수 없으면(운영 서버 값 등) 표시를 지우지 않는다. `docs/TODO-human-check.md`에 아래 형식으로 모은다.

   ```markdown
   | 파일:줄 | 확인할 것 | 확인 방법(명령어) |
   |---|---|---|
   ```

   확인 방법에는 사람이 그대로 실행할 수 있는 명령어를 적는다. 명령어에 비밀값을 넣지 않는다.
4. `AUTO_CREATE_ENABLED`, `MM_EXTRACT_PATH`는 코드 기본값과 `.env.example`(`backend/`, `ai/`, `frontend/`), compose, deploy 설정을 대조해 문서와 일치시킨다. 서로 다르면 어느 파일이 어떤 값인지 그대로 적는다. 운영 서버의 실제값은 저장소에서 알 수 없으므로 TODO로 넘긴다.
5. 끝나면 같은 grep을 다시 돌려 남은 건수가 TODO 항목 수와 맞는지 확인한다.

## 작업 2. README 빈자리 채우기

- **테스트 계정(#606):** `backend/app/cli/seed_demo.py`와 `backend/app/cli/demo_seed/`를 읽고, 심사용 계정·샘플 회의를 만드는 명령과 사용 절차를 README와 `docs/user/quick-guide.md`에 적는다. 명령은 시드 코드의 실제 진입점·인자에서 확인한다. 비밀번호는 시드 코드에 공개 가능한 데모 값으로 정의돼 있을 때만 적고, 환경 변수나 운영 값에서 오면 TODO로 넘긴다.
- **대표 GIF(#654):** 만들 수 없다. README의 자리 주석은 유지하고, 촬영 시나리오(화면, 순서, 길이)를 `docs/TODO-human-check.md`에 적는다. 시나리오의 화면과 순서는 실제 화면 구성과 사용자 가이드에서 확인한 것만 쓴다.
- **"준비 중" 문구:** 이번에 실제로 채운 항목에 한해서만 제거한다. 채우지 못한 항목의 문구는 남긴다.

## 작업 3. 환경 구성 문서화

1. `.env.example`(`backend/`, `ai/`, `frontend/`), `backend/docker-compose*.yml`, `.github/workflows/deploy.yml`, `deploy/`를 읽는다.
2. `docs/dev/deploy.md`에 "환경 분리 현황" 표를 추가한다. 기존 내용과 겹치면 새로 쓰지 않고 기존 절을 가리킨다.

   | 항목 | 로컬 | 운영 | 출처 |
   |---|---|---|---|
   | DB | | | |
   | 시크릿 보관 위치 | | | |
   | 배포 트리거 | | | |
   | 롤백 방법 | | | |

   시크릿은 보관 위치와 변수 이름만 적고 값은 적지 않는다.
3. 스테이징 환경이 설정에서 확인되지 않으면 없다고 명시한다. 배포 전 CI 3종 게이트(`.github/workflows/`의 ai·backend·frontend CI)와 롤백 절차가 그 역할을 어떻게 대신하는지, 워크플로와 배포 스크립트에서 확인한 조건 그대로 적는다. 게이트가 실제로 배포를 막는지(필수 체크인지, deploy가 의존하는지)를 확인하지 못했으면 TODO로 넘긴다.

## 문서 검사

- `python tools/check_frontend_docs.py`, `python tools/check_frontend_history.py`: 해당 문서를 고쳤을 때 돌린다.
- 새 문서를 만들면 `docs/index.md`나 해당 영역의 개요 문서에서 링크되는지 확인한다. 문서 사이트 빌드(mkdocs)는 쓰지 않는다.
- 고친 문서의 상대 링크가 실제 파일을 가리키는지 확인한다.

실행한 명령과 결과를 그대로 적는다. 실패나 미실행을 통과로 쓰지 않는다.
