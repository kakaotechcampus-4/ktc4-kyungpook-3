# AI 파트 기능 구현 루프

요청: $ARGUMENTS

규칙은 `ai/CLAUDE.md`와 `docs/agent-rules.md`를 따른다. 이 스킬은 순서만 정한다. 응답을 끝낼 때마다 Stop hook이
`ai/` pytest를 다시 돌리고, 실패하면 끝내지 못하게 막는다. 막히면 출력된 실패를 고친다.

## 0. 준비

- `git status`를 본다. 사용자의 커밋 안 된 변경은 건드리지 않는다. 이번 기능과 무관한 변경이 섞여 있으면 멈추고 묻는다.
- 현재 브랜치가 `develop`이나 `main`이면 `feature/<짧은-이름>` 브랜치를 만든다.
- 요청이 계획 파일 경로면 그 파일을, 설명이면 관련 코드·테스트·계약·결정 기록을 읽는다. 코드가 문서와 다르면 코드를 믿는다.

## 1. 계획 (응답에 적고 바로 진행)

- 태스크로 쪼갠다. 태스크마다 **먼저 실패해야 하는 테스트, 검증 명령, 완료 조건**을 적는다.
- 아래 경우에만 멈추고 질문한다. 질문은 한 번에 모아서 묻는다.
  - 결과를 바꾸는 설계 선택인데 코드·문서로 정할 수 없을 때
  - `shared/schemas.py`나 BE API 계약을 바꿔야 할 때
  - 비용이 드는 실제 API 호출(LLM, STT, 임베딩)이 필요할 때
- 그 외에는 합리적인 기본값을 골라 계획에 적고 진행한다.
- 계획은 응답에만 쓴다. `plan.md`나 전체 계획 파일은 쓰지 않는다.

## 2. 구현 루프 (태스크마다)

1. 테스트를 먼저 쓰고 돌려서 **예상한 이유로 실패하는지** 확인한다.
2. 그 테스트를 통과시키는 최소한의 구현을 한다.
3. 관련 테스트, 그다음 전체 테스트를 돌린다: `ai/` 안에서 `.venv/bin/python -m pytest -q`.
4. 실패하면 원인을 고친다. 테스트를 지우거나 단언을 약하게 만들어 통과시키지 않는다.

같은 태스크에서 세 번 고쳐도 통과하지 않으면 멈추고 실패 내용을 보고한다.

## 3. 리뷰 루프

1. diff를 `ai/CLAUDE.md`의 "깨면 안 되는 규칙"에 하나씩 대 본다.
2. `code-review` 스킬을 `high --fix`로 실행한다. 고친 뒤 전체 pytest를 다시 돌린다.
3. 새 지적이 나오지 않을 때까지 반복한다. 최대 세 번. 고치지 않은 지적은 이유와 함께 보고에 남긴다.

## 4. 기록

- 진행 로그를 `ai/docs/basis_for_decision/ai/YYYY-MM-DD-<slug>.md`에 남긴다. 양식은 `ai/docs/README.md`.
- 여러 선택지 중 하나를 고른 결정이 있었으면 `decision-record` 스킬로 결정 기록을 남긴다.
- `shared/schemas.py`나 BE 호출이 바뀌었으면 `contract-update` 스킬을 쓴다.
- 대상 마일스톤이 명확할 때만 `milestone-result` 스킬을 쓴다.

## 5. 마무리

- 기능 브랜치에 커밋한다. 형식은 `type(scope): 한국어 요약` (예: `feat(judge): ...`, `fix(stt): ...`, `docs(ai): ...`).
  push와 PR은 사용자가 요청할 때만 한다.
- 보고에 넣을 것:
  - 태스크별 결과
  - 실제로 돌린 명령과 결과 (통과·실패 수). 돌리지 못한 것은 못 했다고 쓴다
  - 리뷰에서 고친 것과 남긴 것
  - 남긴 기록 문서
  - 남은 위험과 다음 할 일
