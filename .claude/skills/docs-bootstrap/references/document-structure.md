# 문서 구조와 작성 규약

<part>는 실제 파트 경로다. 계약·계획·요청 문서는 모두 `<part>/docs/` 아래에 둔다. 요청 폴더명은 복수형 `requests/`를 사용한다. 아래는 공통 역할의 경로이며 허용 폴더 전체 목록이 아니다.

```text
docs/
├── agent-rules.md
├── README.md
└── 파트별 전체 흐름.md
<part>/
├── README.md
└── docs/
    ├── README.md
    ├── contracts/
    │   └── <contract-name>.md
    ├── requests/
    └── plan/
        ├── <part>-plan.md
        └── mN/
            ├── plan.md
            ├── result.md
            ├── basis-for-decision/
            │   └── YYYY-MM-DD-<slug>.md
            └── trouble-shooting/
                └── YYYY-MM-DD-<slug>.md
```

result와 개별 기록은 선택적이며 발생 시 작성한다. 최초 구조화는 기존 기록을 보존하고 빈 plan만 미리 만든다. frontend/docs/design/, frontend/docs/mascot/ 등 추가 영역을 유지하고 README에서 링크한다.

## 문서별 필수 내용

이 표를 실제 저장소의 docs/README.md에 맞춰 반영한다. 규칙의 상세 권한은 agent-rules.md를 참조한다.

| 문서 | 역할 및 항목 | 작성 주체·시점 |
|---|---|---|
| docs/agent-rules.md | 개발 전후 작업 의무, 보호 영역, 스킬 사용 시점 | 초기 구조화 시 생성, 이후 명시적인 규칙 변경 요청 시 보완 |
| docs/README.md | 구조, 역할, 파트·전체 흐름·공통 규칙 링크, 작성 주체·시점, 양식, 명명 규칙 | 에이전트가 초기 생성 및 필요한 때 갱신 |
| 파트별 전체 흐름.md | 목적, 주요 처리 순서, 파트 책임·경계, 데이터 흐름·의존성, 계약 링크 | 코드·기존 문서 근거로 작성 |
| 파트 README.md | 목적, 책임, 코드 경로, 연결 지점, 계약·요청·전체 계획 링크, 마일스톤 상태 및 존재하는 계획·결과 링크, 추가 문서 영역 | 초기 생성 및 개발 후 갱신 |
| <part>/docs/README.md | 대표 문서 경로, 보존한 추가 영역, 기존 문서와 새 경로의 대응 | 초기 생성 및 구조 보완 시 갱신 |
| <part>/docs/contracts/*.md | 목적, 제공자·소비자, API·인터페이스, 입력·출력·데이터 형식, 오류·제약, 코드 근거, 합의 상태와 차이 | 코드 기반 초기 작성 및 계약 변경 시 갱신 |
| <part>/docs/requests/*.md | 요청·수신 파트, 배경, 작업, 기대 결과·완료조건, 처리 상태·결과, 관련 계약·마일스톤 | 실제 요청이 있을 때 수신 파트에 기록 |
| <part>/docs/plan/<part>-plan.md | 전체 목표·범위, 마일스톤 정의·산출물·완료조건, 의존성 | 사용자가 관리, 에이전트 읽기 전용 |
| <part>/docs/plan/mN/plan.md | 목표·배경, 구현 범위·순서, 계약·의존성, 검증 방법·완료조건 | 초기에는 빈 파일, 이후 사용자가 작성하거나 명시적 계획 작성 요청으로 작성 |
| <part>/docs/plan/mN/result.md | 실제 구현·코드, 조건별 충족/미충족/미검증 및 근거, 실제 검증, 계획 대비 차이·이유·영향, 잔여 작업·제한, 관련 기록 링크 | 에이전트가 실제 개발 결과를 기록 |
| <part>/docs/plan/mN/basis-for-decision/*.md | 문제·배경, 실제 검토한 대안, 선택과 이유, 장단점·제약, 영향, 관련 코드·계획·결과 | 의미 있는 선택 시 에이전트가 기록 |
| <part>/docs/plan/mN/trouble-shooting/*.md | 증상, 조사·원인, 실제 시도·결과, 해결 또는 미해결, 고민·인사이트·재발 방지 | 사람이 직접 작성·반영 |

## 해석 및 보존

- 확인한 구현을 합의로 단정하지 않는다. 합의 근거가 없으면 확인 필요를 표시한다.
- 전체 계획 또는 기존 plan의 내용이 부족해도 초기화 과정에서 채우지 않는다.
- plan이 비어 있으면 완료조건이나 마일스톤 완료를 추정하지 않는다.
- 코드로 과거 의사결정 이유나 검증 성공을 추정하지 않는다.
- 실제 날짜를 사용하고, 확인되지 않은 상태는 확인 필요로 표시한다.
- 복수의 기존 계획이 서로 다르면 조용히 합치거나 한쪽을 덮어쓰지 않는다.
- 자료가 특정 마일스톤에 속한다는 근거가 없으면 원래 위치를 유지한다.
